Tom Core — the foundation layer of the Tom Framework

> Attribution. The Tom Framework is developed by Peter Nicolai Alexis Kyaw. > These packages are BSD-3-Clause licensed and internal (publish_to: none).

Tom Core is the set of packages every Tom application is built on: a platform-neutral kernel (dependency injection, observable state, security, resources, logging) and the runtimes layered on top of it — a server stack, two Flutter layers, and a set of agentic building blocks.

This repository (al-the-bear/tom_core) holds the whole layer. This document is the map; each package has its own README.md and doc/ folder for the detail. Nothing about a package's API is re-documented here — one phrase of "what it is" plus the link is the contract.

> New here? The richest on-ramp is the > tom_core_samples/ learning path (see > Sample learning path) — a shared todo app built up > from a server, a Flutter client and four UI showcases. For the foundation, > read tom_core_kernel; for the broadest live UI > reference, run tom_flutter_form_test > (the form stack) or tom_flutter_ui_test > (the full widget set).

What you can do with Tom Core

  • Build a backend service — HTTP host, an endpoint pipeline, a type-safe

relational persistence layer with datasources and migrations, configuration, caching, and authentication/authorization — from one dependency (tom_core_server). - Build a Flutter app from authorization-aware, observable, resource-bound widgets — a Material/Cupertino widget set, a declarative form system, and a fluent layout engine (tom_flutter_ui). - Share one model of state, security, and resources across server and client — the platform-neutral tom_core_kernel is the single source of those cross-cutting concerns. - Assemble agent runtimes from generic, domain-free, dart:io-free building blocks (tom_core_agentic).

How the layer fits together

Everything roots at the kernel. The two runtimes (server and Flutter) re-export it, so an app depends on one of them and gets the kernel API for free. The UI library is the rich widget set that the Flutter runtime's thin integration layer complements. The agentic blocks sit beside the kernel, depending only on tom_basics. 

                    tom_core_kernel            (platform-neutral foundation)
                   /       |        \
       tom_core_server  tom_core_flutter  tom_flutter_ui
         (backend)      (Flutter glue)    (widget library)

       tom_core_agentic  (agent building blocks; depends only on tom_basics)

Repository tooling

Tools that span the whole repository live in tool/; anything scoped to one package lives in that package's own tool/.

Every check_*.py below is a gate: it counts documentation faults and exits non-zero when it finds any. They are run together by tool/check_gates.py, which tom_flutter_ui/test/repo_doc_gates_test.dart invokes — so a gate that starts failing surfaces in flutter test / testkit :test rather than waiting for somebody to run it by hand. 

python3 tool/check_gates.py            # run them all, report, gate
python3 tool/check_gates.py --update   # re-record the baselines to today
python3 tool/check_gates.py --timings  # ... and list what each gate took
python3 tool/check_gates.py --self-test  # check the runner's own verdicts

Each gate is pinned to a fault count in tool/gate_baselines.json, not to zero. Demanding zero on the day the runner landed would have meant repairing several hundred documentation faults before anything at all was enforced, and until they were, every new fault would land unnoticed among them. So the backlog is frozen where it is and the next fault is a failure. Clearing a backlog is separate work, and lowering its baseline is part of that work.

The ratchet turns both ways: a count below its baseline fails too, asking for the baseline to be lowered, because otherwise repaired ground reopens silently. Gates are discovered by glob, so a checker added tomorrow is enforced tomorrow — it fails as unbaselined until it is recorded. To be run, a gate must be named check_*.py in tool/ and end its main() with report_faults(n) from tool/gate_report.py; report_*.py names a tool that reports and never gates.

Each gate gets GATE_TIMEOUT_SECONDS (fifteen minutes), set from a measured run with room for a loaded machine. A gate stopped at the budget is reported as timed-out, naming the limit and the last line the gate printed — its content not judged — rather than as a gate that forgot its count, which is the opposite remedy. Each gate runs as its own process group and the whole group is killed: a gate shells out to dart analyze, and an analyzer left running would compete with every gate after it, and hold the runner's pipes open past the limit it had just enforced. --self-test runs throwaway gates that stall (with a child process), stay silent and refuse, and checks the verdict on each and that nothing is left running. The analyzer-backed gates keep their clean verdicts in tool/gate_cache.py, keyed on every input the verdict depends on — the package, its path dependencies' sources, its resolved package config, the SDK and the gate itself — so a run after an unrelated edit re-analyzes only what moved. A faulty verdict is never cached; --no-cache forces a full run.

Several gates shell out to dart, and each refuses to run without one rather than guess. The runner does not leave that to the shell: when dart is not on PATH it looks for an SDK (tool/dart_sdk.py) and puts it on every gate's PATH, saying so above the results. A gate that still cannot run exits 2 with its reason, and is reported cannot-run with that reason — not as a gate that forgot to print its count, which is a different failure with a different remedy.

The gates are not the package suites. A green gate run says the documentation still describes the code; it says nothing about whether the packages' own tests pass, and a change that reaches several packages is exactly the change most likely to leave a sibling's suite red while the package it was about, and the gates, are green. tool/run_suites.py runs what "green" means for this repository — every package suite and the gate suite — with one verdict: 

python3 tool/run_suites.py                   # all eight package suites, then the gates
python3 tool/run_suites.py kernel server     # a subset, by name or unique part of one
python3 tool/run_suites.py --no-gates flutter_ui
python3 tool/run_suites.py --list            # what would run, and with which runner

It runs Flutter packages under flutter test and the rest under dart test, each with its own configuration — a package's dart_test.yaml decides its concurrency; nothing is forced. It reports progress every 30 seconds (the longest suites take a quarter of an hour), prints a table of per-suite verdicts and durations, keeps each run's output under tool/ztmp/suites/, and exits non-zero if any suite failed. Run it before calling a cross-package change finished. It is deliberately not a check_*.py: the gate runner would discover it and start eight test suites.

The table above and the prose below it are an inventory of tool/, and both are kept by hand — adding a script touches neither. So a gate can land, be picked up by check_gates.py's glob, run on every build, and be documented nowhere; the reader who came to the README to learn what the repository checks gets a confident, incomplete answer, and the undocumented gate is the first candidate for deletion because nothing points at it.

This has already re-opened once, which is why it is a gate rather than a promise. check_kernel_bridge.py and check_section_numbers.py each ran undocumented long enough to be noticed and written up — and by the time they were, check_unimplemented_claims.py had silently taken their place. Clearing the backlog was never the difficulty. Nobody who reviewed the commit that added a script made a mistake either: the omission is in a file that commit did not touch, so there is no diff in which to see it.

Three counts are kept apart: a script with no row, a row naming no script (the reverse drift, left behind by a rename), and a check_*.py with no invocation block. gate_report.py, gate_cache.py and dart_sdk.py legitimately have no block — they are helpers a gate or the runner imports rather than gates to run, and their rows say so. Accuracy is not checked, only presence: whether a summary is true needs judgement, whether a row exists does not. That is the same line check_doc_inventories.py and check_test_inventories.py draw.

It reports four faults and exits non-zero if it finds any: sections the contents omit, entries whose link resolves to no heading, entries listed in an order the document does not follow, and links in the body pointing at an anchor of their own document that no heading provides. The third is the one a reader cannot easily catch, and a presence check passes it silently.

The body-link check is why the gate scans every document rather than only the 117 that carry contents. check_doc_links accepts any #fragment and names this gate as the one that decides whether the heading exists, so an anchor nobody indexed was an anchor neither gate looked at: a [§10](#…) in running prose whose heading had since been reworded resolved to nothing, and so did two appendix cross-references that had picked up a doubled dash. STALE is this same fault confined to the contents block.

Documents drift from their contents whenever a section is added without the list being touched, so the check is worth running after editing any document that has one. 

python3 tool/check_doc_inventories.py         # every completion document
python3 tool/check_doc_inventories.py --fix   # re-measure and write back

The completion documents in the _ai layer open by naming a module's directory and how much is in it, then tabulate it a file at a time. Those numbers are measurements taken by hand, so every commit to a module can falsify them, and nothing about editing a module brings its completion document into view. The check re-measures: it reports line counts that have moved, tabulated files that no longer exist, files on disk the table omits, and opening claims that disagree with the directory. --fix writes the measurements back; the two faults it leaves alone are adding and retiring rows, because each needs a sentence saying what the file carries.

A package document's Dependencies section tells a reader what the package is wired to, and it is written once and never revisited. Measured against the pubspecs, eleven of these sections existed and seven were incomplete, with 28 declared entries missing between them and four further package documents carrying no section at all. The omissions all fell the same way: every one was a build-time entry (build, build_runner, tom_reflection_generator, lints, test, flutter_test, flutter_lints) and the runtime half was in every case complete. That is the worst half to drop, because it is exactly what a reader needs in order to reproduce a generated file — a section listing what a package links and omitting what built it reads as finished and answers the wrong question.

The check requires each declared name to appear as a whole inline code span, so build.yaml is not evidence for build and tom_reflection is not evidence for tom_reflection_generator. It is one-directional on purpose: a name in the section that the pubspec does not declare is not a fault, because these sections earn much of their value from naming what is absent — no Flutter, no tom_core_server, tom_reflection arriving transitively through the kernel. A document is audited when its opening inventory resolves to a directory with a pubspec.yaml, the same rule check_doc_inventories.py uses, so module documents are skipped rather than faulted.

Module documents get the same audit one level down, against imports rather than against a pubspec. A dependency table is the one part of a prose document that is wholly derivable from the source, and the part that goes stale most quietly: an import added to a file changes nothing a reader can see, so the table keeps listing what the module used to need and the omission looks exactly like a dependency that was never there. It is checked in both directions, and the Imported by column per dependency — a table can name the right four dependencies and still attribute them to the wrong files.

That is only possible because there is one shape to parse. These 57 sections came in four table layouts plus 51 written as prose, which is why exactly one of them had ever been checked: a checker tolerant of five formats can verify only what each format happens to state, and | Dependency | Used for | names no importing file at all. The For column is prose and is held only to being non-empty; requiring every name in it to resolve was tried and rejected, because those cells routinely name a type the dependency does not declare, which is the sentence worth writing.

Formatting drift is invisible to the check everybody runs: dart analyze says nothing about line wrapping, so a file can be analyzer-clean, test-green, reviewed and merged while being unformatted. The cost is not the whitespace — it is that every later change drags an arbitrary slice of the pending reformat into its diff, so a 173-line change arrives as a 6,000-line one and stops being reviewable. This repository has paid that bill four times, and on the day this gate landed a fifth package had four drifted files that nothing could see.

The scope is every .dart file under tom_ai/core, found by walking it rather than from a list of directories to keep up to date. Left out: dot-directories, tool/ztmp (the scratch tree check_doc_dart_blocks.py writes documentation snippets into — their wrapping is not a package's defect), and generated output. tom_core_kernel and tom_core_server keep their own in-suite formatting_test.dart, which is where a developer working in those packages gets the signal; this covers the other 21, which had nothing.

A module's error keys are its public vocabulary of failure, and the section is written as a reference a client author branches on. So a key that is raised and not listed is a branch nobody knows to write, and a key that is listed and not raised is a branch that can never be taken. Both are silent — neither the compiler nor any test notices, because the section lives in another repository from the code it describes. The check reports them as ABSENT and UNKNOWN.

Deciding what counts as an error key cannot be done from the shape of a string literal, because plenty of dotted lowercase literals are configuration keys, claim names or table names. So it works in two passes: the first argument of every SomethingException( establishes a key, those keys establish their families, and any other dotted literal of an established family counts too. The second pass is what catches the keys that reach a client without being thrown — handed to a result object, assigned to an error field, returned by a local _error helper. Deriving the families from the raises rather than listing them keeps the rule general while still excluding oauth.providers, a configuration key whose family no exception establishes.

This table has proved as prone to decay as the inventories: one hand census found six glosses describing the wrong condition, and a later one found thirteen keys missing outright — including an entire family, every failure an external login can report. A hand census also invents keys, which is why UNKNOWN is worth reporting at all.

Three genres, two assertions. A completion document's Error keys section promises to be the whole vocabulary in one place, so both faults are reported against it. A sample's package document and a package's hand-written module guide (tom_core_*/doc/) are read whole instead, and only ABSENT is.

The weaker assertion is not a shortcut in either case. A guide distributes its keys by topic on purpose — authentication.md houses seventeen login.error.2fa.* in an ### Outcomes table and the rest across two Failure keys tables — so reading only the first matching section would report the other twenty-odd as missing. And prose about an API is full of dotted tokens that are not keys: preferences.getOr is a method reference, and no shape tells it from a key of the preferences family. Over the whole corpus UNKNOWN produced six findings on the guides and four were exactly that.

Adding the guides is what the 330 in this gate's baseline are. The gate had audited only sections headed exactly Error keys, in one repository; the guides spell theirs Failure keys and live in this one, so they were reported clean by never being opened — which is how six keys went missing from authentication.md while the run before it read 0 defective across 2 sections. 33 guides carry a vocabulary, 24 are short of it, and four documents hold most of the debt. It is frozen rather than repaired for the reason the ratchet exists: writing 330 reference entries is separate work, and until it is done every new unnamed key would land unnoticed among them.

A guide is matched to its module by position — PROSE_PACKAGES, the same map check_module_dependencies.py walks — because unlike a completion document a guide does not open with its source path. Both genres are required to resolve, and separately: one is found by a glob and the other by that map, so either can stop resolving while the other still does, and a single combined count would hide it. Breaking the map makes the run exit 2, not report clean.

A [name] in a /// comment renders as a link when it resolves and as plain text when it does not, so renaming a member turns every reference to it into prose without anything failing. The obvious detector, the comment_references lint, is the wrong tool here: it flags hundreds of correct references to real classes in sibling files (353 of 5556, measured — see report_crosslib_refs.py below), and satisfying it would mean adding imports that exist only for prose, several of them cycles. This check takes the part of the problem that has no such ambiguity — a private name can only ever resolve inside its own library, so whether it exists is answerable from that library alone. That is also exactly the shape a rename leaves behind. 

python3 tool/check_dartdoc_build.py                  # the gated packages
python3 tool/check_dartdoc_build.py tom_core_server  # one package, ad hoc

The other half of the same question, and the only thing in the toolchain that answers it: dart doc itself. The gate above asks whether a referenced name exists; this one builds the documentation and requires the build to say nothing at all.

The two are complements rather than rivals, and the difference is the population. comment_references judges every reference in the tree, which is why it cannot be turned on here. dart doc judges only what is reachable from the package barrel — the surface that ships, where a reference either resolves for the reader or does not and there is no import graph to trade away. Eleven references in tom_core_kernel, against the 353 the lint would have raised.

Left alone the class does not stay still: eight unresolved references were recorded in this package on 2026-08-19, and three weeks later the same command reported eleven — two of the original eight repaired in passing, five new ones arrived, across four unrelated modules. Each is one bracketed word inside a comment that reads perfectly, which is why review does not catch them and a build does.

Every warning counts, not only unresolved references: a documentation build that is allowed to say one thing is a build nobody reads. The rendered HTML is thrown away — 18 MB for tom_core_kernel alone, and what the gate wants is the log, which names every fault by file and line. The log is kept under tool/ztmp/dartdoc/. Packages are gated only once they are silent, the same rule check_doc_dart_blocks.py states.

Fenced blocks are skipped and inline code spans blanked, which is correctness rather than tidiness in both directions: a naive scan reads operator [](Object? key) in every api_summary_*.md as a link, and rewrites the template inside a `markdown fence into something true only of the file containing it. Both happened while this gate was being written.

A fourth rule, REFERENCE, catches the shape this gate was blind to by construction — a bracketed inline code span with no target and no definition, in a file carrying no [label]: target line: 

An edge binds one [`BearerTokenAuthenticator<P>`], parameterised on its
principal type.

That is dartdoc's square-bracket syntax carried into a markdown file, where markdown renders it as literal brackets around a code span, so the reader meets punctuation where the author meant a pointer. (The example sits in a fence because fences are skipped — otherwise this paragraph would be a live instance of what it describes, which is the same reason check_source_citations.py keeps this README out of its own scope.)

The blindness is worth stating because it is the argument for putting the rule here rather than in a gate of its own. The three rules above scan for ](, and they run after inline code has been blanked — but the label of one of these is the code span, so after blanking the line reads [ ] with nothing left to match. A reference with no definition also has no target, so nothing in a link-resolving checker can ever see one. Thirty-four sat across four packages while this gate reported zero, eighteen of them in a single tom_flutter_ui page and nine in a tom_core_agentic page that no scan had read.

Only bracketed code spans are matched. A bare [Some Name] in prose is ordinary English punctuation far more often than a broken link, and a rule that could not tell them apart would be the gate crying wolf. The repair is almost always to drop the brackets: of the thirty-four, not one had an anchor it could have pointed at, so making them links would have meant inventing thirty-four targets — and a cross-document #fragment is accepted here and validated by nothing, which is a worse answer than a plain code span. 

python3 tool/check_doc_ai_citations.py                 # the whole repository
python3 tool/check_doc_ai_citations.py tom_flutter_ui  # one subtree

Finds shipped files that cite a document in the AI-state layer. That layer is a separate repository (tom_agent_state) mounted by symlink, absent from any checkout of tom_ai/core, so such a citation cannot resolve for anyone reading a package. Two sites in tom_flutter_ui/doc/ cited a quest planning document, and the section doing so called it the canonical layout contract — a shipped document deferring its authority to a file its reader cannot obtain, which leaves the contract effectively unstated.

Two faults, for the two shapes a citation takes. AILINK is a path under _ai/. AINAME is the shape a citation takes once its author knows the document well enough to stop saying where it lives: a bare filename — a quest's deferral note, or a completion document's name. Three of those in one package's library and docs had been written by three different passes, and one pointed at a document that did not even carry the claim it was cited for. A name is a fault when it belongs to a .md or .yaml file in the quest folders of _ai/ — each quest's machine-local history/ excluded — and to no file anywhere in this repository, so README.md or pubspec.yaml never match. When the quest tree is absent the gate reports NOQUESTS as a fault rather than passing half-measured.

The cited file exists, so this is not a dangling link but an unreachable one, and that distinction is why the defect survives a scan: neither find nor git ls-files follows the _ai symlink, so a citation of a file that is present reads as "file does not exist" to any tool run from the container root. Keying on the citation rather than on the target is what makes the answer stable.

Every .dart and .md file is in scope, CHANGELOG.md included — it ships, and a reader following an entry to a document they cannot open is stranded as surely as one following doc/. _copilot_guidelines/, test/ and tool/ are out of scope because their readers work inside this workspace, where the mount is present; generated Dart is skipped because its comments are copies of scanned source. One _ai/ path is not a citation: _ai/trail/ is where the Tom extension writes its prompt trail in whichever workspace it runs in, and the agent models that mirror that layout name it as code names any runtime directory. 

python3 tool/check_open_ends.py          # the report
python3 tool/check_open_ends.py --quiet  # findings only

Finds completion documents that never say what is still open. completion/README.md requires every document to close with a ### What is still open subsection, because the section reads as a claim either way: present means the unit was assessed and this is the result, absent means it was not assessed — which is not the same as nothing being open, and is the reading a later scan has to assume.

Two faults, and the second is the cheap evasion. MISSING is no heading at all. EMPTY is a heading with nothing under it — a legitimate claim ("assessed, nothing open") that the contract asks be written as one, with the date, because a bare heading and a forgotten heading look identical.

This is the one gate in the suite whose count is expected to fall rather than sit at zero, and it is held rather than driven there in a sweep: writing every missing section in one pass would produce the artifact the requirement exists to prevent — a section per document asserting an assessment nobody performed. The section is written when the unit is assessed, so each completed assessment lowers the number by one and the ratchet then requires the drop be recorded. 

python3 tool/check_open_ends_ledger.py             # the report
python3 tool/check_open_ends_ledger.py --self-test # plant each fault, require detection

Holds each ### What is still open section to the quest todos still open on its unit. The gate above asks whether the section is there; this one asks whether it is still true.

A section is written once, when the unit is assessed. Every todo filed against that unit afterwards is a fact about it the section does not know, and nothing connected the two — so a section goes on saying "nothing is open" while work is queued against the same code. The mcp_auth section did exactly that one turn after it was written, with three todos filed and unworked; two other sections said literally "Nothing." while four unclosed todos sat on their units.

The join is an equality, not a heuristic. A completion document is named <project>_<module>_{new,changes}.md and a todo carries scope.project and scope.module, so nothing here reads prose to decide what a document is about. UNNAMED is a todo open on the unit that the section never names; PHANTOM is an id the section names that the corpus does not contain.

A todo whose scope.files names the completion document is out of scope for it — a todo asking for the section to be written would otherwise report itself as an open end forever. That is a rule about what the todo is about rather than an exemption list, so the next one needs no edit here.

The obvious third question — a struck-through item citing a todo that is not completed — is deliberately not asked. A closed item legitimately cites an open todo when a finding moved rather than ended, which is what mcp_auth's reference-link item does: closed on that page, still open on two others, with the id named so a reader can follow it. Faulting that would fault the sentence worth writing. 

python3 tool/check_suite_figures.py             # the report
python3 tool/check_suite_figures.py --self-test # plant each fault, require detection

Holds tom_core_samples/assets/architecture/ and every document that embeds from it to one another. A figure store fails silently in three ways — a figure nobody embeds, an embed whose file was renamed (a renderer shows a blank), and an inventory that misses a figure — and the "adding a figure" checklist in tom_core_samples/assets/README.md has four manual steps, the last of which, registering the figure, is the one that gets skipped.

ORPHAN, DANGLING and INVENTORY are those three; the inventory is compared in both directions, and each row's "Embedded by" links must be exactly the documents that embed the figure. SITE, ALT and SVG hold the convention: the <!-- Figure: … --> comment above each embed and the Text / mermaid equivalent disclosure below it, alt text that is a sentence rather than a label, and a viewBox and opening description comment on every SVG. Fenced blocks and inline code are skipped, so the README's own recipe is not read as an embed. Whether an SVG parses is check_figure_wellformed's question, and a line number cited inside one is check_source_citations'.

Its first run faulted figure 09 as an orphan. A1's alt text contains projectRoleFieldGrades[role], balanced brackets CommonMark allows in link text, which the embed pattern had not. The pattern now allows one level of nesting — the fault was the checker's, and the self-test runs against the real files, so a pattern that stops matching shows up as a failure rather than as a cleaner repository.
