Shutdown cleanup module for graceful process termination.

This module provides a comprehensive system for managing cleanup operations when a process receives termination signals (SIGHUP, SIGINT, etc.). It ensures that resources are properly released and cleanup handlers are executed in an orderly fashion before the process exits.

The module supports three types of cleanup mechanisms: - [TomDisposable]: Objects that implement a dispose() method - [TomClosable]: Objects that implement a close() method - [TomSignalHandler]: Custom signal handlers for specialized cleanup logic

Each of the three may be asynchronous. The shutdown awaits whatever an entry returns before it calls the next one, within a per-phase budget ([TomShutdownCleanup.phaseTimeout]) that keeps one entry that never finishes from holding the process open.

Quick Start

Registering a resource is the whole setup. Signal listening is already active — [TomShutdownCleanup] registers SIGHUP and SIGINT in its constructor — so there is no arming step to remember or to get wrong. 

// Use the default global instance
tomShutdownCleanup.addClosable(myDatabaseConnection);
tomShutdownCleanup.addDisposable(myStreamController);

See also: - [TomShutdownCleanup] for the main cleanup coordinator - [TomCloseAdaptor] for adapting objects without explicit interfaces

class TomClosable

abstract class TomClosable

Interface for objects that can be closed during shutdown.

Implement this interface for objects that need to be closed when the process terminates. The [close] method will be called automatically by [TomShutdownCleanup] when a termination signal is received.

Example

class MyConnection implements TomClosable {
  Socket? _socket;

  @override
  void close() {
    _socket?.close();
    print('Connection closed');
  }
}

// Register with shutdown cleanup
final connection = MyConnection();
tomShutdownCleanup.addClosable(connection);

Methods

FutureOr<void> close()

Closes resources held by this object.

This method is called automatically during shutdown cleanup. Implementations should close all connections, streams, or other resources that require explicit closing.

May be asynchronous. The shutdown awaits a returned Future before it closes the next object, so a flush, a socket close or a queue drain has finished by the time the phase moves on; a failure inside that future is reported like one thrown by the call itself.

The wait is bounded. Every phase has [TomShutdownCleanup.phaseTimeout] to finish in, and a phase that overruns it is abandoned — the entry it was waiting on and every entry behind it — so a close that never completes costs the rest of its phase, not the whole shutdown.

class TomCloseAdaptor

class TomCloseAdaptor implements TomClosable

Adaptor that wraps objects with close/dispose methods to implement [TomClosable].

This class uses reflection to find and invoke close or dispose methods on objects that don't explicitly implement [TomClosable] or [TomDisposable]. It reaches the method through the global tomReflector, so it works on classes in your own build that carry @tomReflector — typically ones already annotated for JSON — and not on types from outside it.

Example

// A class of your own, annotated for reflection, whose teardown method
// you would rather not re-expose by implementing TomClosable.
@tomReflector
class SessionStore {
  void close() { /* ... */ }
}

final adaptor = TomCloseAdaptor(SessionStore());
tomShutdownCleanup.addClosable(adaptor);

// Specify a custom method name
@tomReflector
class Worker {
  void shutdown() { /* ... */ }
}

tomShutdownCleanup.addClosable(TomCloseAdaptor(Worker(), 'shutdown'));

Limitations

  • The target method must have no required parameters
  • The target's class must be annotated with @tomReflector and its

generated reflection data must have been initialized, which means a build_runner step in the package that declares the class - Consequently the adaptor cannot wrap a type you do not own: dart:io's HttpClient, or any class from a package you cannot annotate, is out of reach no matter what methods it declares. Wrap such an object in a small class of your own that implements [TomClosable] instead — which is also cheaper, because it needs no reflection at all

The constructor throws — at registration, not during the shutdown — with one of three keys, each carrying the target's runtime type as the type parameter: - shutdown_cleanup.close_adaptor.not_reflectable: the object's class is not reflectable. A [TomReflectorException], the type the package raises for that condition everywhere. - shutdown_cleanup.close_adaptor.no_close_method: no close/dispose method — or no method of the given name — anywhere in the class's chain. A [TomCloseAdaptorException]; method holds the name asked for, or null when none was. - shutdown_cleanup.close_adaptor.method_requires_parameters: the method has a required parameter the adaptor cannot supply. A [TomCloseAdaptorException]; method and parameterCount name it.

All three are [TomException]s, so a caller catches them in one clause.

Static

static ClassMirror<dynamic> _reflectClass(Object closableObject)

Resolves the class mirror of [closableObject], insisting it is reflectable.

This is the adaptor's most likely failure rather than an exotic one: the class is reached for when a type does not implement [TomClosable] or [TomDisposable], and the types that do not are frequently the ones nobody can annotate. Left unguarded, tom_reflection answers with a NoSuchCapabilityError — an [Error], not an [Exception] — that names the type and nothing else: not the operation that wanted it, and not the annotation that would fix it. A caller guarding the constructor with on Exception would miss it entirely, even though the constructor's two other failures are exceptions. Reporting it as a [TomReflectorException] is what the rest of the package already does for this same condition.

It is not logged on the way out. Unlike the shutdown diagnostics this happens at construction time, in the caller's own control flow, and the thrown object carries the full detail to whoever asked for it.

static MethodMirror? _resolveCloseMethod(ClassMirror<dynamic> classMirror, String? methodName)

Resolves the close/dispose method to invoke, walking the superclass chain.

ClassMirror.declarations holds only the type's own members, so a close()/dispose() inherited from a superclass or mixin is invisible to the leaf type alone. This walks from the concrete type up its superclass chain, so the most-derived class wins and, at each level, an explicit [methodName] is honoured (otherwise close is preferred over dispose). Returns null when no matching method exists anywhere.

class TomShutdownCleanup

class TomShutdownCleanup implements TomDisposable

Central coordinator for graceful shutdown cleanup operations.

[TomShutdownCleanup] manages the orderly cleanup of resources when the process receives termination signals. It automatically listens for SIGHUP and SIGINT signals by default, and supports adding additional signals as needed.

The cleanup process executes in the following order: 1. Signal handlers (custom cleanup logic) 2. Closables (objects implementing [TomClosable]) 3. Disposables (objects implementing [TomDisposable])

Every entry is awaited before the next one is called, and each phase has [phaseTimeout] to finish in. A failing entry — whether it throws or its future fails — does not stop the ones behind it: the failure is reported with its exception and the top frames of its stack, written to [output] (print by default), and suppressed by [silent].

Basic Usage

Registration is the only setup step; the constructor has already begun listening for SIGHUP and SIGINT. 

// Use the global instance
tomShutdownCleanup.addClosable(databaseConnection);
tomShutdownCleanup.addDisposable(streamController);

Running it yourself

// Returns once every entry has finished, or its phase was abandoned.
await tomShutdownCleanup.performShutdown();
exit(0);

Custom Signal Handlers

tomShutdownCleanup.addSignalHandler((signal) async {
  print('Received signal: $signal');
  await flushJournal(); // awaited before the closables run
});

Adding Additional Signals

// Listen for SIGTERM in addition to default signals
tomShutdownCleanup.addSignal(ProcessSignal.sigterm);

Lifecycle

An instance is single-use. It is armed from construction, runs its shutdown once — [performShutdown], or the first watched signal — and is then spent: [hasShutDown] reads true for the rest of its life, every later [performShutdown] is handed that finished shutdown, and an entry registered afterwards is kept but never runs. Nothing resets it, because "the cleanup runs exactly once" is the guarantee the rest of this class is built on — a second run would close again what the first had closed.

A subsystem that restarts within one process therefore builds a new instance for each run and disposes the one it replaces.

Nesting coordinators

A coordinator is a [TomDisposable], so one may be registered on another — a hosted runtime that keeps a coordinator per session hands it to its own. The outer shutdown then disposes the inner coordinator in its disposables phase, awaited like any other entry: the inner watchers are cancelled and its registrations dropped.

Disposing does not run the inner shutdown, so its resources would be let go unclosed. To have them closed, run the inner shutdown from a signal handler on the outer — the handlers phase is awaited, and comes before the disposables phase that releases the inner coordinator: 

outer
  ..addSignalHandler((signal) => inner.performShutdown(signal: signal))
  ..addDisposable(inner);

Creating Custom Instances

// Create a separate cleanup handler for specific signals
final customCleanup = TomShutdownCleanup();
customCleanup.addSignal(ProcessSignal.sigusr1);
customCleanup.addSignalHandler((signal) {
  // Handle USR1 signal specifically
});

// A custom instance that outlives the program needs nothing further. One
// that does not — in a test, a sample, or any bounded scope — must be
// disposed, because its watchers keep the process alive:
await customCleanup.dispose();

Methods

Future<void> performShutdown({ProcessSignal signal = ProcessSignal.sigint, bool fromSignal = false})

Runs the shutdown cleanup — registered signal handlers, then closables, then disposables — exactly once across the instance's life, and completes when it has finished.

Every entry is awaited, within [phaseTimeout] per phase, so the returned future completes only once the teardown has happened or been given up on. That is what makes it safe to exit the process after awaiting it.

The first call starts the shutdown and every later one — manual or signal-driven, during it or after it — is handed that same shutdown rather than a second run. A caller that awaits it therefore always waits for the real thing, whoever started it. Do not await it from inside one of the entries: the entry would be waiting for the shutdown that is waiting for the entry, and only the phase timeout would end it.

External code calls this directly to run the cleanup without an OS signal; that manual path always runs (it ignores [paused]) and stays quiet. The signal-driven path passes [fromSignal] true, which honours [paused] (skip while paused) and gates the status messages on [silent]. [signal] is forwarded to the registered signal handlers.

Future<void> _executeCleanup(ProcessSignal signal, {required bool announce})

Runs the three cleanup phases in order — signal handlers, then closables, then disposables — each finishing, or being abandoned, before the next begins.

Future<void> _runPhase<T>(List<_Registration<T>> registrations, String label, FutureOr<void> Function(T) action)

Runs [action] over every registration in [registrations] in order, awaiting each entry that returns a Future, within a budget of [phaseTimeout] for the phase.

This is the single owner of the per-entry policy all three phases share. A failing entry — thrown by the call or by the future it returned — never aborts the phase: a Failed to call $label $item: $exception diagnostic is written to [output], followed by the top [_diagnosticStackDepth] frames, unless [silent]. The exception and its trace are part of the report because a shutdown runs once, usually unattended, and cannot be re-run to find out what went wrong. Message and trace go out in a single line so that concurrent output cannot separate a failure from its evidence.

The list is consulted afresh for each entry rather than iterated as it stood when the phase began, because entries run the application's code and that code may register or unregister: an entry unregistered before the phase reaches it is not run, and one registered while the phase runs still is.

When the budget runs out the phase is abandoned: the entry being awaited is left to finish on its own, and the ones behind it are not called. A synchronous entry is never awaited, so a phase of synchronous entries runs straight through without yielding.

void _reportFailure(String label, Object? item, Object exception, StackTrace stackTrace, {bool abandoned = false})
void _reportAbandoned<T>(String label, List<_Registration<T>> registrations, {required T? waitingOn})

Reports that the [label] phase ran out of [phaseTimeout]: [waitingOn] had not finished — or, when null, the budget was already spent before the next entry could be called.

void _emit(String line)

Writes [line] to [output], or to print when [output] throws.

The one place a line leaves the module. The fallback is what keeps the shutdown record from vanishing with the sink that was meant to hold it — a logging system is among the things a shutdown tears down — and what keeps a failing sink from failing the shutdown it is reporting on.

void addSignal(ProcessSignal processSignal)

Adds an additional system signal to listen for.

By default, SIGHUP and SIGINT are already registered. Use this method to add additional signals like SIGTERM.

Idempotent per signal: registering one that is already watched does nothing. Without that, the second watcher would drive the cleanup a second time on every arrival — harmless to the cleanup itself, which runs once, but it makes a single Ctrl-C report itself twice and claim on its own first arrival that shutdown had already been performed. Since the constructor registers SIGHUP and SIGINT, that collision is one an ordinary caller can walk into simply by naming a default.

[processSignal] - The signal to start listening for.

Example

tomShutdownCleanup.addSignal(ProcessSignal.sigterm);
Future<void> cancelAll()

Releases everything the instance holds: cancels every OS-signal watcher — SIGHUP, SIGINT and any added with [addSignal] — and drops every registered signal handler, closable and disposable.

It runs nothing. The registered entries are let go, not closed: call [performShutdown] first if they still need releasing. Afterwards the instance no longer keeps the process alive and no longer holds a reference to anything registered on it, so a manual [performShutdown] finds nothing to do.

It empties the instance without spending it. A registration made afterwards is held again, and a later [performShutdown] runs it — unless the shutdown has already run, which spends the instance regardless (see "Lifecycle"). Called during a running shutdown, it leaves the entry being awaited to finish and drops the entries not yet reached.

Safe to call more than once.

Future<void> dispose() override

Tears the instance down — the same operation as [cancelAll], under the name teardown is looked for by. Call this for any short-lived [TomShutdownCleanup] so its watchers stop keeping the process alive and its registrations stop keeping their entries reachable; the process-lifetime global [tomShutdownCleanup] normally never needs it.

This is [TomDisposable]'s method, so a coordinator registered on another is torn down by the outer shutdown — see "Nesting coordinators".

Static

static int _diagnosticStackDepth

Frames kept from a failing cleanup's stack trace.

Bounded rather than unlimited: a shutdown can fail in several entries at once, and full traces from each would bury the failure list in the very output an operator is scanning. The frames that identify a close() or dispose() failure are the top ones.

static Duration defaultPhaseTimeout

The [phaseTimeout] a new instance starts with.

Long enough for a flush, a socket close or a pool drain on a healthy system; short enough that a teardown that has hung is given up on before an operator reaches for kill -9.

static _Registration<T>? _firstUnreached<T>(List<_Registration<T>> registrations)

typedef TomShutdownUnregister

typedef TomShutdownUnregister = void Function()

Takes back one registration made on a [TomShutdownCleanup].

Returned by [TomShutdownCleanup.addSignalHandler], [TomShutdownCleanup.addClosable] and [TomShutdownCleanup.addDisposable], in the manner of a stream subscription's cancel. Calling it removes that registration and nothing else — the same object registered twice has two registrations — and releases the coordinator's reference to the entry. Calling it again, or after the entry has run, does nothing.

typedef TomSignalHandler

typedef TomSignalHandler = FutureOr<void> Function(ProcessSignal)

Handler function type for processing system signals.

Called when a registered signal is received by the process. The [onData] parameter contains the specific signal that was received.
