import 'package:tom_core_kernel/src/tombase/http_connection/server_connection.dart';

Server connection and HTTP client module.

This library provides a comprehensive HTTP client infrastructure for making server requests. It includes:

  • [TomServerCall] - Low-level HTTP request handling with abort support
  • [TomServerChannel] - HTTP client management with connection pooling
  • [TomServerEndpoint] - Type-safe endpoint execution with serialization
  • [TomHttpClientFactory] - Pluggable HTTP client creation

Example

// Create a channel to a server
final channel = TomServerChannel('api.example.com', 443);

// Create and execute a server call
final call = channel.prepareCall(TomServerCallSpecs(
  'POST',
  Uri.parse('https://api.example.com/users'),
));

call.send(TomServerCallLoad(
  stringBody: '{"name": "John"}',
  contentType: 'application/json',
));

final response = await call.readAsString(utf8);

class TomHttpClientAbstractFactory

abstract interface class TomHttpClientAbstractFactory

The contract for producing an HTTP client.

Implement it to supply a client of your own — one carrying an interceptor, a proxy, a pinned certificate, or a scripted response in a test: 

class MyClientFactory implements TomHttpClientAbstractFactory {
  @override
  Client getClient() => MyClient();
}

TomHttpClientFactory.setGlobalHttpClientFactory(MyClientFactory());

Implementing this rather than extending [TomHttpClientFactory] is what a producing factory wants: [TomHttpClientFactory] is the resolver, whose getClient forwards to an instance factory or to the global one, and a subclass that forgets to override it forwards forever — registered as the global, to itself.

class TomHttpClientFactory

class TomHttpClientFactory implements TomHttpClientAbstractFactory

Resolves an HTTP client through a per-instance override or the global factory.

It produces no client of its own — [TomDefaultHttpClientFactory] does that, and so does any [TomHttpClientAbstractFactory] an application registers. This is the type the framework holds when it has somewhere to ask: a [TomServerChannel] with no factory of its own carries one, and it answers from whatever the process has been configured with.

Example

// Set a custom global factory
TomHttpClientFactory.setGlobalHttpClientFactory(MyCustomFactory());

// Or initialize with default
TomHttpClientFactory.initialize();

Methods

Client getClient() override

Resolves a client, delegating to [instanceClientFactory] — or, if none was set, to the global factory.

This class creates no clients of its own; it only forwards. A [TomHttpClientAbstractFactory] implementation is what eventually produces one. Delegation therefore has to end somewhere, and it does not when the chain leads back to a factory already in it — most easily by registering a plain TomHttpClientFactory as the global, which then forwards to itself.

Such a chain would recurse until the stack ran out, reporting a wiring mistake as a StackOverflowError that names neither the factory nor the registration. It is refused under server.connect.client_factory_delegation_cycle instead.

Sets the global HTTP client factory.

static void initialize([TomHttpClientAbstractFactory? defaultFactory])

Initializes the factory system.

If not already initialized, sets the global factory to the provided factory or the default.

Deliberately one-shot: the first caller in a process wins, so a library initializing on the way past cannot displace the host's choice. The consequence is that [defaultFactory] is ignored once anything has initialized — call [resetGlobalHttpClientFactory] first if you need a second initialization to take effect.

static void resetGlobalHttpClientFactory()

Returns the factory system to its unconfigured state, so a later [initialize] or [setGlobalHttpClientFactory] takes effect again.

The global factory is process-wide state and [initialize] is one-shot, so without this a test suite would be stuck with whatever the first test installed, and every test after it would silently share that decision.

Only the statics are restored. A [TomHttpClientFactory] that has already resolved keeps the delegate it cached in [instanceClientFactory]; discard such instances rather than expecting this to reach them.

class TomRequestTimeoutException

class TomRequestTimeoutException extends TomException

Exception thrown when a request outlives its [TomServerCallSpecs.timeout].

Deliberately not a subtype of [TomRequestAbortedException], even though a timeout aborts the request on its way out: the two mean opposite things to the caller. An abort is this application's own decision and repeating it would be pointless; a timeout is the server failing to answer in time, which is the textbook case for a retry. A caller that wants to treat them alike can catch [TomException]; one that wants to retry only timeouts could not separate them again if this were a subclass.

class TomServerCall

class TomServerCall

Handles a single HTTP request/response cycle.

Provides methods to send a request, read the response, and abort pending requests. Each instance can only be used once - call [reset] to reuse.

Example

final client = Client();
final specs = TomServerCallSpecs('GET', Uri.parse('https://api.example.com/data'));
final call = TomServerCall(client, specs);

call.send(TomServerCallLoad());
final bytes = await call.read();
final response = utf8.decode(bytes);

Methods

void applySpecValues()

Applies specification values to the request.

void applyLoadValues(TomServerCallLoad load)

Applies payload values to the request.

Writes whichever body [load] carries. It carries at most one — the type checks that when it is built and cannot be changed afterwards — so nothing is re-checked here. Were two ever to arrive, the fields would be applied in order and package:http would reject the second against the content type the first had already set, leaving the request half-written.

The order of the two lines that precede the body is load-bearing, because package:http reads both back when the body is assigned. The encoding is the charset the body is encoded with, and the content type is the header that charset is then written into; a type applied after the body would be a type the body never saw, replacing the labelling package:http had just derived and dropping the charset with it.

void reset({String? stringBody, Uint8List? byteBody, Map<String, String>? bodyFields})

Resets the call for reuse with new body content.

Clears the response and creates a new abortable request.

TomServerCall send(TomServerCallLoad load)

Sends the request with the given payload.

Can only be called once per call instance (use [reset] to retry). Returns this instance for method chaining.

The rejection of an already-sent call happens before anything is applied, so a refused send leaves the request describing what was actually sent. A rejection that still mutated would leave the object describing a request that never happened, which a caller inspecting it after the throw, or a later [reset], would read back as real.

[load] needs no check here: it is immutable and validated its single body on construction, so the value that arrives is the value that was built.

Throws [TomServerConnectionException] if called more than once.

void _requireSent(String what)

Refuses a read of [what] before [send], under the one key server.send.illegal_state_read_must_be_after_send.

The key lives here rather than at each reader, for the same reason it does in [_ensureNotYetRead]: a key's last segment names the condition (see [TomException]), and "nothing has been sent" is one condition however many members can meet it. Supplied by the caller it became seven keys for that one condition — six accessors each naming itself, plus [read] — so code handling "this call has not been sent" had to match seven, and an eighth reader would have brought an eighth.

[what] names in prose the value the caller was after ("the response headers"). It is the detail those seven keys were carrying, and it reaches the message and the read parameter instead, where a detail belongs and costs the contract nothing. A new reader passes only [what] — there is no key to choose, so the convention holds without anyone deciding again.

Future<StreamedResponse> _requireSentResponse(String what)

Awaits the in-flight response, refusing a read of [what] before [send] exactly as [_requireSent] does.

Split from [_requireSent] because [read] needs the guard without the await: it defers awaiting the response into [_awaitTransfer] so that its timeout covers the headers as well as the body.

void _ensureNotYetRead()

Guards against reading the response more than once, throwing [TomServerConnectionException] when the body has already been consumed.

The key lives here rather than at each reader: there is one "already consumed" condition, so it has to raise one key. Letting each caller pass its own turned a single condition into a contract that could drift — and it did, one reader having spelled the key read_only_once.

Future<Uint8List> read()

Reads the response body as bytes.

Can only be called once after [send] — the body is a stream, and draining it leaves nothing for a second reader. Every reader reaches the body through here, so all of them refuse a second read under the one key server.send.illegal_state_only_read_once.

Throws [TomServerConnectionException] under server.send.illegal_state_read_must_be_after_send if called before send, or server.send.illegal_state_only_read_once if called again. Throws [TomRequestAbortedException] if the request was aborted.

Future<Uint8List> _awaitTransfer()

Awaits the response and drains its body, translating an abort raised by either stage into [TomRequestAbortedException].

Split out of [read] so that a single deadline can be placed around both stages at once, and so that an abort arriving before the headers do is reported the same way as one arriving mid-body.

Future<String> readAsString(Encoding ec)

Reads the response body as a string with the given encoding.

Can only be called once after [send], and refuses a second read exactly as [read] does — it is [read], with a decode on the end, so it carries no guard of its own.

Future<Map<String, String>> getResponseHeaders()

Gets the response headers after sending.

Throws [TomServerConnectionException] under server.send.illegal_state_read_must_be_after_send if called before send.

Gets the HTTP status code after sending.

Throws [TomServerConnectionException] under server.send.illegal_state_read_must_be_after_send if called before send.

Future<int?> getResponseContentLength()

Gets the response content length after sending.

Throws [TomServerConnectionException] under server.send.illegal_state_read_must_be_after_send if called before send.

Future<bool> getResponseIsRedirect()

Checks if the response is a redirect after sending.

Throws [TomServerConnectionException] under server.send.illegal_state_read_must_be_after_send if called before send.

Future<String?> getResponseReasonPhrase()

Gets the reason phrase after sending (e.g., "OK", "Not Found").

Throws [TomServerConnectionException] under server.send.illegal_state_read_must_be_after_send if called before send.

Static

static void _requireFormContentType(String? contentType)

Refuses a form body that [contentType] labels as something else.

package:http encodes form fields as application/x-www-form-urlencoded and rejects any other declared type — with a bare StateError that names neither the call nor the setting that disagreed, raised partway through writing the request.

The check belongs here rather than on [TomServerCallLoad] because the label has two sources: the load's own contentType and the spec's headers. Only the request has seen both, so a constructor check would pass every load whose spec carried the offending header — a guard that reads as complete and is not.

A type that merely carries parameters — ...urlencoded; charset=utf-8 — is the same type, so the media types are compared rather than the strings. An unparseable value is left alone: package:http reports a malformed content type in its own terms, and guessing here would name the wrong fault.

Static

static int jsonDecodingError

Internal error code for JSON decoding failures.

static int noResponseError

Internal error code when no response was received.

Raised by [TomServerEndpoint.send] when the request never produced a response — a refused connection, an expired deadline, an aborted request. Such an error carries no status (statusCode is 0) and no body; the underlying failure is in [exception].

static int serverError

Internal error code for general server errors.

Distinct from [noResponseError] because the two are different answers to the same question: this one means the server replied and the reply was a failure, that one means there was no reply to read. A caller switching on [internalError] has to be able to tell "the service said no" from "the service was not reachable" — they call for different handling and different retries.

static bool isSuccessStatusCode(int statusCode)

Whether [statusCode] is in the HTTP 2xx success range.

The one definition of "the server accepted this" in the module. Both [hasError] and the response handling in [TomServerEndpoint.send] read it, because when each spelled the test for itself they disagreed: send treated anything other than exactly 200 as a failure, so a 201 Created was routed away from the deserializer while hasError went on reporting no error.

static bool isNoContentStatusCode(int statusCode)

Whether a response with [statusCode] is defined to carry no body.

204 No Content and 205 Reset Content have no payload by definition (RFC 9110 §15.3.5–6), so for those an empty body is the expected shape and there is nothing to deserialize — as opposed to a status that promised a body and sent none, which stays a failure to parse.

class TomServerCallLoad

class TomServerCallLoad

Payload data for an HTTP request.

Supports three types of body content: - [stringBody] - Text content (JSON, XML, etc.) - [byteBody] - Binary content (files, images, etc.) - [bodyFields] - Form fields for URL-encoded requests

Only one type of body can be set at a time, and a load never changes after it is built: every field is final, so the constructor's check is a promise about the whole object rather than about one moment in its life. A load that exists describes exactly one request body — no consumer has to re-check it.

Example

// JSON body
final jsonLoad = TomServerCallLoad(
  stringBody: '{"name": "John"}',
  contentType: 'application/json',
  encoding: utf8,
);

// Form data
final formLoad = TomServerCallLoad(
  bodyFields: {'username': 'john', 'password': 'secret'},
);

Constructors

TomServerCallLoad.new({String? stringBody, Uint8List? byteBody, Map<String, String>? bodyFields, String? contentType, Encoding? encoding})

Creates a new request payload.

Only one of [stringBody], [byteBody], or [bodyFields] may be set; supplying more than one throws [TomServerConnectionException]. Because the fields are final, passing that check is the only way a load can come into existence.

A [bodyFields] body must also be labelled as a form, but that check is not here: the label can equally come from [TomServerCallSpecs.headers], which a load never sees. It is made once, against the request's effective content type, in [TomServerCall.applyLoadValues].

Properties

final String? contentType

The Content-Type header value, or null to let the body choose one.

Applied to the request ahead of the body, so package:http labels the bytes with what the caller named. Left null, the body picks the default its own shape implies: text/plain for [stringBody] and application/x-www-form-urlencoded for [bodyFields], both carrying the [encoding]'s charset. [byteBody] implies nothing and stays unlabelled.

There is deliberately no contentLength beside this. A Content-Type is the caller's to state — the bytes do not say what they mean — whereas a Content-Length is a fact about the body that the request measures for itself, and that this module's non-streaming request refuses to be told. Streaming uploads, where the length genuinely is unknown until it is declared, go through [TomHttpFileTransferClient] rather than through a load.

final Encoding? encoding

Character encoding for the body.

final String? stringBody

String body content (mutually exclusive with [byteBody] and [bodyFields]).

final Uint8List? byteBody

Binary body content (mutually exclusive with [stringBody] and [bodyFields]).

final Map<String, String>? bodyFields

Form field body (mutually exclusive with [stringBody] and [byteBody]).

A copy of what the constructor was given, so later edits to the caller's map cannot add a body to a load that was built without one.

factory TomServerChannel.forUri(Uri uri, {TomHttpClientAbstractFactory? clientFactory})

Creates a channel for the server [uri] addresses.

The port is [uri]'s own when it names one, and otherwise its scheme's: 443 for https, 80 for anything else. A URI writes its port only when it differs from the scheme's default, so deriving it any other way sends an ordinary https://host/path to port 80.

This is the derivation every caller that builds a channel from a URI shares — the channel behind an endpoint, a file-transfer client, a server's own login call — so the address a channel opens agrees with the address written into the call's specs.

class TomServerEndpoint

class TomServerEndpoint<T extends Object, R extends Object>

Type-safe API endpoint executor with automatic serialization.

Handles the complete request/response cycle for a typed endpoint: - Serializes request objects to JSON - Sends HTTP requests - Deserializes response objects - Handles error responses

Example

final endpoint = TomServerEndpoint.createApiServerEndpoint<
  CreateUserRequest,
  UserResponse
>(userApi['createUser']);

final (response, error) = await endpoint.send(CreateUserRequest(name: 'John'));
if (error?.hasError ?? false) {
  print('Error: ${error!.errorKey}');
} else {
  print('Created user: ${response.id}');
}

Constructors

TomServerEndpoint.new(TomServerChannel channel, TomServerCallSpecs specs, {Map<int, Type>? statusCodeResponseTypes})

Creates a new server endpoint.

Properties

TomServerChannel channel

The server channel for HTTP communication.

TomServerCallSpecs specs

The call specification.

Map<int, Type>? statusCodeResponseTypes

Maps failing status codes to the types their bodies carry.

Consulted only when the response is not a 2xx, so an entry never diverts a success away from [R]. An entry is honoured whatever type it names, [R] included: a failing status does not fill the result object, so the body arrives as [TomServerCallError.statusCodeResponse] either way.

Methods

Future<(R, TomServerCallError?)> send(T load, [R? responseObject])

Sends a request and returns the typed response.

Returns a tuple of (response, error). Check [TomServerCallError.hasError] to determine if the request succeeded.

Every way a call can fail reaches the caller through that tuple, including the ones where no response arrives at all — a refused connection, an expired deadline, an aborted request all come back as [TomServerCallError.noResponseError] with the underlying failure in exception, not as a throw past the tuple. The one exception is a server error that asks the client to rethrow, which raises [TomServerConnectionException] by request of the server.

  • [load]: The request object to send
  • [responseObject]: Optional pre-created response object to populate

Static

static TomServerEndpoint<requestType, responseType> createApiServerEndpoint<requestType extends Object, responseType extends Object>(TomApiEndpoint<dynamic, dynamic> apiEndpoint, {Map<String, Object?> parameters = const {}, TomServerCallSpecs? specs, TomServerChannel? channel, Uri? baseUri})

Creates a server endpoint from an API endpoint definition.

Automatically configures the channel, specs, and error handling based on the [TomApiEndpoint] configuration.

The address comes from [TomApiEndpoint.resolveUri], so this factory addresses exactly the route the declaration describes: path captures are substituted and mapped query parameters appended under the endpoint's own [TomApiEndpoint.urlParameterMapping]. Joining the templates here instead would make the declarative half of the contract unreachable through the very API that exists to build a call from it.

  • [apiEndpoint]: The endpoint definition from a [TomApi]
  • [parameters]: Values for the endpoint's URL parameters, keyed by

request-DTO field name — see [TomApiEndpoint.resolveUri] for how the two kinds bind. Ignored when [specs] names the address itself. - [specs]: Optional custom call specs. Supplying these bypasses resolution: the caller has then named the address outright. - [channel]: Optional custom server channel - [baseUri]: Where to address the call, defaulting to [TomClientRemoteContext.baseUri] — the API server. An authentication endpoint passes [TomClientRemoteContext.authenticationUri] here explicitly; that URI addresses the authentication server and nothing else, and the two differ only in a split deployment, so a call that named the wrong one would look correct on a single host.

Throws [TomEndpointException] when [apiEndpoint] does not match the type arguments, or when one of its path captures has no answering entry in [parameters].
