Tom Bean Locator - Dependency Injection and Service Locator System.

This module provides a lightweight dependency injection container that uses Dart reflection to automatically discover, instantiate, and wire service beans. It supports environment-specific and platform-specific bean implementations.

Key Features

  • Automatic Bean Discovery: Classes annotated with @TomComponent are

automatically discovered and instantiated. - Interface-Based Injection: Register beans by interface type for loose coupling. - Environment Support: Different bean implementations for dev/test/prod. - Platform Support: Platform-specific beans for iOS, Android, Web, etc.

Usage

// Define a service interface
abstract class UserService {}

// Implement for specific environment
@tomReflector
@TomComponent(UserService)
class ProductionUserService implements UserService {}

// Access via TomBean
final userService = TomBean<UserService>().get();

class TomBean

class TomBean<T>

A type-safe handle for accessing dependency-injected beans.

[TomBean] provides lazy resolution of beans registered in the bean context. Beans can be resolved by type or by name.

Resolution by Type

// Define service interface
abstract class UserService { ... }

// Register implementation (via @TomComponent annotation)
@tomReflector
@TomComponent(UserService)
class UserServiceImpl implements UserService { ... }

// Resolve by type
final service = TomBean<UserService>().get();

Resolution by Name

// Register with name
TomBean.withName("config", AppConfig());

// Resolve by name
final config = TomBean<AppConfig>.fromName("config").get();

Callable Syntax

TomBean supports callable syntax for concise access:

final TomBean<UserService> userService = TomBean();
// Later:
final user = userService().getUser(id);  // Calls get() then getUser()

Constructors

factory TomBean.fromName(String name)

Creates a bean handle that resolves by name.

[name] The registered name of the bean.

Example:

final config = TomBean<AppConfig>.fromName("appConfig").get();

The name need not be registered yet. A handle may be held as a field and the bean registered later in startup; the handle resolves on first use. [initializeBeanContext] does not force such a handle to resolve — see [validateBeanReferences] — so a still-unregistered name is not a boot failure.

factory TomBean.withName(String name, Object bean)

Registers a named bean and creates a handle for it.

[name] The unique name for the bean. [bean] The bean instance to register.

Throws [TomBeanLocatorException] if a bean with [name] already exists.

Example:

TomBean.withName("config", AppConfig());
factory TomBean.overrideWithName(String name, Object bean)

Registers a named bean, replacing whatever was registered under [name].

Where [TomBean.withName] refuses a name that is already taken — the guard that stops two startup paths from silently clobbering each other — this factory is the deliberate exception, for substituting an implementation in a test.

Example:

TomBean.overrideWithName("config", StubAppConfig());

Two consequences are worth knowing, because both fail silently:

  • A handle that has already resolved keeps the instance it resolved. Only

handles created (or first used) after the override see the replacement. - [initializeBeanContext] empties the registry, so an override must be applied after the pass that would otherwise bind the original.

factory TomBean.withType(Type t, Object bean)

Registers a bean by type and creates a handle for it.

[t] The type to register the bean under. [bean] The bean instance to register.

Throws [TomBeanLocatorException] if a bean with [t] already exists.

Example:

TomBean.withType(UserService, UserServiceImpl());

Note: registering a type before [initializeBeanContext] takes precedence over any @TomComponent registration for the same type — discovery leaves a key that is already bound alone. To substitute an implementation once the context is initialized, use [TomBean.overrideWithType]; this factory throws there rather than replacing.

[bean] is not checked against [t] here, and cannot be. [t] arrives as a Type value, and Dart has no expression that decides whether an object is an instance of one: is needs a type, not a value of type Type. Reflection does not close the gap either, and that is measured rather than assumed — tomReflector.canReflectType answers false for any class carrying no @tomReflector, which is precisely the population this factory exists to serve, and superinterfaces comes back empty even for a class it can reflect.

So the check happens where the relation is decidable: resolving TomBean<X>() has a real type argument, and a bean registered under X that is not an X raises beanlocator.bean_access.bean_not_assignable_to_type naming both the type asked for and the type found — rather than reporting the bean as missing, which sends the reader looking for a registration that is in fact right there.

factory TomBean.overrideWithType(Type t, Object bean)

Registers a bean by type, replacing whatever was registered under [t].

Where [TomBean.withType] refuses a type that is already bound — the guard that stops two startup paths from silently clobbering each other — this factory is the deliberate exception, for substituting an implementation in a test: 

initializeBeanContext();
TomBean.overrideWithType(UserService, MockUserService());

Three consequences are worth knowing, because all three fail silently:

  • A handle that has already resolved keeps the instance it resolved. Only

handles created (or first used) after the override see the replacement. - [initializeBeanContext] empties the registry, so an override must be applied after the pass, and re-applied after every later pass. - [bean] must be assignable to the type consumers ask for. It is not checked here — see [TomBean.withType] for why that is not possible — and a mismatch is raised by resolution as beanlocator.bean_access.bean_not_assignable_to_type.

Methods

Type getType()

Returns the type parameter [T].

T get()

Resolves and returns the bean instance.

Resolution strategy: 1. If already resolved, return cached instance 2. If named, look up by name in context 3. Otherwise, search by type assignability

Only a successful resolution caches. A handle that failed — nothing registered, or two implementations satisfying the same type — holds no instance, so every later call re-runs the lookup and throws again with the same key and the same parameters. A failure that answered once and then started returning a value would be worse than the failure.

Throws [TomBeanLocatorException] if resolution fails.

T _resolveByName()

Resolves bean by registered name.

T _resolveByType()

Resolves bean by type assignability.

The walk collects every assignable bean before deciding anything, and nothing writes [_bean] until exactly one candidate is known. That ordering is the point: assigning the first match as it is found and only raising on the second leaves the handle holding that first match, so [get] short- circuits on the cache and every later call answers with whichever implementation the registry happened to iterate first — the arbitrary resolution the ambiguity error exists to prevent, and silent, because the caller who receives the answer is not the caller who saw the throw. Ambiguity is an error, not a preference, so it is raised on every call.

Static

static Map<Type, Object> _tomBeansByType

Beans registered under a [Type] — by [TomBean.withType], by [installByEnvironment], and by annotation discovery.

Separate from [_tomBeansByName] rather than one Map<Object, Object> holding both, because the two are different namespaces that were only sharing a container. A String key can never equal a Type key, so the shared map was not unsafe; what it cost was that nothing said so. The declaration named Object, which is the one thing a registry should never be vague about; [_resolveByType] had to skip non-Type keys at runtime, a filter the type system expresses for free; and that walk iterated every named bean in order to reject it. Nothing reads the two together — resolution by name and resolution by type are separate methods with separate errors — so the only operation spanning both is emptying them, which [resetBeanContext] and a re-run of [initializeBeanContext] each do explicitly.

static TomBean<T> installByEnvironment<T>(Map<String, T Function()> factories, {String? environment})

Selects and installs exactly one implementation of [T] by the current runtime environment.

[factories] maps an environment name to the factory that builds the implementation for that environment. The active environment name — taken from [environment] when given, otherwise [TomRuntime.getCurrentEnvironment] — selects which single factory runs; the built instance is registered by type via [TomBean.withType], so a later TomBean<T>().get() resolves it.

This is the environment-selector form of dependency injection: the caller picks the environment name (e.g. from a launch flag), and the locator picks the collaborator from that name. Exactly one factory runs and exactly one bean is registered — there is no runtime dispatcher choosing between two installed implementations.

Throws [TomBeanLocatorException] if no factory is registered for the active environment. A missing mapping is a wiring bug, not a silent fallback. The same exception type — key beanlocator.environment.runtime_environment_not_initialized — reports an unconfigured runtime when [environment] is omitted and there is no active environment to read. Passing [environment] answers that question at the call site, so it needs no configured runtime at all.

static Object? getBeanByType(Type type)

Returns the bean registered for [type], or null if not found.

static Object? getBeanByName(String name)

Returns the bean registered with [name], or null if not found.

static void resetBeanContext()

Clears all registered beans and resets the initialization flag.

This empties the global bean context, drops every pending unresolved handle, and marks the context as uninitialized so a subsequent [initializeBeanContext] starts from a clean slate.

The bean context is process-global static state. Without a way to clear it, registrations leak between independent units of work — most visibly in tests, where a bean registered by one test would otherwise still be present in the next. Call this between such units to isolate them.

class TomBeanLocatorException

class TomBeanLocatorException extends TomException

Exception thrown when bean locator operations fail.

This exception is used throughout the bean locator system to indicate errors during: - Bean instantiation and registration - Bean resolution by name or type - Duplicate bean detection

Exception Keys

This is the complete set the module raises — every failure inside the bean locator arrives as this type, so on TomBeanLocatorException is a sufficient handler.

  • beanlocator.initialization.duplicate_bean_with_name: [TomBean.withName]

was given a name another bean already occupies. Use [TomBean.overrideWithName] to replace a binding deliberately - beanlocator.initialization.duplicate_bean_with_type: [TomBean.withType] was given a type another bean already occupies, including one discovery has bound. Use [TomBean.overrideWithType] to replace a binding deliberately - beanlocator.initialization.no_matching_implementation_found: every implementation of an interface was ruled out by its @TomEnvironment or @TomPlatform selector, leaving discovery nothing to bind - beanlocator.initialization.ambiguous_implementation: two implementations qualify equally for one interface - beanlocator.initialization.constructor_takes_arguments: a discovered component declares a constructor with a required parameter, and discovery calls the unnamed constructor with no arguments - beanlocator.bean_access.bean_not_found_by_name: nothing is registered under the name the handle resolves by - beanlocator.bean_access.bean_not_found_by_type: a bean is registered under the name, but is not an instance of the type the handle asks for - beanlocator.bean_access.no_bean_found_uninitialized: nothing is registered for the requested type — typically a handle resolved before [initializeBeanContext] ran, or an interface with no component - beanlocator.bean_access.bean_not_assignable_to_type: the requested type is registered, but to something that is not an instance of it. The sibling of the key above, and worth its own: a caller told the bean is missing goes looking for a registration that is right there - beanlocator.bean_access.more_than_one_implementation_found: two registered beans satisfy one requested type - beanlocator.environment.no_factory_for_environment: installByEnvironment has no factory for the active environment - beanlocator.environment.runtime_environment_not_initialized: An operation needed the active environment and the runtime was never configured. The operation and subject parameters name what was being wired.

class TomComponent

class TomComponent

Annotation to mark a class as a Tom component/service bean.

When applied to a class along with @tomReflector, the bean locator will automatically discover and instantiate the class during initialization.

Usage

Without Interface (Concrete Type)

@tomReflector
@tomComponent  // Uses TomNoInterface type
class MyService { ... }

With Interface

@tomReflector
@TomComponent(UserService)  // Registered as UserService interface
class MyUserServiceImpl implements UserService { ... }

Platform/Environment-Specific Beans

Combine with @TomEnvironment or @TomPlatform annotations to provide different implementations: 

@tomReflector
@TomComponent(UserService)
@TomEnvironment("test", isTest: true)
class MockUserService implements UserService { ... }

A selector matches the active deployment when the names agree — which TomEnvironment or TomPlatform instance carries the name is irrelevant, so the environment TomRuntime is given may be built at runtime from configuration. The name is the identity: TomEnvironment("test") and TomEnvironment("test", isTest: true) are the same environment as far as selection is concerned, and "none" is reserved for the sentinels that mean "unconstrained".

Dependencies come from fields, not from the constructor

Discovery builds every component by calling its unnamed constructor with no arguments. A component cannot therefore declare its dependencies as constructor parameters; it holds [TomBean] fields and resolves them on use: 

@tomReflector
@TomComponent(OrderService)
class OrderServiceImpl implements OrderService {
  final TomBean<UserService> _users = TomBean();

  Order place(int id) => Order(_users.get().find(id));
}

Declaring a required parameter anyway is refused by name at discovery with beanlocator.initialization.constructor_takes_arguments, rather than left to fail inside the reflector. Three consequences are worth knowing before designing around the constraint:

  • A component cannot be immutable in its dependencies. A final field

holding the collaborator itself cannot be initialized, because there is no constructor argument to initialize it from. The final above is on the handle, which is a weaker promise: the handle cannot be replaced, but what it resolves to is decided later. - A missing dependency is not detected at construction. The component builds regardless; the binding is answered for when the handle resolves, or by the next [validateBeanReferences] pass while it is still pending. - Optional parameters are not affected. The pass omits them, so a defaulted argument is no obstacle to discovery.

Static

static ClassMirror<dynamic>? _findImplementation(List<_TomImplementationInfo> infos, TomComponent tc)

Finds the best matching implementation from a list of candidates.

Selection priority (highest to lowest): 1. Exact match: both environment AND platform match 2. Platform match: platform matches, no environment constraint 3. Environment match: environment matches, no platform constraint 4. Default: no environment or platform constraints

Each tier reuses the same single-winner scan ([_findSingleMatch]); only the candidate predicate differs. Returns null if no tier matches.

The tiers are tried in order and the first one with a match wins, so a lower tier never overrides a higher one. A tier with two matches is an error rather than a reason to fall through — see [_findSingleMatch].

static ClassMirror<dynamic>? _findSingleMatch(List<_TomImplementationInfo> infos, TomComponent tc, bool Function(_TomImplementationInfo) matches, String matchDescription)

Returns the single candidate satisfying [matches], or null if none does.

Throws [TomBeanLocatorException] when two candidates satisfy [matches]: within one tier the selectors carry no further information, so there is no principled way to prefer one over the other. Picking either would silently bind a deployment to an arbitrary implementation — the failure mode where the code runs, the tests pass, and production misbehaves. An ambiguous binding is a wiring bug, and it must surface as one.

[matchDescription] names the tier for the trace log and the error.

function _environmentMatches

bool _environmentMatches(TomEnvironment selector, TomEnvironment? active)

Whether the @TomEnvironment selector [selector] designates [active].

Environments are matched by name, never by instance. TomRuntime keys its registry by name — [TomRuntime.setCurrentEnvironment] takes a name, and registering a second environment under a name already present is a duplicate rather than a second environment — so the name is the environment's identity, and this comparison simply agrees with that.

The distinction is not academic. An annotation is necessarily a const, and const expressions are canonicalised, so comparing instances happens to work for as long as the value handed to the runtime is written as an identical const. Nothing keeps it written that way: TomRuntime's own documented setup builds environments with a plain constructor call, and an application reading its environment name from configuration has no const to write. An instance comparison would then match nothing, and the report would be [initializeBeanContext] announcing that an interface has no implementation while the implementation sits right there carrying what looks like the very same selector.

function _refuseConstructorArguments

void _refuseConstructorArguments(ClassMirror<dynamic> classMirror)

Refuses a component whose unnamed constructor takes required arguments.

Discovery builds every component with newInstance("", []), so a class that declares a required parameter names a constructor the pass will never call. Left to newInstance, that arrives as NoSuchCapabilityError: no capability to invoke the constructor "" — which points at the reflector's configuration, not at the parameter, and sends the reader to add capabilities that would not have helped. It is also an exception type this module never tells anyone to catch.

Decided by inspection rather than by catching, so the message can name the parameters the class actually declares.

function _requireCurrentEnvironment

TomEnvironment _requireCurrentEnvironment(String operation, Object subject)

Returns the active environment, raising the locator's own exception when the runtime has not been configured.

[TomRuntime.getCurrentEnvironment] signals an unconfigured runtime with a bare Exception. That is tom_basics' contract, not this module's: every example and every line of the bean locator's documentation teaches callers to write on TomBeanLocatorException, and a bare Exception walks straight past such a handler — the caller does not get a worse message, it gets no handler at all. The bare exception also names neither the bean nor the interface whose selector asked for the environment, which is the only context that makes the failure actionable: "environment has not been initialized" does not say what was being wired when it was needed.

So the boundary is translated here, once, rather than at each call site. [operation] names what the locator was doing and [subject] what it was doing it to; both travel in the exception parameters so a handler can react to them without parsing the message.

function initializeBeanContext

void initializeBeanContext()

Initializes the bean context by discovering and instantiating all beans.

This function scans all classes annotated with @tomReflector for @TomComponent annotations and:

1. Instantiates classes marked with @tomComponent (no interface) 2. Finds best-match implementations for interface-based components 3. Validates all bean references

Initialization Order

1. Clear any existing registry if re-initializing 2. Discover annotated classes via reflection 3. Filter by environment and platform constraints 4. Instantiate and register beans 5. Validate the pending TomBean references

Which handles are validated

Every handle constructed since the last pass (or since [TomBean.resetBeanContext]) is pending, and validation resolves it — so a handle created between two passes is checked by the second one exactly as a handle created before the first is checked by the first. Whether a dependency is verified must not depend on which side of a call it happened to be declared on.

Handles awaiting a named registration are the documented exception; see [validateBeanReferences].

Usage

// Set up the runtime first. The environment has to be registered before it
// can be made current — `setCurrentEnvironment` resolves a *name* against
// the registry and falls back when the name is unknown.
TomRuntime.addEnvironment(const TomEnvironment("dev"));
TomRuntime.setCurrentEnvironment("dev");

// The platform likewise: `TomRuntime.initializePlatform()` detects it, but
// only once `TomPlatformUtils.setCurrentPlatform` has supplied a real
// implementation — the fallback throws. Naming it directly also works.
TomRuntime.setCurrentPlatform(platformLinux);

// Then initialize beans
initializeBeanContext();

// Now beans can be resolved
final service = TomBean<MyService>().get();

function validateBeanReferences

void validateBeanReferences()

Resolves every pending handle so that wiring errors surface at startup.

A pending handle is any [TomBean] constructed since the last validation (or since [TomBean.resetBeanContext]). [initializeBeanContext] ends by calling this, which is where most callers meet it. It is public because that is not the only moment worth checking:

A handle constructed after the last pass is checked by the next one, and an application that initializes once has no next one. Wiring assembled after boot — a handle held by a plugin loaded later, a bean registered by a feature that starts on demand — accumulates unvalidated, and its first error is whatever call first needed it. Re-running [initializeBeanContext] is not the remedy: it rebuilds the registry from scratch and drops every imperative [TomBean.withName] and [TomBean.withType] registration made since. Call this instead, at the end of whatever assembled the wiring: 

initializeBeanContext();          // boot
TomBean.withName('config', loadConfig());
startLateFeature();               // constructs more handles
validateBeanReferences();         // and vouches for them, registry intact

Calling it twice is not an error and not a second check: a handle it has vouched for is dropped from the pending list, so the second call sees only what was constructed since the first.

Validation vouches for what the pass itself could have supplied. Discovery registers under Type keys only — a concrete bean under its runtime type, an interface implementation under the interface — so a typed handle that is still unresolvable at the end of the pass names a binding nothing produced. That is a wiring bug, and reporting it at boot is the whole point of validating at all.

A handle awaiting a named registration is a different case and is skipped. Nothing in discovery ever registers a name: names enter the registry solely through the imperative [TomBean.withName]. Resolving such a handle here would therefore demand, at boot, something the pass has no way to provide — turning the supported "create the handle now, register the bean later in startup" pattern into a startup failure for the sole reason that the handle happened to exist when the pass ran.

The skip is narrow on purpose. A named handle whose name is registered is validated like any other, so a name bound to the wrong type is still caught at boot — that question is answerable now, and no later registration repairs a mismatch.
