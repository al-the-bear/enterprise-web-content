Schedule expressions — the when half of a background job.

A CE-JB job declares a trigger of one of three kinds (cron | calendar | event). This library turns each of those into something the scheduler can ask a single question of: given that I last considered the world at time T, when does this job next want to run?

That question — [TomSchedule.nextFireAfter] — is deliberately the whole contract. A schedule computes fire times; it never holds a timer, never touches a clock of its own, and never knows whether a computed window actually ran. All of that belongs to the scheduler, which means a schedule is a pure function and can be tested by evaluating it against fixed dates with no waiting and no fakes.

The shipped schedules

  • [TomCronSchedule] — the standard five-field POSIX cron expression, for

"at these minutes of these hours of these days". [TomCalendarSchedule] — recurrences cron cannot express, which is exactly why it is a separate kind rather than a second spelling of the first: last-day-of-month, and the nth (or last) weekday of a month. [TomIntervalSchedule] — a fixed period from an anchor, for cadences that are not aligned to the wall clock at all ("every 90 seconds"). [TomOnceSchedule] — a single absolute instant, then never again. The only non-recurring clock-driven schedule, and the one that expresses a deadline or a timer wait. [TomEventSchedule] — not clock-driven. It answers null to every [TomSchedule.nextFireAfter] and instead exposes a [Stream]; the scheduler subscribes and enqueues a run per event.

Time zones

Every schedule answers in the zone it was asked in: a UTC [DateTime] in gives a UTC one out, a local one gives local. That is the flag only, and the two recurring families differ in what the zone goes on to mean.

  • [TomCronSchedule] and [TomCalendarSchedule] read and write **wall-clock

fields*, so a local `0 3 ` means 03:00 civil time. Across a DST boundary they hold 03:00, and the gap to the previous run becomes 23 or 25 real hours. [TomIntervalSchedule] computes in epoch microseconds* and never consults the zone, so a 24-hour period is always 24 real hours and its wall-clock time shifts by an hour across that same boundary.

Asked in UTC, both give the same DST-immune absolute cadence, because there is no civil time left to disagree about. The schedule does not decide which you want — the scheduler's clock does.

That mirror image is this module's most surprising property, and no unit test pins it. Each half follows from its own arithmetic rather than from a policy that could drift: the cron half from the local branch of _at, the interval half from epoch arithmetic that cannot see a zone at all. A DST assertion would therefore be re-testing DateTime, and pinning one for real needs a zone-controlled process, which the fleet's Windows host cannot run. What the suite does pin is the mechanism on each side — that cron reads its fields in the caller's zone, and that the interval grid is absolute — which is what the DST behaviour is a consequence of.

[TomOnceSchedule] is the exception that proves the rule: it names one absolute instant rather than a wall-clock position, so there is nothing for a zone to change. It still answers in [from]'s zone, but only because the contract says the answer is comparable to the question.

class TomCalendarSchedule

class TomCalendarSchedule extends TomSchedule

Recurrences that cron cannot express.

This type exists for a narrow reason: cron's day-of-month field counts forward from the 1st and has no way to say "the last day of the month" (the 31st is not the last day of April) or "the second Tuesday". Those two rules cover the great majority of real calendar-driven work — month-end billing, period close, a report on the first Monday — and neither can be written as a cron expression at all.

Anything cron can say should be said with [TomCronSchedule]; having two spellings for one recurrence is how two jobs end up disagreeing about what "daily" means.

class TomCronSchedule

class TomCronSchedule extends TomSchedule

A standard five-field POSIX cron expression.

┌───────── minute        (0-59)
│ ┌─────── hour          (0-23)
│ │ ┌───── day of month  (1-31)
│ │ │ ┌─── month         (1-12 or JAN-DEC)
│ │ │ │ ┌─ day of week   (0-7 or SUN-SAT, both 0 and 7 mean Sunday)
* * * * *

Each field accepts *, a single value, a low-high range, a comma-separated list of either, and a /step suffix on * or on a range (*/15, 1-10/2). Month and day-of-week names are accepted case-insensitively.

Two behaviours worth knowing before you write an expression

Day-of-month and day-of-week are OR-ed, not AND-ed. This is POSIX behaviour and it surprises people every time: when both fields are restricted, the expression fires on a day matching either. 0 0 1 * MON is "midnight on the 1st, and every Monday" — not "the 1st when it is a Monday". When only one of the two is restricted, only that one applies. [TomCalendarSchedule] exists partly so that intersecting rules have a spelling that means what it looks like.

A step restricts, which decides where that rule lands: 0 0 */2 * * fires on odd days, and 0 0 */2 * MON is odd days or Mondays. Only a bare * — or */1, the same thing spelled with a no-op step — leaves a day field unrestricted. Vixie cron differs here, reading every */n as unrestricted and so ANDing that example into odd Mondays.

There is no seconds field. Not on either end — a six-field expression is rejected rather than guessed at, because the two common conventions put seconds at opposite ends and a misread expression fires 60× too often. A sub-minute cadence is [TomIntervalSchedule]'s job.

Static

static int _searchYears

How far ahead [nextFireAfter] searches before concluding "never".

Nine years, which is what lets null be read as never rather than not within the window. The rarest date a cron expression can name is February 29th, and the longest gap between two of them is eight years, not four: 2100 is divisible by 100 but not by 400, so the leap day skips from 2096 to 2104. The limit is anchored on the search start's own month and day and the scan is half-open, so a search beginning on a February 29th needs one year more than the gap it crosses — hence nine.

Every other combination of fields recurs at least once a year, so nine covers the whole expression language and a null means the expression is unsatisfiable (0 0 30 2 *) rather than merely distant.

static bool _isUnrestricted(String field)

Whether [field] as written restricts nothing, which is what decides the OR question in [_matchesDay].

A step expression restricts. POSIX words the day rule as applying when both day fields are "not *", and */2 is not * — it names half the days. Reading it as unrestricted computes that restriction and then throws it away, which makes 0 0 */2 * * fire every day.

*/1 is the one step that does not restrict: it is a wildcard with a redundant step, expands to every value, and counting it as a restriction would pull the other day field into an OR its author plainly did not ask for. The line is therefore drawn at how the field is written — a plain wildcard, with or without the no-op step — and not at which values it happens to cover, so an explicit 1-31 restricts like any other range.

This is stricter than Vixie cron, which tests only a field's first character and so counts every */n as unrestricted. Under that reading 0 0 */2 * MON means odd days and Mondays; under the POSIX wording, which is the rule this class documents, it means odd days or Mondays.

class TomEventSchedule

class TomEventSchedule extends TomSchedule

A trigger fed by a source rather than a clock.

CE-JB's third trigger kind. [nextFireAfter] always answers null and [isClockDriven] is false, so the scheduler never polls it; instead it subscribes to [events] and enqueues one run per emitted element.

The emitted value is available to the job body as the run's payload, so an event-triggered job can act on what happened rather than merely that something did.

class TomIntervalSchedule

class TomIntervalSchedule extends TomSchedule

A fixed period measured from an anchor instant.

Use this when the cadence is not aligned to the wall clock — "every 90 seconds", "every 45 minutes" — which cron cannot express because its fields are calendar positions, not durations.

Fire times are computed from [anchor] by whole multiples of [period], not by repeatedly adding to the previous answer, so a scheduler that was down for an hour resumes on the original grid instead of drifting by the outage.

class TomOnceSchedule

class TomOnceSchedule extends TomSchedule

A single absolute instant: fire once at [at], then never again.

The other clock-driven schedules all recur. This one is what expresses a deadline — "escalate this ticket at 09:00 on the 1st", "expire this invitation in seven days" — and it is the shape a timer wait takes when a multi-step process is built out of jobs rather than out of a process engine. Without it, a caller needing one future instant has to abuse [TomIntervalSchedule] (which will fire again) or write a subclass at the call site.

It needs no scheduler support because [TomSchedule] already accommodates it: null from [nextFireAfter] means never again, so the whole implementation is "the instant, if we are not past it yet".

An instant, not a wall-clock position

[at] is an absolute moment. Its zone affects nothing — a deadline of 2026-08-01T09:00Z is the same moment whether it is compared against a UTC or a local clock, and unlike the recurring schedules there is no DST question to answer because there is no recurrence to shift. [nextFireAfter] still returns its answer in [from]'s zone, so the value can be compared and stored like any other schedule's, but that is a rendering, not a reinterpretation. [describe] prints UTC for the same reason: a deadline in an alert should not depend on which host formatted it.

Nothing to validate, including a deadline in the past

The sibling schedules reject expressions that cannot mean anything. A [DateTime] always means something, including one already behind us: that is a schedule which will never fire, and null is exactly how the contract spells it. The schedule cannot judge otherwise without reading a clock, and [nextFireAfter] must stay pure — the scheduler replays windows deterministically after a restart and would get different answers from a schedule that had opinions about now.

For the same reason there is deliberately no TomOnceSchedule.after( Duration) convenience. It would have to read the clock at construction, and job definitions are typically rebuilt at start-up — so a "fire in three days" schedule would quietly push its own deadline three days further out on every restart, and a process that restarted often would never fire at all. Compute the instant once, persist it, and pass it here.

Being planned is what survives a restart

A one-shot fires late rather than not at all when the process is down over its instant, because the scheduler enqueues the window as soon as it sees the job — the run is then durable store state, and [TomMissedWindowPolicy.skip] does not un-plan it. The case that genuinely does not fire is a job first registered after its instant has passed: first sight anchors on the present for every schedule kind, so there is no window to catch up on. The scheduler raises [TomJobAlertKind.neverFires] for that rather than staying quiet about it.

class TomSchedule

abstract class TomSchedule

A job trigger, reduced to the one question the scheduler asks of it.

Implementations must be pure: [nextFireAfter] may not read a clock, and two calls with the same argument must return the same answer. The scheduler relies on that to replay windows deterministically after a restart.

DateTime? nextFireAfter(DateTime from)

The first fire time strictly after [from], or null when this schedule will never fire again.

null is a real answer, not an error: 0 0 30 2 * (February 30th) can never match, and an [TomEventSchedule] is never clock-due. Callers must treat it as "stop asking", not as a failure.

The returned value is in the same zone as [from] — UTC in, UTC out.
