import 'package:tom_core_kernel/src/tombase/http_connection/file_transfer.dart';

Streaming file transfer — the client half of the framework's file storage.

The server side (tom_core_server's file_storage module) stores a file as a stream and reads it back as a stream, so a large attachment never has to exist in memory at either end. This library is the matching client contract: a [TomFileSource] to send, a [TomFileMetadata] to describe what was stored, and a [TomFileTransferClient] that moves bytes between them with progress reporting and cancellation.

Why this is not the existing [TomServerCall]

TomServerCall is a request/response API: a body is a String, a Uint8List or form fields, and read() accumulates the whole response into a BytesBuilder. That is the right shape for JSON endpoints and the wrong shape for a 400 MB video. This library keeps the same connection machinery ([TomServerChannel], the bearer token, the client factory) but never materialises the payload.

Slots, not keys

A transfer addresses a slot — an application-owned path such as invoices/4711/scan — and never a storage key. Storage keys are generated by the server and handed back in [TomFileMetadata.key]; a client that could name its own key would turn any upload endpoint into an open write surface on the blob store. The slot is what the application already controls through its own authorization rules.

Example

final client = TomHttpFileTransferClient(
  baseUri: Uri.parse('https://api.example.com/files'),
);
final cancellation = TomTransferCancellation();

final stored = await client.upload(
  slot: 'invoices/4711/scan',
  source: TomFileSource.bytes('scan.pdf', pdfBytes),
  onProgress: (p) => print('${(p.fraction ?? 0) * 100}%'),
  cancellation: cancellation,
);

await for (final chunk in client.download('invoices/4711/scan')) {
  sink.add(chunk);
}

class TomFileMetadata

class TomFileMetadata

What the server knows about a stored file.

Returned by [TomFileTransferClient.upload] and [TomFileTransferClient.describe]. The [key] is the server-generated storage key — opaque to the client, but worth carrying around because it is what identifies this exact stored revision.

Constructors

Creates metadata for a stored file.

factory TomFileMetadata.fromJson(Map<String, dynamic> json)

Reads metadata from the JSON descriptor the server returns.

Tolerant of missing optional members so a server can grow the descriptor without breaking older clients; a missing [key], [mediaType] or [byteCount] is a protocol error and throws.

Properties

final String key

The server-generated storage key.

final String mediaType

The media type the file was stored with.

final int byteCount

The stored size in bytes.

final String? fileName

The original file name, when the server kept one.

final DateTime? storedAt

When the file was stored, when the server reports it.

final String? digest

The SHA-256 of the stored bytes as lowercase hex, when the server has one.

What a client does with it: verify a download it has just finished, skip an upload whose bytes it can see are already stored, or recognise two keys as one file. Nullable here and not on the server's own TomStoredBlob, for two reasons that are both about this being the wire: a server may be older than this field, and a blob the server did not write itself has no recorded hash. Absent means "not told", never "empty file" — the digest of zero bytes is a real and well-known value.

class TomFileSource

class TomFileSource

The bytes to upload, together with what the server needs to know about them.

Why [open] is a function and not a stream

A Dart stream can be listened to once. Retry-after-failure — which the whole progress/cancel UX exists to offer — needs the same bytes a second time, so the source hands out a factory: every call to [open] starts a fresh read. A source built from an in-memory buffer replays trivially; one built from a file replays by re-opening the file.

Example

// Small file, already in memory.
final small = TomFileSource.bytes('note.txt', utf8.encode('hello'));

// Large file, streamed from disk and re-openable.
final large = TomFileSource.stream(
  fileName: 'video.mp4',
  byteCount: await file.length(),
  open: () => file.openRead(),
);

Constructors

Stream<List<int>> open()

Starts a fresh read of the file's bytes.

Every call returns an independent stream; see the class doc for why.

A factory that hands back the same single-subscription stream instead of building a new one satisfies the type but breaks that contract, and the second transfer fails with Dart's own StateError: Stream has already been listened to. That is left as it is rather than being translated into a transfer error key: it is a defect in the calling code, not a condition a running system can encounter, and Dart's message already names it exactly.

class TomFileTransferClient

abstract class TomFileTransferClient

Moves file bytes between an application and a file store.

Four operations, matching the server-side TomBlobStore contract one for one, addressed by slot rather than by storage key (see the library doc). Implementations must stream: neither [upload] nor [download] may buffer a whole file.

Constructors

const TomFileTransferClient.new()

Creates a transfer client.

Methods

Future<TomFileMetadata> upload({required String slot, required TomFileSource source, void Function(TomTransferProgress)?? onProgress, TomTransferCancellation? cancellation})

Uploads [source] into [slot], returning what the server stored.

[onProgress] is called as bytes leave the client. [cancellation] aborts the request; the returned future then completes with a [TomFileTransferException] keyed file_transfer.cancelled.

Stream<List<int>> download(String slot, {void Function(TomTransferProgress)?? onProgress, TomTransferCancellation? cancellation})

Streams the file stored in [slot].

The stream is lazy — nothing is requested until it is listened to — and errors with file_transfer.not_found when the slot is empty.

Future<TomFileMetadata?> describe(String slot)

Describes the file stored in [slot], or null when the slot is empty.

Cheap by design: it must not transfer the file's bytes, so a UI can show name, type and size without downloading anything.

Future<bool> remove(String slot)

Deletes the file in [slot], returning whether anything was deleted.

Deleting an empty slot returns false rather than throwing — the caller's intent ("make sure nothing is stored here") is already satisfied.

void close()

Releases any connections held by this client.

class TomFileTransferException

class TomFileTransferException extends TomException

Exception thrown when a file transfer fails.

Error keys are stable and worth matching on. Each names a condition a running system can meet — a caller may branch on one, and tom_flutter_ui turns each into a user-facing line — so a mistake in the calling code is deliberately not among them:

  • file_transfer.not_found — no file is stored in the requested slot.
  • file_transfer.cancelled — the caller cancelled the transfer.
  • file_transfer.rejected — the server refused the transfer (status code in

parameters['statusCode']). - file_transfer.invalid_descriptor — the server's description of a stored file was unreadable: not valid JSON, not a JSON object, missing key / mediaType / byteCount, or a HEAD that described nothing at all. - file_transfer.invalid_slot — the slot was empty or contained . or .. segments (see [TomHttpFileTransferClient.uriForSlot]).

class TomTransferCancellation

class TomTransferCancellation

A cancel signal shared with an in-flight transfer.

Wraps the Future-based abort trigger package:http expects, so callers deal with a cancel() method instead of hand-rolling a Completer. One instance covers one transfer; [cancel] is idempotent so a UI can wire it to a button without tracking whether it already fired.

Example

final cancellation = TomTransferCancellation();
final upload = client.upload(slot: slot, source: source, cancellation: cancellation);
cancelButton.onPressed = cancellation.cancel;

class TomTransferProgress
