TomScheduler

package:tom_core_kernel/src/tombase/scheduling/scheduler.dart

import 'package:tom_core_kernel/src/tombase/scheduling/scheduler.dart';

The scheduler runtime — the loop that turns schedules into dispatched work.

Everything the scheduler does happens in one method, [TomScheduler.tick]. [TomScheduler.start] merely arranges for it to be called periodically. That shape is deliberate: a runtime whose behaviour is only reachable through a timer can only be tested by waiting, and a test that waits for a nightly job is a test nobody writes. Here the entire loop — window planning, catch-up, claiming, dispatch, timeout, retry and alerting — is a single awaitable call driven by an injectable clock, so a year of scheduling is exercised in milliseconds and the code under test is the code that runs in production.

One pass, in order

1. Recover. Runs whose lease expired go back to pending. This is how a run that was in flight when the process died becomes visible again. 2. Plan. For each clock-driven job, work out which windows have elapsed since the last one on record and enqueue them per the job's [TomMissedWindowPolicy], then enqueue the next future window. Enqueueing is keyed by window, so this is idempotent and a replayed tick is a no-op. 3. Dispatch. Claim the due runs, hand each body to the [TomJobDispatcher], and record the outcome — success, a retry with backoff, or terminal failure with an alert.

What this runtime does not do

It does not execute anything. Bodies go to a dispatcher, which in production is the kernel's existing isolate pool.

Running more than one of these

Two schedulers pointed at the same store will both claim the same due run unless something arbitrates between them. Supply a [TomLeaseLock] and this scheduler becomes cluster-safe: every run is gated on a lease, the lease is renewed while the work runs, and a node that dies has its work picked up when its lease lapses. Leave the lock null — the default — and the scheduler behaves exactly as a single-node runtime, with [TomJobDefinition.allowOverlap] serialising a job's runs within this process only.

The execution guarantee is at-least-once, and it is stated in full in doc/scheduling/scheduling.md. Job bodies must be idempotent. The lock makes duplicate execution rare and bounded; it does not make it impossible, and a runtime that claimed otherwise would be lying about a case its users will eventually hit.

class TomScheduler

class TomScheduler implements TomClosable

Drives registered [TomJobDefinition]s against a [TomJobStore].

Constructors

TomScheduler.new({required TomJobStore store, required TomJobDispatcher dispatcher, Duration tickInterval = const Duration(seconds: 30), Duration leaseTimeout = const Duration(minutes: 15), String? ownerId, DateTime Function()?? clock, void Function(TomJobAlert)?? onAlert, Random? random, int maxRunsPerTick = 16, int maxCatchUpPerTick = 20, double tickJitter = 0.1, TomLeaseLock? lock, Duration leaseTtl = const Duration(minutes: 1), Duration? leaseRenewInterval})

Creates a scheduler.

[ownerId] defaults to a value derived from the process start time, which is enough to tell one scheduler's leases from another's in the store. In a cluster it must be distinct per node, and the default satisfies that only by luck — two nodes started in the same microsecond would collide. Set it explicitly to something stable and unique, such as the host name plus the process id.

[leaseRenewInterval] defaults to a third of [leaseTtl], which leaves room for two renewals to fail before the lease lapses.

Properties

final TomJobStore store

Durable storage for planned and in-flight runs.

final TomJobDispatcher dispatcher

Where work bodies are executed.

final Duration tickInterval

How often [start] runs a [tick]. Positive.

final Duration leaseTimeout

How long a claim may go unrenewed before the run is considered abandoned and returned to the queue.

A running attempt renews its claim every [leaseRenewInterval], with or without a [lock], so a claim goes unrenewed only when the node holding it has stopped — crashed, killed, or partitioned from the store. This is therefore how long a dead node's run waits to be recovered, and it is independent of how long any job takes: a slow but healthy attempt keeps its claim fresh however long it runs, and [TomJobDefinition.timeout] bounds attempts separately.

Must be strictly above [leaseRenewInterval] — comfortably above it, so a late renewal or a slow store does not lapse a live claim — which is checked here, because both are this scheduler's own arguments.

final String ownerId

Identifies this scheduler in [TomJobRun.claimedBy].

final DateTime Function() clock

The clock. Injectable so tests can move time without waiting.

final void Function(TomJobAlert) onAlert

Where alerts go. Defaults to the framework log.

final Random random

Randomness for retry jitter. Injectable so backoff is reproducible.

final int maxRunsPerTick

The most runs claimed in one pass.

At least 1. Zero is not "no limit": the claim stops once it holds this many, so a zero budget claims nothing on every pass while planning keeps filling the queue behind it.

final int maxCatchUpPerTick

The most catch-up runs enqueued in one pass, across all jobs.

[TomJobDefinition.catchUpLimit] bounds one job's backlog; this bounds the whole registry's, and the difference matters after a long outage: fifty jobs each within their own limit still add up to a planning pass that runs for minutes and a queue in which nothing due now can be seen for the backlog. Quartz caps the same thing with maxMisfiresToHandleAtATime, and this default is its default.

Clipping defers, it does not drop. A job whose catch-up was clipped skips its look-ahead enqueue for that pass, which leaves the last window on record behind the backlog so the next pass resumes exactly where this one stopped. The work arrives a tick or two later; none of it is lost.

final double tickJitter

How much of [tickInterval] may be shaved off at random, 0-1.

Jitter — not partitioning — is the answer to N nodes waking together. A cluster started by the same deployment ticks in lockstep otherwise, and every node then contends for the same claims in the same millisecond; the contention is harmless but the wasted round-trips are not free, and they grow with the node count.

Applied downward only, so a tick never falls later than [tickInterval] and the interval keeps its meaning as a maximum. Set it to 0 for an exact period.

final TomLeaseLock? lock

Cluster coordination, or null for a single-node scheduler.

When present, no run is executed without first winning its lease, so two schedulers sharing a store cannot both execute the same run.

final Duration leaseTtl

How long a coordination lease is taken for.

Short is good: it bounds how long a dead node blocks its work. It is safe to keep it short because [leaseRenewInterval] pushes it forward for as long as the work is genuinely running, so this does not need to exceed the slowest job. Positive, and strictly above [leaseRenewInterval].

final Duration leaseRenewInterval

How often a running attempt renews its store claim — and, with a [lock], its lease.

Must be comfortably shorter than [leaseTtl] — a third of it by default — so a single missed renewal does not lapse the lease, and shorter than [leaseTimeout] for the same reason about the claim. The gap is the margin that absorbs a slow store, a GC pause or a moment of clock skew.

final Map<String, TomJobDefinition> _jobs
final Map<String, StreamSubscription<Object?>> _eventSubscriptions
final Map<String, ({Future<void> finished, String jobName})> _inFlight

Runs currently dispatched: run id to the attempt in progress.

The in-process view of what the store has leased to us. Keyed by run so a completion removes exactly its own entry; the entry names the job so the [TomJobDefinition.allowOverlap] check is a lookup rather than a scan, and carries the attempt's future so [drain] can wait for it.

The future is a completer's rather than [_runOne]'s own, because [_runOne] removes its entry from this map on the way out: reading the future back out of the map to await it would be a race with the removal that ends it. A completer is written once, at dispatch, and completed once, after the run is finished and its entry gone.

final Map<String, ({Timer heartbeat, String jobName})> _overrunning

Bodies still executing after their attempt timed out: run id to the job and the heartbeat keeping the run's lease alive.

A timeout fails the attempt — the store records it and schedules the retry — but it cannot stop the body, because Dart cannot cancel arbitrary asynchronous work. The body goes on running, and it is still the one execution the overlap rule is about. So the protection the attempt held is kept until the body settles: the job (or, when overlap is allowed, the run) counts as busy in [_dispatchDue], and the run's lease is neither released nor left to lapse. Releasing either at the timeout would let the retry start a second body beside the first — the duplicate allowOverlap: false exists to prevent, produced by the one path certain to leave a body running.

final Map<String, TomLease> _leases

Coordination leases currently held, keyed by run id.

Exposed through [heldLeases] so an operator can ask what this node is sitting on without going to the substrate.

final Set<String> _lostLeases

Runs whose lease was lost mid-flight, and whose outcome this node must therefore not record. Cleared when the run finishes here.

final Set<String> _neverFiresReported

Jobs already reported as never firing.

The condition is detected on the planning pass, which runs every tick, and it cannot resolve itself — so without this the alert would repeat for the life of the process. Cleared whenever the registry entry changes, so a corrected job that is still wrong reports again.

Methods

void register(TomJobDefinition job)

Registers [job], replacing any previous definition of the same name.

An [TomEventSchedule] job is subscribed immediately, so events that arrive before [start] are still enqueued — they are just not dispatched until a tick runs.

void deregister(String name)

Removes [name] from the registry and cancels any event subscription.

Runs already in the store are left alone: they were planned, and dropping them silently would make deregistration a way to lose work.

Future<void> start()

Runs one [tick] immediately, then repeats roughly every [tickInterval].

The immediate pass matters on restart: it is what recovers abandoned leases and catches up missed windows without waiting out a full interval.

"Roughly" is [tickJitter]: each interval is shortened by an independent random fraction, so a cluster started together does not stay in lockstep.

void _scheduleNextTick()

Arms a one-shot timer for the next pass and re-arms from its own callback.

A one-shot chain rather than [Timer.periodic] because each interval is drawn separately — a periodic timer can only have one period, and a jitter applied once is a constant offset, not jitter.

Duration _nextTickDelay()

[tickInterval] less a random fraction of up to [tickJitter] of it.

void stop()

Stops the periodic timer. In-flight runs are left to finish.

Returns immediately: it stops new passes, not the work already started. stop() followed by await drain() is the pair that quiesces a scheduler, and in that order — draining one that is still ticking races the timer for what "idle" means.

Future<void> close() override

Stops the scheduler, cancels event subscriptions, closes the dispatcher and releases the leases it holds, completing once the releases have landed.

Runs already dispatched are not waited for — [close] is the shutdown path, and their leases will expire so another process picks them up. A shutdown that would rather finish the work than hand it on calls [stop] and awaits [drain] first.

Releasing the held leases is what lets peers take the work immediately instead of waiting out [leaseTtl], so a shutdown awaiting this has handed the work on by the time it continues. A lease that fails to release is logged and left to expire — the behaviour a hard kill would have produced anyway — rather than failing the close.

Future<void> tick()

Runs one complete scheduling pass, starting the runs it finds due.

Safe to call directly — this is what unit tests drive. Overlapping calls are collapsed: a pass still running when the timer fires again is not re-entered, because two concurrent planners would both see the same window as unplanned.

Awaiting this does not await the work. A pass recovers, plans, claims and dispatches; the bodies it dispatched are still running when it returns, deliberately, so that a slow job cannot hold up the next window of a fast one. To wait for them, follow it with [drain].

Future<void> drain()

Completes once every run this scheduler has in flight has finished.

The other half of [tick]. A pass returns as soon as the work is started, which is right for a timer and useless to anyone who needs to know the work is done — a test asserting an effect, a shutdown path that wants the queue emptied before it closes, or a caller like TomMessageOutbox.tick() whose own contract is "the pass is complete". Without this they had only pumpEventQueue() and a guess.

"Finished" means the attempt returned and its outcome was written to the store — success, a scheduled retry, or terminal failure — not that the run succeeded. A drain reports that no attempt is still executing here; the store reports what happened.

A body that outlived its timeout is not waited for: its attempt finished at the timeout, and the body may never settle, so a drain that waited for it could hang for good. It still holds its job until it does — see [overrunningCount].

Re-checks after each wave, because a run that finishes may leave another claimable and a concurrent pass may have started more. It therefore completes only when the scheduler is genuinely idle, which also means a caller draining a running scheduler is racing the timer: call [stop] first if the intent is to quiesce.

Future<void> _recoverAbandoned(DateTime now)

Returns expired leases to the queue and alerts on each.

The scheduler is the one caller that can see the job registry, so it is the one caller that can answer [TomJobDefinition.requestsRecovery] — a store asked in isolation would have to guess. A job the registry does not know answers false, which is the safe reading: an unregistered job is one this node cannot run anyway, and declining is reversible where a repeated side effect is not.

Future<void> _planWindows(TomJobDefinition job, DateTime now)

Enqueues whatever [job] owes: missed windows per its policy, plus the next future window.

The two halves are anchored differently on purpose. Catch-up is anchored on the last window on record, because that is what defines "missed". Look-ahead is anchored on now, not on the record — anchoring it on the record too would enqueue one window further into the future on every tick, walking the plan forward forever.

Future<bool> _enqueueMissed(TomJobDefinition job, DateTime last, DateTime now)

Enqueues the missed windows [job]'s policy asks for, dating each run to the window it belongs to but making it due immediately.

Returns whether the whole backlog was enqueued. false means the pass's shared [maxCatchUpPerTick] budget ran out and the remainder is left for the next pass — see the caller for why that requires skipping look-ahead.

int _countMissed(TomJobDefinition job, DateTime last, DateTime now)

How many windows elapsed between [last] and [now] — used only to report what a skip policy is dropping.

Future<bool> _enqueueWindow(TomJobDefinition job, DateTime scheduledFor, DateTime runAt)

Adds a run for [scheduledFor] unless one already exists.

The existence check is the idempotence guarantee that makes a tick safe to replay after a crash.

Returns whether a run was actually added, which is what lets the catch-up budget count work rather than attempts.

Future<void> _enqueueEvent(TomJobDefinition job, Object? payload)

Enqueues a run for an event-triggered job, carrying [payload].

Each event gets its own window keyed by arrival time, so two events in the same instant collapse into one run and a rapid source cannot flood the queue with duplicates of the same moment.

String _nextRunId(String jobName)
Future<void> _dispatchDue(DateTime now)

Claims every due run this scheduler is willing to take, and starts it.

String _leaseResource(TomJobDefinition job, TomJobRun run)

The resource a run's coordination lease is taken on.

The key is the policy. A job that forbids overlap leases its own name, so the whole cluster runs at most one of it at a time — the cluster-wide reading of [TomJobDefinition.allowOverlap]. A job that allows overlap leases the individual run, so concurrent windows are fine but no single window is executed twice.

Future<TomLease?> _acquireLease(TomJobDefinition job, TomJobRun run)

Wins the coordination lease for [run], or reports why it could not.

Returns null both when there is no lock (the single-node case, where the caller proceeds anyway) and when a peer holds the lease; the caller distinguishes them by whether [lock] is set.

Future<void> _runOne(TomJobDefinition job, TomJobClaim claim, TomLease? lease)

Executes one attempt of the run held by [claim] and records the outcome.

The claim is threaded through rather than the run, because every write below is fenced on it: this node may have been partitioned long enough for the lease to lapse, and the outcome it is about to record then belongs to a peer's attempt rather than to its own. See the rule on [TomJobStore].

[lease] is the coordination lease held for this run, or null when the scheduler is running single-node.

void _holdUntilSettled(TomJobDefinition job, TomJobRun run, Future<Object?> body, Timer heartbeat)

Keeps [run]'s overlap protection — its busy mark and its lease, kept alive by [heartbeat] — until [body] settles, after its attempt timed out.

See [_overrunning] for why. The body's value and its error are both dropped: its attempt was failed at the timeout, so neither is an outcome any more, and dropping them here is a decision rather than an unhandled error surfacing later. The heartbeat's store half is harmless meanwhile — the attempt's claim is no longer the store's, and a renewal of a claim the store no longer holds is a no-op.

bool _stillOurs(TomJobRun run)

Whether this node may still write [run]'s outcome to the store.

Once a lease is lost the run belongs to whichever node took it over. Writing our result anyway would clobber theirs — marking succeeded a run they are still executing, or failing one they already completed. Our work is not wasted, it is simply no longer authoritative, and the discrepancy is reported as [TomJobAlertKind.leaseLost] rather than hidden.

Timer _startHeartbeat(TomJobDefinition job, TomJobClaim claim)

Starts the renewal timer that keeps [claim] — and its lease, with a [lock] — alive while the work runs.

Renewal is what decouples both expiries from job duration. Without it the lease TTL would have to exceed the slowest possible run, and a dead node would then block its work for exactly that long; and [leaseTimeout] would have to exceed every job's timeout, a relation between two independently supplied numbers that nothing could check, whose violation abandons a healthy run and starts a second copy beside it. Started with or without a lock for that second reason: a single-node scheduler's claim needs renewing as much as a cluster's.

Future<void> _renewLease(TomJobDefinition job, TomJobClaim claim)

One heartbeat: push the lease expiry forward, when there is a lock, and refresh the store claim.

Future<void> _releaseLease(TomJobDefinition job, TomJobRun run)

Gives up the lease held for [run], if any.

Future<void> _failAttempt(TomJobDefinition job, TomJobClaim claim, Object error, StackTrace stack)

Fails one attempt, scheduling a retry when the policy allows one.

Two things can cut the retry budget short: exhausting it, and an error the body classified as [TomPermanentFailure]. The second is checked first because it is the stronger statement — "no attempt will ever succeed" makes "you have two attempts left" irrelevant.

Future<void> _failFinally(TomJobDefinition job, TomJobClaim claim, Object error, StackTrace stack)

Marks [run] terminally failed and alerts.

Static

static int maxCatchUpScan

How many windows the catch-up scan will step through before giving up.

A guard, not a policy: without it, a job with a minutely schedule whose store was last written a year ago would spin through half a million iterations on its first tick. At the default this is roughly ten weeks of minutely windows, far beyond any outage worth catching up on.

static void _logAlert(TomJobAlert alert)

The default alert sink: everything goes to the framework log, with a severity that matches how bad the news is.

static void _cancel(StreamSubscription<Object?>? subscription)

Cancels [subscription] without waiting for it.

Cancellation of a broadcast/controller subscription completes on a later microtask; nothing downstream depends on that completion, and making [register], [deregister] and [close] async just to await it would put an await point in the middle of registry mutation.
