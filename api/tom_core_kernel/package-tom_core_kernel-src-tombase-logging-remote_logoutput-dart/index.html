Remote logging output for sending log messages to a centralized server.

This library enables applications to send log messages to a remote logging server for centralized collection, analysis, and monitoring.

Features

  • Asynchronous log transmission to remote servers
  • Automatic fallback to local console on connection failure
  • Re-entrancy protection to prevent infinite loops
  • Configurable sender identification

Setup

See [TomRemoteLogOutput] for the wiring snippet. It is deliberately not repeated here: this library and its primary class are read together, and when the two carried the same snippet both went stale at once — each showing a TomServerEndpoint constructor the class does not have.

See also: - [TomRemoteLogServer] for the server-side implementation - [TomRemoteLogMessage] for the message format - [TomRemoteLogResult] for response handling

class TomInMemoryLogReplayStore implements TomLogReplayStore

In-memory [TomLogReplayStore] — the zero-config default.

Buffered records live in a plain list and are lost if the process exits while the queue is non-empty. This matches the historical behaviour of the replay queue; use a durable store (e.g. a file-backed one) to harden the restart-during-outage edge.

class TomLogReplayStore

abstract interface class TomLogReplayStore

Pluggable backend for [TomRemoteLogOutput]'s replay queue.

The replay queue buffers records that failed every send attempt so they can be re-sent, oldest-first, once the endpoint recovers. This interface lets the storage of that queue be swapped out: the default keeps records in memory (see [TomInMemoryLogReplayStore]), while a durable implementation can persist them so buffered records survive a process restart during an outage.

Implementations own ordering: records must be returned in the same order they were [append]ed (FIFO). [oldest] / [removeOldest] drive the drain loop; [trim] enforces the bound; [clear] resets the queue.

class TomRemoteLogMessage

class TomRemoteLogMessage

Message format for transmitting log entries to a remote server.

This class is serialized and sent over HTTP to the remote logging endpoint. It contains all information needed to reconstruct the original log message on the server.

Sender Identification

Install [globalSettingSenderIdResolver] to say which application sent the message:

TomRemoteLogMessage.globalSettingSenderIdResolver = () => 'web-frontend-01';

A collector names its per-client files after the sender, so this is what keeps two servers of one deployment out of each other's log.

Static

static String Function() globalSettingSenderIdResolver

Answers "which application sent this", asked once per message.

A function, not a value, and that is the whole of the design. The obvious alternative — a String assigned at startup — copies whatever the application was called at the instant of the assignment, and an application's name is often not settled then: a tom_core_server deployment names itself in its configuration subclass constructor, which runs after the base constructor that would do the installing, so the copy captures the empty string. Every one of five servers in this workspace made that mistake with the analogous tomAppId. A resolver cannot be early, because it is not read until there is a message to answer for.

The default answers the empty string rather than a placeholder. An unset sender then looks unset — a collector's file named for the isolate alone says "nobody said who this was", where a plausible-looking default says "this is who it was" and is wrong for every application at once.

A consumer of tom_core_server needs to install nothing: TomBaseServerConfiguration installs a resolver over tomAppId when it registers itself as the isolate's active configuration.

class TomRemoteLogOutput

class TomRemoteLogOutput extends TomLogOutput

Log output that sends messages to a remote logging server.

This output implementation transmits log messages over HTTP to a centralized logging server for collection and analysis.

Configuration

// Optional: identify this client in the collector's log stream.
TomRemoteLogMessage.globalSettingSenderId = 'client-001';

// Set up the remote endpoint. TomServerEndpoint takes a channel (host and
// port) and call specs (method and full URL) — there is no baseUrl/path
// constructor. Building it opens no connection: the channel creates its
// HTTP client lazily, on the first call.
TomRemoteLogOutput.remoteEndpoint =
    TomServerEndpoint<TomRemoteLogMessage, TomRemoteLogResult>(
      TomServerChannel('logs.example.com', 443),
      TomServerCallSpecs(
        'POST',
        Uri.parse('https://logs.example.com/api/logs'),
      ),
    );

// Activate remote logging
tomLog.logOutput = TomRemoteLogOutput();

That snippet is a copy of step 3 of example/samples/logging/05_isolate_and_remote_logging_example.dart, where it is compiled, analyzed and asserted. Change it there and copy it out: documentation has no build to fail, so a constructor invented here is caught by nobody.

Fallback Behavior

If the remote endpoint is unavailable or not configured, messages are written to [globalSettingFallbackOutput] (console by default).

The fallback is the last sink in the chain, so if it throws — a full disk for a file sink, a closed port, a misconfigured custom output — the record is lost. It is never lost silently: the failure is announced once per installed fallback on [TomPlatformUtils.outError], which sits below the logging stack and so cannot be broken by the same misconfiguration. The throw itself never reaches the caller.

Error Handling and Resilience

A send is considered failed whenever it does not reach a server that accepted it: the endpoint could not be reached at all, the server answered with an error, or the send threw. In every case the record is never silently dropped, and the accompanying warning names which of the three happened — an unreachable endpoint is not reported as a rejection.

"The server answered with an error" covers both channels the endpoint can report one on, because a record is equally lost either way: a transport-level failure ([TomServerCallError] — a non-2xx status, an internal error) and an application-level refusal carried in the response body ([TomRemoteLogResult.hasError]) on an otherwise perfect HTTP 200. The second is what a healthy collector uses to say "received, not stored", and the server's own [TomRemoteLogResult.errorMessage] is reproduced in the warning.

On failure the output:

1. retries the send up to [globalSettingMaxSendRetries] additional times, waiting [globalSettingRetryBackoff] × attempt between tries (linear backoff; a zero backoff retries immediately); 2. if every attempt fails, writes the original record to [globalSettingFallbackOutput] (console by default) so it is not lost; 3. if a replay queue is enabled ([globalSettingReplayQueueMaxSize] > 0), enqueues the record for a later retry. The queue is bounded and drops the oldest record on overflow.

Whenever a subsequent record is sent, the output first drains the replay queue oldest-first, stopping as soon as a queued record fails again (the endpoint is still down). This lets records that piled up during an outage flush in order once the endpoint recovers.

Delivery is serialised: records are handed to the endpoint one at a time, in the order [output] was called, however many callers or instances there are. [output] returns before its record has been sent (see its signature), so overlapping calls are the normal case rather than the exception — and without serialisation each of them would run its own drain over the shared replay queue, re-sending records another drain had read but not yet removed. The guarantee covers one isolate, which is exactly the scope of the queue it protects: both are statics, and Dart statics are per-isolate.

Serialisation is between records, not the whole logging call: [output] still returns immediately, and the caller is never blocked.

The defaults (no retries, no backoff, no replay queue) keep behaviour predictable and testable without a live server: one attempt, fall back on failure. Opt into resilience by setting the globalSetting* knobs.

The configured remote endpoint for log transmission.

Must be set before remote logging will work. If null, all messages fall back to [globalSettingFallbackOutput].

static int globalSettingMaxSendRetries

Number of additional send attempts after the first one fails.

A value of 0 (the default) means a single attempt with no retry. A value of n means up to n + 1 total attempts before the record is routed to the fallback / replay queue.

A negative value is read as 0, not as "retry forever". The three resilience knobs share that rule — see [globalSettingReplayQueueMaxSize], where it matters most.

static Duration globalSettingRetryBackoff

Base delay between retries; the wait before retry k is backoff × k.

[Duration.zero] (the default) retries immediately with no delay, which keeps tests fast and behaviour deterministic. A negative duration is read as [Duration.zero]; retries never wait a negative time and never skip a retry because of one.

static int globalSettingReplayQueueMaxSize

Maximum number of records held in the in-memory replay queue.

0 (the default) disables the queue entirely. When greater than zero, records that exhaust their retries are enqueued (dropping the oldest on overflow) and re-sent, oldest-first, on the next successful transmission.

A negative value is read as 0 — it does not mean "unlimited". That is worth saying because plenty of buffering APIs use -1 for exactly that, so -1 here is a plausible way to try to say "never drop anything", and it says the opposite: buffering off, every record that exhausts its retries dropped after the fallback write. There is no unbounded setting, deliberately — a queue that grows without limit while an endpoint is down is the failure this one exists to prevent, and the records it would hold are already safe in [globalSettingFallbackOutput]. To buffer a lot, name a large number.

The mistake is silent by design rather than by omission: this is read on the path that reports some other failure, so refusing a value here would make a misconfiguration take down the reporting, and warning about it would emit a line per record for the length of the outage — which is the flood the fallback's one-shot report exists to avoid.

static TomLogReplayStore globalSettingReplayStore

Backend that stores records awaiting replay after failing every send attempt.

Defaults to an in-memory store ([TomInMemoryLogReplayStore]), so the replay queue is zero-config and stays entirely in process. Assign a durable implementation (e.g. a file-backed store) to make buffered records survive a restart while the endpoint is down. Bounded by [globalSettingReplayQueueMaxSize]; drained oldest-first on the next successful send. Shared across instances since a single remote endpoint is assumed.

static Future<void> _deliveryLane

Tail of the delivery lane: completes when the most recently claimed record has finished draining, sending and (if it failed) being buffered.

Shared with [globalSettingReplayStore], whose scope it matches: both are per-isolate statics, so the lane serialises every record an isolate produces against the same isolate's queue.

static void clearReplayQueue()

Discards every buffered record.

Use when reconfiguring [remoteEndpoint] so records queued for a previous endpoint are not replayed to the new one.

static Future<void> flush()

Settles every record this isolate has handed to [output], then gives the replay queue a chance to drain.

[output] returns before its record has been sent — deliberately, since a logging call must never block the code that made it — so at any moment there may be records in flight and records buffered from an earlier outage. A process that exits straight after logging loses both, and had no supported way to wait. This is that way: call it once, at shutdown, after the code that logs has stopped.

It deliberately does not make an individual [output] call awaitable. A sink that a caller can await per record invites exactly the coupling this one exists to avoid.

It covers exactly what was logged before it was called. [output] claims its place in the delivery lane before its first await, so every call that had started is already in the chain this awaits; a record logged while the flush runs appends behind it and is not waited for. Waiting for those too would mean re-reading the lane until it stopped moving, which in a process that never stops logging is a loop that never ends. Call it after the code that logs has stopped, and call it again if that was not true.

The drain takes a lane slot of its own, exactly as a record does, so it cannot overlap a delivery in flight — and it runs in the same inRemoteLogging zone [output] uses, so a line the transport logs on its way out does not re-enter remote logging.

Returning does not promise delivery succeeded. A record the endpoint still refuses stays buffered, which is what the replay queue is for; the promise is only that nothing is left half-done.

The lane and the queue are per-isolate statics, so this flushes whatever this isolate produced, whichever instance is installed.

static Future<String?> _sendOnce(TomRemoteLogMessage remoteMessage)

Sends [remoteMessage] once, translating every way the send can fail into a single failure description.

Returns null only when a server accepted the record, or a human-readable failure description naming which kind of failure it was: the server was never reached, the server answered with an error, or the endpoint threw.

The endpoint reports failure on two independent channels and both are read here. [TomServerCallError] is purely transport-level — it knows the status code and nothing about the payload — so a collector that answers HTTP 200 carrying a [TomRemoteLogResult.hasError] body signals no transport error at all. Testing only the transport channel treated such a rejection as a complete success and dropped the record without retry, fallback or replay.

static bool _isUnreachable(TomServerCallError error)

Whether [error] means the request never produced a response, as opposed to producing one that failed.

The internal code decides it on its own. [TomServerCallError] distinguishes the two conditions — noResponseError means there was no reply to read, serverError means the server replied and the reply was a failure — so there is nothing left for a second test to separate. A statusCode == 0 check beside it would be load-bearing only if the two codes shared a value, and a redundant condition on an error path is a condition nobody can tell is dead.

static Future<String?> _sendWithRetry(TomRemoteLogMessage remoteMessage)

Sends [remoteMessage] with bounded retry and linear backoff.

Returns null once a send succeeds, or the last failure description if every attempt (the first plus [globalSettingMaxSendRetries] retries) fails.

static Future<void> _drainReplayQueue()

Re-sends buffered records oldest-first, stopping at the first one that still fails (the endpoint is presumed down again).

A record is removed only once the server has accepted it, so a crash mid-drain replays it rather than losing it. That leaves the record readable by anyone else draining at the same time, which is why callers must hold a delivery-lane slot (see [output]): the lane, not this loop, is what stops a second drain from re-sending what this one has in flight.

static void _enqueueForReplay(TomRemoteLogMessage remoteMessage)

Buffers [remoteMessage] for later replay, dropping the oldest record when the queue exceeds [globalSettingReplayQueueMaxSize]. A non-positive size disables buffering.

static void _logToFallback(TomLogLevel loggerLevel, TomLogLevel logLevel, String level, Object message, String isolateName, DateTime timeStamp, String? origin, String cause)

Writes the original record (and a warning describing [cause]) to the fallback output so a failed transmission never loses data.

static void _reportFallbackFailure(Object record, Object error, StackTrace stackTrace)

Announces on the platform's error channel that [globalSettingFallbackOutput] itself failed, and that [record] is therefore lost.

The record cannot be saved — the fallback is the last sink in the chain, so there is nowhere left to write it. That makes discarding the failure tempting, but "must not throw" and "must not tell anyone" are different requirements, and only the first one is a property of a well-behaved logging sink. Silence here would make every other guarantee in this class unverifiable in production: a process with a misconfigured fallback would report perfect health while losing every record.

The report goes to [TomPlatformUtils.outError] rather than to any [TomLogOutput], because the logging stack is the thing that just failed; routing the news through it would be the same mistake one level up.

It is written once per installed fallback. A fallback that is broken is normally broken for every record, so a per-record report would turn one misconfiguration into exactly the flood the fallback exists to prevent. Installing a different output re-arms it (see [globalSettingFallbackOutput]).
