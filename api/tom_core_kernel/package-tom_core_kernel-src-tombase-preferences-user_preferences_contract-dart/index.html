The wire contract for server-stored user preferences (C-13): the DTOs and the [TomApi] declaration both halves of the framework bind to.

The store is server-side — a table, a repository, a row scope — and cannot live here. What has to live here is the part the two halves must agree on: the shape of a preference on the wire, and the URI / method / request type / result type / access policy of every endpoint that carries one (G-API-1, G-API-3). The kernel is the framework's contracts package: it is the one package a client and a server both already depend on, so declaring the API anywhere else would mean one of them re-stating it — and a re-stated contract is a contract that drifts.

A preference carries its own type

A preference value is stored as JSON text plus the name of the type it was written as ([TomUserPreferenceDto.valueType]). The type name is not decoration: it is what lets a reflected object round-trip ([TomReflectionInfo.createInstanceFromJson] needs a ClassMirror), and it is what makes a mismatched read fail loudly instead of quietly parsing a Duration as an int. Reading a preference is therefore typed on both sides — the caller says what it expects, and the stored value says what it is.

class TomUserPreferenceDto

class TomUserPreferenceDto

One stored preference as it travels the wire.

A reflection-first wire DTO (G-DTO): @tomReflector, plain non-final fields, no hand-written serializer.

Constructors

TomUserPreferenceDto.new({String key = '', String valueType = '', String value = '', DateTime? updatedAt})

Creates a preference DTO. Every field defaults, because the reflection path instantiates a blank instance and fills it field by field.

Properties

String key

The preference key — see [TomUserPreferenceKeys] for the ones the framework itself reads.

String valueType

The name of the type [value] was written as.

A scalar's Dart type name (String, int, double, bool, DateTime), or the simple name of a @tomReflector class. It is stored with the value rather than derived from it because JSON forgets: 3 is an int and a double, "2026-01-01T00:00:00Z" is a String and a DateTime, and a map is every reflected class at once.

String value

The value's JSON text.

Text rather than a decoded Object? so the DTO is flat: a Map<String, Object?> field would have to survive the reflection serializer twice — once as the DTO's own field and again as the preference's payload — and the two nestings do not compose.

DateTime? updatedAt

When the preference was last written, in UTC, or null for one that has never been stored.

UTC because the constructor converts it, not because callers remember to: a DateTime cannot carry the zone in its type, so a server writing DateTime.now() instead of DateTime.now().toUtc() would satisfy every check and still hand a client an instant whose meaning depends on which machine wrote it. That is the same rule the value path already applies to a stored DateTime — see [TomUserPreferenceCodec.dateTimeType] — and it applies here for the same reason: a preference follows the user across devices.

The conversion preserves the instant; it only settles how the instant is named. Reflection now applies the same normalisation on the way out — a bare DateTime is written as toUtc().toIso8601String(), so the wire is safe whatever a caller assigned — which makes this the field's rule rather than the wire's last line of defence. It is still worth having here: a reader of updatedAt gets a UTC instant from the object as well as from the payload, so the two cannot disagree, and code that never serializes the DTO sees the same value the code that does would send.

Assigning the field directly afterwards is not intercepted — a wire DTO's fields are plain and public (G-DTO), so there is no setter to hook. Every DTO the framework itself produces goes through this constructor.

class TomUserPreferenceWriteRequest

class TomUserPreferenceWriteRequest

The request for writing one preference.

Carries the same three fields as the result minus the timestamp: when a preference was written is the server's answer, never the client's claim.

This request is the write's only statement of which preference it means — the write URI is the bare collection, not /{key} — so [key] is read from the body and nothing else can contradict it.

Future<List<TomUserPreferenceDto>> listPreferences()

[tomUserPreferencesListEndpointId] — every preference of the caller, ordered by key, ascending.

The order is part of the contract rather than an implementation's accident, and it is stated here rather than on either implementation because both of them answer it: a server that sorts and a client that forwards an unsorted list are not two flavours of one API, they are two APIs. Anything that renders the list, or diffs one caller's list against another's to decide what to sync, reads the sequence — so leaving it unstated makes those callers depend on whatever each side happens to do.

The key is the ordering column because it is the one field that is unique within a caller's preferences and never changes while the preference exists: rewriting a value must not move it in the list, which rules out updatedAt, and there is no insertion order that survives a store being rebuilt.

Ascending by code unit — plain ASCII order, so Theme precedes theme. That is exact rather than approximate only because [TomUserPreferenceKeys] admits ASCII alone: over that alphabet code-unit order, byte order and alphabetical order are the same order, so a Dart compareTo and a byte-collated SQL ORDER BY cannot disagree. A store whose backing column carries a case-insensitive collation does deviate from this, and that is a defect in the store rather than a second permitted reading of this sentence.

Unpaged, and bounded. There is no page and no filter: every caller of this list wants all of it, and the list is small by construction — at most [tomUserPreferencesMaxPerPrincipal] entries, each holding at most [TomUserPreferenceCodec.maxValueBytes] of value.

Future<TomUserPreferenceDto> readPreference(TomUserPreferenceKeyRequest request)

[tomUserPreferencesReadEndpointId] — the caller's preference under [TomUserPreferenceKeyRequest.key].

A preference the caller has never written is a failure keyed [tomUserPreferencesNotFoundErrorKey] — on the wire, a 404 carrying the error envelope with that errorKey. A bare 404 is not absence: it is a denial, or a route that is not there.

Future<TomUserPreferenceDto> writePreference(TomUserPreferenceWriteRequest request)

[tomUserPreferencesWriteEndpointId] — writes one preference of the caller, replacing any previous value.

The written preference is [TomUserPreferenceWriteRequest.key] and only that: the endpoint is a PUT at the collection, so unlike [readPreference] and [deletePreference] the URL names no key.

Refuses a value longer than [TomUserPreferenceCodec.maxValueBytes] (preferences.encoded.too_large, a 400), and a write that would add a key beyond [tomUserPreferencesMaxPerPrincipal] preferences ([tomUserPreferencesLimitExceededErrorKey], a 409). Replacing a key the caller already holds is never refused for the count.

Future<void> deletePreference(TomUserPreferenceKeyRequest request)

[tomUserPreferencesDeleteEndpointId] — deletes the caller's preference under [TomUserPreferenceKeyRequest.key].

Idempotent: deleting a preference that is not there succeeds, so a delete never answers [tomUserPreferencesNotFoundErrorKey] and a 404 from it is always a refusal.

Future<void> clearPreferences()

[tomUserPreferencesClearEndpointId] — deletes every preference of the caller.

The operation an account reset performs. It is an endpoint of its own rather than a loop over [listPreferences] and [deletePreference] because only the server can make it one statement: a loop that fails half way leaves an account in a state nobody asked for, and it is the account store — the one shared across every device a user owns — that would be left in it. The device store draws the same distinction, for the same reason, in TomDevicePreferences.clear.

Idempotent and unconditional: a caller holding no preferences is cleared with a 200, and there is no filter, because a partial clear is [deletePreference] repeated and a caller that wants one already has it.

Answers nothing. How many rows went is the store's business — a count on the wire would invite a caller to branch on it, and the only branch it could support ("some were already gone") is the case the idempotence exists to make uninteresting.

function registerTomUserPreferencesApi

void registerTomUserPreferencesApi()

Registers [tomUserPreferencesApi] with the global [tomRemoteApis] registry.

Idempotent, and called by both halves: a server calls it before mounting the endpoints, a client before building a caller. Registration is explicit rather than implicit in a top-level initializer because a deployment that stores no preferences should not carry the API in its registry.
