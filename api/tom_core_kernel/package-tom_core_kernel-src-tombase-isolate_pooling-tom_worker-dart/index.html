Isolate pooling and worker management for concurrent task execution.

This library provides a robust framework for managing isolates in Dart/Flutter applications. It enables parallel processing by spawning worker isolates that can execute commands independently from the main isolate.

Key Features

  • Worker Isolates: Spawn and manage isolated execution contexts
  • Bidirectional Communication: Send commands to workers and receive responses
  • Command Pattern: Execute commands as objects with built-in result handling
  • Executor Pattern: Register handlers to process incoming messages
  • Worker Pools: Manage multiple workers with automatic load distribution

Example Usage

// Create a worker context
final context = TomWorkerContext(
  defaultTomEnvironment,
  platformLinux,
  [],
  'MyWorker',
);

// Spawn a worker
final worker = await TomWorker.spawn(
  TomWorker.startRemoteIsolate,
  context,
);

// Execute a command
final result = await worker.executeCommand(myCommand);

// Clean up
worker.close();

The environment and platform are top-level constants from tom_basics, not static members: defaultTomEnvironment / noTomEnvironment, and platformLinux, platformMacos, platformWindows, platformAndroid, platformIos, platformWeb, platformFuchsia / noTomPlatform. An application with its own environments constructs them directly, e.g. const TomEnvironment("staging").

Platform support

Native only. This library is built on dart:isolate, which both web compilers mark as unsupported, so none of it runs in a browser.

That is why the platform constant above is not a target switch. Nothing here reads [TomWorkerContext.tomPlatform]; it is application data copied into the isolate, where a [TomWorkerContext.initializeIsolate] override can read it back — a spawned isolate starts with fresh memory and none of the creator's TomRuntime configuration. The constants are the framework's vocabulary for the whole workspace, so platformWeb is accepted and stored faithfully; it just names a platform on which no worker can be spawned.

See also: - [TomWorker] for individual worker management - [TomWorkerPool] for managing multiple workers - [TomExecutor] for custom command handlers - [TomCommand] for encapsulated command objects

class TomCommand

abstract class TomCommand

Base class for self-executing commands sent to worker isolates.

Unlike executors which are registered handlers, commands encapsulate both data and behavior. When a command is received by a worker, its [execute] method is called automatically.

When to Use

Use [TomCommand] when: - The command logic is self-contained - You want to send data and functionality together - Higher isolation between command types is desired

Use [TomExecutor] when: - Multiple command types share common handling logic - You need a central point for command processing - Commands are simple data objects

Example

class ComputeFactorialCommand extends TomCommand {
  final int number;
  ComputeFactorialCommand(this.number);

  @override
  Future<Object?> execute() async {
    return factorial(number);
  }
}

// Send to worker
final result = await worker.executeCommand(ComputeFactorialCommand(10));

Methods

Future<Object?> execute()

Executes this command and returns the result.

Override this method to implement the command's logic. The result is sent back to the caller.

Returning null does not deliver null: the dispatch substitutes it before sending, with the string "null" towards the worker and with [TomExecutor.noResult] towards the creator. Return an explicit sentinel if the caller has to recognise "absent".

The default returns that same "null" string, so an unoverridden command guarantees a sendable, non-null response — and is therefore indistinguishable from a command that resolved to null.

class TomExecutor

abstract class TomExecutor

Base class for command executors that handle messages in worker isolates.

Executors provide a way to define custom handlers for incoming commands. Multiple executors can be registered, and they are called in order until one produces a result (i.e., returns something other than [noResult]).

Pattern Overview

The executor pattern allows separation of command handling logic from the worker infrastructure. Each executor can focus on a specific type of command or domain.

Example

class MyExecutor extends TomExecutor {
  @override
  Object execute(Object command) {
    if (command is MyCommand) {
      return processMyCommand(command);
    }
    return TomExecutor.noResult; // Let next executor handle it
  }
}

// Register the executor
TomWorker.addExecutor(MyExecutor());

Important Notes

  • Return [noResult] to indicate the command was not handled
  • Executors exist in both isolates and may handle different commands
  • The creator-side worker handles responses from the created worker

Static

static Object noResult

Sentinel value indicating that an executor did not process a command.

Return this value from [execute] to allow the next executor in the chain to handle the command. It is an answer to the dispatch, not to the caller: a chain that declines end to end is reported as [notHandled] instead, so a caller never receives this as "nothing handled it".

It does reach a caller in one other role, on [TomWorker.executeInCreator]: a handler that answers null is substituted with this sentinel before the response is sent, because a bare null on that path is reserved. So on the receiving side of that call it means the handler answered nothing, which is the opposite of what returning it from [execute] means, and [notHandled] is what carries the other half.

It carries no value equality and is recognised by identity — including on the far side of a worker's port. That holds because [TomWorker.spawn] starts its isolate with Isolate.spawn, which places it in the creator's isolate group, and an isolate group shares its canonical constants: a const instance sent across the port arrives as the same instance, not a copy. An isolate started with Isolate.spawnUri is a group of its own and would not share it. isolate_pooling_test.dart asserts same(...) on both sentinels after a real round trip in each direction.

static Object notHandled

Sentinel value a dispatch answers with when nothing claimed a command.

Sent when the executor chain declined end to end, and when no executor is registered at all. Both are the same condition from a caller's side — this message reached the other isolate and came back unclaimed — and both are almost always a missing TomWorker.addExecutor at start-up.

It is a second sentinel because one cannot carry this meaning and "the handler answered null": the two are opposites — "there was no answer" against "the answer is nothing" — and nothing downstream can tell one value apart from itself. Spelled the same way, a process that forgets to register an executor reports a plausible answer for ever: TomAuthorizationCache.getPrincipal reads every lookup as a cache miss and storePrincipal reports every write as a success, neither of which a suite notices, because both are answers rather than failures.

A caller that must distinguish them compares against this:

final result = await TomWorker.executeInCreator(command);
if (identical(result, TomExecutor.notHandled)) {
  throw StateError('no executor is registered for $command');
}

Like [noResult] it carries no value equality, for the same reason, and is recognised by identity across the port for the same reason — see [noResult].

class TomWorker

class TomWorker

Manages communication with a worker isolate.

[TomWorker] provides the core functionality for spawning isolates and managing bidirectional communication between the main isolate and worker isolates.

Architecture

┌─────────────────┐         ┌─────────────────┐
│  Main Isolate   │◄───────►│ Worker Isolate  │
│   (Creator)     │ SendPort│   (TomWorker)   │
│                 │◄───────►│                 │
│  TomWorker      │ReceiveP │  Executors      │
│  instance       │         │                 │
└─────────────────┘         └─────────────────┘

Example

// Spawn a worker
final worker = await TomWorker.spawn(
  TomWorker.startRemoteIsolate,
  TomWorkerContext(env, platform, [], 'Worker'),
);

// Execute commands
final result = await worker.executeCommand(MyCommand());

// Check if busy
if (worker.isBusy()) {
  print('Worker is processing requests');
}

// Shutdown
worker.close();

Future<Object?> executeCommand(Object command)

Sends a command to the worker isolate and awaits the result.

This is the primary method for executing work in a worker isolate. The command can be either a [TomCommand] subclass (which executes its own logic) or any object that will be processed by registered executors.

  • [command]: The command to execute

Returns the result of executing the command, or [TomExecutor.notHandled] when nothing in the worker claimed it — because no executor is registered there, or because every registered executor declined. Every command is answered: an unanswered one would leave this future pending forever, and liveness supervision could not rescue it, since the isolate is healthy and still answers pings. Compare the result against [TomExecutor.notHandled] if "nothing handled this" is a case the caller must distinguish, which for most callers it is: it reports a missing addExecutor at start-up rather than anything about the command. Both directions spell that case the same way, so one check serves whichever way a command travelled.

Never resolves to null, despite the Object? in the signature. A command or executor result of null is substituted with the string "null" before the response is sent, so a nullable-returning command is indistinguishable from one that returned that literal text — and a null-checking caller never sees the case it is checking for. Return an explicit sentinel to carry "absent" across the boundary. Note that the creator-bound direction differs: [executeInCreator] substitutes [TomExecutor.noResult] instead.

A command that throws inside the worker rethrows here, with the original exception object, so the failure can be caught by type exactly as if the command had run locally. An exception that cannot cross the port — one holding a closure or a port — arrives as a [RemoteError] built from its toString() instead: still a throw, but not matched by an on clause for its original type. [executeInCreator] carries failures the same way, so the contract does not depend on which direction a command travels.

Throws [TomWorkerException] if this worker has been closed — the same fail-fast [TomWorkerPool.execute] gives for the identical mistake one layer up. The closed worker's isolate has already been told to shut down, so a dispatch accepted here would never be answered.

A command accepted before [close] is unaffected: it was accepted while the worker was open and still resolves normally.

Example:

final result = await worker.executeCommand(ProcessDataCommand(data));
TomWorkerException _closedException(String site, String attempt)

Builds the refusal thrown when this worker is used after [close].

[site] names the rejected operation in the key and [attempt] describes it in the message; both carry the isolate name, because a pool closes many workers at once and "which one" is the first question to answer.

void superviseExit(void Function() onDeath)

Registers a one-shot [onDeath] callback for unexpected isolate exit.

Uses [Isolate.addOnExitListener] as the primary death signal: it fires for every way the isolate can terminate — an uncaught error, [Isolate.kill], or an out-of-memory kill — which a request-response ping alone cannot observe once a command is already hung.

A normal [close] is not an unexpected death: [close] sets [isClosed] and tears down the exit port before the isolate terminates, so [onDeath] does not fire for orderly shutdowns.

Idempotent: calling it again while already supervised is a no-op.

void _handleUnexpectedDeath()

Handles an unexpected isolate exit reported by the [superviseExit] port.

Marks the worker closed, fails every in-flight request with a [TomWorkerDiedException] (so callers stop hanging on their completers), releases the ports, and finally invokes the supervisor callback — which an owning [TomWorkerPool] uses to respawn a replacement, and a directly supervised worker uses for whatever recovery it chose.

The requests are completed before the callback, and they are [Completer.sync] completers, so the awaiting caller resumes first. State the callback maintains is therefore still stale inside the caller's catch — a pool's workerCount still counts this worker at that point.

Future<bool> ping(Duration timeout)

Sends a liveness probe to the worker and awaits its pong within [timeout].

Returns true if the worker answered in time, false on timeout. A timed-out probe abandons its request slot so a late pong is silently ignored (see the null-safe branch in [_handleResponsesFromIsolate]); it deliberately does not kill the isolate — that decision belongs to the supervisor, which only pings idle workers.

The worker answers before any command or executor dispatch, so a command running asynchronously does not delay the reply. A command occupying the isolate synchronously does: nothing in that isolate runs until the loop yields, so this returns false for a worker that is healthy and merely busy computing. This method does not check [isBusy] — a caller probing a worker it also dispatches to must interpret false accordingly, or probe only when idle as pool supervision does.

void killUnresponsive()

Force-kills the worker's isolate at [Isolate.immediate] priority.

Intended for supervisors that detected an unresponsive (hung) worker via [ping]. The kill triggers the [superviseExit] listener, which fails any in-flight requests and runs the death callback — respawning a replacement in a pool, or whatever recovery a directly supervised worker registered.

void sendExecutorToIsolate(TomExecutor te)

Sends an executor to the worker isolate.

The executor will be added to the worker's executor list and will process subsequent commands. Use this to dynamically add command handlers to running workers.

  • [te]: The executor to send

Throws [TomWorkerException] if this worker has been closed: the send would land on a port whose isolate is shutting down, losing the executor while the caller believes it registered.

void close()

Closes this worker and shuts down the isolate.

After calling this method: - No new commands can be sent — [executeCommand] and [sendExecutorToIsolate] throw [TomWorkerException] rather than dispatching to an isolate that will never answer - The worker isolate receives a shutdown signal - Resources are released

Commands already in flight are not cancelled: they were accepted while the worker was open, so the response port stays open until the last of them resolves.

Idempotent. Check [isClosed] to verify the worker's state.

static Future<TomWorker> spawn(void Function(TomWorkerContext) initializer, TomWorkerContext workerContext, {Duration readyTimeout = const Duration(seconds: 30)})

Spawns a new worker isolate with the given initializer and context.

This is the primary factory method for creating workers. It handles the isolate creation, port setup, and initialization sequence.

  • [initializer]: Function to run in the new isolate (typically

[startRemoteIsolate]) - [workerContext]: Configuration for the new worker - [readyTimeout]: How long the new isolate has to signal readiness before the spawn is abandoned. Covers the whole startup — the isolate's first message, [TomWorkerContext.initializeWorker] and [TomWorkerContext.initializeIsolate] — because the caller cares how long spawn may take, not how that time is divided. Must be positive.

Returns a [Future] that completes when the worker is ready.

A startup that cannot finish fails the future rather than stalling it: an isolate that dies before signalling readiness is reported at once (isolate.died_before_ready.spawn), and one that stays alive but silent is given up on when [readyTimeout] expires (isolate.ready_timeout.spawn). Either way the isolate is killed, because a failed spawn returns no [TomWorker] and so leaves the caller no handle with which to [close] it.

Throws [TomWorkerException] if [readyTimeout] is not positive: such a bound expires before any isolate could answer, so every spawn under it would fail.

Example:

final worker = await TomWorker.spawn(
  TomWorker.startRemoteIsolate,
  myContext,
);
static void _completeFromResponse(Completer<Object?> completer, Object response)

Resolves [completer] from a command [response] received over a port.

A [_TomRemoteFailure] payload signals that the command threw in the other isolate, so the awaiting future is completed with an error carrying the original exception; any other payload is the successful result. Shared by the two response handlers (worker→creator and creator→worker) so both channels resolve pending requests identically — a caller cannot tell from its await which direction the command travelled.

static void _sendFailure(SendPort port, Object Function(Object) respond, Object error, StackTrace stack)

Sends [error] back over [port] as a failure, so the awaiting side rethrows.

[respond] wraps the payload in whichever response envelope the channel uses ([_TomCreatorResponse] or [_TomIsolateResponse]); everything else about reporting a failure is identical in both directions and lives here.

The thrown object is sent as-is where the port accepts it, so the caller can catch it by type. Not every object can cross a port, though — a closure, a [ReceivePort] or anything holding one is rejected — and the send that discovers this happens inside a port handler, where a throw would be caught by nobody and would leave the request unanswered forever. So an unsendable failure is retried as a [RemoteError] built from its toString(): the caller loses the type but still gets an error naming what went wrong, which beats waiting on a future that never completes.

static Future<Object?> executeInCreator(Object command)

Executes a command in the creator isolate and awaits the result.

Use this for request-response communication from a worker to the main isolate. The command will be processed by executors registered on the creator's [TomWorker] instance.

  • [command]: The command to execute in the creator

Returns the result of executing the command, or [TomExecutor.notHandled] when nothing on the creator side claimed it — because no executor is registered there, or because every registered executor declined. As on the worker side, every command is answered; an unanswered one would leave this future pending forever. Compare with [TomExecutor.notHandled] if "nothing handled this" is a case the caller must distinguish, which for most callers it is: it means a missing addExecutor at start-up rather than anything about the command. 

final result = await TomWorker.executeInCreator(command);
if (identical(result, TomExecutor.notHandled)) {
  // The creator received the message but nothing claimed it.
}

Never resolves to null: a creator result of null is substituted with [TomExecutor.noResult] before the response is sent, so on this call that sentinel means the handler answered nothing and nothing else. Spelling that and "nothing claimed it" with one value would conflate opposites, and a process missing an addExecutor would then report plausible answers rather than a fault; see [TomExecutor.notHandled] for what that costs.

The null substitution is still not the one the opposite direction makes — [executeCommand] uses the string "null" — so the two remain non-interchangeable in that respect. Only the unclaimed case is spelled the same both ways.

A command that throws on the creator side rethrows here, with the original exception object, so the failure can be caught by type exactly as if the command had run locally: 

try {
  final principal = await TomWorker.executeInCreator(LookUpCommand(token));
} on TomAuthorizationCacheException {
  // The creator-side handler threw; this is not a result.
}

Distinguishing a thrown failure from a returned result matters more than it may appear: a caller that treats every answer as a value has no way to tell "this went wrong" from "this is the answer", and silently degrades a reported failure into whatever its fallback for an unrecognised result is.

The exception arrives with its own type wherever it can cross the port. An exception that cannot be sent — one holding a closure or a port — arrives as a [RemoteError] built from its toString() instead: still a throw, still naming the failure, but not matched by an on clause for its original type.

Throws [TomWorkerException] if called from the main isolate.

Example:

// From within a worker isolate:
final config = await TomWorker.executeInCreator(GetConfigCommand());

class TomWorkerContext

class TomWorkerContext

Configuration context for initializing worker isolates.

This class holds the configuration and state needed to spawn and initialize a worker isolate. It provides hooks for custom initialization logic in both the isolate and worker contexts.

Lifecycle

1. Context is created with environment configuration 2. [initializeIsolate] is called in the new isolate (static context) 3. [initializeWorker] is called on the TomWorker instance

Both hooks report failure by throwing; see [initializeIsolate].

Example

class MyWorkerContext extends TomWorkerContext {
  MyWorkerContext() : super(
    defaultTomEnvironment,
    platformLinux,
    [],
    'MyWorker',
  );

  @override
  Future<void> initializeIsolate() async {
    // Set up isolate-specific resources. Throwing here — directly, or out
    // of setupDatabase — aborts the spawn instead of producing a worker
    // with half its setup done.
    await setupDatabase();
  }

  @override
  Future<void> initializeWorker(TomWorker worker) async {
    // Configure the worker instance
    worker.sendExecutorToIsolate(MyExecutor());
  }
}

class TomWorkerDiedException

class TomWorkerDiedException extends TomException

Exception used to fail a command whose worker isolate died mid-flight.

When liveness supervision is enabled on a [TomWorkerPool] (or a worker is supervised directly via [TomWorker.superviseExit]) and the worker's isolate terminates unexpectedly — an uncaught error, [Isolate.kill], or an out-of-memory kill — every request still awaiting a response is completed with this exception rather than hanging forever on its completer.

The command is not re-dispatched: re-running a command that may have already produced side effects before the isolate died would risk executing non-idempotent work twice. Recovery instead means restoring capacity — a pool respawns a replacement worker automatically, a directly supervised worker leaves that to its onDeath callback — while the in-flight caller observes this failure and decides how to react.

class TomWorkerPool

class TomWorkerPool

Manages a pool of worker isolates for parallel task execution.

[TomWorkerPool] provides automatic load balancing by distributing commands across multiple workers. When all workers are busy, requests are queued until a worker becomes available.

Use Cases

  • CPU-intensive computations that benefit from parallelization
  • Batch processing of independent tasks
  • Request handling where isolation is required

Example

// Create a pool with 4 workers
final pool = await TomWorkerPool.withSize(4, context);

// Execute commands - automatically distributed
final results = await Future.wait([
  pool.execute(ProcessCommand(data1)),
  pool.execute(ProcessCommand(data2)),
  pool.execute(ProcessCommand(data3)),
  pool.execute(ProcessCommand(data4)),
]);

Liveness supervision (opt-in)

By default the pool performs no liveness supervision — behaviour is unchanged from an unsupervised pool. Pass a [healthCheckInterval] to [withSize] to enable it. When enabled:

  • Every worker is watched via [TomWorker.superviseExit]. If an isolate

dies for any reason (uncaught error, [Isolate.kill], OOM), each in-flight command on it is failed with a [TomWorkerDiedException] instead of hanging forever, and the pool respawns a replacement worker (via [TomWorker.spawn] with the pool's stored context) to restore capacity. - A periodic timer pings idle workers to catch hangs that never emit an exit signal. A ping is answered before any command or executor dispatch, so it does not queue behind in-flight work; a worker running asynchronous work answers it at once. Busy workers are skipped because synchronous work blocks the isolate's event loop — a tight compute loop would leave the probe unread past [healthCheckTimeout] and force-kill a worker that is healthy and computing. Busy-worker crashes are covered by the exit listener regardless. Because a probed worker is reserved out of the free list and only returns to it once its command has resolved, a probe never races a running command: [healthCheckTimeout] bounds a round trip to an idle isolate, not the runtime of any command. A worker that fails to answer in time is force-killed, which routes it through the same death/respawn path.

A failed in-flight command is deliberately not re-dispatched: re-running a command that may have already produced side effects before the isolate died would risk executing non-idempotent work twice. The caller observes the [TomWorkerDiedException] and decides how to react.

Notes

  • Workers are created during pool initialization
  • A pool needs at least one worker; [withSize] rejects a smaller size

rather than returning a pool on which every command would wait forever - A command that finds every worker busy is queued, and the next worker released is handed to it directly, in arrival order - Consider pool size based on CPU cores and task characteristics

Fails every parked caller once no worker can ever serve them.

A waiter has no timer of its own, so a pool that has stopped replacing and has nothing left would hold its callers forever.

Future<void> _runHealthCheck()

Pings every idle worker; force-kills any that do not answer in time.

Each probed worker is reserved (pulled out of [_free]) for the duration of its ping so [execute] cannot dispatch real work onto it mid-probe — that would make a timed-out ping kill a worker that just started legitimate work. Responsive workers are returned to rotation; unresponsive ones are killed, which routes them through [_handleWorkerDeath] for respawn.

Future<TomWorker> _acquire()

Takes a worker for the caller, parking it in [_waiting] when none is free.

The free list is only read when nothing is queued. Serving a newcomer while someone waits would be a fairness bug the fast path cannot see, and the check that prevents it is cheaper than reasoning about whether the case can arise.

void _handOut(TomWorker tw)

Gives [tw] to the longest-waiting caller, or returns it to the free list.

The worker never passes through [_free] on its way to a waiter: leaving it there for the waiter to find is what a polling design does, and it is what lets a newcomer take it first.

Future<Object?> execute(Object command)

Executes a command using an available worker from the pool.

If every worker is busy the caller is queued, and the next worker to be released is handed to it directly. Waiting costs nothing while it lasts, and callers are served in arrival order.

The wait is unbounded: a pool whose workers are all occupied by long commands keeps its callers parked until one finishes. [close] releases them, with the same exception a call made after the close would raise.

  • [command]: The command to execute

Returns the result of executing the command.

Throws [TomWorkerException] if the pool has been closed, and (when supervision is enabled) [TomWorkerDiedException] if the worker handling this command dies before it completes.

Example:

final result = await pool.execute(MyCommand());

Shuts down every worker in this pool and releases their isolates.

After calling this method the pool is empty and must not be reused. Supervision (if enabled) is stopped first. Each worker is closed via [TomWorker.close]; workers still processing in-flight commands close their response ports once those commands resolve (see [TomWorker.close]).

Static

static Future<TomWorkerPool> withSize(int size, TomWorkerContext context, {Duration? healthCheckInterval, Duration healthCheckTimeout = const Duration(seconds: 5), Duration readyTimeout = const Duration(seconds: 30), int respawnLimit = 10, Duration respawnWindow = const Duration(minutes: 1)})

Creates a worker pool with the specified number of workers.

Each worker is spawned using [TomWorker.spawn] with the provided [context]. The spawns run together, and the method returns once every worker is ready — so construction costs about one spawn rather than [size] of them, which matters because each awaits the context's [TomWorkerContext.initializeWorker].

If any spawn fails, the workers that did come up are closed before the error is rethrown: the caller receives no pool, so nothing else would ever close them.

  • [size]: Number of workers to create; must be at least 1
  • [context]: Configuration for each worker (also retained to respawn

workers that die when supervision is enabled) - [healthCheckInterval]: opt-in; when non-null, enables liveness supervision (exit detection + idle-worker pings) and must be positive. Defaults to null (supervision off). - [healthCheckTimeout]: how long a probed idle worker has to answer a ping before it is treated as hung and force-killed. Only used — and only validated — when [healthCheckInterval] is set; must be positive. - [readyTimeout]: startup bound handed to [TomWorker.spawn] for every worker, including later replacements. The pool performs every spawn its callers ever make, so a bound it did not forward would be one nobody could set; see [TomWorker.spawn] for what it covers. - [respawnLimit] / [respawnWindow]: how many replacements supervision may spawn within a rolling window before it gives up (see [isRespawnExhausted]). Defaults to ten a minute, which no pool losing workers to ordinary causes reaches and which a churning one reaches in well under a second. Only used — and only validated — when [healthCheckInterval] is set, since nothing replaces a dead worker without supervision; both must be positive.

Returns a [Future] that completes when all workers are ready.

Throws [TomWorkerException] if any argument would produce a pool that cannot do useful work. Each such value is a caller bug — an unvalidated config entry, or an arithmetic slip like numberOfProcessors - 1 on a single-core container — and accepting it defers the symptom to a dispatch far from the mistake. The rejection carries the offending value so the error points back at the expression that produced it.

class _TomRemoteFailure

class _TomRemoteFailure

Internal marker that a command threw, rather than returned, in the other isolate.

Both response wrappers carry a plain [Object], so without a marker a caught exception sent back as the response would be indistinguishable from a result the command deliberately returned. The awaiting side unwraps this and completes its future with an error, so a caller sees the same throw it would have seen had the command run locally.

[error] is the thrown object itself wherever the port accepts it, so the caller can still catch it by type — the whole point of propagating a failure rather than a description of one. When it is not sendable the sender substitutes a [RemoteError] built from its toString(); see [TomWorker._sendFailure].
