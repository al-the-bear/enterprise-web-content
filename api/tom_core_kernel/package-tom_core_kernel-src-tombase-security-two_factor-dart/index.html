The wire shape of a pending second-factor (2FA) challenge.

The framework's login is a two-pass flow: pass 1 verifies the primary credential, and — when the resolved principal still owes a second factor — answers with a token that is not yet an authenticated session but a challenge carrier. Pass 2 takes that token plus the submitted second factor and, on success, returns exactly the token pair a 2FA-free login would have produced.

Why the challenge lives in the token

Bearer verification in this framework is stateless: every server call reconstructs the principal from the presented token and nothing else. A pending challenge is therefore carried the same way — in the interim token's claims — rather than in a server-side "pending login" record. That keeps pass 2 stateless too (any server instance can complete a login started by any other) and needs no new fields on the fixed wire types [TomAuthenticationMessage] / [TomAuthenticationResult].

Public claims vs. encrypted claims

[Tom2FAChallenge] is the client-visible half: which mechanism is in play, a displayable [hint], how many attempts remain, when the challenge lapses, and an opaque [clientData] map the mechanism's own client UI interprets. Whatever the server needs to verify a submission (a hashed one-time code, a nonce, …) is deliberately not here — it travels in the token's encrypted section under [Tom2FAClaims.verificationData], where the client cannot read it.

The server never interprets [clientData] or the verification blob; both are produced and consumed by the mechanism's adaptor. That is what keeps the mechanism set out of the framework: adding SMS or WebAuthn needs no change here.

class Tom2FAChallenge

class Tom2FAChallenge

A second-factor challenge awaiting an answer.

Produced by the server at the end of pass 1 and carried in the interim token's public claims. Immutable: consuming an attempt yields a new instance via [withConsumedAttempt] rather than mutating in place, so the value can be passed around without anyone wondering who advanced the counter.

static Tom2FAChallenge? fromClaims(Map<String, dynamic>? payload)

Reads a challenge back from a token's public [payload], or returns null when the payload carries none.

Tokens arrive from outside the process, so every claim is read defensively. A payload that says it requires 2FA but carries an unusable mechanism or expiry yields null — the caller then treats the token as simply not answerable, which is the safe reading.

"Says it requires 2FA" is decided by [Tom2FAClaims.isTrue], so a payload carrying either encoding is decoded. Being defensive about shape and lenient about encoding point the same way here: both keep a token that owes a factor from quietly looking like one that does not.

The remaining claims fall back instead of rejecting, and all but one fall back to what the constructor would have chosen anyway ([hint] to '', [attempt] to 0). [attemptsAllowed] is the exception: it falls back to 0, not to the constructor's 3, so a challenge whose budget is unreadable arrives already [isExhausted]. That is deliberate and fail-closed — a malformed token must not be able to mint attempts. Being sent back to pass 1 on a challenge that was in fact answerable is a recoverable annoyance; handing three free guesses to whoever shaped the payload is not. [Tom2FAPendingEnrolment.fromClaims] does the same.

class Tom2FAClaims

class Tom2FAClaims

The claim names under which a pending 2FA challenge travels in a token.

Collected in one place because they are written by the server (when issuing the interim token) and read by the client (to drive the second-factor UI) — two sides that must agree exactly. All but [verificationData] are public claims; [verificationData] is a key in the token's encrypted section.

static String requires2FA

Public claim: "true" while the token still owes a second factor.

A string rather than a bool to match the rest of this claim family, which is string-encoded throughout: one payload that spells its booleans two ways is a payload every reader has to know a table about. Written as a string by every Tom tier — but read with [isTrue], which accepts the JSON boolean too, and refuses anything else. This claim gates authenticated, so a reader that silently took an unreadable value for "nothing owed" would fail open.

static bool isTrue(Object? raw)

Reads a boolean claim that may have crossed the wire in either encoding.

The single rule for every boolean claim in both 2FA claim families — this one and [Tom2FAEnrolmentClaims] — on both tiers. The two families disagree about encoding for historical reasons: [requires2FA] and [Tom2FAEnrolmentClaims.pendingEnrolment] are strings, while [Tom2FAEnrolmentClaims.skippable] and [Tom2FAEnrolmentClaims.skipSpendsGrace] are JSON booleans. A deployment mixing framework versions can plausibly present either, so reading both costs one comparison and removes an entire class of upgrade report.

Applying it to the gates — the reads that decide whether a token authenticates, and whether a challenge or enrolment is built at all — is the point, not a convenience. At every one of them leniency is the fail-safe direction: reading true as well as "true" makes more tokens count as still owing a second factor, and makes more challenges and enrolments renderable. The strict reading fails the other way, and at [requires2FA] it fails open — a token that says, in the encoding this reader did not expect, that it has not finished logging in would otherwise authenticate.

Deliberately not general truthiness: only the four encodings the framework itself produces are recognised — true/'true' and false/'false' — plus an absent claim, which is the ordinary case and reads as false. Widening past what any Tom tier writes would start guessing at other issuers' conventions rather than reconciling our own.

Anything else throws. 'True', 1, 'yes' and any other value are refused with security.two_factor.unreadable_claim rather than being read as "nothing owed". Silence was the old behaviour and it picked the unsafe side: a token whose issuer meant this login is not finished, and spelled it in an encoding this reader did not expect, authenticated in full. Tokens are signed, so such a value can only arrive from an issuer the deployment already trusts — which is exactly the external-identity case, where a third party's reasonable encoding choice must become an error rather than a bypass. A refusal is loud, appears in the log with the offending value, and denies access; the alternative was neither.

class Tom2FAEnrolmentClaims

class Tom2FAEnrolmentClaims

The claim names under which a pending 2FA enrolment travels in a token.

Deliberately a sibling of [Tom2FAClaims] rather than more entries in it: a token can be owed a second factor and be part-way through setting one up, and a single set of names could not express both at once — a forced enrolment is precisely the case where the two overlap.

The split follows [Tom2FAClaims] exactly. Everything but [offerData] is a public claim the enrolment UI reads; [offerData] is a key in the token's encrypted section, because it carries the freshly generated secret and the server must confirm the typed code against its own copy rather than against whatever came back from the client.

static String offerData

Encrypted claim: the whole offer, including the mechanism's server-only section, so any instance can confirm what another began.

static String offeredTypes

Public claim: the mechanism keys this principal was offered, in preference order.

Carried rather than recomputed because the offer is what the server permitted at the moment the login branched: a client that came back naming a mechanism must be checked against the list it was actually given, not against whatever the policy would answer on a second evaluation.

static String skippable

Public claim: true when the user may decline the offer and complete the login without a second factor. A JSON boolean, unlike the string-encoded [Tom2FAClaims.requires2FA] — the two claim families settled on different spellings, and neither is worth churning the other to match. That they disagree is exactly why both are read with [Tom2FAClaims.isTrue].

Decided once, on the pass that made the offer, and carried — so the authority for "may I skip?" is the token the server signed, never a flag the client sends back.

static String skipSpendsGrace

Public claim: true when declining the offer spends one of the principal's grace logins rather than being free. A JSON boolean, like [skippable].

Recorded on the pass that made the offer because that pass is the one that knows why skipping was allowed — an optional policy (free) or a required one with grace left (charged). Re-deriving it at skip time would ask the policy a second question whose answer had already been acted on.

class Tom2FAMethodDescriptor

class Tom2FAMethodDescriptor

How a mechanism names itself to a user who is being asked to choose one.

A mechanism key ('totp', 'sms') is an identifier: it dispatches a challenge back to the right adaptor and it is stable across releases, which is exactly why it must never be shown to anyone. A user offered a choice of second factors needs a label, an explanation and something to render — and all three are user-facing text, so under G-RES-1 they are resource keys, resolved against the caller's locale by whichever tier does the rendering.

The descriptor is therefore three keys and an identifier, and deliberately carries no literal text at all. A descriptor holding 'Authenticator app' would be a translation defect that no test could distinguish from a correct value, because it looks right in the one locale it was written in.

Why it lives in the kernel

It is produced by the server's mechanism registry but consumed by a client rendering a choice, and it travels between them inside [TomAuthenticationResult.availableTwoFactorMethods]. That makes it a wire type, and wire types live where both tiers can see them — beside [Tom2FAChallenge], which is client-visible for the same reason.

Constructors

Tom2FAMethodDescriptor.new({String type = '', String displayNameKey = '', String descriptionKey = '', String iconKey = ''})

Describes a mechanism with explicitly chosen keys.

Prefer [Tom2FAMethodDescriptor.scoped] unless the mechanism's text really does live outside the [resourceScope] convention — a deployment adapting a vendor SDK whose strings already ship under another prefix, say.

Every parameter is optional, and the fields are mutable, because this is a wire DTO: reflection constructs it empty and fills it in (G-DTO-1/2).

Tom2FAMethodDescriptor.scoped(String type)

Describes a mechanism whose text lives under two_factor.<type>.*.

Derives all three keys from [type], which is what makes the convention structural rather than a matter of per-mechanism discipline: a mechanism cannot half-follow it, and adding one cannot silently invent a fourth naming scheme.

The mechanism key this descriptor belongs to — the same value the server's registry resolves and a challenge dispatches on.

Resource key of the mechanism's short label ("Authenticator app").

Resource key of the one-sentence explanation shown beside the label.

String iconKey

Resource key of the icon to render. A key rather than an asset path because the two client tiers (Flutter, web) name their assets differently, and the mechanism must not have to know which one is asking.

class Tom2FAPendingEnrolment

class Tom2FAPendingEnrolment

A second-factor enrolment awaiting the user's next move — the exact analogue of [Tom2FAChallenge], one step earlier in the story.

Where a challenge says "prove you hold the factor you already set up", a pending enrolment says "you have none; here are the mechanisms you may set up, and here is the one you picked, half-built". Both ride in an interim token's public claims and both leave the principal unauthenticated, so the client's job is the same shape in each case: read the claims, render the mechanism's panel, post an answer.

Two states, one type

The flow has two stops and this type covers both, distinguished by [hasOffer]:

  • Choosing — [offeredTypes] is populated and [type] is empty. The client

renders a chooser (or skips straight past it when only one mechanism is on offer) and posts the chosen key back. Confirming* — [type] names the mechanism and [clientData] carries what the user needs to set it up (for TOTP: the otpauth:// URI and the base32 secret). The client renders that mechanism's enrolment panel and posts the confirmation code.

One type rather than two because a single token claim set carries whichever stop the login is at, and a client that had to pick between two readers before knowing which it held would only be re-deriving [hasOffer].

Why the client gets its own view

The server has a richer reading of the same token — it can also decrypt [Tom2FAEnrolmentClaims.offerData] and recover the secret it generated. That reading necessarily lives server-side. The client needs, and may have, only the public half; giving it a type of its own means a client tier never imports a server type to read a token it legitimately holds.

Methods

bool isExpired([DateTime? now])

Whether the offer has lapsed as of [now] (defaults to the current instant). A lapsed offer can no longer be answered; the client must restart at pass 1.

Always false while the user is still choosing — there is no generated material to go stale, so a chooser left open is a UX question, not a security one.

A begun offer with no [expiresAt] is the opposite case and answers true. [fromClaims] never builds one, so this is the backstop for a directly constructed value; it answers as the server would, because a panel that showed a live confirmation form for a state the server refuses is worse than one that says the offer lapsed.

[now] may be in either zone: isBefore compares instants, not wall clocks, so no normalisation is needed on either side.

String toString() override

Static

static Tom2FAPendingEnrolment? fromClaims(Map<String, dynamic>? payload)

Reads a pending enrolment back from a token's public [payload], or returns null when the payload carries none.

Read as defensively as [Tom2FAChallenge.fromClaims], and for the same reason: the payload came from outside the process. A token that says it has a pending enrolment but carries neither a chosen mechanism nor an offer to choose from yields null — there is nothing a client could render, and pretending otherwise would strand the login on a blank panel.

A begun enrolment whose expiry is unreadable is likewise null: the deadline is what stops a generated secret being confirmable forever, so a panel that could not tell the user when the offer lapses must not be rendered at all.

[attemptsAllowed] falls back to 0 rather than to the constructor's 3, so an offer whose budget is unreadable arrives already [isExhausted] — the same fail-closed rule [Tom2FAChallenge.fromClaims] applies, for the same reason.

class TomTotp

class TomTotp

The RFC 4226 (HOTP) / RFC 6238 (TOTP) derivation primitives, and the base32 codec authenticator secrets are exchanged in.

Pure functions of their inputs — no clock, no configuration, no state — so they say nothing about policy (how wide a skew window to accept, how many digits to demand). Policy belongs to whoever verifies; this class only answers "what is the code for this secret and this counter?".

Why this lives in the kernel

Three tiers need the same answer and must not disagree about it: the server verifying a submitted code, enrolment tooling handing a fresh secret to a user, and a client or authenticator producing the code in the first place. A second implementation anywhere would be a second opportunity to be subtly wrong — and a one-digit disagreement here reads as "the user typed it wrong", which is a miserable bug to chase. So the derivation is defined once, in the package every tier already depends on.

static int counterFor({DateTime? at, Duration period = defaultPeriod})

The RFC 6238 time-step counter for [at] (default: now) given [period].

Centralised because the counter is where the two sides of a TOTP exchange most easily drift apart: it is UTC seconds — not milliseconds, not local time — divided by the step.

Throws [ArgumentError] unless [period] is at least one second. The step is taken as period.inSeconds, which truncates, so a sub-second period is rejected as well as a zero or negative one — it is a positive duration that would still divide by zero.

static String generateCode(List<int> key, int counter, [int digits = defaultDigits])

Generates the RFC 4226 HOTP value for [counter] from the raw [key].

[key] is the decoded secret — run a base32 authenticator secret through [decodeBase32] first. The result is always [digits] characters, zero-padded on the left, because a code that lost its leading zero would not match.

static String codeFor(String secret, {DateTime? at, int digits = defaultDigits, Duration period = defaultPeriod})

The TOTP code for the base32 [secret] at [at] (default: now).

The convenience an authenticator or an enrolment self-check wants: it hides the decode-and-count step that is the usual source of a mismatch. Returns an empty string when [secret] is not decodable, so a bad secret shows up as a code that matches nothing rather than as a thrown exception in a UI.

static List<int> decodeBase32(String secret)

Decodes an RFC 4648 base32 [secret] into raw bytes.

Case-insensitive; spaces, - separators and = padding are ignored, because authenticator secrets are routinely shown to users in grouped lowercase. Returns an empty list for input containing a character outside the alphabet — an unusable secret, which the caller turns into a failed verification rather than a guess.

static String encodeBase32(List<int> bytes)

Encodes raw [bytes] as an RFC 4648 base32 secret (no padding).

The counterpart of [decodeBase32], for enrolment tooling that generates a secret and must hand the same value to an authenticator app.
