class ScopeCapture

class ScopeCapture

Captures a [TomScope] at construction time and wraps callback functions so they execute within that scope when called later.

Flutter calls builder callbacks (e.g., itemBuilder, builder) outside the original zone. This wrapper ensures Tom widgets created inside those callbacks still get the correct scope for resource resolution.

Usage in Tom widget constructors:

class TomFoo extends TomNodeBase {
  final WidgetBuilder _builder;
  TomFoo({required WidgetBuilder builder, super.scope})
      : _builder = ScopeCapture(scope: scope).wrap1(builder);
}

Why a family of fixed arities

[run] is the whole mechanism; wrap0…wrap5 and their nullable …n twins are sugar for the positional shapes that recur. The family is written out by hand because Dart has no variadic generics: no single method can accept "a function of any signature" and return one of the same signature with its static types intact. Function.apply would accept the function, but the result is untyped, and every call site would lose the compiler's checking of the callback it passed.

Anything else — a sixth argument, or named parameters like Flutter's InputCounterWidgetBuilder — is a closure of the target type around [run]: 

final capture = ScopeCapture(scope: scope);
final InputCounterWidgetBuilder counter =
    (context, {required currentLength, required maxLength,
        required isFocused}) =>
        capture.run(() => build(context, currentLength: currentLength,
            maxLength: maxLength, isFocused: isFocused));

class TomScope

abstract class TomScope

A hierarchical, zone-propagated identifier used to namespace resource lookups (e.g. app.checkout.orderForm).

Scopes form a parent chain rooted at [defaultScope]. The active scope is carried on the current [Zone], so [current] resolves to whichever scope was installed by the nearest enclosing [withScope] / [runInScope] call.

Runs [body] inside this scope's zone.

Returns the full scope path as a dot-separated string. Used as a prefix for resource lookups.

Static

static TomScope defaultScope

The root scope used when no scope is installed on the current zone.

Immutable by design: it is the root of every scope path, so reassigning it at runtime would change resource resolution for the whole process. Use [withScope] or [runInScope] instead — they install a scope on a child zone, so the change reaches that body and the callbacks it schedules, never the caller or the rest of the process.

static TomScope current
static T withScope<T>(String scope, T Function() body)

Runs [body] in a new child scope named [scope], parented to [current].

Every call builds a new scope, so a name never recognises itself: withScope('app', () => withScope('app', ...)) nests a second app and resolves to app.app. Two nested bodies that each asked for a scope named app are two namespaces, and merging them by name would hand the inner one the outer one's keys — a tree node whose key equals its parent's would share its parent's resources. The identity short-circuit belongs to [runInScope], which is given an instance it can recognise; code that may be nested inside itself should hold its scope and install it with [runInScope].

The scope rides on a child [Zone], which bounds reachability, not lifetime. The caller's own continuation after this call never sees the scope — but anything [body] schedules (a Future, Timer or stream subscription) inherits the zone and observes the scope whenever it later runs. A fire-and-forget Future started here therefore keeps this scope for its entire life, however long that outlasts [body].

Zone inheritance covers callbacks the async machinery schedules; it does not cover a closure that is merely stored here and invoked directly by someone else later, which runs in the invoker's scope. Wrap those with [ScopeCapture].

static String buildScopePath(TomScope scope)

Builds the scope path for any TomScope instance. Returns a dot-separated string (e.g., "app.checkout.orderForm").

The parent chain must be acyclic. The walk is iterative and unguarded, so a loop does not raise StackOverflowError — it spins silently, appending segments until the heap is exhausted and the isolate dies. In a server that is the whole process.

No guard is needed for scopes this module builds, because none of them can form a loop: [withScope] and the [TomScopeBase] constructor take a parent that already exists, and [TomScopeMixin.initScope] refuses one that is not yet initialised and then writes the link once. Every parent is therefore strictly older than its child, and a chain that only ever moves backwards in time cannot return to where it started.

The requirement binds anything that implements [TomScope] by hand: such a type supplies its own [parent], outside that argument and outside any check this module can make.

The path is rebuilt on every call; nothing is cached. The walk is linear in the depth and costs a fraction of a microsecond at the depths scopes reach in practice — more than the map lookup a caller then does with the result, but small beside anything a lookup is done for. Rebuilding is also what keeps the answer right for every [TomScope]: a scope that mixes in [TomScopeMixin] has a write-once identity, but this method accepts any implementation, including one whose [id] or [parent] is computed, and a cached path would outlive a change to either.

void initScope({required String scopeId, TomScope? parentScope})

Initialises this scope's identity.

The single write-once entry point: call it exactly once, from the constructor or — for a scope whose parent is only known later — on the constructed instance. [TomScopeBase] and [TomScope.withScope] both route here, so the checks below hold for every scope the module builds.

[scopeId] must be non-empty and must not contain ., because ids are joined with . to form the scope path. Both are refused with a [TomScopeException]: an id that carries the separator forges a segment boundary, so the scope renders as a path belonging to a different, deeper chain — and the path is what resource and authorization lookups are keyed on. Ids written as literals in source can never trip this; ids derived from data are exactly what the check is for.

[parentScope] must already have an identity of its own. Checking it here rather than when the path is built is what keeps the check O(1): an initialised scope then has a fully initialised chain by induction, since the identity is write-once and a parent cannot lose one later.

The same rule is also what keeps the chain acyclic, which [TomScope.buildScopePath] relies on and does not verify. Requiring the parent to be initialised already makes it strictly older than its child, and writing the link once means it stays that way — so following parents always moves backwards in time and can never arrive back at where it started. Closing a loop would need this call to accept a scope that is not yet initialised, or to run a second time on a scope that already is; neither is allowed.

A second call is refused with scope_ids.init_scope.already_initialised, naming the class, the id the scope already has and the one the call tried to give it — even when the two agree, since a scope whose identity two callers both write has two owners. An unusable [scopeId] is reported first: it is the mistake that survives fixing the double call.

function _requireScopeIdentity

void _requireScopeIdentity(TomScope? scope, String attemptedAction)

Refuses a [TomScopeMixin] instance whose [TomScopeMixin.initScope] has never run, naming the class and the missing call.

[attemptedAction] opens the message, so the reader learns what was refused before why. Anything that is not an uninitialised mixin passes: a hand-rolled implements TomScope has no initialisation window this module knows about.

Without this, a half-built instance installs silently and the failure surfaces at whichever later call first asks for a path — a resource lookup or an authorization check, on a stack that mentions neither scopes nor the constructor that skipped [TomScopeMixin.initScope].

function _requireUsableScopeId

void _requireUsableScopeId(String scopeId)

Refuses a scope id that cannot survive being joined into a path.

The path is this module's entire output — a prefix for resource and authorization lookups — and it is built by joining ids with [_scopePathSeparator]. An id containing the separator therefore forges a segment boundary: 'a.b' under no parent renders exactly as the unrelated chain 'a' → 'b', so a scope named from data (a tenant, a row key, a user-supplied label) can name another scope's resources. An empty id is the same defect seen from the other end — it renders as a bare '' at the root, which consumers are told to read as "no scope at all", or as a doubled separator further down.

Checked once per scope, at the only place an id is ever accepted, rather than on every path build.

function _runScoped

T _runScoped<T>(TomScope scope, T Function() body)

Shared scope-installation policy for [TomScope.withScope], [TomScope.runInScope] and [TomScopeMixin.runInScope].

Every install goes through here, which is what makes the identity check below a property of the module rather than of one call site.

If [scope] is already the current zone scope (identical reference), [body] runs directly without creating a new zone — this prevents duplicate scope nesting. Otherwise [body] runs in a child zone carrying [scope]. [TomScope.withScope] never takes the first branch: the scope it passes is one it has just built, so it nests on every call.
