class TomTimezone

Represents a timezone with its name and location data.

[TomTimezone] provides a unified interface for working with timezones across the Tom framework. It wraps the timezone package's functionality and provides:

  • Timezone lookup: Find timezones by name or UTC offset
  • Offset calculation: Get UTC offset for any timezone at any point in time
  • DateTime conversion: Convert between timezones and to/from TZDateTime
  • DST awareness: Automatically handles daylight saving time transitions

Initialization

On native (Flutter / VM) platforms the timezone database is loaded synchronously on first access from the embedded IANA data, so no manual initialization is required.

On the web the database must be fetched over the network and therefore cannot be loaded synchronously: applications must call (and await) tomSetupTimezones() during startup before any timezone access. If the database is still empty on first access, lookups throw a [StateError] naming the missing call rather than returning empty results. It is an [Error] and not a [TomTimezoneException] on purpose — see that class for where the line falls.

Common Usage

// Get a timezone by name
final tokyo = TomTimezone.fromName('Asia/Tokyo');
print(tokyo?.timezone); // 'Asia/Tokyo'
print(tokyo?.timezoneOffsetMin); // 540 (UTC+9)

// Get the UTC timezone
final utc = TomTimezone.utc;

// Get current time in a timezone
final now = tokyo!.now();

// Convert DateTime to TZDateTime
final tzDt = tokyo.toTZDateTime(DateTime.now());

Finding Timezones

// By name (case-insensitive)
final tz = TomTimezone.fromName('America/New_York');

// By UTC offset (returns first matching timezone)
final tz2 = TomTimezone.firstWithOffset(540); // UTC+9

// All timezones with a specific offset
final tzList = TomTimezone.allWithOffset(0); // All UTC+0 timezones

factory TomTimezone.fixedOffset({required String name, required int utcOffsetMinutes})

A zone named [name] that sits at [utcOffsetMinutes] at every instant.

For a zone the IANA database of this runtime does not hold. A serialized value carries an offset beside its zone name, and that is what a parse falls back to when the name resolves to nothing — the value keeps the name it was stored under and is read at the offset it was stored with, rather than being refused because this host's database is older or smaller than the one that wrote it. See the module guide's "Serialization Format".

It observes no daylight saving and has no transitions, so [getUtcOffsetOn] answers [utcOffsetMinutes] for every instant, past or future. That is the honest reading of what the string says: one offset, with nothing to say when it might have been different.

It does not join the database. [fromName] does not resolve it, [timezones] does not hold it, and the offset lookups do not find it — a value that arrives over the wire must not be able to write to the index every other lookup in the process reads.

[utcOffsetMinutes] outside ±840 minutes (±14:00) throws [TomFormattingException], the bound the rest of the module keeps.

Example:

final zone = TomTimezone.fixedOffset(
  name: 'Mars/Olympus',
  utcOffsetMinutes: 330,
);
print(zone.toString()); // +05:30_Mars/Olympus

Properties

final String timezone

The IANA timezone name (e.g., 'America/New_York', 'Europe/London').

final Location location

The underlying timezone location from the timezone package.

Provides access to low-level timezone operations and data.

This is the shared object the database holds, not a copy: every lookup of a zone hands out the same instance, which is what makes identical comparisons between zones meaningful. It also means its contents are the database's — the package's Location exposes its transition and zone lists as plain mutable lists, so emptying or sorting one rewrites what that zone's offsets are for the rest of the process. The lookups this class owns hand out unmodifiable views for that reason; this one cannot, because the type belongs to the timezone package. Read it, and leave its lists alone.

Methods

String toString() override

Returns a string representation of this timezone.

Format: {offset}_{timezone}, where offset is Z for UTC or +HH:MM/-HH:MM for other timezones.

The offset is the zone's offset now. A zoned value does not render its zone through this method but through [toStringOn] at its own instant, because the offset belongs to the value: a January Berlin value written in July still reads +01:00.

Example:

print(TomTimezone.utc.toString()); // 'Z_UTC'
print(TomTimezone.fromName('Asia/Tokyo')!.toString()); // '+09:00_Asia/Tokyo'
String toStringOn(DateTime when)

Returns a string representation of this timezone at a specific date/time.

Format: {offset}_{timezone}, as [toString], with the offset calculated for the given date and accounting for DST transitions.

Every zoned value renders its zone through this method, at its own instant, so whatever this returns is the tail of every serialized string the module produces — which is why it ends where the zone name ends. A trailing character nobody asked for is carried into every stored value, every map key and every URL built from one, and is invisible in each of them.

[when] The DateTime to calculate the offset for.

Example:

final newYork = TomTimezone.fromName('America/New_York')!;

// Winter (EST: UTC-5)
print(newYork.toStringOn(DateTime.utc(2024, 1, 15))); // '-05:00_America/New_York'

// Summer (EDT: UTC-4)
print(newYork.toStringOn(DateTime.utc(2024, 7, 15))); // '-04:00_America/New_York'
int getUtcOffsetOn(DateTime dt)

Returns the UTC offset in minutes for this timezone at a specific date/time.

This is useful for determining the offset at a historical or future date, accounting for daylight saving time transitions.

[dt] The DateTime to get the offset for.

Example:

final newYork = TomTimezone.fromName('America/New_York')!;

// Winter (EST): -300 minutes (-5 hours)
final winter = newYork.getUtcOffsetOn(DateTime.utc(2024, 1, 15));

// Summer (EDT): -240 minutes (-4 hours)
final summer = newYork.getUtcOffsetOn(DateTime.utc(2024, 7, 15));

DateTime changeToThisLocation(DateTime dt, TomTimezone inTimezone)

Reads [dt] as a wall-clock reading in [inTimezone] and re-renders it in this timezone.

The instance form of [changeLocation], with this timezone as the target. See there for the full semantics — in particular that only the calendar fields of [dt] are read, never the instant it denotes.

[dt] The wall-clock reading to convert. [inTimezone] The timezone the reading is expressed in.

Example:

final tokyo = TomTimezone.fromName('Asia/Tokyo')!;
final newYork = TomTimezone.fromName('America/New_York')!;

// Noon on a Tokyo clock.
final tokyoNoon = DateTime.utc(2024, 6, 15, 12, 0);
final nyTime = newYork.changeToThisLocation(tokyoNoon, tokyo);
print('${nyTime.day} ${nyTime.hour}'); // 14 23 (11 PM the previous day)

static void _initialize()

Lazily initializes the timezone database synchronously on first access.

If the database has already been loaded (e.g. the application called [tomSetupTimezones] during startup, which is mandatory on web), the existing data is used. Otherwise the embedded database is loaded synchronously via [tomSetupTimezonesSync]. On web there is no synchronous load path, so [tomSetupTimezonesSync] throws a [StateError] naming the missing startup call instead of silently returning empty results.

static void _populateTimezonesMap()
static void populateFromLocations(Map<String, Location> locations)

Fills the lookup caches from [locations] and registers the [utc] singleton, which the IANA database does not supply under that name.

Takes the location map rather than reading tz.timeZoneDatabase directly so that a test can drive the failure branch below. On a native platform the embedded database always loads, so "it did not load" is the one state that cannot be provoked through the public entry points — and it is precisely the state whose handling must not go untested.

Populates once per isolate. A second call is refused with timezone.database.already_populated rather than replacing the database or being ignored. Replacing it would detach every [TomTimezone] a caller already holds from the index those instances are compared and looked up through; ignoring it would mark the module initialized against a database nobody asked it to keep, which is the case that matters on web, where a partial database can arrive before the full one. Refusing puts the choice where it belongs: populate once, before the first lookup, and sequence a tomSetupTimezones() that must win ahead of any access.

static TomTimezone? firstWithOffset(int utcOffsetMinutes)

Returns the first timezone whose offset right now is [utcOffsetMinutes].

The match is against the current offset, so the answer has a shelf life. A zone that observes daylight saving is in one bucket in winter and a different one in summer — roughly a third of the IANA database moves this way — and the index is built once at first access and never rebuilt, so a process that runs across a transition keeps answering for the season it started in. Use offset lookup for discovery ("who is at +05:30 at the moment", a zone picker) and store the [timezone] name it yields, never the offset it was found under. For the offset a zone had at a particular instant, ask the zone with [getUtcOffsetOn].

First means first in the bucket, which is IANA name order rather than the best-known zone at that offset: firstWithOffset(0) yields Africa/Abidjan, not UTC. Where a particular zone is wanted, name it with [fromName]. For the zones at an offset at a particular instant, which does not go stale, use [firstWithOffsetOn] and [allWithOffsetOn].

[utcOffsetMinutes] The UTC offset in minutes (e.g., 540 for UTC+9).

Returns null if no timezone is at that offset now.

Example:

final tz = TomTimezone.firstWithOffset(540); // UTC+9
print(tz?.timezone); // Some zone currently at +09:00
static List<TomTimezone>? allWithOffset(int utcOffsetMinutes)

Returns every timezone whose offset right now is [utcOffsetMinutes].

The same shelf life as [firstWithOffset], and for the same reason: the bucket holds the zones that were at this offset when the index was built, not the zones that are ever at it. allWithOffset(0) in July does not contain Europe/London, which is on BST and sits at 60; in January it does. Treat the result as a snapshot, not as a membership rule, or ask [allWithOffsetOn] for the zones at an offset at a given instant.

The list is unmodifiable, and for the same reason [timezones] is: it is a view onto the bucket [firstWithOffset] reads, so sorting or filtering it in place would not shape a local result, it would rewrite the index for the rest of the process. Neither operation reads as dangerous, which is why the refusal is at the call rather than in a comment. Take a copy to work with: [...?TomTimezone.allWithOffset(0)].

[utcOffsetMinutes] The UTC offset in minutes.

Returns null if no timezone is at that offset now.

Example:

final tzList = TomTimezone.allWithOffset(0); // Zones at +00:00 today
for (final tz in tzList ?? <TomTimezone>[]) {
  print(tz.timezone); // 'UTC', 'Africa/Abidjan', 'Etc/GMT', ...
}
static List<TomTimezone> allWithOffsetOn(int utcOffsetMinutes, DateTime when)

Every timezone whose offset at [when] is [utcOffsetMinutes].

The at-instant counterpart of [allWithOffset], and the one to reach for when the question is about a moment rather than about today. It asks each zone what its offset was at [when] instead of reading the offset index, so a daylight-saving boundary is a fact about [when] and the answer does not change as the process runs: allWithOffsetOn(0, january) holds Europe/London in any season, and allWithOffsetOn(0, july) does not.

The price is the scan: O(zones) per call against a database of a few hundred, where [allWithOffset] is a map hit. That is the trade — a correct answer for an instant, or a fast answer for the season the process started in.

Zones come in the database's own order, as they do from [allWithOffset], and the list is unmodifiable for the same reason every other lookup's is. An offset no zone was at answers with an empty list rather than null: the scan always has an answer, and "none" is one.

Example:

final winter = DateTime.utc(2024, 1, 15);
for (final zone in TomTimezone.allWithOffsetOn(0, winter)) {
  print(zone.timezone); // 'UTC', 'Europe/London', 'Africa/Abidjan', ...
}
static TomTimezone? firstWithOffsetOn(int utcOffsetMinutes, DateTime when)

The first timezone whose offset at [when] is [utcOffsetMinutes], or null when no zone was at it then.

[firstWithOffset] with an instant, and [allWithOffsetOn]'s first element — first meaning first in the database's order rather than the best-known zone at that offset, so name a particular zone with [fromName] where one is wanted. The scan stops at the first match.

Example:

final summer = DateTime.utc(2024, 7, 15);
TomTimezone.firstWithOffsetOn(60, summer)?.timezone; // a zone at +01:00 then
static Iterable<TomTimezone> _zonesWithOffsetOn(int utcOffsetMinutes, DateTime when)

The zones at [utcOffsetMinutes] on [when], computed rather than indexed.

Lazy, so [firstWithOffsetOn] pays for one match and [allWithOffsetOn] for the whole database, from one definition of what "at this offset then" means.

static TomTimezone findTimezone(String? name, int? utcOffsetMinutes, {DateTime? at})

Finds a timezone by name, optionally validating its UTC offset.

This is the strict lookup: where [fromName] answers "is this zone here?" with a zone or null, this one treats every lookup it cannot satisfy as an error, so it never returns null and a caller writes one handler.

[name] The timezone name (optional). [utcOffsetMinutes] The expected UTC offset in minutes (optional).

Returns: - The named zone, when it exists and — if an offset was given — its current offset is that offset - The first zone at [utcOffsetMinutes] if [name] is null. This branch reads the same offset index as [firstWithOffset] and inherits its shelf life

Throws [TomTimezoneException] in four cases, one key each, so a caller branches on the key rather than on the message: - timezone.lookup.name_not_found — [name] is not in the database. This happens whether or not an offset was supplied, so a name-only lookup throws too — unlike [fromName], which returns null for the same name. Parameters: name, and utcOffsetMinutes when one was given. - timezone.lookup.offset_mismatch — [name] is in the database but sits elsewhere. Parameters: name, utcOffsetMinutes as asked for, actualUtcOffsetMinutes as found, and at when one was given. - timezone.lookup.offset_not_found — [name] is null and no zone is at [utcOffsetMinutes]. Parameters: utcOffsetMinutes, and at when given. - timezone.lookup.no_criteria — both arguments are null, leaving nothing to look up.

[at] decides when the offset is read. Left out, every offset in the call is the zone's offset now, so a zone that observes daylight saving matches a different value in summer than in winter, and the name-less branch reads the offset index with the shelf life [firstWithOffset] describes. Supplied, both are computed for that instant instead — the name branch compares against [getUtcOffsetOn], the name-less branch scans as [firstWithOffsetOn] does — so the answer is the same whenever it is asked.

Example:

// Valid: UTC has offset 0
final tz = TomTimezone.findTimezone('UTC', 0);

// Throws: UTC doesn't have offset 60
TomTimezone.findTimezone('UTC', 60); // TomTimezoneException

// Throws: no such zone, even with no offset to disagree with
TomTimezone.findTimezone('Mars/Olympus', null); // TomTimezoneException

// Throws: no zone is at +00:07
TomTimezone.findTimezone(null, 7); // TomTimezoneException

// Throws: both arguments null, nothing to look up
TomTimezone.findTimezone(null, null); // TomTimezoneException

// -05:00 is New York in winter, so this agrees in January
TomTimezone.findTimezone('America/New_York', -300, at: winter);
static String convertMinutesToUtcOffset(int totalMinutes)

Converts a UTC offset in minutes to a formatted string.

[totalMinutes] The UTC offset in minutes (positive = east of UTC).

Returns: - 'Z' for offset of 0 - '+HH:MM' for positive offsets - '-HH:MM' for negative offsets

Example:

print(TomTimezone.convertMinutesToUtcOffset(0));    // 'Z'
print(TomTimezone.convertMinutesToUtcOffset(540));  // '+09:00'
print(TomTimezone.convertMinutesToUtcOffset(-300)); // '-05:00'
print(TomTimezone.convertMinutesToUtcOffset(330));  // '+05:30'

Throws TomFormattingException when [totalMinutes] lies outside ±840 (±14:00), which no real zone does — see the top-level function. An offset obtained from this class is always inside that range, so [getUtcOffsetStringOn], [toStringOn] and [toString] cannot throw; only this static entry point, which takes an arbitrary int, can.

Delegates to the top-level [formatting.convertMinutesToUtcOffset] so the two entry points cannot drift apart; this one exists because offsets are most often formatted from a timezone.

static DateTime changeLocation(DateTime dt, TomTimezone inTimezone, TomTimezone toTimezone)

Reads [dt] as a wall-clock reading in [inTimezone] and re-renders it in [toTimezone].

This is a reinterpretation, not a rendering: only the calendar fields of [dt] are read — year, month, day, hour, minute, second and the sub-second parts. Whatever instant [dt] itself denotes, and whether it was built with DateTime() or DateTime.utc(), is ignored. Those fields are resolved to an instant in [inTimezone], and that instant is then rendered in [toTimezone].

Two consequences worth knowing:

  • The result never depends on the host machine's timezone, so the same

call answers the same everywhere. DateTime(2024, 6, 15, 12) and DateTime.utc(2024, 6, 15, 12) are the same reading and convert alike. - To re-render an instant you already hold — the other, equally common operation — use [toTZDateTime] instead, which preserves the moment.

A reading that no clock in [inTimezone] ever showed (the spring-forward gap) or that it showed twice (the autumn fall-back) still resolves to exactly one instant. Which one is package:timezone's choice, not a policy stated here: both cases fall out of its guess-and-correct Location.translateToUtc, and for Europe/Berlin in 2024 both land on standard time. It is deterministic, so it is safe to rely on — but pin it with a test if a caller depends on the exact side.

[dt] The wall-clock reading to convert. [inTimezone] The timezone the reading is expressed in. [toTimezone] The timezone to render the resulting instant in.

Example:

final utc = TomTimezone.utc;
final tokyo = TomTimezone.fromName('Asia/Tokyo')!;

final utcMidnight = DateTime.utc(2024, 6, 15, 0, 0);
final tokyoTime = TomTimezone.changeLocation(utcMidnight, utc, tokyo);
print(tokyoTime.hour); // 9 (9 AM in Tokyo)

// The source zone is what makes the answer differ: the same reading,
// taken as a Tokyo clock rather than a UTC one, is already 9 AM there.
print(TomTimezone.changeLocation(utcMidnight, tokyo, tokyo).hour); // 0

class TomTimezoneException

class TomTimezoneException extends TomException

The module's exception, raised where a request about a zone cannot be satisfied: by the strict lookup [TomTimezone.findTimezone], and by [TomTimezone.populateFromLocations] on a second population.

Extends [TomException], so every failure carries a key and the values involved and is caught, reported and translated like any other in the framework. One key per failure, so a caller branches on the key rather than on a message:

  • timezone.lookup.name_not_found — no zone carries the name given.
  • timezone.lookup.offset_mismatch — the named zone is at a different

offset from the one supplied beside it. - timezone.lookup.offset_not_found — no zone is at the offset given. - timezone.lookup.no_criteria — neither a name nor an offset was given. - timezone.database.already_populated — the database already holds one.

What raises something else, and why

The module refuses in four shapes, and which one a caller meets follows the entry point rather than the mistake — "a zone that is not in the database" reaches three of them.

A parse failure is a [FormatException]: the parseFromString of each variant throws it for a string that does not match the serialized form. The lenient lookup [TomTimezone.fromName] raises nothing at all and returns null.

The fourth is a [StateError], and it is the one failure here deliberately left outside this class: asking for a synchronous load of the database on a platform that has none — the browser, before tomSetupTimezones() has been awaited. Everything above answers a question about a value the caller passed, and a caller can catch it, report it and carry on with the rest of its work. That one says the module is not usable yet; every later access fails the same way and no handler repairs it, which is a fault in the application's startup and so an [Error]. See refuseSynchronousTimezoneLoad in sync_load_refusal.dart.

Example:

try {
  TomTimezone.findTimezone('UTC', 60); // UTC should have offset 0, not 60
} on TomTimezoneException catch (e) {
  print('Error: ${e.key}'); // timezone.lookup.offset_mismatch
}
