The value codec both halves of the preference contract use.

A preference is a typed value that has to survive a JSON column, so something has to decide how an int, a DateTime and a reflected object each become text and come back. That decision belongs to neither half alone: the server writes with it and a client reads with it, and two encoders that disagree by one convention (a local DateTime, an enum written as its index) produce a preference that is stored successfully and read wrongly.

So it lives here, once, next to the DTO it fills.

What it will not do

It refuses a read whose stored [TomUserPreferenceDto.valueType] does not match the type the caller asked for, rather than coercing. A preference that was written as a Duration and is read as an int is a bug in the caller — answering 3 (whatever that would mean) hides it, and the value the caller then acts on is not the one the user chose.

That is a property of the codec, not of the calling convention. [TomUserPreferenceCodec.decode] takes the whole [TomUserPreferenceDto] because the check needs the stored type name alongside the text, and there is deliberately no public sibling that takes the text alone: a guarantee with an unguarded way around it holds only for the callers who happen to pick the guarded method.

class TomUserPreferenceCodec

Encodes and decodes preference values against [TomUserPreferenceDto].

What a preference value may be

Four shapes, and nothing else:

ShapeStored asNamed by
String, int, double, bool plain JSON itself
DateTimean ISO 8601 instant in UTCDateTime
a List/Map<String,…> of one scalar array or object List<int>
a @tomReflector enum {"name": "<constant>"} the registry
a @tomReflector class a JSON object of members the registry

A value of any other shape is refused when it is named, by [typeNameOf]. That includes a collection that is not one of the ten supported ones — an untyped [], a mixed List<Object>, a Map keyed by anything but String, a nested collection, a list of reflected objects: those raise preferences.type.unsupported_collection, whose message names the actual restriction rather than advising an annotation a List<Object> cannot carry. Wrap such a value in a reflected class, whose members can then evolve under a name that survives.

Why collections are a shape of their own rather than something to wrap. The element type is in the stored name, so it survives the round-trip on the same terms a scalar does — the name is composed from this class's own constants, not from Type.toString(), which [typeNameForType] explains is not durable enough to store. And because the name carries the element type, [validateEncoded] can check every element of a stored row without reflecting anything: a collection is the one non-scalar shape the boundary verifies completely, which a reflected class is not.

The two reflected shapes share one rule — the value's class must carry @tomReflector — so there is no separate thing to know about enums. What the annotation buys is the same in both cases: a name that is a literal the generator emitted rather than one the compiler is free to rewrite, and, for an enum, the constants to match a stored name against on the way back.

Scalars are written as plain JSON; a reflected object goes through the same reflection path the endpoint pipeline uses for every other DTO ([TomReflectionInfo.convertToJsonString] / [TomReflectionInfo.createInstanceFromJson]), so a preference object is serialized exactly as it would be if it were an endpoint result.

static int maxValueBytes

The longest a preference's encoded value may be, in UTF-8 bytes of its JSON text: 16 KiB.

A preference is a setting, not a document. The ceiling is what lets that sentence be enforced rather than hoped for: together with [tomUserPreferencesMaxPerPrincipal] it bounds everything a principal can store, and so bounds the one answer that returns all of it — [TomUserPreferencesApiService.listPreferences]. 16 KiB is generous for a setting, including a reflected settings object with dozens of members, and small enough that a caller reaching it has put data in a preference that belongs in a table of its own.

Bytes rather than characters because the server stores the text in a byte-sized column: a character count would admit a value the column cannot hold. Enforced on both paths — [encodeValue] (so [encode] too) refuses with preferences.encode.too_large, and [validateEncoded], the server's check on a body that did not come from this codec, with preferences.encoded.too_large — so a value one store would take is a value every store takes, and a preference can move between them.

static List<_ScalarKind> _scalars

The five scalar shapes, in the order [typeNameOf] tests a value against them.

The order is load-bearing, and int before double is the reason. On the web both are JS numbers and an integral double answers to is int, so the first row that matches decides the stored name; swapping the two would change what a whole platform writes. On the VM the types are disjoint and the order is free — which is exactly why it needs saying here, where the order is set, rather than being discovered by a reader who reshuffles the rows and sees every test still pass.

Only the value tests are ordered. [_identityOf] matches a row by its [_ScalarKind.dartType], and Type equality is exact, so no row can shadow another there.

static final rather than const, because a function literal is not a constant expression. That is the same trade [_collectionTypes] makes: a table that holds what the code does cannot drift from the code that does it, which is worth more than a constness nothing here asks for.

Every question either side of the column asks about a scalar is answered from these rows — the Dart type, the stored name, the write-side and read-side shape tests, the narrowing back to a Dart value, and the two typed collection constructors. A sixth scalar is one row, which is the property this table exists for: the alternative had the write side reading the table while the read side re-listed the same five names in three switches, none of which failed to compile when a row was added — so a forgotten edit was a preference that stored and then could not be read.

static List<String> scalarTypes

The scalar type names, in the order [typeNameOf] tests them.

A view of [_scalars] rather than a list of its own. The ordering above is therefore not a claim about this list that someone has to keep true; it is the only order there is, and [typeNameOf] and [validateEncoded] read the same rows this is projected from.

static String enumNameField

The JSON member an enum value is stored in: its constant name.

The name and not the index, which is the convention this module's own dartdoc names as worth settling centrally. An index is positional, so inserting a constant into the enum silently changes the meaning of every preference already stored — the user's saved choice becomes its neighbour's, on the next release, with nothing to notice it by. The name moves only when the constant is renamed, and a renamed constant is refused loudly rather than misread (see [decode]).

static String typeNameOf(Object value, [String key = ''])

The [TomUserPreferenceDto.valueType] that [value] is stored under.

A scalar's own type name, a supported collection's composed name, or — for anything else — the name the reflection registry holds for the value's class.

Those three are consulted in that order, and only one of the two precedences decides an answer. The scalar table comes before the registry to keep a scalar's stored name in the same row as the predicates that produce and check it — not to change what it is named, because the registry knows all five core scalars and returns the same strings. Which is why no behavioural test can catch that half of the ordering, and why the agreement itself is asserted instead. The precedence that does decide an answer is collections before the registry, two paragraphs down.

Throws preferences.type.not_reflected when the registry does not know the class. That is the point rather than a limitation: the name written here is read back by another release on another platform, and a name the registry cannot produce is one no reader can ask for. See [typeNameForType] for why the registry is the identity.

A collection that is not one of the ten supported shapes throws preferences.type.unsupported_collection here, before reflection is asked about it. Reflection would answer for some of them — the registry knows List — and the value would then be stored under that name and silently encoded as {}, every element dropped. Refusing at the name is what turns that into an error the writer can read.

This is a question about the value, so the answer is its runtime class — which is not always the type a caller would write down for it. See [typeNameForType] for the two shapes where the two methods part company.

[key] only names the preference in that exception, and is optional because a caller may ask for a value's stored name before it has decided where to put it.

static TomUserPreferenceDto encode(String key, Object value, {DateTime? updatedAt})

Encodes [value] into the DTO stored under [key].

[updatedAt] is the server's write timestamp; a client building a write request leaves it null, because when a preference was written is the server's answer.

Throws a [TomUserPreferenceKeyException] when [key] does not satisfy [TomUserPreferenceKeys]. This is the write path's first gate: a DTO is the addressed artifact, so a key that cannot be addressed must not reach one — the alternative is a value that encodes successfully and is then unstorable. Unlike [typeNameOf] and [encodeValue], whose key is optional and only names the preference in an exception, the key here is the preference's identity.

static String encodeValue(Object value, [String key = ''])

Encodes [value] to its JSON text, without the surrounding DTO.

[key] names the preference being written, and appears in the exception when the value cannot be encoded. It is optional because a caller may encode a value before it has decided where to put it.

Every failure leaves here as a [TomUserPreferenceCodecException], which is the only exception the rest of the module tells callers to catch. That includes the scalar path: jsonEncode refuses a non-finite double, and double.nan is an ordinary outcome for a computed preference whose divisor turned out to be zero, not a programming error worth a different exception type.

An enum is written as {"name": "<constant>"} — see [enumNameField] for why the name and not the index, and the class dartdoc for why an object and not a bare string.

This writes the text; it does not ask what the value is stored under. So an unreflected object reaches preferences.encode.failed here, while the same object given to [encode] is refused one step earlier, by [typeNameOf], as preferences.type.not_reflected — a value with no durable name has nothing to be written under, whatever its text. An unreflected enum takes that same split: its text is writable here, since a constant name needs no registry, and it is [encode] that refuses it for having no name to be stored under. A mixed List<Object> takes it too — ["a",1] is perfectly good JSON, so it is written here and refused by [typeNameOf] for naming no supported shape.

A refusal names the cause it detected rather than a single generic one, and carries it as a cause parameter for a caller that has to branch:

causeThe valueThe remedy
value_not_jsona non-finite numberstore a finite one
element_not_json a collection holding one the same, one level on
map_key_not_string a Map<int, …> key it by String
element_not_scalar a List<Thing> wrap the whole collection
not_a_list_or_map a Set, a lazy Iterable toList() it
unreflected_classan unannotated classannotate it

Only the last is fixed by the annotation, which is why they are told apart: a Set and a Map<int, …> have no class of their own to annotate, and a List<Thing> stays an unsupported shape however well Thing is annotated, because the element type is part of the stored name. A non-finite element keeps the preferences.encode.not_json key its top-level twin has — [1.0, double.nan] is a well-formed List<double> that [typeNameOf] names, so the defect is the number, not the shape.

A text longer than [maxValueBytes] is refused as preferences.encode.too_large, whatever produced it.

static TomUserPreferenceCodecException _notEncodable(Object value, String key, Object error, StackTrace stack)

The refusal for a value whose JSON text could not be written.

The cause is worked out from the value, not from [error]. Both jsonEncode and the reflection registry report the same thing — "could not convert" — which is the one fact the caller already has. Five situations arrive here and they have five different remedies, and for four of them a @tomReflector annotation is not something the caller could add: a Set and a Map<int, …> have no class of their own to annotate, a List<Thing> stays an unsupported shape however well Thing is annotated, and a non-finite number is not a shape problem at all.

Each refusal therefore names its own remedy, and carries a cause parameter — element_not_json, map_key_not_string, element_not_scalar, not_a_list_or_map, unreflected_class — so a caller that has to branch is not left parsing the prose. The top-level non-finite case, which has its own throw site, reports value_not_json.

A non-finite element keeps preferences.encode.not_json rather than taking a shape key: [1.0, double.nan] is a perfectly well-formed List<double>, [typeNameOf] names it, and the defect is the same one a bare double.nan has. The same defect gets the same key.

static void validateEncoded(String valueType, String valueJson, {String key = ''})

Checks that [valueJson] is JSON and is shaped like a [valueType].

For the boundary: a write request arrives with the value already encoded, so nothing on the way in has proved that the declared type and the text agree. Storing a disagreeing pair costs nothing now and fails every future read of that key — including reads on other devices, which is where it would be found.

A reflected [valueType] is only required to be a JSON object. Which class it names is deliberately not checked: a preference type may be one only the client knows, and a server that insisted on reflecting it would refuse to store values it is not meant to interpret.

A collection is the exception, and gets a complete check — every element against the element type, and every instant against the zone rule. Not a stricter policy, the same one: the element type is part of the stored name, so verifying it asks the server nothing it does not already have. This is what a class name cannot offer, and the reason collections are a first-class shape rather than something to wrap.

That is also why an enum is stored as an object: this check sees a type name and cannot tell an enum from a class without reflecting it, so giving enums a shape of their own would mean either weakening the rule for every class or asking the server the question it must not ask.

A text longer than [maxValueBytes] is refused first, as preferences.encoded.too_large: it is the cheaper question, and a body that is going to be refused anyway should not be parsed.

[key] only names the preference in an error.

static T decode<T extends Object>(TomUserPreferenceDto dto)

Decodes [dto] as a [T] — the only way in to a stored preference value.

Throws a [TomUserPreferenceCodecException] when the stored [TomUserPreferenceDto.valueType] is not the one [T] is stored under — the mismatch is reported rather than coerced, because a preference read as the wrong type is a value the caller will act on believing it is the user's. The whole DTO is required rather than just its text because that check needs the stored type name; a caller holding only the text should say what it believes the text to be, by building the DTO, rather than be given a way to skip saying it.

A DateTime comes back in UTC, and only if the stored text names its own zone — see [parseInstant] for why a zoneless one is refused rather than localised. An int widens to a double when [T] asks for one.

A collection comes back as the exact List<E> or Map<String, E> it was stored as, not as a List<dynamic> the caller has to cast: the element type is in the stored name, so the read knows it. Every element obeys the rule its own type obeys one level up — the zone check and the widening included — so a List<double> reads a JSON [1, 2] back as [1.0, 2.0], and a list holding one zoneless timestamp is refused whole.

A reflected [T] is rebuilt member by member. A JSON member the class does not declare is ignored, and a member the class declares but the payload omits keeps its declared default. The valueType comparison is what makes that safe: a caller asking for the wrong class is refused before a single member is assigned.

An enum [T] is matched against the constants it declares now, and a stored name that is not among them raises preferences.decode.unknown_enum_constant rather than defaulting. The tolerance the class path allows is deliberately absent here: an omitted member falls back to the value the class itself declares, whereas an unmatched constant has no such answer — only the user's actual choice would do, and that is precisely what has been lost.

What no read can catch is a stored row whose valueType and text disagree, because a JSON object is shaped like every reflected class at once and nothing in the payload says which one wrote it. Such a row decodes to a fully-defaulted instance. [validateEncoded] does not close that gap either, and says why it does not try.

static String typeNameForType(Type type, [String key = ''])

The [TomUserPreferenceDto.valueType] a value of type [type] is stored under.

A scalar is named by itself; anything else is named by the reflection registry, and throws preferences.type.not_reflected if the registry does not know it. [key] only names the preference in that exception.

Why the registry and not the type. Type.toString() is the compiler's rendering, and this name is written into a database column, sent across the wire and read back by another release on another platform. That rendering is not durable enough for the job: it is not preserved by web minification, it carries the generic instantiation (so one class reached from two call sites can produce two names), and for an SDK type it can be a private name — a Uri renders as _SimpleUri, which no caller can write and therefore no caller can read back. The registry name is a literal the generator emits, so it survives all three.

A collection is named by neither route: its name is composed from this class's own constants (List<String>), which has the same property for the same reason — nothing in it is a compiler rendering. That is why a Map<String, int> is storable although a map literal's runtime class is the private _Map.

It is the same registry [decode] resolves its type argument through, which is what makes the two halves symmetric: a value can be written under a name exactly when it can be read back under it.

Where this and [typeNameOf] diverge. They answer different questions — [typeNameOf] names the class a value turned out to have, this names the class a type denotes. For a value stored under the class it is declared as those are the same string, which is what makes the two cases below easy to miss:

  • A subclass value is named by its own class rather than by the

supertype the caller declared, so a row written from a Sub is refused by decode<Base> as preferences.decode.type_mismatch. That is the intended strictness rather than a gap: reading it as the supertype would silently drop the members only the subclass declares. Store a preference under the class it is declared as. An instantiated generic* Type has no entry of its own, because the registry is keyed by declaration: it holds BoxPreference and not BoxPreference<int>. [typeNameOf] gets past that by resolving from the instance, but a bare Type offers no route back to the declaration, so typeNameForType(BoxPreference<int>) throws where typeNameForType(BoxPreference) answers. Read a generic preference under its bare class literal — the instantiation is deliberately not part of the stored identity, and so is not restored by the read.

static DateTime? parseInstant(String text)

Parses [text] as a UTC instant, or returns null if it does not name one.

Stricter than DateTime.parse, and deliberately so. DateTime.parse accepts a timestamp with no zone designator (2026-03-04T05:06:07, or a bare 2026-03-04) and reads it as local time in the reading process's zone — so one stored string would mean a different instant on every device, which is precisely what [dateTimeType] promises cannot happen.

The zone test is delegated to the SDK rather than written as a pattern: DateTime.parse returns a UTC-flagged value for exactly those strings that carry a designator — Z, +HH:MM, +HHMM or +HH — so [DateTime.isUtc] on the parse result is the answer, and there is no second, drifting copy of the ISO 8601 grammar to keep correct.

Callers that build a write request themselves can use this to check their text before sending it, and get the same verdict the boundary will give.

static T _decodeValue<T extends Object>(String json, String key, String storedName, ClassMirror<dynamic>? reflectedClass)

Narrows the JSON text [json] to a [T]; [key] only names the preference in an error.

[storedName] is the name [decode] resolved [T] to and has already matched against the row, and [reflectedClass] is the registry entry behind it, or null when [T] is a scalar or a collection. Both are passed rather than looked up again because [decode] cannot have compared the stored name without resolving them, and a second lookup could only either repeat that work or disagree with it.

Private, and deliberately so. Given the text alone there is nothing to contradict the caller's [T]: a stored DateTime read as a String succeeds here, because "2026-03-04T05:06:07Z" is a string. Only the stored [TomUserPreferenceDto.valueType] says otherwise, so [decode] compares it first and is the sole caller.

static Object _narrowScalar(String scalarType, Object? raw, String key, String requested)

Narrows the decoded JSON [raw] to the scalar named [scalarType].

[requested] is the type the caller asked for, which is [scalarType] at the top level and the whole collection name — List<DateTime> — when this is narrowing an element. It appears only in errors, so that a bad element is reported against the preference the reader actually asked for.

The narrowing itself belongs to the row — [_ScalarKind.narrow] — so that a scalar is described in one place on both sides of the column. What is here is the single failure text for "not decodable as the requested type", which every row would otherwise state for itself.

An int widens to a double — for the row, not for the reader. JSON writes 1.0 as 1, so a double preference a non-Dart client wrote arrives integral, and [validateEncoded] admits it on that understanding: the read-side predicate for double is is num. The widening is the second half of that admission, and the two now sit in the same row, so removing one and keeping the other would take an edit that reads wrong.

A caller reading an int-declared preference as a double never gets here. [decode] compares the stored name against the requested one before any narrowing, and refuses — the widening is not a way around a declared type.

A DateTime must name its zone — see [_narrowInstant] and [parseInstant].

static Object? _narrowInstant(Object? raw, String key, String requested)

Narrows the stored text of a [dateTimeType] row to the instant it names.

The [_ScalarKind.narrow] of the DateTime row, written out rather than inlined into the table: the other four narrowings are a type test and a value, and this one has a rule to state and two errors to tell apart.

A timestamp that names no zone is refused, not read as local. Reading it would have to invent an offset — this device's — and a preference follows its user across devices, so the invented instant would differ from the one the writer meant, differently on each of them. Text that is not a timestamp at all is a different failure and says so, because "not an instant" would send a reader looking for a zone in a value that has no date in it.

null only for a [raw] that is not a String, which is the plain mismatch [_narrowScalar] reports for every row.

static T _decodeCollection<T extends Object>(Object? raw, String key, String storedName, ({String element, bool isMap}) parts)

Rebuilds the collection [storedName] describes from the decoded JSON [raw].

The elements are narrowed one at a time by [_narrowScalar], so an element obeys exactly the rule a top-level value of that type obeys — the zone check and the int-to-double widening included — rather than a second, looser copy of it.

The typed collection is built by the same row, through [_ScalarKind.listFrom] / [_ScalarKind.mapFrom]. It has to be typed: a List<Object> would satisfy the cast below in name only and fail the caller at the first use. Reading the constructor out of the row rather than out of a switch is what makes a sixth scalar one row rather than one row and two edits made somewhere else.

static TomUserPreferenceCodecException _notDecodable(String key, String requested)

Raised when a stored row is not shaped like the type it was read as.

static T _decodeEnum<T extends Object>(Object? raw, String key, ClassMirror<dynamic> enumClass)

Resolves the enum constant [raw] names, against the constants [enumClass] declares now.

Refused rather than defaulted when nothing matches. This is not a hypothetical: the row may have been written by a release whose enum had a constant this one has dropped or renamed, which is the ordinary cost of letting an enum evolve. Falling back to the first constant would hand the caller a setting the user never chose, and it would look exactly like one they did — so the read fails and says which name it could not place.

class _ScalarKind

class _ScalarKind

One scalar shape: the Dart type it is, the name it is stored under, and the two questions the codec asks about it.

One row rather than parallel lists, because it is one fact. That int is stored as int, is recognised by is int, and looks like a JSON integer is a single sentence about a single shape. Split across a list of names, a chain of is tests, a chain of Type comparisons and a switch over those names, the parts can fall out of step without anything failing to compile — and a name the write side produces that the read side will not accept is a preference that stores successfully and never comes back.

The two predicates are deliberately not one. They are asked on opposite sides of the column: [matchesValue] of a live Dart value on the way in, [matchesJson] of whatever jsonDecode returned on the way out. double is where that shows — is double going in, is num coming back.

final Object? Function(Object?, String, String) narrow

Turns decoded JSON into the Dart value of this shape, or null when [raw] is not of this shape.

The counterpart of [matchesJson] on the way out, and in the same row for the same reason: a shape the codec admits at the boundary has to be one it can then build. double is where the pair earns its keep — its [matchesJson] is is num, because JSON writes 1.0 as 1, and this is the widening that admission promises.
