The durable job queue — pending and in-flight runs that survive a restart.

A scheduler that keeps its plan in memory forgets everything the moment the process exits: work that was queued is lost, and work that was half done is lost twice over, because nothing records that it was ever started. This library is the store that stops both.

What is persisted, and why that is the whole model

The unit of persistence is the [TomJobRun] — one attempt-carrying record per schedule window. Two fields on it do most of the work:

  • [TomJobRun.scheduledFor] is the window the run belongs to, and it is the

idempotence key. The scheduler enqueues by window, so replaying a tick — or restarting mid-tick — cannot produce a second run for the same window. [TomJobRun.runAt] is when the run should next be attempted*. A retry is therefore not a new record and not a new state; it is the same run with a higher [TomJobRun.attempt] and a later [runAt]. That keeps the state machine at four values and makes "what is outstanding" a single query.

A claimed run carries [TomJobRun.claimedBy] and [TomJobRun.claimedAt] — a lease. If the process dies holding it, the record stays running with a stale timestamp, and [TomJobStore.recoverAbandoned] hands it back. That is what "in-flight runs survive a restart" means concretely: not that the work continues, but that it is visibly outstanding again rather than silently gone.

Implementations

  • [TomMemoryJobStore] — no durability. Correct for tests and for jobs whose

loss on restart is acceptable. [TomFileJobStore] — mirrors the queue to a JSON file on every mutation and reloads it on construction, following the same pattern as the kernel's file-backed log replay store. This is what makes the scheduler durable without a database*, which matters because tom_core_kernel has no persistence layer and must not grow one for this.

A relational implementation belongs in tom_core_server, over the same [TomJobStore] contract; the lease fields are already shaped for the multi-node lock that will need it.

class TomFileJobStore

class TomFileJobStore extends TomMemoryJobStore

A [TomJobStore] that mirrors the queue to a JSON file on every mutation.

Constructing it reloads whatever the previous process left behind, so a scheduler pointed at the same path resumes with its pending runs intact and its in-flight runs visible as expired leases. That is the whole of the durability requirement met without a database — which matters, because tom_core_kernel deliberately has no persistence layer.

Writes are synchronous, flushed and atomic: the new queue is staged in a sibling file and renamed over the target, so an interrupted write leaves the previous queue rather than a truncated one. That is not a refinement but the difference between losing one mutation and losing the whole queue — the file is rewritten whole each time, and [_load] can only discard an array it cannot parse.

The queue is small (one record per window, purged once terminal), so rewriting it whole is cheaper than the bookkeeping an append-only journal would need to compact.

Shared by several stores

Several stores may point at one file — scheduler processes on one host, or on a shared mount, or isolates in one process — and they then share one queue. Every operation takes an exclusive file mutex (a [TomFileLeaseLock] on the sibling directory <path>.lock), re-reads the file, applies itself, writes the file back if it changed anything, and releases the mutex. So a claim is atomic across every store on the file: a run is claimed by exactly one of them, and a run one store completed is completed for all.

Each store's own copy of the queue is therefore only a working copy, refreshed at the start of every operation, and never the truth. That is the whole difference from its superclass, and the reason neither half is optional: a store that read the file once and then mirrored its own copy to it would overwrite every other store's writes and act on runs they had already completed.

The mutex is a lease, 30 seconds long, so a process that dies while holding it — in the middle of one operation, which takes milliseconds — blocks its peers for at most that long before one of them takes it over. A holder paused for longer than that mid-operation could still write a stale queue over a newer one, the hazard every lease carries; the operation is short enough that this needs a stall of half a minute inside it.

The claim being atomic does not make the lease lock redundant for a scheduler: it is still what enforces allowOverlap across nodes, and it is what fences a node paused past its lease.

The filesystem must make exclusive create and rename atomic between the processes sharing it — true of local filesystems and of well-behaved network ones; see [TomFileLeaseLock].

Creates a store backed by [path], loading any previously persisted runs.

Writes to [path] if — and only if — what it finds there is damaged: the unreadable content is moved to [_corruptPath] and whatever could be salvaged is written back. void _load()

Reads runs from [file] if it exists, leaving the queue empty when the file is missing, empty, or not a JSON array.

A record that fails to decode is skipped rather than aborting the load: a single corrupt entry must not stop the scheduler from starting, since starting is how the rest of the queue gets drained. For the same reason this method never throws — the store is built during startup wiring, so a throw here would turn a past crash into a boot failure, taking down the process the durable queue exists to protect.

What it does not do is stay quiet. Every unreadable state degrades to "carry on with what could be salvaged, and say what was lost", because an empty queue and a destroyed queue otherwise look identical at startup.

void _recoverFrom(String detail)

Reports the loss described by [detail], moves the damaged file aside to [_corruptPath], and writes whatever was salvaged back to [file].

Called only after the salvaged runs are already in the queue, since the rewrite persists exactly what [snapshotSync] holds.

void _report(String message)

Logs [message] as an error — the channel an operator actually watches.

Never throws. The store is constructed during startup wiring, and a broken log output must not be what stops the scheduler from starting: reporting a recoverable loss cannot be allowed to become an unrecoverable one.

tomLog already guards the sink it writes to, so the catch below is not what makes the common case safe. It is here because "loading never throws" is this store's own contract, and resting that on another package's internal try would make a refactor there a boot failure here.

void _persist()

Writes the current queue to [file], creating parent directories as needed and flushing so the bytes reach disk before returning.

The write is atomic — see [tomWriteFileAtomically]. It has to be: the queue is rewritten whole on every mutation, and [_load] can do nothing with a truncated array but discard it. An overwrite interrupted by a kill or a full disk would therefore not lose a run, it would lose the entire durable queue, silently, at the next start.

class TomJobClaim

class TomJobClaim

A ticket proving that one particular claim of [run] was won.

[TomJobStore.claimDue] issues one per run it hands over, and every transition out of a claim takes the ticket rather than the run. That is the same arrangement TomLeaseLock uses — acquire returns a TomLease and renew/release take it back — and it is here for the same reason: a caller cannot record an outcome for work it did not claim, because it has nothing to call the method with.

What the ticket has to identify

Not the run, and not the node: this claim of this run. [owner] alone is not enough, because a node can re-claim a run it had previously lost — and then its first attempt's outcome would be accepted as its second's.

So the fence is [token], a counter that rises on every claim of the run and never repeats. It is exactly TomLease.token, for exactly the same reason: two acquisitions of the same thing have to be orderable, or "the current holder" is not a decidable question. That the queue lacked one while the lock had one is why the two could disagree.

Why not the claim instant

[TomJobRun.claimedAt] looks like a cheaper answer — it is already stored, and it already distinguishes two claims. But it is the heartbeat: [TomJobStore.renewClaim] moves it forward while the attempt runs. A ticket fenced on it would be invalidated by the first heartbeat of the very attempt it certifies, so the claimant would silently lose the right to report its own outcome. The identity must be the thing that does not move, which is the whole reason the lock separates token from expiresAt.

class TomJobRun

class TomJobRun

One attempt-carrying occurrence of a job.

Mutable by design: a run is a record that moves through states, and copying it on each transition would leave the store deciding which copy is current. All mutation goes through [TomJobStore], so the persisted mirror can never drift from the in-memory one.

When the lease was last heard from, null when unclaimed. Compared against the lease timeout by [TomJobStore.recoverAbandoned].

This is the heartbeat, not the claim's identity: [TomJobStore.renewClaim] pushes it forward for as long as the attempt runs. Which claim is current is [claimToken]'s job.

int claimToken

Which claim of this run is current: strictly increasing across claims, never decreasing, and never reset.

The fencing token of [TomJobClaim], and the counterpart of TomLease.token on the coordination lock — the same problem, solved the same way, because the two must agree about who holds a run. It starts at 0 on an unclaimed run and is incremented by [TomJobStore.claimDue] on every claim, including a re-claim by the node that held it before.

It is a separate field from [claimedAt] because the two answer different questions and only one of them may move during an attempt. A heartbeat that doubled as the identity would invalidate the claim it was proving alive.

DateTime? startedAt

When the body actually began executing, null if it never did.

The distinction between "claimed" and "started" is what makes recovery safe to reason about. A running run with no [startedAt] was reserved and then lost — the node died between the claim and the dispatch — so nothing was executed and re-queueing it cannot repeat a side effect. A running run with [startedAt] was interrupted mid-execution, and whether it is safe to run again is a property of the job, not of the store: see [TomJobDefinition.requestsRecovery].

Quartz draws the same line with two trigger states, ACQUIRED and EXECUTING. It is one nullable instant here because the instant is also worth having — "how long had it been running when the node died" is the first question asked after an incident.

String? lastError

The most recent failure message, retained on retry so a run that eventually fails can report why it kept failing.

DateTime? completedAt

When the run reached a terminal state.

final Object? payload

Trigger payload for an event-driven run; null for clock-driven ones.

Restricted to a JSON-encodable value so a durable store can round-trip it.

class TomJobStore

abstract class TomJobStore

Durable storage for job runs.

Every method is asynchronous so a database-backed implementation fits the same contract without the in-memory one having to pretend to be slow.

Claiming must be atomic. [claimDue] transitions a run to running and stamps the lease in one step; an implementation that let two callers observe the same run as claimable would double-fire it. The in-process implementations here are atomic by virtue of Dart's single-threaded event loop — they perform no await between selecting and stamping.

*A transition out of a claim only ever records a run; it never creates one, and never overrules another claimant. [release], [markStarted], [renewClaim], [complete] and [fail] are all no-ops unless the store still holds the run, still holds it as running, and* still holds it under the [TomJobClaim] being presented. Each of the five is reached by a caller holding a ticket it obtained some time earlier, so each can be handed a claim the store has since finished, re-queued, handed to another node via [recoverAbandoned], or dropped entirely via [purgeFinished] — and in every one of those cases the outcome of the attempt this caller is reporting is no longer the run's outcome.

The two halves of the guard answer two different questions, and only both together are sufficient:

  • Does the store still hold this run, as running? Without it, writing

back would resurrect a purged row — [purgeFinished] is the only thing bounding the store, and a re-inserted run carries a freshly stamped [TomJobRun.completedAt] that restarts its retention clock, so it survives every subsequent cutoff. Is it still held under this claim?* State alone cannot see the case the lease timeout exists for. A node partitioned for longer than the timeout returns to a run that recovery re-queued and a peer re-claimed: the row exists and is running, so a state-only guard passes, and the returning node's outcome silently overwrites an attempt the peer is still executing. The peer then heartbeats a run already marked succeeded, and its own completion no-ops.

The rule costs nothing when nothing went wrong — a run this node still owns is running under its own claim by definition — and it is what makes the five safe to call without first re-reading the store.

Future<void> enqueue(TomJobRun run)

Adds [run] to the queue.

The caller is responsible for idempotence via [findWindow]; the store stores what it is given.

Throws a schedule.job.payload [TomScheduleException], before changing the queue, when [TomJobRun.payload] is not JSON-encodable — see [encodePayload].

Future<TomJobRun?> findWindow(String jobName, DateTime scheduledFor)

The run already recorded for [jobName] at [scheduledFor], or null.

This is what makes enqueueing idempotent, and therefore what makes a tick safe to replay after a crash.

Future<DateTime?> lastWindow(String jobName)

The latest window ever enqueued for [jobName], or null if the job has no history in this store.

The scheduler uses null to mean "first sight of this job" and anchors on the present instead of treating all of history as missed.

Future<List<TomJobClaim>> claimDue(DateTime now, String owner, {int limit = 16, bool Function(TomJobRun)?? accept})

Atomically claims up to [limit] runs that are due at [now], marking each running and leasing it to [owner].

Returns one [TomJobClaim] per run won — the ticket every transition below requires. When [accept] is supplied, only runs it approves are claimed; the scheduler uses it to enforce per-job overlap policy without a second round-trip.

Future<void> release(TomJobClaim claim)

Returns the run held by [claim] to pending without charging it an attempt.

The voluntary counterpart of [recoverAbandoned]: a runner that claimed a run and then found it could not proceed — most usually because a cluster peer holds the coordination lease for it — hands it straight back instead of sitting on the claim until the lease times out.

The attempt count is deliberately untouched. Nothing was attempted, and charging an attempt would let a busy cluster exhaust a job's retry budget through contention alone.

A no-op unless the store still holds the run as running under [claim] — a completion that raced the release must win, and a run recovery has since handed to a peer must not be pushed back into the queue underneath it.

Future<void> markStarted(TomJobClaim claim, DateTime now)

Records that [claim]'s body actually began executing at [now].

Called once per attempt, immediately before the body is handed to the dispatcher, and it is the only thing that distinguishes an interrupted execution from an abandoned reservation. Without it every running row looks the same after a node dies, and recovery has to guess.

A no-op unless the store still holds the run as running under [claim]: the outcome of a run this node has lost belongs to whoever took it over. Stamping startedAt onto it would tell recovery that a different node's attempt had begun.

Future<void> renewClaim(TomJobClaim claim, DateTime now)

Refreshes the lease timestamp on [claim] to [now].

A long-running attempt must be able to say it is still alive, or [recoverAbandoned] would hand its work to a second runner while the first is still going. This is the store half of that heartbeat; the lock half is TomLeaseLock.renew.

A no-op unless the store still holds the run as running under [claim] — a heartbeat for a lease this node no longer owns would keep recovery off a run it has already reassigned.

The [TomJobClaim] itself does not move: it names the claim that was won, and a renewal extends that claim rather than starting a new one. What advances is the stored lease stamp, [TomJobRun.claimedAt]; the token the ticket carries is untouched, so the claimant keeps the right to record its own outcome for as long as the attempt lasts.

Future<void> complete(TomJobClaim claim, DateTime now)

Marks [claim]'s run succeeded at [now] and releases its lease.

A no-op unless the store still holds the run as running under [claim] — see the rule on [TomJobStore]. Calling it twice therefore records the first completion only; the second does not move [TomJobRun.completedAt] forward, so a duplicate outcome cannot extend the run's retention.

Future<void> fail(TomJobClaim claim, String error, DateTime now, {DateTime? retryAt})

Records a failed attempt of [claim]'s run.

When [retryAt] is non-null the run returns to pending with its attempt count incremented and runAt set to [retryAt]; when it is null the run becomes terminally [TomJobRunState.failed].

A no-op unless the store still holds the run as running under [claim], exactly as [complete] is. The retrying branch has a second reason to check: it increments the attempt count, and charging a retry to a run that now belongs to another node would eat a retry budget this caller is no longer spending.

Future<List<TomJobRun>> recoverAbandoned(DateTime now, Duration leaseTimeout, {bool Function(String)?? requestsRecovery})

Reclaims runs left running by a holder that vanished.

A lease older than [leaseTimeout] is treated as abandoned. The attempt count is not incremented: the run may never have started, and charging it an attempt for the scheduler's own death would let a crash loop consume a job's whole retry budget. Returns every run whose state this call changed, so the caller can alert on each; read [TomJobRun.state] to see which way it went.

Re-queued, or terminally failed

A run that was claimed but never started ([TomJobRun.startedAt] is null) always returns to pending, unpenalised: nothing ran, so nothing can repeat.

A run that had started was interrupted mid-execution, and re-running it repeats whatever it had already done. Whether that is safe is a property of the job, so [requestsRecovery] is consulted: it returns true for a job that has declared itself recoverable ([TomJobDefinition.requestsRecovery]), and such a run goes back to pending like any other. A run whose job says otherwise becomes terminally [TomJobRunState.failed] with an explanatory [TomJobRun.lastError], because silently re-running a non-idempotent job is the worse of the two failures and the operator needs to see the decision.

Passing null — the default — recovers everything, which is what a caller that cannot see the job registry must do. A store cannot invent the answer, and re-queueing is the behaviour every caller had before the distinction existed. TomScheduler always supplies the predicate.

Future<List<TomJobRun>> all()

Every run currently held, in insertion order. Primarily for diagnostics and tests.

Future<int> purgeFinished(DateTime before)

Removes terminal runs that completed before [before], returning how many were dropped.

Without this the queue is an append-only log that grows forever. It is a caller-driven operation rather than an automatic one because how much history to keep is a deployment decision, not the store's.

Static

static String recoveryDeclinedError

What an interrupted run's [TomJobRun.lastError] says when its job did not ask to be recovered.

A constant because it is the operator-facing explanation of a decision the framework made on the job's behalf, and it must read the same whichever store recorded it.

static bool isRecoverable(TomJobRun run, bool Function(String)?? requestsRecovery)

Whether an abandoned [run] may be offered again.

A run that never started always may — nothing executed, so nothing can repeat. One that was interrupted mid-execution may only when its job says so, which is what [requestsRecovery] answers; a null predicate means the caller cannot see the job registry, and re-queueing is then the only answer it can give.

Shared rather than duplicated because both stores must decide identically — but only the decision is shared. Each store applies the resulting transition in its own idiom: field assignment in memory, a different UPDATE in SQL.

static String? encodePayload(TomJobRun run)

The JSON text a durable store writes for [run]'s payload, or null when there is no payload.

This is also the contract's definition of "JSON-encodable", and every implementation of [enqueue] calls it — including the in-memory one, which has nothing to write. The restriction belongs to the contract rather than to any one medium: a payload only the memory store would accept is a payload that fails on the first deployment that has a file or a database, and it should fail on the developer's machine instead.

Throws a schedule.job.payload [TomScheduleException] naming the job and the offending type. The raw [JsonUnsupportedObjectError] says only that some object could not be converted, which is of little use several frames below whichever event handed the payload over.
