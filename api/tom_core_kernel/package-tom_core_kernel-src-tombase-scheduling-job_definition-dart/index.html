The what half of a background job: its work body and its operational policy — retry, backoff, timeout, overlap and failure alerting.

CE-JB declares all four of retry, backoff, timeout and alerting as part of a job's definition. They live here, on the definition, rather than inside the job body for one reason: a policy the body implements is a policy every body implements differently, and the moment two jobs disagree about what "retry three times" means, the declaration in the spec has stopped describing the system. The runtime honours these; the body does the work.

The dispatcher seam

A job's work body is a [TomCommand] — the same unit the kernel's isolate pool already runs. The scheduler never executes one itself; it hands it to a [TomJobDispatcher]. That seam is what keeps the promise not to build a second execution engine: [TomWorkerPoolJobDispatcher] is a thin adapter over [TomWorkerPool], and the only other implementation, [TomInlineJobDispatcher], exists so tests and single-threaded deployments do not have to spawn isolates to exercise scheduling logic.

class TomJobDefinition

class TomJobDefinition

A registered job: a trigger, a work body, and the policy around both.

Constructors

TomJobDefinition.new({required String name, required TomSchedule schedule, required TomCommand Function(TomJobRun) body, TomRetryPolicy retryPolicy = const TomRetryPolicy(), Duration timeout = const Duration(minutes: 5), TomMissedWindowPolicy missedWindowPolicy = TomMissedWindowPolicy.runOnce, int catchUpLimit = 10, bool allowOverlap = false, bool requestsRecovery = false})

Creates a job definition.

Properties

final String name

The job's identity. Used as the store key, so it must be stable across restarts — a renamed job loses its history and re-anchors as if new.

final TomSchedule schedule

When the job fires.

final TomCommand Function(TomJobRun) body

Produces the work body for one run.

A factory, not a single instance, for two reasons: a command may carry per-run state, and a command dispatched to an isolate is copied, so reusing one instance across runs invites the illusion that mutations to it are visible back on the scheduler side.

The run is passed in so a body can read its window ([TomJobRun.scheduledFor]), its attempt number, or an event payload.

final TomRetryPolicy retryPolicy

How failed attempts are retried.

final Duration timeout

How long one attempt may take before it is treated as failed.

A timed-out attempt is failed and retried per [retryPolicy]. The work itself is not cancelled — Dart cannot cancel arbitrary asynchronous work, an isolate command cannot be interrupted from outside, and killing the worker would take unrelated work with it. The timeout bounds the scheduler's wait, not the body.

So the body is still treated as executing until it settles: the scheduler keeps the protection the attempt held — the job counts as busy (with [allowOverlap] true, only its own run does) and the run's cluster lease is kept and renewed — and the retry is not started until the body returns or throws. What a late body produces is discarded; the attempt was already failed. Two consequences follow. A body that finishes late has done its work and its retry will do it again, one after the other — a duplicate the at-least-once contract already asks bodies to absorb. And a body that never settles holds its job (or window) indefinitely, which TomScheduler.overrunningCount shows; give a body that can hang a deadline of its own, shorter than this one.

final TomMissedWindowPolicy missedWindowPolicy

What to do about windows missed while the scheduler was down.

final int catchUpLimit

The most windows [TomMissedWindowPolicy.runAll] will replay.

final bool allowOverlap

Whether a new run may start while a previous one is still in flight.

false by default, which is the safe reading for the common case of a job that reads and rewrites the same rows. This is single-node serialisation only — it holds within one scheduler, not across a cluster.

final bool requestsRecovery

Whether a run interrupted mid-execution may be re-queued.

false by default, which is the safe reading: a body that died halfway through may have written half its effects, and re-running it repeats them. Set it to true only for a body that is idempotent, or whose work is worthless unless completed — a report regenerated from scratch, a sync that recomputes the whole delta.

This governs only the interrupted case. A run that was claimed and never started is always re-queued regardless, because nothing executed and nothing can therefore repeat; [TomJobRun.startedAt] is what tells the two apart.

Quartz spells the same opt-in REQUESTS_RECOVERY and defaults it off for the same reason.

class TomRetryPolicy

class TomRetryPolicy

How a failed attempt is retried.

Backoff is exponential from [initialBackoff] by [multiplier], and never exceeds [maxBackoff] — jitter included. [jitter] spreads the retries of jobs that failed together — without it, a downstream service that dropped every job at once gets them all back simultaneously, which is how a brief outage becomes a long one.

That pile-up is worst once every job has saturated at the ceiling, which is what a long outage produces, so the curve plateaus a jitter's width below [maxBackoff] rather than clamping the jittered value. See [backoffFor].

The fields have ranges — maxAttempts >= 1, multiplier >= 1, jitter in 0..1, a non-negative [initialBackoff] and a positive [maxBackoff] — enforced by [validate] rather than by the constructor, which must stay const for annotation use.

Constructors

const TomRetryPolicy.new({int maxAttempts = 3, Duration initialBackoff = const Duration(seconds: 30), double multiplier = 2.0, Duration maxBackoff = const Duration(minutes: 30), double jitter = 0.1})

Creates a retry policy.

The arguments are not checked here. This constructor has to stay const — @TomScheduledJob(retry: TomRetryPolicy(…)) is an annotation argument, and Dart requires those to be compile-time constants — and a const constructor has no body to throw from. The checks therefore run in [validate], which [TomJobDefinition] calls; see there for why that is the honest boundary rather than merely the available one.

Properties

final int maxAttempts

Total attempts including the first, so 1 means "no retry".

At least 1. 0 is rejected rather than read as "unlimited": it would behave as [none], since [allowsRetryAfter] asks whether the attempt number is below this and no attempt is below zero.

final Duration initialBackoff

The delay before the second attempt.

May be zero, which retries at once. Never negative.

final double multiplier

The factor each successive backoff is multiplied by.

At least 1. Below 1 the "backoff" would shrink on every failure — 10 s, 5 s, 2.5 s — which is the pathology exponential backoff exists to prevent. Exactly 1 is allowed and means a constant delay between attempts.

final Duration maxBackoff

The ceiling backoff never exceeds, [jitter] included.

Positive, where [initialBackoff] need only be non-negative: retrying at once is a real choice, but a zero ceiling clamps every backoff to nothing and turns [maxAttempts] into a tight spin against whatever just failed.

Because jitter is added on top, the exponential curve plateaus at maxBackoff / (1 + jitter) — with the defaults, 27 min 16 s under the 30 min ceiling — and jitter fills the gap.

final double jitter

The fraction of the computed backoff that may be added at random, 0-1.

Applied additively upward only, so jitter never makes a retry earlier than the backoff the policy promised, and never later than [maxBackoff], whose plateau reserves the room it needs. 0 disables jitter; a negative value is rejected rather than read as "off", since it would silently mean that.

Methods

void validate(String job)

Throws a schedule.retry.* [TomScheduleException] if this policy would misbehave, naming [job] so the report identifies which one to fix.

Called by [TomJobDefinition], which every policy passes through on its way into a scheduler. That placement is deliberate rather than a workaround for the const constructor: an unattached policy governs nothing, so the moment a bad value starts producing wrong answers is the moment a job adopts it — and only then is there a name to put in the message.

Each rule below rejects a value that is currently accepted and then quietly does the wrong thing, which is the shared reason they are errors and not merely unusual settings.

bool allowsRetryAfter(int attempt)

Whether an attempt numbered [attempt] may be followed by another.

Duration backoffFor(int attempt, [Random? random])

The delay before the attempt following [attempt] (1-based).

[random] is supplied by the scheduler so jitter is reproducible in tests; omitting it yields the exact, unjittered backoff — the low end of the range a jittered call draws from.

enum TomJobAlertKind

enum TomJobAlertKind

Why a [TomJobAlert] was raised.

Values

attemptFailed

An attempt failed and another will follow.

timedOut

An attempt exceeded [TomJobDefinition.timeout].

runFailed

Every attempt is spent; the run is terminally failed.

runAbandoned

A run whose lease expired was returned to the queue — the scheduler that held it died, or wedged for longer than the lease.

recoveryDeclined

A run that was interrupted mid-execution was not re-queued, because its job does not set [TomJobDefinition.requestsRecovery].

The counterpart to [runAbandoned], and separate from it on purpose: those two outcomes look alike in a store — an expired lease either way — but they mean opposite things to an operator. [runAbandoned] says "it will run again"; this says "it will not, and if that work mattered somebody has to decide what to do about it". The run is left terminally failed with [TomJobStore.recoveryDeclinedError] recorded against it.

windowsMissed

A schedule produced windows that were skipped by its missed-window policy.

neverFires

A registered job's schedule will never produce a window.

The quiet misconfiguration: a job that can never run looks exactly like a job that is merely not due yet, and without this nothing would ever say otherwise. It arises two ways — a recurrence that cannot match (0 0 30 2 * is February 30th) and, more usefully, a TomOnceSchedule whose instant had already passed when the job was first registered, which is what a deadline job restored at start-up after a long outage looks like.

Raised once per job per scheduler rather than once per tick: the condition cannot resolve itself, and an alert that repeats every tick forever is how operators learn to filter a channel.

lockContended

A cluster peer held the coordination lease, so this node did not run the work.

Routine in a healthy cluster — exactly one node wins each run and the rest report this — so the default sink logs it at debug level. It earns its place as an alert because a job that never runs anywhere looks identical to a job nobody scheduled until you can see that every node is conceding.

leaseStolen

This node took over a lease whose holder had let it expire.

The cluster-visible answer to "what happened to a run whose holder vanished": the run was picked up here, and the previous holder is named in [TomJobAlert.lease].

leaseLost

A lease could not be renewed while its work was still running.

The serious one. This node no longer owns the run, another node may already be executing it, and the work in flight here cannot be recalled. See doc/scheduling/scheduling.md — this is the window in which the at-least-once guarantee becomes visible.

enum TomMissedWindowPolicy

enum TomMissedWindowPolicy

What a job does about windows that elapsed while the scheduler was down.

This has to be stated, because every possible behaviour is wrong for some job and there is no default that is merely technical. A nightly report that missed three nights probably wants one catch-up run, not three; a billing job that missed three days probably wants all three; a cache warm-up that missed three days wants none of them.

Values

skip

Ignore every missed window; resume at the next future one.

Right for work whose value is entirely in being current — cache warming, health probes, anything where a late run does the same thing as the next on-time run and merely costs more.

runOnce

Run the most recent missed window once, and ignore the rest.

The default, because it preserves the property most schedules are actually asserting — "this ran today" — without replaying an outage's worth of windows. The run carries the missed window in [TomJobRun.scheduledFor], so a body that cares can see it was late.

runAll

Run every missed window, most recent first, up to [TomJobDefinition.catchUpLimit].

Right when each window has its own work — a per-period aggregation where skipping a window means that period is never processed. The limit is not optional: an unbounded catch-up after a long outage is a self-inflicted denial of service.

mixin TomPermanentFailure

mixin TomPermanentFailure on Object

Marks an error as one that retrying cannot fix.

A [TomRetryPolicy] answers "how many times", but some failures should not be attempted a second time at all: a malformed address, a rejected credential, a request the far side answered with "never". Retrying those burns the whole budget on an outcome that was decided at the first attempt, and — worse — delays the report of a failure the caller could have acted on immediately.

The scheduler already draws this line once: a body factory that throws is failed outright rather than retried, because it would throw identically next time. This mixin extends the same judgement to the body itself, which is the only party that can tell a refusal from an outage.

Mix it into an existing exception to classify it, or throw [TomPermanentJobFailure] when there is no type to reuse: 

class MailRejected extends TomException with TomPermanentFailure { … }

The default remains transient. An unrecognised error is retried, because retrying a permanent failure costs a few wasted attempts whereas dropping a transient one loses the work.
