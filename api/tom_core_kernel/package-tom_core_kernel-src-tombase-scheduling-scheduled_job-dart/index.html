Declarative jobs — a class annotated with [TomScheduledJob] is its own registration.

Without this library a job is declared twice: once as the class that does the work, and once as a hand-written [TomJobDefinition] at start-up that wires a closure to a name, a schedule and a set of policies. Nothing relates the two. A job class can exist and never be registered; a registration can out-live the class it names; and a rename silently breaks the pairing, because the only thing joining them is a string a human typed twice.

Here the class carries its own schedule:

@tomReflector
@TomScheduledJob(cron: '0 3 * * *')
class NightlyReconciliation extends TomJobBase {
  @override
  Future<Object?> execute() async { /* ... */ }
}

and start-up becomes one line:

TomScheduledJobs.registerAll(scheduler);

Why reflection is the right answer here

The kernel deliberately does not discover file-storage backends by annotation (see blob_store_registry.dart): a backend is routinely the deployment's own, its factory is a closure precisely so it can capture a configured HTTP client or credential provider, and an annotation would put a codegen step in front of a one-line registration.

None of those three apply to a job. A job is application code that is already inside the application's own reflection build; its settings are literals — a cron string, a retry count, a timeout — that an annotation expresses natively; and it needs no captured collaborators, because the body is built fresh per run and can resolve what it needs from the bean locator (see [TomJobBase]). The closure in [TomJobDefinition.body] exists only to make the body per-run, and newInstance('', []) per run does that.

Everything is checked at scan time

This is the whole robustness claim. Quartz stores a job's class as a string (QRTZ_JOB_DETAILS.JOB_CLASS_NAME) and resolves it at fire time: a rename parks the trigger in ERROR permanently, and cluster recovery silently skips a firing whose class no longer resolves. A reflected class is present at compile time — the class is the registration, so a rename is just a rename — and every remaining way to get a declaration wrong is reported by [TomScheduledJobs.discover] at start-up, naming the offending class, rather than at 03:00 into a log nobody reads.

Discovery produces definitions; it does not replace them

[TomJobDefinition] and [TomScheduler] are untouched by this library. A job whose schedule is computed from configuration, or whose body has to close over something, can never be an annotation — so a hand-written definition stays fully registrable and the two coexist in one scheduler.

class TomJobBase

abstract class TomJobBase extends TomCommand

The base class for a declaratively scheduled job.

A job is a [TomCommand] — that is what the scheduler dispatches, and nothing about that changes here. [TomJobBase] adds the one thing a command built by reflection cannot be handed through its constructor: the [run] it was created for. Extending it is therefore optional in the strict sense (any [TomCommand] with a no-argument constructor is accepted), but a job that wants to know its window, its attempt number or its event payload has to.

Why the constructor takes no arguments

The body is instantiated per run by newInstance('', []), so there is no call site to pass collaborators from. Resolve them instead — in the constructor or in [execute] — from the bean locator: 

@tomReflector
@TomScheduledJob(cron: '@daily')
class ExpireSessions extends TomJobBase {
  final TomBean<SessionService> _sessions = TomBean<SessionService>();

  @override
  Future<Object?> execute() async =>
      _sessions.get().expireBefore(run.scheduledFor);
}

That is not a workaround for the annotation; it is the same wiring every other framework component uses, and it keeps the job's dependencies resolvable in a worker isolate, where a captured reference would not have survived the copy.

class TomScheduledJob

class TomScheduledJob

Declares that the annotated class is a scheduled job.

Carries what [TomJobDefinition] takes as constructor arguments, with one unavoidable difference: a [TomSchedule] is not a constant, so it cannot be an annotation argument. The trigger is instead declared by four mutually exclusive fields — [cron], [interval], [calendar] and [event] — of which exactly one must be set. Setting none, or two, is a scan-time error.

The class must also carry @tomReflector: the reflection substrate exposes only annotatedClasses, with no by-annotation and no by-supertype query, so a job that is not in the reflection build is not discoverable at all.

Properties

final String? name

The job's identity, defaulting to the class's simple name.

This is the store key. Runs in a [TomJobStore] are keyed by it, so renaming the class of a job that already has stored runs orphans them — the history stays under the old name and the job re-anchors as if new. Pin the old name here when renaming a job that is already in production; that is the entire reason this field is overridable.

final String? cron

A POSIX cron expression, e.g. '0 3 * * *', or a macro such as '@daily'. Parsed and validated at scan time.

final Duration? interval

A fixed period, e.g. const Duration(minutes: 15).

Fire times are computed from the Unix epoch by whole multiples of the period, so they are reproducible across processes and do not drift after an outage.

final String? calendar

A calendar expression — the month-relative rules cron cannot spell.

Whitespace-separated key:value terms, exactly one of which selects the rule:

TermMeaning
day:<n> day of month, 1 .. 31 , or -1 .. -31 counting from the month's end
weekday:<ordinal>/<day> ordinal 1..5 or last; day mon..sun
at:<HH:MM>time of day, default 00:00
every:<months> month interval 1..12, default 1
from:<month> the month 1..12 the interval is anchored on, default 1

For example 'day:-1 at:23:30' is the last day of every month at 23:30, and 'weekday:2/tue at:09:00 every:3' is the second Tuesday of every third month at 09:00.

final bool event

Declares the job event-triggered rather than clock-driven.

A stream is not a constant either, so the source is supplied at scan time through [TomScheduledJobs.discover]'s eventSource resolver, keyed by job name. An event job discovered without a resolvable source is a scan-time error, not a job that quietly never fires.

final TomRetryPolicy retry

How failed attempts are retried.

final Duration timeout

How long one attempt may take before it is treated as failed.

final TomMissedWindowPolicy missedWindow

What to do about windows missed while the scheduler was down.

final int catchUpLimit

The most windows [TomMissedWindowPolicy.runAll] will replay.

final bool allowOverlap

Whether a new run may start while a previous one is still in flight.

final bool requestsRecovery

Whether a run interrupted mid-execution may be re-queued.

false by default — see [TomJobDefinition.requestsRecovery]. Set it only on a body that is safe to run twice; a run that was claimed but never started is re-queued either way.

class TomScheduledJobException

class TomScheduledJobException extends TomException

Raised when an annotated job cannot be turned into a [TomJobDefinition].

Always thrown from the scan, never from a firing, and always naming the class at fault — the point of the annotation route is that a malformed declaration stops start-up instead of failing in the small hours.

static List<TomJobDefinition> discover({Stream<Object?>? Function(String)?? eventSource, bool Function(ClassMirror<dynamic>)?? where})

Scans the reflected classes and returns one definition per annotated job.

Validates every declaration before returning any of them, so a start-up that has one bad job registers none of them rather than half of them.

[eventSource] supplies the stream for a job declared event: true, keyed by the job's resolved name; returning null (or omitting the resolver) makes such a job a scan-time error.

[where] narrows the scan to the classes it accepts. The default — every reflected class — is what an application wants; a deployment that ships one binary but runs different jobs per profile filters here rather than registering and then deregistering, and the validation suite uses it to examine one malformed declaration at a time.

static List<TomJobDefinition> registerAll(TomScheduler scheduler, {Stream<Object?>? Function(String)?? eventSource, bool Function(ClassMirror<dynamic>)?? where})

Discovers every annotated job and registers it on [scheduler].

Refuses to overwrite a name [scheduler] already knows: a discovered job silently replacing a hand-written one — or the reverse, depending on start-up order — is exactly the kind of pairing bug the annotation exists to remove. Registration happens only after the whole scan has validated.

Returns the definitions it registered.

static String _nameOf(ClassMirror<dynamic> candidate)

How a class is identified in a scan failure.

The qualified name where there is one — two classes with the same simple name in different libraries are exactly the case worth disambiguating — but a mirror whose library is unnamed reports a bare .ClassName, and leading punctuation in an error message reads like a typo.
