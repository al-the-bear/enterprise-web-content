import 'package:tom_core_kernel/src/tombase/security/oauth_contract.dart';

The wire contract for external-identity login (C-9): the DTOs and the [TomApi] declaration both halves of the framework bind to when a user signs in through an OAuth 2.0 / OpenID Connect provider.

The flow is server-side — a client secret, a token-endpoint call, a linking table — and cannot live here. What has to live here is the part the two halves must agree on: which providers exist, how a client asks for an authorization URI, and what the provider's redirect carries back (G-API-1, G-API-3). The kernel is the framework's contracts package, so declaring the API anywhere else would mean one of the two tiers re-stating it.

The completion is the application's call, not the provider's redirect

The provider redirects a browser, and every deployment's redirectUri names a page of its own application. That page reads code and state off its own query string and calls [tomOAuthCompleteEndpointId] — an ordinary typed POST like any other. Letting the provider redirect straight to the server would answer a browser navigation with a token pair: tokens in the address bar, in history, in the access log, and in the Referer of whatever the page loaded next.

The completion returns a login, not an OAuth result

[tomOAuthCompleteEndpointId] answers with a [TomAuthenticationResult] — the same type /login answers with, carrying the same token pair, the same requires2FA handshake and the same enrolment offer. That is the contract's half of the decision recorded in the server's authentication module readme: an external identity is a way of resolving a principal, and everything after the principal is resolved is the one login path every credential reaches. A distinct "OAuth result" type here would be the first step towards a second token issuer, and the copy that drifts is the one that stops asking for a second factor.

Why the client never names a redirect URI

[TomOAuthAuthorizationRequest] carries the login context (client, locale, organization) and nothing else. Where the provider sends the user back is server configuration, because a redirect target a caller may choose is an open redirect: an attacker who can name it can have the provider deliver a live authorization code to a host they own.

class TomOAuthApiService

abstract class TomOAuthApiService

The typed service interface behind [tomOAuthApi].

The contract's Dart face: the server implements it, and a client that generates or hand-writes a caller implements the same shape. It carries no annotation because the server-side ones (@tomComponent, @TomApiEndpointImplementation) live in tom_core_server and cannot be named here — the same split the rest of the framework's contracts follow.

Properties

String authorizationUri

The provider's authorization endpoint with the flow's parameters applied — client_id, redirect_uri, scope, state and, when the provider supports it, the PKCE code_challenge. The client navigates to it and does nothing else with it.

String state

The opaque handle of the pending authorization.

Returned so a client can correlate the redirect it later observes with the flow it started. It is not a credential: presenting it does not authenticate anything, because completing the flow additionally requires the authorization code the provider issues and the PKCE verifier the server kept.

class TomOAuthAuthorizationRequest

class TomOAuthAuthorizationRequest

The request that starts an authorization-code flow.

Carries the same login context a password [TomAuthenticationMessage] does, minus the credential — because there is no credential yet; that is what the provider is about to establish. The context is captured now rather than at the callback because the redirect arrives as a plain browser navigation that carries none of it: no client id, no locale, no organization. The server stores it with the pending authorization and replays it when the code comes back, so an externally-authenticated session is issued in exactly the organization and locale the login was started in.

class TomOAuthCallbackRequest

class TomOAuthCallbackRequest

What the provider's redirect carried back, forwarded by the application.

Either [code] + [state] (success) or [error] + [errorDescription] (the user declined, the provider refused). Still named for the callback, because that is what these values are — the redirect's query parameters — even though the redirect landed on the application's page and the application is what posts them here. The provider's snake_cased spellings (error_description) are the application's to translate as it reads its own query string; the server sees only this shape.

class TomOAuthProviderDto

class TomOAuthProviderDto

One configured external-identity provider, as a client sees it.

A reflection-first wire DTO (G-DTO): @tomReflector, plain non-final fields, no hand-written serializer. Deliberately thin — a client needs to render a button and post an id back. Issuer URLs, client ids, secrets and scopes are the server's business and are not on the wire.

Constructors

TomOAuthProviderDto.new({String id = '', String displayNameKey = '', String iconKey = ''})

Describes a provider with explicitly chosen keys.

Every parameter is optional and the fields are mutable, because this is a wire DTO: reflection constructs it empty and fills it in (G-DTO-1/2).

TomOAuthProviderDto.scoped(String id)

Describes a provider whose text lives under oauth.<id>.*.

Derives both keys from [id], which is what makes the convention structural rather than a matter of per-provider discipline: adding a provider cannot silently invent a second naming scheme.

Properties

String id

The provider key, as configured under oauth.providers on the server (google, github, acme-sso). What a client posts back in [TomOAuthAuthorizationRequest.providerId].

String displayNameKey

Resource key of the provider's short label ("Sign in with Google").

A key rather than text (G-RES-1): the label is rendered in the user's language, and the server does not know it at configuration time.

String iconKey

Resource key of the icon to render. A key rather than an asset path because the two client tiers (Flutter, web) name their assets differently, and the provider must not have to know which one is asking.

function registerTomOAuthApi

void registerTomOAuthApi()

Registers [tomOAuthApi] with the global [tomRemoteApis] registry.

Idempotent, and called by both halves: a server calls it before mounting the endpoints, a client before building a caller. Registration is explicit rather than implicit in a top-level initializer because a deployment that configures no providers should not carry the API in its registry.
