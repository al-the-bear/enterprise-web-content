The client half of server-stored user preferences (C-13): the typed face an application reads and writes /preferences/* through.

Why the framework owns this

The kernel declares the contract ([tomUserPreferencesApi]) and tom_core_server implements it, but a preference exists to follow a user across devices — which means it is only a capability once a device can reach it. Without a framework client every application writes the four HTTP calls itself: four spellings of the same URIs, four decodings of the same DTO, four chances to read a broken server as "no such preference". That is the same G-DI-3 failure the device store was built to remove, one layer up.

So this class is the counterpart of TomDevicePreferences, and deliberately carries the same method set — all / read / get / getOr / set / remove — over the same [TomUserPreferenceDto] and the same [TomUserPreferenceCodec]. A call site reads identically whichever store it addresses, which is what lets a preference move between them.

Addressed by the contract, not by strings

No URI is written here. Every request is built by [TomApiEndpoint.resolveUri] from the endpoint's own declaration — its method, its path template and its urlParameterMapping — so the address the client calls and the route the server serves are two readings of one declaration rather than two spellings that agree by inspection.

What a miss looks like

The server answers a key the caller has never written with a 404 carrying the error envelope keyed [tomUserPreferencesNotFoundErrorKey] (TomUserPreferencesErrorHandler), and that is the only answer this client reads as absence: [read] and [get] answer null, [getOr] answers its fallback. Every other failure throws, because a deployment whose preference store is unreachable must not be indistinguishable from a user who has set nothing — an application that could not tell them apart would paper the outage over with a default and never learn.

That includes a bare 404. The endpoint pipeline answers a denied or unauthenticated call that way, deliberately indistinguishable from a route that does not exist, so the status alone says only "refused or not there". Read as absence it would hand a signed-out user the defaults; the envelope's key is what separates "you have not set this" from "you may not ask".

Example

final preferences = TomUserPreferencesClient(
  baseUri: Uri.parse('https://api.example.com'),
);

await preferences.set(TomUserPreferenceKeys.theme, 'dark');
final theme = await preferences.getOr(TomUserPreferenceKeys.theme, 'system');

Paired with the device store, the precedence documented on [TomDevicePreferences] applies — the device value wins, and this client is consulted only for a key this device has never written: 

final theme = await device.getPreferred<String>(
  TomUserPreferenceKeys.theme,
  () => preferences.get<String>(TomUserPreferenceKeys.theme),
);

class TomUserPreferencesClient

class TomUserPreferencesClient implements TomUserPreferencesApiService

Typed access to the calling principal's server-stored preferences.

Implements the kernel's [TomUserPreferencesApiService], so the client and the server are two implementations of one interface; the get / getOr / set surface on top of it is the ergonomic face, shaped to match TomDevicePreferences.

Constructors

TomUserPreferencesClient.new({required Uri baseUri, TomServerChannel? channel, Map<String, String> headers = const {}, Map<String, String> Function()?? headerProvider})

Creates a client for the preferences endpoints of the server at [baseUri].

[baseUri] is the server root, not the /preferences path: the API's own uri is part of the contract and is appended from it. A base that already carries a path (an API gateway prefix, say) keeps it.

[channel] is optional; when omitted one is created for [baseUri]'s host and port. Pass an existing channel to share a connection pool with the rest of an application's calls — [close] then leaves it alone, because it belongs to whoever passed it in.

[headers] are sent with every request, and [headerProvider] supplies the ones that must be computed per request — a credential that rotates would otherwise be captured once at construction. Returning an Authorization header from either suppresses the bearer token from [TomBearerAuthentication], so there is one credential on the request rather than two spellings of one.

Methods

Future<List<TomUserPreferenceDto>> all()

Every preference stored for the calling principal, ordered by key, ascending — the order [listPreferences] states, and the same one TomDevicePreferences.all answers in.

Forwarded as received: this client does not re-sort. The order is the server's to produce, off an index that already covers it, and a client that sorted defensively would be spending a sort on every call to hide the one symptom by which a server breaking the contract could be noticed. Where the two faces disagree the store is wrong, and it should be possible to see that.

Unmodifiable, like TomDevicePreferences.all. It is a decoded snapshot of one response, so adding to it would change nothing on the server — and the call site this face exists for, moving a preference between the two stores, is where a caller holds both results at once.

Future<TomUserPreferenceDto?> read(String key)

The preference stored under [key] as stored, or null when the server has never been given one.

Throws a [TomUserPreferencesClientException] keyed preferences.client.rejected for any other failure — including a 404 that does not carry [tomUserPreferencesNotFoundErrorKey], which is a refusal rather than a miss.

Throws a [TomUserPreferenceKeyException] when [key] is not a legal key — see [TomUserPreferenceKeys]. The check is here rather than left to the server because an illegal key does not survive being made into a URI: an empty key resolves to the list endpoint's own URI, so the request the server would answer is not the one this method was asked to make.

Future<T?> get<T extends Object>(String key)

The preference stored under [key], decoded as a [T].

null when the preference does not exist. Throws a [TomUserPreferenceCodecException] when it exists but was written as a different type — see [TomUserPreferenceCodec.decode].

Future<T> getOr<T extends Object>(String key, T fallback)

[get], with [fallback] for a preference that has never been written.

A type mismatch still throws: an unwritten preference is an ordinary state that a default answers, while a preference stored as the wrong type is a bug, and silently answering [fallback] would hide it.

Future<TomUserPreferenceDto> set<T extends Object>(String key, T value)

Writes [value] under [key], replacing any previous value, and returns the stored DTO.

Scalars and DateTimes are encoded by [TomUserPreferenceCodec]; anything else must be a @tomReflector class, which is what makes a preference a typed object rather than a stringly-typed blob.

Future<void> remove(String key)

Deletes the preference stored under [key].

Throws a [TomUserPreferencesClientException] keyed preferences.client.rejected when the server refuses the delete — see [deletePreference].

Returns nothing, where the device store's remove answers a bool. That is not an oversight and not a gap to be filled later: the delete endpoint is idempotent by design — clearing a preference twice is not a client doing anything wrong — so the server does not report whether a row existed, and a bool invented here could only be a second round trip pretending to be an answer.

Future<void> clear()

Deletes every preference stored for the calling principal.

The operation an account reset performs, and one request rather than a loop over [all] and [remove]: the server deletes in a single statement, so there is no half-completed reset to leave behind on a store every device the user owns reads. TomDevicePreferences.clear is the same method for the same reason on the other face: the two stores carry one method set, and this is its entry on this one.

Idempotent and unconditional: a principal holding nothing is cleared, and there is no filter to narrow what goes. Returns nothing — see [clearPreferences] for why the count stays on the server.

Throws a [TomUserPreferencesClientException] keyed preferences.client.rejected when the server refuses.

Future<List<TomUserPreferenceDto>> listPreferences() override
Future<TomUserPreferenceDto> readPreference(TomUserPreferenceKeyRequest request) override

The preference named by [request], or a failure when there is none.

Throws preferences.client.not_found for a miss, because the contract's result type is not nullable. [read] is the same call with the miss expressed as null, and is what an application should use.

Future<TomUserPreferenceDto> writePreference(TomUserPreferenceWriteRequest request) override

Writes the already-encoded preference named by [request].

The key travels in the body and nowhere else — the write endpoint's URI is the bare collection — so no parameters are passed here, and there is no path key that could name a different preference than the body does.

Throws a [TomUserPreferenceKeyException] when the request's key is not a legal key. A DTO is checked here rather than in its constructor because the DTOs are instantiated blank and filled by reflection — a constructor that refused the empty default would refuse every deserialization.

Future<void> deletePreference(TomUserPreferenceKeyRequest request) override

Deletes the preference named by [request].

Throws a [TomUserPreferenceKeyException] when the request's key is not a legal key — including the empty one [TomUserPreferenceKeyRequest]'s own default produces, which would otherwise resolve to the list endpoint's URI and send a DELETE at the collection.

Every non-2xx answer throws, a 404 included. The server's delete is idempotent — a preference that is not there is deleted with a 200 — so a 404 from this endpoint is never "already gone": it is the pipeline's refusal, and reporting it as success would tell the caller a preference was cleared that is still stored.

Future<void> clearPreferences() override

Deletes every preference of the calling principal.

Answers nothing, and asks for nothing. How many preferences went is the server's business: a count on the wire would invite a caller to branch on it, and the only branch it could support — "some were already gone" — is the case the idempotence exists to make uninteresting.

Every non-2xx answer throws, a 404 included. The clear is idempotent, so a 404 from it is never "nothing to clear": it is the pipeline's refusal, and reporting it as success would tell the caller an account was reset that still holds every preference it did.

Future<_PreferencesResponse> _call(TomApiEndpoint<dynamic, dynamic> endpoint, {Map<String, Object?> parameters = const {}, String? body})

Issues [endpoint] against [baseUri] and reads the whole answer.

[parameters] are keyed by request-DTO field name, as [TomApiEndpoint.resolveUri] expects. [body] is the request's JSON text, or null for the methods that carry none.

Map<String, String> _requestHeaders(TomApiEndpoint<dynamic, dynamic> endpoint)

The headers one request carries, with the bearer token resolved last.

A provider that already named an Authorization header wins and the built-in bearer is suppressed: it is answering the same question with better information, and two credentials on one request is exactly the ambiguity this seam exists to remove.

void _requireSuccess(_PreferencesResponse response, {String? key})

Throws unless [response] carries a 2xx status.

Every rejection is preferences.client.rejected; what tells them apart is carried in its parameters — the status, and, when the server answered with its error envelope, the server's own errorKey. That is how a caller tells a write refused for the account's ceiling ([tomUserPreferencesLimitExceededErrorKey], a 409) from a value the server would not store (preferences.encoded.*, a 400) without parsing the body itself.

Static

static bool _carriesAuthorization(Map<String, String> headers)

Whether [headers] already names an Authorization.

Case-insensitively, because HTTP header names are — a caller who wrote authorization meant the same header, and matching only the capitalised spelling would send two.

static bool _reportsAbsence(_PreferencesResponse response)

Whether [response] is the server saying the preference was never written.

A 404 whose body is the error envelope with errorKey [tomUserPreferencesNotFoundErrorKey], and nothing less: a bare 404 is the pipeline refusing the call, and an envelope naming any other key is a different failure that merely shares the status. A body that is not JSON is not an envelope, so it answers false rather than throwing — the caller then reports the response as the rejection it is.

static String? _envelopeErrorKey(_PreferencesResponse response)

The errorKey of the framework error envelope [response] carries, or null when its body is not one — plain text, or JSON of another shape.

static TomServerCallError _callErrorOf(_PreferencesResponse response)

The whole HTTP answer as the kernel's typed failure record.

Built for every rejection rather than only for a framework envelope, because a caller reaching for [TomException.serverCallError] is asking "what did the call do" — and "the gateway answered 502 with HTML" is an answer. [TomServerCallError]'s own constructor reads the envelope when x-tom-error claims one, which is where errorKey, uuid and requestUuid come from; a body that is not one simply leaves them null.

The server's requestUuid is then copied onto the exception, so a client failure names the request the server logged it under. Both sides of one failed call carry the same id, which is the only way the two logs can be read together.

class TomUserPreferencesClientException

class TomUserPreferencesClientException extends TomClientException

A failure raised by the server-preferences client.

The sibling of TomDevicePreferenceException, and a [TomClientException] for the same reason: a caller can tell a preference failure from any other client-side error with one is check. The key is a stable dotted code — preferences.client.not_found, preferences.client.rejected, preferences.client.invalid_response — so callers branch on the code rather than on message text.

A value failure — a type mismatch, unparseable JSON in the preference itself — arrives as the kernel's [TomUserPreferenceCodecException] instead, because it means the same thing in both stores and is already named there.

class _PreferencesResponse

One server answer: the status that says what happened and the text that says what it was.

A pair rather than two futures because the status and the body are read together at every call site, and a TomServerCall can be read only once.
