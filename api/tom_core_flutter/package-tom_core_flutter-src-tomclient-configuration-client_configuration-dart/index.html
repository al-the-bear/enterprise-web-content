class TomBaseClientConfiguration

abstract class TomBaseClientConfiguration extends TomObservable implements TomObserver<TomObservable>

Base class for a client app's machine-scoped configuration holder.

Named for symmetry with TomBaseServerConfiguration (tom_core_server), and the same idea one scope down: a single object that owns every configuration value of one tier, so the values are addressable as a set rather than scattered across whatever module first needed them.

Scope — (client app, machine), and nothing else

A [TomBaseClientConfiguration] holds settings of this install of this app on this machine: the server URL to talk to, a log level, a polling interval, whether the debug overlay is on. There is no user parameter in this class, in the store interface, or in the persisted format — by design. A value that varies per user belongs in one of the two preference holders this package also ships, which have a different lifecycle (they follow the account or the device, and the account one needs a login before it can be read): [TomUserPreferencesClient] for a value that follows the user onto every device, [TomDevicePreferences] for one that stays on this machine. A value that configures the server belongs in TomBaseServerConfiguration. Adding any of them here turns the holder into a junk drawer and quietly breaks the guarantee that reading a client setting never needs a session.

Those three scopes are related rather than merely adjacent: a setting declared [TomOverridableBy.user] or [TomOverridableBy.device] may be shadowed by a preference of the same key, and [TomEffectiveSettings] resolves the chain.

Per-field validation is likewise not this class's job, and nothing else in the module does it either. The type is checked — [coerceSettingValue] throws client_configuration.value.type_mismatch on a raw value that cannot be read as the declared type — but the value never is: a TomSetting<int> stores and serves a refresh interval of -1. There is no hook to add a check either, because [TomSetting]'s constructor is private and settings are created only by the *Setting methods below. Range, format and enum constraints are therefore the caller's, applied after [load] or at the point of use.

Resolution order

A setting's value is, highest precedence first:

0. the environment, for a setting declared with an [TomSetting.envAlias] that [TomClientEnvironment] reports set; 1. the persisted override — what this install last saved; 2. the shipped config-resources value for the key ([TomConfigResourceProvider]); 3. the declared default at the declaration site.

Only layer 1 is persisted. A key the install never changed is re-resolved from layers 2–3 at every start, so shipping a new default in an app update actually reaches installs that never touched that key. Persisting the full value set instead would freeze the shipped defaults at the moment of the first save. Layer 0 is not persisted either, for the opposite reason: it is the operator's value, not the install's, and baking it into the store would outlive the variable being unset.

All four layers produce this install's value. A value belonging to a narrower scope — the user, or the user on this device — lives in a preference store and may shadow the whole stack, but only for a setting whose declaration opens it: see [TomOverridableBy] and [TomEffectiveSettings].

Lifecycle

class AppConfiguration extends TomBaseClientConfiguration {
  AppConfiguration({super.store});

  late final TomSetting<String> serverUrl;
  late final TomSetting<int> refreshSeconds;
  late final TomSetting<bool> darkMode;

  @override
  void declareSettings() {
    serverUrl = stringSetting('client.server.url', 'https://api.example.com');
    refreshSeconds = intSetting('client.refresh.seconds', 60);
    darkMode = boolSetting('client.ui.darkMode', false);
  }
}

final config = AppConfiguration(store: myStore);
await config.load();          // adopt this install's persisted overrides
config.darkMode | true;       // per-field observers fire; so do holder observers
await config.save();          // persist the overrides — and only those

[declareSettings] is called from the constructor, mirroring TomClass.prepareForSelfObservation. It exists because Dart field initialisers cannot call instance methods, so stringSetting(...) cannot appear in a field initialiser — and because it makes the declaration set complete by the end of construction, which is what lets [settings], [save] and [resetAll] be exhaustive rather than "exhaustive so far".

It also fixes the construction order: every baseline is resolved against [TomConfigResourceProvider] before the constructor returns, so the provider must already be installed. Building the holder first throws resources.config_provider.not_installed rather than serving declared defaults that look configured — an application with no configuration bundle installs an empty provider rather than none.

Observation

Both granularities are available and both are live at once:

  • per field — observe the [TomSetting]; it is a [TomObject], so a

TomObservingWidget bound to it rebuilds on that one setting; - whole holder — observe the holder; it observes each of its settings and re-emits, so a single observer sees every change.

Saving is explicit

There is no autosave. Persisting is asynchronous, and a setter that silently starts an unawaited write gives the caller no way to know whether it landed, no way to handle its failure, and a fresh write per keystroke when a settings screen is bound field-by-field. Call [save] when the install's edit is complete.

Future<void> load()

Adopts this install's persisted overrides.

Every declared setting ends up at its persisted override if the store has one and at its baseline if it does not — so load() puts the holder in exactly the state a fresh start would produce, whatever it held before. That makes it idempotent and makes it the right call after an external change to the store.

Observers see one notification for the whole load, not one per setting, because a load is a single event.

Throws client_configuration.store.not_configured when no [store] is wired.

Future<void> save()

Persists the install's overrides — and only those.

A setting sitting at its baseline is not written, and is removed from the store if it was there before; see the class documentation for why storing the full value set would be wrong. Neither is a setting the environment configured — [TomSetting.isOverridden] is false for one, so it never enters the written document, and unsetting the variable later restores the layers below rather than finding the operator's value baked in.

That applies to a persisted value which merely equals the baseline, and the consequence is worth stating: an install cannot pin a setting to the value it sees today. Such a key survives [load] — it is applied, and it is the right value — and is deleted by the next save, after which the setting follows whatever the shipped default becomes. There is no error and no signal; pinning would need a third state per setting (untouched / set-to-baseline / overridden) and a store format able to carry it, which the module does not have.

Keys in the store that this build does not declare are carried forward untouched. A build that has dropped a setting — or an older build during a staged rollout — must not destroy an install's value for a key it simply does not know about.

Carry-forward is seeded by re-reading the store, not from the snapshot [load] took. The snapshot answers a different question — what this store held when this holder started — and the two diverge in two ways that both break the promise above. A holder pointed at a second store would deposit the first store's keys into it while destroying the second's own. And a key written by anyone else since this holder loaded — a second holder over the same location, an external edit — is not in the snapshot, so it would be deleted rather than carried forward, which is precisely the loss this mechanism exists to prevent.

What re-reading does not do is make a store location shareable. The carry-forward covers keys this build does not declare; a key two holders both declare is written from the saving holder's own view, and a holder that has not adopted the other's change holds that key at its baseline — so it writes "no override" over it, sequentially, with no concurrency involved. On top of that, read-then-write is not atomic, so two saves that genuinely overlap lose the earlier reader's change even if both reloaded. Nothing detects either; see the module documentation.

Throws client_configuration.store.not_configured when no [store] is wired.

class TomClientEnvironment

abstract class TomClientEnvironment

Where a setting's [TomSetting.envAlias] is looked up.

A seam, not a test hook — though it is both. dart:io's process environment is the right source on a desktop install and is what [reader] starts as, and it is empty or absent everywhere else: a browser has none, and a mobile app is launched by the OS rather than by a shell. Those platforms have their own answer to "what did the operator configure" — a --dart-define baked at build time, a value fetched at startup, an MDM-delivered payload — and only the app knows which. So the framework reads through one function the app can replace, rather than picking one and calling it the environment. 

TomClientEnvironment.reader = (name) => myLaunchArguments[name];

Replace it before the holder is constructed: settings resolve their environment value at declaration, which happens in the constructor.

class TomSetting

class TomSetting<T> extends TomObject<T>

One observable, addressable client setting.

A [TomSetting] is a [TomObject] — so everything that already works on an observable value works on a setting unchanged: the ~/|/<</call() operators, addObserver, and TomObservingWidget. What it adds is the two pieces of identity a setting has and a plain observable value does not:

  • [key] — the dotted configuration key. This, not the Dart field name, is

the setting's identity: it is what the shipped config resources are keyed by and what the override store persists. Two builds may name the field differently; the key is the contract. - [baseline] — the value this setting has when the install has not overridden it: the shipped config-resources value if the key is present there, otherwise [declaredDefault].

[isOverridden] is therefore simply "current value differs from baseline", and that is exactly the set of values [TomBaseClientConfiguration.save] persists. Nothing else needs to track dirtiness.

Resolved once, at declaration time, from the config resources with [declaredDefault] as the fallback. It deliberately does not track later mutations of the config provider: a setting whose baseline could shift underneath a running app would make [isOverridden] — and therefore what gets persisted — depend on when you asked.

final String? envAlias

The environment variable this setting may also be read from, verbatim, or null when it is not declared with one.

Looked up through [TomClientEnvironment.reader] at declaration time.

final bool isFromEnvironment

Whether [TomClientEnvironment] supplied this setting's value.

An environment-configured setting sits above the install's override: [TomBaseClientConfiguration.load] does not adopt a stored value for it, [TomBaseClientConfiguration.save] never writes it, and [reset] restores the environment's value rather than the [baseline]. The operator has taken the setting out of the install's hands.

It is not enforced against set, because a [TomSetting] is a [TomObject] and taking its setter away would take the observable with it. An in-memory change simply does not survive: nothing persists it and [reset] and a reload put the operator's value back. A settings screen reads this to disable the field, which is what this member is for.

final TomOverridableBy overridableBy

Which narrower client scope may shadow this setting, if any.

Declared here, at the wider scope, and applied by [TomEffectiveSettings.valueOf]. It does not change what [get] answers: this holder stays synchronous and login-free, and a preference store is neither. What it changes is what an effective read returns once a store is in the picture.

A setting that opens itself carries a key both preference stores accept — the declaration validates it against [TomUserPreferenceKeys], because a key the stores would refuse could never be shadowed and the declaration would be a promise nothing can keep.

bool _readsAsBaseline(Object? raw)

Whether [raw] reads as this setting's [baseline].

The store is loosely typed — a 3 may arrive as '3' — so the comparison coerces first. Used by [TomBaseClientConfiguration.hasUnsavedChanges] to recognise a persisted entry that is not an override: [save] does not write one and [isOverridden] does not report one, so a holder that loaded one and was not touched has nothing unsaved.

A value that will not coerce cannot be the baseline, but it also cannot reach here: [TomBaseClientConfiguration.load] throws on it first.

enum TomOverridableBy

enum TomOverridableBy

Which narrower client scope, if any, may shadow a [TomSetting].

A client value lives at one of three scopes, from widest to narrowest: the install (this app on this machine — a [TomSetting]), the user (it follows the account onto any device — a server-stored preference), and the user on this device (a device-stored preference). Shadowing is opt-in and declared at the wider scope: an install setting is scope-pinned unless it says otherwise, so a narrower store that happens to hold the same key cannot silently take a value over.

The value names the narrowest scope permitted, and every scope between the setting and that one is permitted too — so [device] opens [user] as well. [TomEffectiveSettings] is what applies the declaration.

[none] is the arm every security and infrastructure setting keeps, and it is the default on the declaration methods. That is not the fail-safe rule weakened: none is the closed arm, so a setting whose author said nothing about shadowing is pinned, and opening one is the deliberate act.

Values

none

Scope-pinned: neither preference store may shadow this setting.

user

A server-stored user preference under the same key may shadow it.

device

A device-stored preference may shadow it — and so may a user one, which lies between the two.

function coerceSettingValue

T coerceSettingValue<T>(String key, Object? raw)

Reads [raw] as a [T], or throws.

Both external sources are loosely typed — a JSON store round-trips int/double/bool/String, and a YAML config resource may well spell a double as 30 or a port as "8080". Rejecting those outright would make perfectly reasonable config files fail, so this accepts the widenings that have exactly one sensible reading:

  • the exact type, unchanged;
  • int → double (30 reads as 30.0);
  • String → int / double / bool, when it parses.

Anything else throws client_configuration.value.type_mismatch naming the key — a silent fallback to the default would hide a typo in a config file behind behaviour that merely looks like "the default was used".

Note there is deliberately no Object → String leg: accepting anything via toString() would make a mis-typed key impossible to detect.
