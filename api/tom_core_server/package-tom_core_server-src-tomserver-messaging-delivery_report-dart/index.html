Delivery reports: what a carrier says about a message after it accepted it, and how that answer is matched back to the message it concerns.

The gap this closes

A transport's receipt records that the far side took responsibility, and for SMS and email that is the beginning of delivery rather than the end. A gateway answers 202 and hands back an id; the handset is reached, or is not, minutes or hours later, and the carrier says so on a callback. [TomDeliveryReceipt.remoteId] exists precisely so that callback can be matched to the message — every transport that has an id to give fills it in — and nothing read it back. So the module could report that a message was paid for and never that it arrived.

Three pieces, and why they are separate

PieceWhat it doesWhy it is not part of the next one
[TomDeliveryReportProtocol] Maps a carrier's callback body to a [TomDeliveryReport] The wire shape is a vendor's; the correlation is not
[TomDeliveryReportStore] Remembers which message a remoteId belongs to, and the last state reported Durable and query-by-id; a protocol is pure
TomDeliveryReportService Receives the callback over HTTP Needs the endpoints pipeline; the other two do not

The split is what lets a deployment whose gateway offers no callback still use the store — recording the correlation costs nothing and a support engineer answering "was this delivered" can at least resolve an id — and lets a deployment that receives reports some other way (a file drop, a queue consumer) reuse the protocol and the store without the endpoint.

Why an index rather than the outbox's job store

The outbox already writes a run per message, so the job store looks like the natural place to resolve one. It is not: [TomJobStore] is addressed by run id and offers no lookup by any other field, so remoteId → message is a full scan of every run ever queued. The index is its own small table, with the same memory-plus-SQL pair every other store in the framework has.

class TomDeliveryReportProtocol

abstract class TomDeliveryReportProtocol

Turns a carrier's callback into a [TomDeliveryReport].

The same seam [TomSmsGatewayProtocol] is, for the same reason: the callback shape is a vendor's and changes when the vendor changes, so it is configuration rather than code. A protocol is pure — it is handed the decoded body and the query parameters and returns a value — which is what makes every carrier's mapping testable without an HTTP server.

Constructors

const TomDeliveryReportProtocol.new()

Creates a protocol.

Methods

List<TomDeliveryReport> decode(TomDeliveryCallback callback)

The reports carried by one callback.

A list rather than one report because carriers batch: several gateways post an array of statuses in a single call, and a protocol that could only answer one would make the endpoint drop the rest. A callback carrying a single status answers a one-element list.

Returns an empty list for a body this protocol cannot read, which the endpoint answers 400 for. Throwing would be the other option and is worse: a carrier retries a 500 and gives up on a 400, so a malformed body has to be refused rather than deferred.

Methods

Future<void> remember(TomDeliveryCorrelation correlation)

Records that [correlation]'s message was accepted under its remote id.

Replaces any row for the same id. A carrier re-using an id across messages would be a carrier that cannot be correlated at all, so the later message is the one worth keeping.

Future<TomDeliveryCorrelation?> messageOf(String remoteId)

The correlation for [remoteId], or null when none was remembered.

Future<TomDeliveryCorrelation?> record(TomDeliveryReport report)

Applies [report] to the correlation it names and returns the updated row, or null when nothing was remembered under that id.

A null is not an error: a report can arrive for a message this node never sent (another deployment sharing a gateway account), or after the correlation was purged. The caller decides what to do about it, and the endpoint answers 404 so a carrier's own dashboard shows the mismatch.

Future<int> purgeSentBefore(DateTime before)

Drops correlations for messages sent before [before], answering how many went.

A correlation index that never forgets grows with every message ever sent. How long to keep it is a deployment's decision — it is a delivery audit trail — so nothing purges automatically, exactly as [TomMessageOutbox.purgeFinished] leaves the same decision open.

enum TomDeliveryState

enum TomDeliveryState

What became of a message after the far side accepted it.

Distinct from [TomDeliveryOutcome], and the distinction is the whole point: an outcome is what this attempt achieved — the gateway took it, refused it, or was unreachable — while a state is what the carrier did with it afterwards. A message can be TomDeliveryOutcome.delivered and [TomDeliveryState.failed]: accepted for delivery, and then not delivered.

Values

delivered

The carrier says it reached the recipient.

failed

The carrier says it did not, and will not try again.

expired

The carrier gave up after its own retry window — a handset switched off for a day, a mailbox that stayed over quota. Separated from [failed] because the remedy differs: an expiry is worth re-sending later, a failure is an address to stop using.

unknown

A report arrived and its state was not one this module recognises.

Kept rather than dropped: the report happened, and an operator reading a row that says unknown with the carrier's own word in detail learns more than one that says nothing. It is also the value a protocol maps an unmapped code to, which is what keeps a new carrier status from being silently read as success.
