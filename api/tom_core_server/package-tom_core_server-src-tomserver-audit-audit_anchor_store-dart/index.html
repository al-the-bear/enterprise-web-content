Where published audit anchors are kept, and the scheduler that publishes them.

The store is the part the framework cannot supply

An anchor is only worth as much as the store's independence from the server it attests to. A store the audited process can rewrite is not an anchor store; it is a second copy of the same claim, and an attacker who rewrote the trail rewrites it too. So the interesting implementations of [TomAuditAnchorStore] are the ones this package cannot ship — an object store with versioning and a deny-delete policy, a WORM volume, a countersigning service, another organisation's inbox.

What ships here is the seam ([TomAuditAnchorStore]) plus two implementations that are honest about what they are: [TomMemoryAuditAnchorStore] for tests, and [TomFileAuditAnchorStore] for a directory that the deployment has arranged to be outside the server's reach — a read-only-to-the-app mount, a share the process may append to and nothing more. A file store in the application's own writable tree provides no anchoring guarantee whatever.

No external store ships in this package, and none will. Not an omission waiting to be filled: an S3 store's guarantee is not in its code but in the bucket's object-lock mode, its retention period and a credential that cannot delete — none of which the class can see, so TomS3AuditAnchorStore would be a name that reads like a guarantee over configuration that may supply none. The seam is the deliverable; a deployment implements [TomAuditAnchorStore] against whatever it has arranged, in its own package, where the arrangement and the code sit together.

Note what is not here either: a SQL anchor store. Anchoring the trail into the same database that holds it would be ceremony without a guarantee — one credential, one blast radius. doc/audit.md says the same thing at length.

The posture is declared, and never believed

Because the framework cannot check independence, it does the next thing: [TomAuditAnchorStore.independentOfServer] makes the posture a stated fact that defaults to false, so a deployment that never thought about it reads as "not independent" rather than as nothing at all. Without it a dashboard says anchored over anchors as rewritable as the trail, which is worse than saying nothing.

This is not the config flag that pretends. A flag pretends when something acts on it — when a status turns green because a boolean said so. Nothing does: [TomAuditAnchorPublisher.describe] prints it and TomAuditAnchorReport carries it, and isClean is computed without ever looking at it. It is reported, never trusted.

class TomAuditAnchorPublisher

class TomAuditAnchorPublisher implements TomClosable

Publishes anchors for a sink's chain on a schedule.

Why this is not a TomScheduler job

The scheduler exists to run a job once across the cluster, which is exactly wrong here. Each node keeps its own chain — the chain is per [writer] precisely so that several nodes may append to one table — so each node must anchor its own head. A cluster-single-fire publisher would anchor one node and leave the rest unanchored, which is worse than not anchoring at all because the dashboard would say it was covered.

Why every tick publishes, even when nothing was written

An anchor over an unchanged head is not redundant: it says the head was still this at time T, which narrows when a later divergence must have happened. Anchors are a couple of hundred bytes; an hourly publisher costs about two megabytes a year, and the alternative — suppressing duplicates — buys that back by discarding the evidence that bounds the attack window.

Methods

String describe()

One line naming the arrangement, for a start-up log.

Reports rather than reassures. A deployment anchoring into a directory it can itself rewrite has a copy of the head hash, not an anchor, and that is something to read off the boot output rather than to discover during an investigation — so the line says which it is, in words, instead of printing a boolean whose polarity a reader has to remember.

The posture comes from [TomAuditAnchorStore.independentOfServer], which the deployment declares and nothing verifies. Printing it is the whole of what the framework does with it.

Future<void> start()

Begins publishing every [interval], starting with one immediately.

The immediate publication matters: a process that starts, is compromised and is killed inside one interval would otherwise never anchor at all, and the gap would be exactly the interesting one. Refuses a closed publisher, and does so through [publishNow] rather than with a check of its own: the immediate publication happens before the timer is armed, so that one guard already covers this path. A second copy here would be a second wording of the same rule with nothing keeping the two in step.

void stop()

Stops the schedule. [publishNow] still works.

Future<TomAuditAnchor> publishNow()

Captures the sink's position and publishes it, returning the anchor.

Throws when the store refuses — a caller that asked for a publication is entitled to learn that it did not happen. The scheduled path swallows and logs instead; see [_tick].

Also throws once the publisher is closed. This is the single choke point every publication passes through — [start] and [_tick] both come here — so the guard sits here rather than being restated at each entry point: an anchor is a claim that this process was watching the chain at that moment, and a publisher that has announced it stopped is no longer in a position to make one.

Future<void> _tick()

The scheduled publication: never throws into the timer.

A store outage must not take the server down, but it must not be silent either — an unanchored chain that nobody was told about is the worst of both worlds, so the failure is logged at error level every time it happens.

Future<void> close() override

Publishes a final anchor, then closes.

The last anchor of a graceful shutdown is the one that pins the chain's final head; without it every entry written since the last tick is left unanchored. This is [TomClosable]'s method, so a publisher registered with the shutdown cleanup delivers that anchor before the shutdown moves on. Register it after the sink it anchors: closables close in registration order, so the sink drains its queue first and the final anchor pins the head the drain left.

The timer is stopped before the final anchor is taken, so a scheduled tick cannot interleave and leave the last word to a publication the caller did not ask for.

A store failure is thrown, unlike the scheduled path which only logs: a caller that asked for a publication is entitled to learn it did not happen. The publisher is closed either way — a shutdown that left the timer running because the store was down would be a process that does not exit.

Idempotent: every call is handed the same close. Shutdown paths run twice more often than anyone plans for, and a second final anchor would be a second claim about the same head from a publisher that had already stopped.

class TomAuditAnchorStore

abstract class TomAuditAnchorStore implements TomClosable

An append-only archive of published anchors.

Reading is offered because verification needs it, but a store is free to make reads expensive or to serve them from a different credential than the one that appends: the append path is what runs on the audited server, and it wants the narrowest possible permission.

Future<void> append(TomAuditAnchor anchor)

Appends [anchor]. Must throw rather than silently drop.

Fail-loud for the same reason [TomAuditSink.write] is: a publisher that cannot tell a successful publication from a swallowed error would let a chain run unanchored while reporting that it was anchored.

Future<List<TomAuditAnchor>> read(String writer)

Every stored anchor for [writer], oldest first.

Only that writer's. An implementation that groups anchors by some derivation of the name — a file per writer, a partition key — must still filter on the writer recorded in each anchor, because such derivations are rarely injective and the caller cannot see where the grouping put things. Anchors from another chain are worse than no anchor at all: they make [latest] answer the routine check with a position that belongs to a different trail.

Future<TomAuditAnchor?> latest(String writer)

The most recently published anchor for [writer], or null.

The one a routine check uses: it pins the furthest position that can be verified, and every older anchor is implied by it as long as the chain between them verifies.

FutureOr<void> close() override

Releases whatever the store holds; nothing, by default.

class TomFileAuditAnchorStore

class TomFileAuditAnchorStore extends TomAuditAnchorStore

A JSON-Lines anchor store, one file per writer, append-only.

The format is the same as the file audit sink's and for the same reason: appending a line is the one file operation that cannot damage what came before it. Files are never rotated — anchors are small and their whole value is that the old ones survive.

String description

Methods

File fileFor(String writer)

The file holding [writer]'s anchors.

The writer name is sanitised into the file name rather than trusted: it reaches this far from configuration, and a writer called ../../etc must produce a strange file name, not a write outside [directory].

The mapping is deliberately not injective — node/a and node_a name the same file — and [read] is written knowing it. Making it injective would mean encoding the original name into the file name (escaping, or a hash suffix), which buys a tidier directory listing at the cost of file names an operator can no longer match to a node by eye. The store already records the writer inside every line, so the file name does not have to carry that weight.

Future<void> append(TomAuditAnchor anchor) override
Future<List<TomAuditAnchor>> read(String writer) override

Every stored anchor for [writer], oldest first.

Filtered by the writer recorded in each anchor, not by the file it was found in, because [fileFor] is lossy: two writer names can share one file and the file therefore holds two chains. Returning both would mean [latest] hands the routine check an anchor describing a different trail — which reads as tampering on a healthy chain when the foreign position is ahead, and, when it is behind the retained window, as beforeRetention: no finding at all, so a genuine rewrite passes the check unexamined.

The filter is applied after parsing, and that ordering is load-bearing. Matching the writer in the raw text first would be faster and would skip the malformed lines that do not look like ours — but a line too damaged to parse is a line too damaged to attribute, and the archive's whole claim is that its contents cannot be edited. Every line is parsed so that every line is checked.
