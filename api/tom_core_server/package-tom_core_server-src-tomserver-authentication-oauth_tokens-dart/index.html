The provider's own tokens — delegated authorization, not authentication.

The framework's position, stated once

By default the framework keeps nothing. A login exchanges an authorization code, reads the claims it needs to identify the user, and lets the provider's access_token and refresh_token fall out of scope with the request. That is the correct default and not an omission: the framework mints its own session, so a provider credential retained after the login is a credential nobody uses — and one whose compromise reaches beyond this deployment, because a refresh token is a long-lived key to a third party that this deployment can neither revoke nor observe being used.

A deployment that genuinely needs delegated access opts in, per provider, and then the framework does the holding. "Read the user's calendar", "list their repositories", "send mail as them" all need a live provider access token long after the login, and there is no way to have one without keeping the refresh token that mints it. The choice is therefore not whether the credential exists but who holds it, and the honest answer is that a framework which stops at "we keep nothing" pushes three hard problems onto every application at once: encryption at rest, retention tied to the identity link, and refresh. The third is the dangerous one — an application left to solve it reaches for the login path, because that is the code it can see that already talks to the token endpoint, and a second login path that mints sessions on a background refresh is exactly the drift the C-9 seam exists to prevent.

So the position has two halves, and both are load-bearing:

  • Nothing is stored unless [TomOAuthProviderConfig.storeTokens] is true for

the provider. A deployment that wants "Sign in with …" acquires no third-party credential, ever, and does not have to know this library exists. When it is* stored, it is stored the way a credential must be: encrypted with the framework's existing asymmetric primitive ([TomJwtConfiguration.encrypt] — the same one behind a 2FA enrolment secret), keyed by the same (issuer, subject) pair as the identity link, and deleted when that link is deleted.

Refreshing lives on [TomOAuthFlow] and nowhere else. It is not a login: it consults no [TomAuthenticationService], asks no 2FA policy and produces no session. See [TomOAuthFlow.accessTokenFor].

What is not encrypted, and why that is deliberate

[TomExternalIdentityToken] keeps token_scope, obtained_at and expires_at as ordinary columns beside the encrypted blob. They are not secret — knowing that a grant covers calendar.readonly and expired last Tuesday lets nobody call anything — and they are exactly what an operator needs to answer "is this grant live, and what does it cover?" without the private key. Putting them only inside the ciphertext would make a routine operational question require the one key that must never leave the server.

The authoritative expiry is nonetheless the one inside the payload: the column is a projection for humans, and nothing in this library decides anything from it.

class TomExternalIdentityToken

class TomExternalIdentityToken

The persisted form of one [TomOAuthTokenGrant] — a row of tom_external_identity_token.

A table of its own rather than three more columns on tom_external_identity, which was the tempting shape because it makes the cascade automatic. Two things decided against it. The link row is a value that travels: [TomExternalIdentityStore.identitiesOf] hands it to an account-settings page, and a credential riding along on that listing is a leak waiting for the first serialiser that does not know to exclude it. And the two stores are separate beans precisely so a deployment can substitute one without the other — putting the credential on the link row would have made holding tokens conditional on also using the framework's link table.

[TomOAuthTokenGrant] is not mapped column by column. What is stored is [tokenData] — the grant's JSON, encrypted; see [TomPersistentOAuthTokenStore] for the scheme. The three plain columns beside it are the operator projection, not the source of truth.

class TomOAuthTokenGrant

class TomOAuthTokenGrant

One token grant as a provider issued it.

A value rather than the raw response map, for the reason [TomOAuthCredential] is one: expires_in is a duration from the moment of the response and becomes meaningless the instant it is stored, so something has to resolve it against a clock exactly once. Doing that at the boundary — here — means nothing downstream has to know when the response arrived.

Records a grant. Both instants are normalised to UTC, because the value crosses a storage boundary and a local-time instant read back on a server in another zone is silently wrong.

factory TomOAuthTokenGrant.fromTokenResponse(Map<String, Object?> response, {TomOAuthTokenGrant? previous, DateTime? now})

Reads a grant from a provider's token-endpoint [response].

[previous] carries a refresh over: RFC 6749 §6 lets a provider omit refresh_token from a refresh response, meaning keep using the one you have, and a reader that took the omission literally would discard the long-lived credential on the first refresh and work perfectly until the access token expired.

A grant with no declared lifetime is never expired — the provider said nothing, and guessing a lifetime would throw away a working token.

bool expiresWithin(Duration margin, [DateTime? now])

Whether [accessToken] expires within [margin] of [now].

The margin is the point: a token that expires in two seconds is useless to a caller about to make a request over a slow link, so "is it still valid?" is the wrong question and "will it still be valid when it arrives?" is the right one.

class TomOAuthTokenStore

abstract class TomOAuthTokenStore

Where a provider's tokens live, keyed by the identity they were granted for.

Keyed on (issuer, subject) — the identity link's unique key — and not on a local username, for the reason the link itself is not: a user may hold two grants from two providers, and a local account is not what a provider issued against.

An interface for the same reason [TomExternalIdentityStore] is one, and separate from it for a reason worth stating: a deployment may keep its identity links in a table of its own and still want the framework to hold the credentials properly, or keep the links here and refuse to hold credentials at all. Folding token storage into the link store would have made those two choices one choice.

class TomPersistentOAuthTokenStore

class TomPersistentOAuthTokenStore implements TomOAuthTokenStore

A [TomOAuthTokenStore] over tom_external_identity_token, with the grant encrypted at rest.

The encryption scheme, and why this one

The grant is JSON-encoded and passed through [TomJwtConfiguration.encrypt] — RSA-OAEP, block-chained, base64-wrapped for a TEXT column — and read back through the inverse. It is the framework's existing at-rest asymmetric primitive, the same one behind a 2FA enrolment secret and a token's encrypted claims section, so a deployment that has provisioned real keys has provisioned these keys and one that has not gets the same loud dummy-key warning here as everywhere else.

A provider refresh token is the most dangerous thing this framework ever writes to a database. A password hash resists an offline attack; a 2FA secret is confined to this deployment's logins. A refresh token is a live, bearer credential at a third party, useful to whoever holds it, valid long after the session that produced it, and revocable only by the user noticing. Storing it in the clear would make a database backup a set of keys to other people's mail.

[cipher] is a constructor argument for the reason [TomPersistent2FAEnrolmentStore] takes one: a deployment may want these long-lived secrets under a different key pair from its frequently rotated signing key. Unset, it follows [TomJwtConfiguration.defaultSignConfiguration] at call time, so installing production keys after boot is obeyed.
