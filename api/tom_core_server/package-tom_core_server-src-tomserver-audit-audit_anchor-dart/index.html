External anchoring of the audit chain head — what turns tamper-evidence into something an attacker with full write access cannot quietly repair.

The gap the chain leaves

Each entry hashes its predecessor, so editing, removing or reordering one entry breaks every link after it and [verifyAuditChain] says so. That defeats accident and casual malice, which is most of what a trail is for.

It does not defeat an attacker who can rewrite the whole trail. Having changed an entry they recompute every hash from that point onward, and the result verifies perfectly — because the chain proves only internal consistency, and internal consistency is a property a forger can restore. The same applies, even more cheaply, to deleting entries from the end: a truncated chain is a valid chain.

The missing ingredient is the standard one. The head hash must be recorded somewhere the attacker does not control, at a moment they cannot revisit. Then a rewrite is no longer invisible: the rewritten chain has a different hash at the anchored position, and the recorded one contradicts it.

What an anchor is

A [TomAuditAnchor] is a three-part claim — chain writer had entryCount entries whose head was headHash, at createdAt — optionally signed. It is published on a schedule by [TomAuditAnchorPublisher] into a [TomAuditAnchorStore], and checked later by [verifyAgainstAnchor].

Signing and publication defend against different adversaries

Neither half is sufficient, and it is worth being exact about which is which rather than letting a signature imply a guarantee it does not give:

  • Publication — writing the anchor somewhere the server cannot reach

afterwards — is what stops the server from revising its own history. Without it, an attacker who owns the server owns the anchors too and rewrites both. A signature is what stops whoever holds the store* from inventing an anchor the server never issued. Without it, a compromised archive can manufacture a divergence, or launder one away.

So a signing key held on the same server it attests to adds nothing against server compromise — it defends the store, not the chain. The guarantee this module delivers is exactly: given an anchor that reached a store the attacker cannot rewrite, a wholesale rewrite or a truncation of the chain is detectable. Where that store lives is a deployment decision, and the framework deliberately does not pretend to make it — see doc/audit.md § "Tamper Evidence, and Tamper Proofing".

Positions, not offsets

An anchor is a claim about a position, so the chain has to be able to state positions that survive retention. That is what [TomAuditEntry.index] is for: once a prefix has been pruned, an entry's offset in what remains is no longer its place in the chain, and a check that confused the two would report tampering on every retention pass.

Checks the signature on an anchor.

Constructors

TomAuditAnchorVerifier.new()

Methods

bool verify(TomAuditAnchor anchor)

Whether [anchor] carries a valid signature from a key this verifier knows.

An unsigned anchor, or one signed by an unknown key, is false: the verifier's job is to say whether the anchor can be relied on, and neither of those can.

Implementations must not throw. The input is an anchor that may have been tampered with — that is the situation the verifier exists for — so malformed key ids, signatures and payloads are ordinary traffic, not programming errors, and the caller's only two useful answers are true and false. [verifyAgainstAnchor] enforces this at the seam rather than trusting it, because implementations legitimately leave the process and an expired HSM session is not something it can rule out; but an implementation that relies on being caught reports every one of its own failures as an unexplained bad signature.

enum TomAuditAnchorStatus

enum TomAuditAnchorStatus

How a chain stands relative to an anchor.

Values

matched

The chain is intact and ends exactly where the anchor says it did.

extended

The chain is intact, agrees with the anchor at the anchored position, and has grown since. The ordinary state of a live trail.

beforeRetention

The chain is intact but the anchored position has been pruned away, so there is nothing left to compare. Inconclusive rather than clean: a deployment that does not prune should treat this as a finding.

truncated

The chain is intact but stops short of the anchored position: entries the anchor counted are no longer there.

Truncation is the attack a hash chain is blind to — lopping entries off the end leaves a perfectly valid chain — and this status is the only thing that sees it.

diverged

The chain is intact but the entry at the anchored position hashes differently from what the anchor recorded.

The wholesale-rewrite signal, and the point of the whole mechanism. An attacker who edited an entry and recomputed every hash after it produces a chain that verifies and an anchor that does not match.

chainBroken

The chain fails its own verification, so the anchor was not consulted. A partial edit — what the chain alone already catches.

signatureInvalid

The anchor's signature is missing, unknown or wrong, so the anchor itself cannot be relied on and nothing was concluded from it.

writerMismatch

The anchor describes a different chain than the entries do.

function verifyAgainstAnchor

TomAuditAnchorVerification verifyAgainstAnchor(Iterable<TomAuditEntry> entries, TomAuditAnchor anchor, {String? writer, TomAuditAnchorVerifier? verifier})

Checks that [entries] are consistent with [anchor].

[entries] may be a suffix — retention prunes from the front — which is why every comparison goes through [TomAuditEntry.index] rather than through an entry's offset in the list.

The checks run in a fixed order — writer, then signature, then chain validity, then position — and that order is most specific answer first. Several of these conditions usually fail together: compare a window against an anchor for a different chain and the chain check fails too, because the hashes were never meant to line up. Reporting the most specific one names the mistake the caller actually made. A caller told chainBroken when the real problem is that they passed the wrong writer goes looking for tampering in a trail that is intact.

The chain verification itself is computed up front, before any of these checks, and is reported on [TomAuditAnchorVerification.chain] whichever one answers — so short-circuiting on a more specific status never costs the caller the chain result, only its precedence.

Pass [writer] to assert the entries really are the chain the anchor names; pass [verifier] to require the anchor's signature. Omitting [verifier] checks the position only, which is the honest thing to do for an unsigned anchor taken from a store that is itself trusted.
