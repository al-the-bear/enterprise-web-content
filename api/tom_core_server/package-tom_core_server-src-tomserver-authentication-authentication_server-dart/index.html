class TomAuthenticationAdaptor

class TomAuthenticationAdaptor

Marks a class as an authentication adaptor and constrains which login flows it participates in.

[guestOnly] restricts the adaptor to guest logins; [userOnly] restricts it to authenticated-user logins. Leaving both false (the default) makes the adaptor eligible for either flow. The annotation is reflection-discoverable, so a runtime can enumerate the registered adaptors and route a login to the right one.

class TomAuthenticationData

class TomAuthenticationData

The data carried into a single authentication attempt.

A [TomAuthenticationServer] builds this from an incoming TomAuthenticationMessage and passes it to the configured [TomAuthenticationService]. It identifies what is being logged into (organization / application / process / client) and who ([username]), plus the credential ([key], e.g. the password) and the client locale (language / country / timezone). The fields are mutable so a service can enrich them while resolving the login.

class TomAuthenticationServer

class TomAuthenticationServer

Orchestrates the server-side login flow and issues JWT tokens.

A server endpoint subclasses this and exposes [authenticateGuest] / [authenticatePass1] / [authenticatePass2] as HTTP endpoints. Each takes a TomAuthenticationMessage (the wire request), delegates credential checking to the configured [TomAuthenticationService], and — on success — encodes the resulting principal into two JWTs in the returned [TomAuthenticationResult]: an authentication token (public claims) and an authorization token (public claims plus the encrypted access-control payload).

Which service is used is selected per flow via the static [globalSettingGuestAuthenticationService] / [globalSettingUserAuthenticationService]; the JWT issuer is [globalSettingJwtOrganization].

Future<TomAuthenticationResult> authenticatePass2(TomAuthenticationMessage m, {TomClientJwtToken? challengeToken})

Second authentication pass: answers the challenge issued by [authenticatePass1] and, on success, returns the completed token pair.

The submitted factor travels in [TomAuthenticationMessage.password] — the message's credential slot — and the challenge itself is recovered from the interim token the client presents as its bearer, so no field had to be added to either wire type and no server-side pending-login record exists. [challengeToken] overrides that lookup; it defaults to the request zone's token, and tests pass one explicitly to run the pass without a zone.

Outcomes

  • Accepted — a result whose token pair is exactly what a 2FA-free login

would have produced for this user: same claims, requires2FA cleared. - Wrong answer, attempts left — a result carrying login.error.2fa.invalid-code and a re-issued interim token with the attempt counter advanced. The client retries with that token. - Wrong answer, attempts exhausted — login.error.2fa.attempts-exhausted and no token. That chain of tokens is burned; the client must restart at pass 1. - Lapsed or absent challenge — login.error.2fa.expired / login.error.2fa.no-challenge, likewise with no token.

What the attempt counter does and does not bound

The counter lives in the token and advances only along the chain of re-issued tokens. A stateless server holds no record of which interim tokens it has already answered, so it cannot tell a replay of an earlier token in the chain from the original presentation of it — and an earlier token is still within its validity and still carries its lower count.

So the counter bounds a cooperative client (and gives a UI its "2 tries left"); it is not by itself a brute-force defence.

What closes that is one recorded fact per token: this one has been answered. [Tom2FAAttemptStore] holds it, and this pass consults it before asking the mechanism anything, so each token in the chain is answerable exactly once and the chain admits exactly [Tom2FAChallenge.attemptsAllowed] guesses however the attacker orders it. A replay is refused with login.error.2fa.challenge-already-answered — including a replay of a correct answer, so one interim token cannot mint two sessions.

The store is resolved rather than required: [Tom2FAMemoryAttemptStore] is the default and is per process, so a cluster bounds per node until a shared store is installed. The challenge's own short [Tom2FAChallengeSpec.validity] still bounds the chain in time on top of that.

Future<TomAuthenticationResult> authenticateUser(TomAuthenticationMessage m, bool guestLogin)

Runs a login: builds [TomAuthenticationData] from the message, delegates to the guest or user service per [guestLogin], and encodes the principal into the authentication/authorization JWTs of the returned result.

Whether a second factor is owed is [Tom2FAPolicy]'s decision, not a field read: the resolved policy is asked once, here, and anything but [Tom2FARequirement.disabled] takes the login down the challenge path. The mechanism's adaptor issues a challenge and the returned result carries an interim token plus [TomAuthenticationResult.requires2FA], to be completed by [authenticatePass2].

The four shapes a deployment can be in

PolicyUser has a usable factorOutcome
disabled—tokens, no mention of 2FA
required / optional yes interim token + challenge, answered by [authenticatePass2]
required no interim token + enrolment offer, answered by [beginTwoFactorEnrolment]
optional (or required with grace left) no the same offer, additionally declinable via [skipTwoFactorEnrolment]

"Has a usable factor" is [Tom2FAEnrolmentStore]'s answer, narrowed to the mechanisms the policy permits. A deployment that installed no store keeps the pre-enrolment behaviour exactly — it is challenged for its factor, and the adaptor remains the only authority on whether the user has one — because there would be nowhere to record an enrolment, and offering one that could not be saved would be a lie.

A [TomLoginException] yields a failed result carrying its key; any other error yields a "login.error.unknown" result.

Future<TomAuthenticationResult> authenticateExternal(TomAuthenticationMessage m, Object credential)

Authenticates a login whose credential was established by an external identity provider, and completes it exactly as a password login completes.

[credential] travels in [TomAuthenticationData.key] — the slot that carries a password for a password login, typed Object? for precisely this reason — and is verified by the configured [globalSettingUserAuthenticationService], which a deployment offering external identity wraps in a TomOAuthAuthenticationService. This method therefore adds no second way to authenticate: it hands a differently shaped credential to the same contract.

What it deliberately does not do is decide anything about the resulting session. The 2FA policy, the enrolment offer, the stored-timezone resolution and the claim set all come from [_completeLogin], the same continuation [authenticateUser] reaches — so an externally authenticated principal is challenged for its second factor and issued exactly the claims a password login would have produced for it. See the module readme: the day this method issues its own tokens, the two copies start to drift, and the copy that drifts is the one that stops asking for a second factor.

Future<TomAuthenticationResult> _completeLogin(TomAuthenticationInfo authInfo, TomAuthenticationMessage m)

Everything that happens after a credential has been verified: the 2FA policy decision, the challenge-or-enrolment branch, and token issuance.

Extracted so that there is exactly one of it. [authenticateUser] and [authenticateExternal] resolve a principal by different means and then join here; nothing below this line knows or asks which of them called it, so a third way of resolving a principal acquires the whole of this behaviour by calling it rather than by agreeing with it.

Exceptions propagate: both callers already wrap their own resolution step in the try that turns a [TomLoginException] into a failed result, and a second catch here would make the failure path two places as well.

Future<TomAuthenticationResult> beginTwoFactorEnrolment(TomAuthenticationMessage m, {TomClientJwtToken? enrolmentToken})

Enrolment pass 1: begins setting up the mechanism the user chose.

The chosen mechanism key travels in [TomAuthenticationMessage.password] — the message's one payload slot, used here exactly as [authenticatePass2] uses it for the submitted code. Every pass in this flow carries a single user-supplied value, and giving each its own wire field would say the passes are more different than they are.

The offer token is recovered from the interim token the client presents, as everywhere else in this flow; [enrolmentToken] overrides that lookup for tests running without a request zone.

Returns an interim token whose public claims carry the mechanism's [Tom2FAEnrolmentOffer.clientData] — for TOTP, the secret and the otpauth:// URI the user scans — and whose encrypted section carries the whole offer, so [completeTwoFactorEnrolment] can check the typed code against material the client could not have edited.

Refuses a mechanism that was not in the offer this token was issued with: the authority for what may be enrolled is the list the server named, never the key the client sends back.

Future<TomAuthenticationResult> completeTwoFactorEnrolment(TomAuthenticationMessage m, {TomClientJwtToken? enrolmentToken})

Enrolment pass 2: confirms the offer and completes the login.

The typed confirmation travels in [TomAuthenticationMessage.password].

On success the factor is written to the [Tom2FAEnrolmentStore] and the full token pair is issued immediately, with no further challenge. A user who has just derived a code from the secret they were handed has demonstrated possession of the factor; challenging them for a second code a moment later would prove nothing that this pass has not already proved.

A wrong code stores nothing and returns a retry — the same offer with one attempt spent, exactly as [authenticatePass2] does for a wrong challenge answer — until [Tom2FAEnrolmentOffer.attemptsAllowed] is exhausted. And as there, the count alone would bound only a cooperative client, so the offer token is spent against [Tom2FAAttemptStore] before the mechanism is asked anything: a replay is refused with login.error.2fa.enrolment-already-answered.

Future<TomAuthenticationResult> skipTwoFactorEnrolment(TomAuthenticationMessage m, {TomClientJwtToken? enrolmentToken})

Declines a skippable enrolment offer and completes the login with no factor.

A pass of its own rather than a flag on [completeTwoFactorEnrolment], because "I set up a factor" and "I chose not to" are different events with different consequences — only the second spends a grace login — and a boolean that switched between them would make the audit trail depend on a parameter's default.

Refuses unless the presented token says the offer was skippable. That flag is one this server signed, so a client that decides for itself that it may decline achieves nothing — but only because the signature is checked: verifyBearerToken does that on the inbound path, and without it the flag would be plain base64 the caller could edit. See jwt_signing.dart.

(TomClientJwtToken, Tom2FAEnrolmentState) _pendingEnrolment(TomClientJwtToken? presented)

The interim token and the enrolment it carries, or a thrown [TomLoginException] when it carries none.

This is what stops the enrolment passes from being an unauthenticated way to attach a factor to an account: a completed token has no pending enrolment, so presenting one is refused here before any mechanism is reached. Only a token this server minted while branching a login into enrolment gets past.

Future<TomAuthenticationResult> _offerEnrolment(TomAuthenticationInfo authInfo, TomAuthenticationMessage m, Tom2FADecision decision, List<String> offerable)

Branches the login into enrolment: an interim token offering every permitted mechanism this deployment can actually set up.

async so the "nothing here can be enrolled" refusal is a rejected future rather than a synchronous throw. Today the sole call site is inside an async body, which captures it either way; the declared return type is the contract a second call site would rely on.

Future<List<Tom2FAEnrolment>?> _usableEnrolments(Tom2FAContext context, List<String> offerable)

This principal's set-up factors among [offerable], or null when no [Tom2FAEnrolmentStore] is installed.

The three outcomes are deliberately distinguishable: null is nobody tracks enrolments here, an empty list is tracked, and this user has none, and a non-empty list names what to challenge. Collapsing the first two would force enrolment on every deployment that never opted in.

Tom2FAEnrolment _primaryOf(List<Tom2FAEnrolment> enrolments)

The enrolment to challenge: the one the user nominated, or the first if none is nominated. [enrolments] must not be empty.

Future<TomAuthenticationResult> _issueTokens(TomPrincipal principal, TomAccessControlDefinition? definition, TomAuthenticationMessage m, {Tom2FAChallenge? challenge, Map<String, Object?>? twoFactorVerification, Tom2FAEnrolmentState? enrolment, bool twoFactorSatisfied = false})

Projects [principal] onto the token pair of a [TomAuthenticationResult].

The single point at which this server mints tokens, so a completed pass 2 and a 2FA-free pass 1 provably produce the same claim set: the only difference between them is the [challenge] / [enrolment] / [twoFactorSatisfied] triple fed into the projection.

[challenge] and [enrolment] are mutually exclusive by construction — a login is either answering a factor or setting one up — and each turns the pair into an interim token that grants no session.

It is also where the principal's stored preferences are applied ([_applyStoredTimezone]) and its client limits are asked of the installed [TomClientLimitsProvider] ([_applyClientLimits]), for the same reason: every token this server mints, on every pass, then carries the same resolved values.

Future<void> _applyStoredTimezone(TomPrincipal principal, TomAuthenticationMessage m)

Resolves [principal]'s effective timezone before it is minted into a token: the preference stored for the user, else the one the client asserted.

The two are different claims and both survive. [TomPrincipal.clientTimezone] is what the device says it is in — a fact only the device knows, and one that changes when the user travels. [TomPrincipal.timezone] is what the user chose, which follows them onto the next device and is therefore the server's to answer. With no stored preference there is nowhere to read the second from, so the client's assertion serves as both.

The preference wins when it exists because it is the only one of the two the user set deliberately; the device's assertion remains the fallback, so a user who has never set the preference keeps the device's answer.

Future<void> _applyClientLimits(TomPrincipal principal)

Replaces [principal]'s client limits with the installed [TomClientLimitsProvider]'s answer, when there is a provider and it has one.

The provider is the seam a subscription service fills; with none installed, the limits stay what the authentication service put on the principal. A provider that fails costs no one their login, for the same reason as a stored-preference failure: an unreachable subscription service would otherwise stop every sign-in. The failure is logged and the authentication service's answer is minted — exactly what a deployment without a provider issues.

Future<String?> _storedTimezone(TomPrincipal principal)

[principal]'s stored timezone preference, or null when there is none to be had.

Read through [TomUserPreferences.getFor] because there is no request zone carrying this principal yet — it has only just been authenticated — and that method installs one, so the read is scoped like every other.

Why: a failure here must not cost the user their login. A deployment that has not run the preferences migration, or a preference someone stored as the wrong type, would otherwise turn an unrelated data problem into "no one can sign in". The failure is logged and the client's assertion is used, which is exactly the behaviour of a deployment that stores no preferences at all.

List<Tom2FAMethodDescriptor> _descriptorsFor(List<String> types)

How the offered mechanisms describe themselves, in the order they were offered.

Asks the registry rather than carrying descriptors in the token: the catalog is a property of the running deployment, and a token minted before a mechanism's resource keys were corrected would otherwise keep handing out the old ones.

class TomAuthenticationService

abstract class TomAuthenticationService

The contract an application implements to authenticate a login.

Implementations resolve the [TomAuthenticationData] against their user store (database, directory, etc.) and return a [TomAuthenticationInfo] carrying the authenticated principal and its access-control definition. On failure they throw a [TomLoginException]. The default implementation, [TomDummyAuthenticationService], accepts everything and is for scaffolding only.

The implementation is the source of what the principal asserts

Everything the returned [TomPrincipal] carries is the implementation's answer: the identity and its numeric ids, the locale, the access-control information, and the client limits — [TomPrincipal.cli], the enabled modules and quotas the client's subscription grants. [TomAuthenticationServer] reads no subscription store and consults no environment; it encodes what it was handed into the tokens.

Two values are resolved after the credential is accepted, each because the implementation is not their authority:

  • [TomPrincipal.timezone], from the user's stored preference — a

server-held preference rather than a fact about the identity being asserted; see _applyStoredTimezone. - [TomPrincipal.cli], from the installed [TomClientLimitsProvider], when one is installed — the seam a subscription service fills, so that what a client bought is answered by the service that sells it. With no provider, the implementation's answer stands; see _applyClientLimits.

class TomDummyAuthenticationService

class TomDummyAuthenticationService implements TomAuthenticationService

A no-op [TomAuthenticationService] that authenticates any non-"GUEST" user.

Provided as the default so a freshly scaffolded server can issue tokens without a user store wired up. It logs an error on every call (unless [showErrorMessage] is cleared) because relying on it outside scaffolding is a mistake — replace it with a real [TomAuthenticationService] via [TomAuthenticationServer.globalSettingUserAuthenticationService] / [TomAuthenticationServer.globalSettingGuestAuthenticationService].
