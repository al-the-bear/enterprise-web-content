A relational audit sink: one row per entry, in the database the application already operates.

Why a table is the hard case

TomFileAuditSink is append-only by construction — the only file operation it performs is "append a line", and rotation renames rather than rewrites. A table has no such property. UPDATE and DELETE are ordinary statements, so a trail stored in one is append-only only because something outside the code says so. That "something" is the deployment's write-once story, and this sink cannot supply it: the grant is the guarantee, and a grant is not a thing a library can hold.

What the framework can do, and does here, is three things:

  • take its own [TomDataSource], named explicitly and never defaulted to

the application's, so the restricted credential has somewhere to live; probe the deployment at open — see [verifyWriteOnce] — and report what it found instead of assuming; and refuse to start when the deployment asked for the guarantee and the probe says it is absent ([requireWriteOnce]).

The full reasoning, and the three postures a deployment may take, are in doc/audit.md § "The Write-Once Story".

Why not through the repository

TomSqlDatasourceRepository is itself an audit chokepoint: every save it performs writes an audit record. A repository-backed sink would therefore audit its own writes, and each entry would produce another. The regress could be broken with TomAuditTrail.runUnaudited, but a bypass is the weaker guarantee — it holds only as long as every write path remembers to wrap itself. Talking to the data source directly makes the regress impossible instead of merely avoided.

Why the chain is per writer

Each entry hashes the previous entry's hash, so a chain has exactly one head. Two processes appending to one table each track their own head in memory; interleaved, their rows read back as a sequence that fails its own verification — not because anything was tampered with, but because it was never one chain. [writer] is therefore a required argument: a per-node chain makes a clustered deployment correct, and making the argument mandatory makes the question impossible to overlook. The unique key on (writer, previous_hash) then turns a fork into a duplicate-key error at insert time rather than silent corruption found at the next audit.

class TomSqlAuditSink

class TomSqlAuditSink implements TomAuditSink

A [TomAuditSink] whose entries are rows in a [TomDataSource].

This sink retains nothing on its own

TomFileAuditSink takes retention and maxFiles as constructor arguments and enforces them itself, on every open and every rotation. This sink has no equivalent. [purgeBefore] and [purgeToMaxEntries] exist, but nothing in the framework ever calls them: a trail in a table grows without bound until the deployment schedules a purge. That asymmetry is easy to read as a gap in the API and is not one — it follows from the same fact as the whole write-once story above. Deleting a row needs DELETE, the credential that serves this sink should not hold it, and a sink cannot quietly prune a table it was deliberately not granted permission to prune.

The intended home for the call is the scheduler — TomScheduler and @TomScheduledJob in tom_core_kernel. A purge is a good fit for it: it is idempotent, which is what the scheduler's at-least-once guarantee requires, and it is exactly the nightly housekeeping a job store exists to drive. tom_core_samples/advanced_ops_server shows the shape in OpsPurgeJob — including computing the cutoff from the run's scheduledFor rather than DateTime.now(), so a recovered run trims the window it was planned for.

Two things to get right when scheduling it:

  • Both purges are scoped to [writer]. A single clustered job trims only

the chain of the sink that node happens to hold, so a deployment with several writers must either run the job on every node or give one job a sink per writer. A nightly purge that silently trims one node's rows is worse than none, because the table still grows and the job reports success. A BEFORE DELETE guard trigger blocks it.* That is the trade auditTrailNoDeleteTriggerDdl makes explicit: a table nothing can delete from is a table nothing can prune. Choose one.

This is not the same case as anchoring, which advanced_ops_server/lib/src/ops_anchoring.dart keeps deliberately off the scheduler. An anchor records one writer's head, so it must be published by each process for itself; a purge is storage housekeeping over rows that are already written, and running it from a job store is right. What the two share is only that the chain is per writer -- see "Why the chain is per writer" above, which is why the purge is writer-scoped too.

Constructors

TomSqlAuditSink.new(TomDataSource datasource, {required String writer, String table = defaultAuditTrailTable, bool createSchema = true, bool requireWriteOnce = false})

Creates a sink over [datasource].

[writer] names this chain — see the library comment; give each process that appends to the same table a distinct, stable value (the node name is the usual choice, never a value that changes across restarts, since the head is recovered by it).

[table] names the trail table. With [createSchema] left true the table is created on first use, which is what a test or a single-service deployment wants; set it false when the schema is owned by the migration module — which is also the arrangement a restricted grant requires, since the serving user should not hold DDL rights on its own audit table.

[requireWriteOnce] turns the start-up probe from a warning into a refusal. Left false by default: a sink that refused to start on a developer machine would push people towards not installing one at all, and an unprotected trail is still better than no trail. A deployment that has made the write-once arrangement should set it true, because a silently mis-granted credential is precisely the failure it exists to catch.

factory TomSqlAuditSink.named(String datasourceName, {required String writer, String table = defaultAuditTrailTable, bool createSchema = true, bool requireWriteOnce = false})

Creates a sink over the registered data source named [datasourceName].

Throws a [TomServerException] keyed audit.sink.unknown_datasource when no such data source is registered — a configuration error far better caught at start-up than on the first audited action, which the fail-closed trail would turn into a failed request. The base class rather than a subtype is deliberate; [TomServerException] says why.

Future<void> open()

Provisions the table, probes the deployment, and recovers the chain head.

Idempotent and awaited by every write, so a sink is never used unopened; exposed so a start-up sequence can pay the cost — and surface a misconfiguration — before serving traffic rather than on the first audited action.

A failed open clears the memo so the next write retries: a database blip during start-up must not wedge the trail for the life of the process.

Future<({int entryCount, String hash})> _recoverHead()

Reads the last chain hash and position for [writer] from the table.

A restart that began a fresh chain would present every pre-restart entry as unverifiable, which is indistinguishable from tampering — so the head is recovered rather than reset. Both values come from the same row, in one statement: read separately they could straddle a concurrent insert and yield a count that belongs to a different head.

Future<List<TomAuditEntry>> readAll()

Reads every retained entry of this writer's chain, oldest first.

Asynchronous — it is a query — and not a [TomAuditSink] member: read-back is per implementation by design, for the reasons set out on that interface. Note what this reads: every row of the chain, so on a large trail prefer [purgeBefore]-bounded windows or a direct query to calling it on a routine schedule.

Future<TomAuditQueryResult> query(TomAuditQuery query)

Answers [query] from this writer's chain, without reading the rest of it.

The counterpart of filterAuditEntries for a trail that is in a table rather than in memory, and the reason the two are separate calls rather than one: here the filter is pushed into the database, where the indexes on (target, action), (actor) and (writer, recorded_at) are — the indexes this table has carried since it was declared. Reading every row back and filtering in Dart would answer the same question and is what [readAll] is for; on a trail of ten million rows it is not a query.

The projection narrows, the record decides

The columns the WHERE clause tests are the lossy ones: they are truncated to fit, so they can say maybe and never yes. Two rules follow, and both are structural here rather than advisory:

  • every search term is cut to its column's width by [_fit] before it is

bound, the same call the insert makes. Comparing a full term against a column the writer shortened would match nothing and report it as "no such entry" — a false negative, which in an audit query is the failure that matters; * every row that comes back is decoded and re-judged by [TomAuditQuery.matches] against the record itself. The cut above admits rows that merely share a prefix, and those are dropped here and counted in [TomAuditQueryResult.rejectedByProjection] rather than returned.

So the answer never contains a row the index merely thought looked right, and never omits one it stored short.

Scoped to [writer], like [readAll] and both purges: a sink is one chain's handle on the table. A deployment whose trail carries several writers asks each of them, which is also how it keeps the entry indexes in the answer meaningful — they are positions within a chain, and there is no order across two.

Paging is by window, not by offset: narrow [TomAuditQuery.to] to the oldest instant already seen and ask again. An offset would have to be counted over the projection's matches rather than the record's, which is the one number this method deliberately does not let a caller act on.

Future<TomAuditChainVerification> verify()

Verifies the retained entries, starting from the oldest retained link.

Retention may have removed the head of the chain, so verification starts from what survives — the point is to detect edits within the retained window, not to complain about a deletion the policy asked for.

Asynchronous, like [readAll] whose whole result it consumes, and not on [TomAuditSink] either.

Future<int> purgeBefore(DateTime before)

Deletes every entry of this writer's chain recorded before [before], returning how many rows went.

Retention on a table is expressed in rows, where the file sink expresses it in files — but the rule is the same one: delete a contiguous prefix, never an interior row. A hole in the middle of a chain is indistinguishable from tampering, so a retention pass that could make one would destroy the property the trail exists to have.

That is why the cutoff is resolved to a sequence boundary before anything is deleted: DELETE ... WHERE recorded_at < :before would look equivalent and is not. Timestamps come from the record, sequence numbers come from the insert, and a clock adjustment — or simply two nodes a few milliseconds apart — is enough to leave an older-stamped row sitting after a newer-stamped one. Deleting by timestamp would then punch a hole.

Future<int> purgeToMaxEntries(int maxEntries)

Keeps the newest [maxEntries] entries of this writer's chain, deleting the prefix in front of them, and returns how many rows went.

String? _fit(String? value, String column)

Truncates [value] to what [column] can hold.

The projection columns are an index, not the record: the authoritative text lives in record and is never truncated. Trimming here rather than letting the database reject the row keeps an over-long username from failing an audited action — the trail is fail-closed, so a rejected insert would take the action down with it.

The width comes from the column's own declaration, and [query] narrows its search terms through the same call. That is what makes a search over a truncated column find the row it shortened: both ends cut at the same place because both ask the same declaration where it is.

Future<void> close() override

Waits for the queued records to be inserted, then closes.

Every [write] that has returned has already committed its INSERT; this waits for the ones still queued, so a shutdown that awaits it has every record written before the close in the table. A record written after the call is refused with audit.sink.closed — see [TomAuditSink.close] for why refusing beats writing it anyway or dropping it silently. Idempotent: every call is handed the same close.

The drain awaits _queue rather than the individual write futures because _queue is the tail of the chain: awaiting it means every record enqueued before this call has run. It swallows nothing — _queue already absorbs write errors so one failure cannot wedge the sink, and each error was delivered to its own caller through the future [write] returned.

The [datasource] is deliberately not closed — it is registered process-wide and is not this sink's to dispose of.
