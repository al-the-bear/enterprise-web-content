The server-side second-factor (2FA) subsystem: the adaptor contract, the mechanism registry, and the built-in TOTP adaptor.

The shape of the flow

A login runs in two passes. Pass 1 checks the primary credential and produces a [TomPrincipal]; if that principal declares [TomPrincipal.requires2FA], the server asks the adaptor registered for the principal's [TomPrincipal.twoFactorType] to issue a challenge, and answers with an interim token carrying it. Pass 2 hands the submitted factor back to the same adaptor to verify, and on success re-issues the token pair without the challenge.

Why mechanisms are adaptors

The framework must not know the mechanism set — a deployment may want TOTP, SMS, e-mail codes, push approval or a hardware key, and adding one must not touch tom_core_server. So the framework only knows two things: how to find the adaptor for a mechanism key (reflection over [Tom2FAAdaptor]), and how to move two opaque blobs between the passes:

  • [Tom2FAChallengeSpec.clientData] — travels in the interim token's public

claims, for the mechanism's own client-side UI; - [Tom2FAChallengeSpec.verificationData] — travels in the encrypted section, for the adaptor's own use on pass 2.

Neither is interpreted by the framework. Expiry, the attempt counter and the dispatch are generic and handled once, in [TomAuthenticationServer], which owns both passes; the adaptor answers only the question it alone can answer — is this submission the right one?

class Tom2FAAdaptor

class Tom2FAAdaptor

Marks a class as a server-side two-factor (2FA) adaptor for a given [type].

The annotated class must implement [Tom2FAService] and expose a no-argument constructor — [Tom2FARegistry] discovers it by reflection and instantiates it once. The [type] is the mechanism key that a principal's [TomPrincipal.twoFactorType] names, and that the issued challenge carries so pass 2 dispatches back to the same adaptor. 

@tomReflector
@Tom2FAAdaptor('sms')
class SmsAdaptor implements Tom2FAService { ... }

class Tom2FAChallengeSpec

class Tom2FAChallengeSpec

What an adaptor produces when asked to issue a challenge.

The split between [clientData] and [verificationData] is the whole point: the first is what the client may see, the second is what only the server may see. For a mailed one-time code, [clientData] might hold the masked address while [verificationData] holds a salted hash of the code — so possession of the interim token never reveals the answer.

class Tom2FAContext

class Tom2FAContext

Everything an adaptor is told about the login it is challenging.

Deliberately narrow: the identity being authenticated plus the tenant and locale coordinates of the attempt. An adaptor that needs more (a device registry, an SMS gateway) resolves it from its own configuration — the framework does not carry mechanism-specific state.

class Tom2FAException

class Tom2FAException extends TomServerException

Raised for 2FA configuration faults — a duplicate or unusable adaptor registration, or a mechanism that cannot be constructed.

Distinct from [TomLoginException]: a login that fails because the user typed the wrong code is an expected outcome and yields a failed [TomAuthenticationResult]; a deployment whose adaptors are wired wrongly is a fault that must surface loudly. Not client-throwable — an authentication misconfiguration must never be described to the caller.

class Tom2FAPrerequisite

abstract class Tom2FAPrerequisite

What an adaptor implements when it can only work if something else was installed — a mail service, an SMS gateway, a push credential.

A separate interface rather than a member on [Tom2FAService], for the reason Tom2FAEnrolmentSupport is separate from it: most mechanisms need nothing beyond themselves, and a base contract whose implementations almost all answer null teaches callers to stop reading the answer. is makes "could this adaptor run here?" a question with a real answer.

Where it is consulted, and where it is not

[Tom2FARegistry.registerAnnotated] asks, and skips a candidate that answers. That is the whole point: the shipped delivered-code adaptors register themselves by annotation, so without this they install into every reflected program — including one that never asked for mail — and the deployment then offers a mechanism it cannot run.

[Tom2FARegistry.register] does not ask. Naming an adaptor in a call is asking for it, and a deployment that builds its adaptors before its collaborators needs that escape; the complaint this interface answers is about the automatic registration nobody asked for.

What the answer is for

A reason, not a bool, because a mechanism that quietly disappears is the hardest kind of absence to debug — every lookup answers null, which is also what a mechanism nobody ever wrote answers. The string is logged as the skip happens, so an operator who wonders where email went is told what to install rather than that something was unavailable.

class Tom2FARegistry

class Tom2FARegistry

Resolves a mechanism key to the adaptor that implements it.

Populated on first use by scanning the reflection registry for classes annotated [Tom2FAAdaptor]; a deployment can also [register] an adaptor built by hand, which is what tests and non-reflected wirings do. Registration is idempotent per key and rejects a second, different adaptor for the same key — two mechanisms answering to 'totp' is a wiring bug, and silently picking one would make the failure surface much later and much less clearly.

Install collaborators before the first login

The scan runs once, lazily, the first time anything reads the registry — and it asks each candidate whether it can run here ([Tom2FAPrerequisite]). An adaptor whose collaborator is not installed yet is indistinguishable from one whose collaborator was never installed at all, so it is skipped, and a successful scan is not repeated: the mechanism stays absent for the life of the process.

So a deployment that ships mail or SMS codes must install its TomEmailService / TomSmsService beans during start-up, before the first login. The skip is logged with what was missing, which is what turns "why does nobody get an e-mail code?" into a one-line answer.

static void register(String type, Tom2FAService service)

Registers [service] under [type], replacing nothing.

Throws [Tom2FAException] if a different adaptor is already registered for [type]. Re-registering the identical instance is a no-op, so a double boot is harmless.

[Tom2FAPrerequisite] is deliberately not consulted here — see that interface for why. Naming an adaptor in a call is asking for it; the scan asks on nobody's behalf, which is the only place the question needs answering.

static Tom2FAService? lookup(String type)

The adaptor for [type], or null when the mechanism is unknown here.

static void reset()

Drops every registration and forces a re-scan on next use.

For tests, which need to install their own adaptors without leaking them into the next test.

static void _ensureScanned()

Runs the annotation scan once, on first use.

"Once" means once successfully. A scan that could not run leaves the registry unarmed, so the next access tries again: the reflector is initialised by generated code at some point during start-up, and whatever touches the registry before that point must not decide the question for the rest of the process. Remembering a failure as though it were a scan is how a registry ends up permanently and silently empty.

static void registerAnnotated(Iterable<ClassMirror<dynamic>> candidates)

Registers every class in [candidates] that carries a [Tom2FAAdaptor] annotation.

The automatic scan hands this the reflection registry's own class list. It is separate from that scan because a candidate set is not always the whole program: a deployment that composes its adaptors from a chosen set of libraries supplies its own, and the tests for the two malformed cases below must supply theirs — a class annotated @Tom2FAAdaptor but unusable cannot live in a reflected library, because the automatic scan would then reach it from every other test in the process.

Throws [Tom2FAException] on the first unusable candidate, naming it. A half-registered registry is not offered as an alternative: an adaptor set that is wrong is wrong at start-up, not at the login that happens to need the missing mechanism.

A candidate whose [Tom2FAPrerequisite.unmetPrerequisite] is non-null is a different case and is skipped, loudly, rather than thrown on. A server with no mail relay is a legitimate deployment, not a broken one, and refusing to start it would make one uninstalled channel cost the deployment every other mechanism it has. What must not happen — and what the skip prevents — is the mechanism being offered: registration is the only thing [Tom2FADecision.offerableMechanisms] consults.

That holds for the registry a caller can still see afterwards, not only for the throw: a failed call registers nothing, and leaves registrations made before it untouched. Both halves matter now that a failed scan is retried — leftovers from the first attempt would collide with the second attempt's fresh instances and report a mechanism that was never at fault.

class Tom2FAService

abstract class Tom2FAService

The contract a second-factor mechanism implements.

Two questions, and only two: what challenge should this user be given? and is this submission correct? Expiry, attempt counting, dispatch and token issuance are the framework's job, so an adaptor stays small and its logic is unit-testable in isolation.

Implementations must be stateless between calls — pass 1 and pass 2 may run in different isolates or on different server instances, so anything the adaptor needs to remember belongs in [Tom2FAChallengeSpec.verificationData].

Returns whether [submission] correctly answers the challenge.

Returns false for a wrong answer — that is an ordinary outcome, and the framework turns it into a retry or an exhaustion failure. Throw only when verification could not be performed (an unreachable dependency).

class TomTotp2FAService

class TomTotp2FAService implements Tom2FAService, Tom2FAEnrolmentSupport

The built-in RFC 6238 time-based one-time-password adaptor.

Chosen as the first concrete mechanism because it needs no delivery channel: the code is derived from a shared secret and the clock, so the whole path — challenge, submission, verification, retry — can be exercised without an SMS gateway or a mail server standing behind it.

Expiry, attempt counting and dispatch are the framework's; the derivation itself is [TomTotp]'s, in the kernel, so the code this verifier expects and the code an enrolment tool or authenticator produces come from one implementation. What is left here is only policy: which secret, how many digits, how much skew to tolerate, how many attempts.

Where the secret comes from

From the installed [Tom2FAEnrolmentStore] — the user's own 'totp' enrolment, whose [Tom2FAEnrolment.secretData] carries the base32 secret under [secretDataKey] — falling back to [globalSettingSecretResolver] when no store is installed or the store holds no TOTP enrolment for this user.

It is deliberately not read from [TomUser.attributes]: those are projected into the token's public claims, so a secret parked there would be readable by anyone holding the token. For the same reason this adaptor stores nothing in [Tom2FAChallengeSpec.verificationData] — it re-resolves the secret on pass 2, so the secret never travels at all.

Enrolment

The adaptor also implements [Tom2FAEnrolmentSupport], so the framework can create an authenticator and not merely verify one that appeared from somewhere else. [beginEnrolment] generates a secret and hands back both the base32 string and an otpauth:// URI built from this verifier's own digits and period, so the app is provisioned with the policy that will be applied to it; [confirmEnrolment] refuses to yield an enrolment until the user has typed back a code derived from that very secret.

static FutureOr<String?> Function(Tom2FAContext)?? globalSettingSecretResolver

Resolves a user's base32 TOTP secret when no [Tom2FAEnrolmentStore] is installed.

The store is the primary source; this hook is the fallback for a deployment that keeps its secrets somewhere the framework does not own (an LDAP attribute, a vault). With neither wired, every TOTP challenge fails with login.error.2fa.not-enrolled.

static int globalSettingDigits

Number of digits in a generated code (RFC 6238 default: 6).

static Duration globalSettingPeriod

Length of one time step (RFC 6238 default: 30 s).

static int globalSettingWindowSteps

How many time steps either side of "now" are accepted, to tolerate clock skew between the server and the authenticator. One step each way is the usual compromise between usability and the size of the accepted window.

static int globalSettingAttemptsAllowed

How many submissions one challenge tolerates.

static Duration globalSettingChallengeValidity

How long a challenge stays answerable. Longer than one code's lifetime, so a user who starts typing just before a rollover is not punished for it.

static String globalSettingIssuer

The name the authenticator app files this account under, shown beside the code — empty means use the application being logged into ([Tom2FAContext.application]).

A setting rather than a constant because the issuer is what the user reads to tell one of a dozen six-digit codes from another; a framework that hardcoded it would put the same word in every deployment's authenticator. Defaulted from the application rather than left blank because that is already the deployment's own name for itself, so the common case needs no configuration and the uncommon one (a suite of applications sharing one account) sets this once.

static int globalSettingSecretBytes

How many bytes of entropy a generated secret carries.

20 bytes = 160 bits, RFC 4226 §4 R6's recommendation and the width of the HMAC-SHA1 key the codes are derived with; more would be truncated into the same strength by the hash, less would weaken it.

static int globalSettingEnrolmentAttemptsAllowed

How many confirmation attempts one enrolment offer tolerates.

static Duration globalSettingEnrolmentValidity

How long an enrolment offer stays confirmable.

Longer than a challenge, because the user has to install an app and scan a code in between, and still bounded, because an unconfirmed secret is a credential nobody is yet watching.

static String clientDataUriKey

The key the otpauth:// provisioning URI is filed under in [Tom2FAEnrolmentOffer.clientData] — what a client renders as a QR code.

static String generateSecret()

A fresh base32 secret, [globalSettingSecretBytes] bytes of cryptographically secure randomness.

Drawn from [RsaKeyHelper.getSecureRandom] — the framework's own CSPRNG — and not from dart:math's Random(), whose output is predictable from a handful of observations. The value being generated is a permanent credential: a guessable one is worse than no second factor, because it is trusted.

static String provisioningUri(String secret, Tom2FAContext context)

The otpauth:// provisioning URI for [secret], as an authenticator app consumes it (the payload behind the QR code).

Every parameter is taken from this adaptor's own settings, so the app is provisioned with the policy this verifier will apply — an app told to produce eight digits every sixty seconds while the server checks six every thirty is a lockout that only shows up at the next login.

algorithm=SHA1 is stated rather than left to the app's default because [TomTotp] derives with HMAC-SHA1; the default happens to agree, but an implicit agreement is not one anybody can check.

static String issuerFor(Tom2FAContext context)

The issuer name to provision, for a login in [context]: the configured [globalSettingIssuer], else the application being logged into.

static String expectedCode(String secret, {DateTime? at})

The code this verifier expects right now, for the base32 [secret] — the adaptor's own policy (digits, period) applied to [TomTotp].

For enrolment self-checks and for tests, so neither has to restate the policy and then drift out of agreement with the verifier.

static bool _matchesWithinWindow(String secret, String submitted)

Whether [submitted] is the code for [secret] at any time step within [globalSettingWindowSteps] of now.

The one place a submitted code is judged. Verification and enrolment confirmation both come here, expressed through [expectedCode], so the two cannot drift: a policy change that made an enrolment self-check accept something the login would refuse is precisely how a user ends up locked out of an account they just successfully set up. The tolerated skew is shared for the same reason — a phone's clock is exactly as wrong at enrolment as it is at the next login.

static bool _constantTimeEquals(String a, String b)

Compares two codes without leaking, through timing, how much of the submission was right.
