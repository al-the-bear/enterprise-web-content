The dialect-neutral schema shape both halves of the CE-DB ↔ CE-MG convergence check are reduced to before they are compared.

The entity model (@TomDbTable / @TomDbColumn) and the cumulative DDL of a migration chain describe the same schema from two sides but in two vocabularies — Dart types on one, SQL type names on the other. Neither can be compared to the other directly, so both are read into the structures here and the diff runs over one vocabulary only.

class TomSchemaBuilder

class TomSchemaBuilder

The mutable accumulator both sides build their [TomSchemaModel] through.

The DDL side needs mutation by construction — replaying a chain means applying CREATE, then ALTER, then DROP to a schema that is only complete at the tip. Rather than give [TomSchemaModel] mutating members that nothing may call after the build, the mutation lives here and the model comes out immutable. The entity side uses the same builder, so both halves of the check are assembled through one API and cannot drift apart in shape.

Every mutation is a silent no-op on a table or column the builder does not have, never an error: [addColumn], [dropColumn], [renameColumn] and [setPrimaryKey] against an unknown table all return with the model unchanged. The builder accumulates; it never reports.

That is a division of labour, not leniency. Whether a statement operating on something absent is a defect depends on the statement text — DROP TABLE IF EXISTS on a table the chain never created is the guard doing its job, the same drop without the guard is a chain defect worth reporting — and the builder is handed parsed names and columns, never the SQL, so it is the one participant that cannot tell those two apart. TomSchemaDdlReader can, and does: it asks [hasTable] / [hasColumn] before mutating, and the answer decides whether it records a TomDdlReplayError, not whether the call is safe to make.

Two consequences follow, and both are why the checking is not moved down here. The reader collects its errors and keeps replaying, so one run reports every divergence in a chain rather than only the first; a builder that threw would end the replay at the earliest defect. And the entity side builds from information_schema rows, where there is no chain to contradict and nothing to report — a builder that demanded a pre-check would impose guards on a caller that cannot fail that way.

Properties

final String name

The column name as written on the side this column was read from.

Lookups are case-insensitive (see [TomSchemaTable.column]); this field keeps the original spelling so a report names the column the way the author wrote it.

final TomSqlTypeFamily family

The type class this column is compared in.

final String declaredType

The type as declared on the source side — a SQL type (VARCHAR(255)) for a column read from DDL, a Dart or TomDbType name for one derived from an entity. Reported, never compared.

final bool nullable

Whether the column accepts NULL.

Parsed from the DDL and carried here, but not part of the comparison: the entity model has no nullability declaration to compare it against (every mapped field is Dart-nullable so an unsaved record can exist). It is modelled anyway so that a future entity-side declaration can turn the comparison on without re-parsing anything. Defaults to true on the entity side, where it is unknown.

final String origin

Where this column came from — the migration artifact basename that last defined it, or the entity type name that declares it.

This is the locality a divergence report points at: "column x is missing from app_items" is only actionable together with "and UserRecord expects it" or "and [004]-add_columns should have added it".

extension TomSqlTypeFamilyCompatibility

extension TomSqlTypeFamilyCompatibility on TomSqlTypeFamily

How tolerantly the two sides of the convergence check compare their [TomSqlTypeFamily] classifications.

The families themselves are the dialect's vocabulary (a dialect decides that TINYINT(1) is a truth value); how much difference between two families is still agreement is the check's policy, and so lives here.

Methods

bool accepts(TomSqlTypeFamily actual)

Whether a column of this (expected) family may be stored as [actual].

The direction matters — the receiver is what the entity model declares, [actual] what the DDL creates:

  • integer ↔ boolean — both ways. A truth value stored as TINYINT(1)

is the normal MariaDB spelling, and an entity that reads that column as an int is equally valid; the entity model does not pin the choice down. decimal accepts integer, but not the reverse. Reading a whole number as a double is lossless; declaring an int over a DECIMAL column truncates, which is a real defect worth reporting. dateTime ↔ date — both ways, for the same reason as integer/boolean: whether the time-of-day part is stored is a storage decision the entity model leaves open. * [unknown] on either side is compatible with everything.
