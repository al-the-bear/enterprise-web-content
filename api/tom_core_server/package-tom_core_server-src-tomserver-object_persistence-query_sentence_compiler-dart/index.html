class TomQuerySentenceCompiler

class TomQuerySentenceCompiler extends TomTypedPersistenceBase with TomQueryBuilder

Compiles a Spring-Data-style query sentence into a [TomQuery].

A query sentence is a whitespace-separated phrase such as find by name = :name order by age desc, count by status IS IN ( :s ), or delete by id = $id. The first word selects the query kind (find → [TomSelect], count → [TomCount], delete → [TomDelete], group → [TomGroupedSelect]); the part before by carries options (distinct, top/first N, skip/offset M, and for group the projection); the part after by is the predicate, optionally followed by a having <predicate> clause and an order by <fields> [asc|desc] clause. The predicate is parsed against the entity's resolved columns (via [TomQueryBuilder] and [TomAnnotationAnalyzer]) into a [TomOperator] tree.

Paging. top/first N caps the rows; skip/offset M skips M of them first, so page P of size N is first N skip P*N. A skip needs a cap — SQL has no bare OFFSET — and a paged sentence should order by something unique, or successive pages are cut from an order the database is free to change between them.

Sort direction. A direction keyword applies to every field back to the previous direction keyword, so order by a b desc sorts both descending (one direction for the whole list, as it always did) while order by a desc b asc mixes them.

The grouped sentence. group projects aggregates instead of entities:

group count ( * ) as total , sum ( amount ) as revenue over status
  by createdAt >= :from having total > :minCount order by total desc

The projection is a comma-separated list of <fn> ( <arg> ) as <alias> (count/sum/avg/min/max; count ( * ) for the row count, and a leading distinct inside the parentheses for count/sum/avg). The optional over <fields> names the group key — omit it to aggregate the whole result set. having filters groups and so addresses the projection by alias, where the by predicate filters rows and addresses columns.

Throws [TomQuerySyntaxException] for a malformed sentence (unknown kind, both top and first, both skip and offset, a skip without a cap, etc.).

Options. The four a sentence can carry — distinct, the cap, the skip and the sort — are parsed once, by one step, for every kind. Each kind then declares which of them it permits (_permittedOptions), and one loop refuses the rest by name: a find or a group takes the cap, the skip and the sort; a delete takes the cap and the sort but no skip, because DELETE has no OFFSET, and no distinct, because a single-table delete has no projection to deduplicate; a count takes only distinct, because it returns one row whatever the others say.

The declaration is what keeps the promise the next sentence makes. A combination a kind cannot express is refused with a message naming the reason — never accepted and then ignored — and so is a word before by that names no option at all, because a token skipped along with its argument changes what the query returns while reading as though it had not. The matrix is in doc/object_persistence.md and asserted against this compiler, cell by cell, by query_sentence_options_test.dart.

_SentenceOptions _parseOptions(List<String> queryOptions, List<String> whereClause, String qs)

Parses everything a sentence carries besides its predicate, once, for every kind.

[queryOptions] is the tokens before by, [whereClause] those after it. The scan runs left to right from the kind word and stops at the first token that names no option, which the caller reads as the projection (group) or as a stray word (every other kind).

Scanning rather than searching is what makes that stop meaningful. While each option was found by searching the whole list, a token belonging to none of them was invisible: nothing knew which tokens had been consumed, so nothing could notice one that had not been.

int _optionArgument(List<String> options, int at, String keyword, String qs)

Reads the whole, non-negative row count [keyword] takes, at [at] + 1.

The argument is rejected — never guessed at — when it is missing, non-numeric or negative: a window the compiler had to invent would return a different result set than the sentence asked for, without saying so.

Zero is accepted and means unpaged, the reading [TomPageRequest.assertWindow] gives limit: 0 for a window built programmatically. Negative is refused for the same reason, and for one more: -1 is the compiler's own "absent" sentinel, so an accepted first -1 could not be told apart from a sentence with no cap.

[keyword] is quoted as the author spelled it — top and first are one option internally, and quoting the other one sends the reader looking for a word their sentence does not contain.

(TomOperator<TomDbBool>, int) _createComparison(List<String> qp, String qs, int i, TomColumnInformation? column, TomOperator<dynamic> current, {required TomOperator<TomDbBool> Function<T>(TomOperator<T>, TomOperator<T>) build, required String key, required String symbol})

Dispatches a two-operand comparison on the SQL type of its left operand.

The right-hand side is parsed as that type, so the parse and the node construction have to agree — which is why this is one method taking a [build] factory rather than a copy of the switch per operator. [key] and [symbol] name the operator in the failure a type outside the switch produces, so the six callers stay distinguishable in an error message.

Every arm parses the right-hand side with [_buildExpression], the operand-level entry point — including the boolean arm, which is the one where the choice is not obvious. Routing a boolean operand through [_buildQuery] instead, the statement-level entry point, would let the operand claim and, or and ) as its own, so a boolean right-hand side would not stop at the comparison: done = TRUE and id > 2 would pull the conjunction into the operand and be refused, and not ( done = TRUE ) and id > 2 would have its closing bracket consumed by the = and compile to NOT ( done = true AND id > 2 ) — a different predicate from the one written. Nor does the statement-level entry point buy the form it looks like it would, a comparison against a whole predicate (done = ( a > 1 or b > 2 )): [_buildQuery] threads the boolean column into the bracket, and the first column inside is then read as a second operand of its type.

_CompiledColumnType _compiledColumnType(TomColumnInformation column, String field)

The type [field]'s column is compiled as.

An explicit @TomDbColumn(columnType: ...) wins over the field's declared Dart type — being able to say "this Dart value is stored as that" is the entire purpose of the annotation, and the declared type is only ever a fallback inference.

An explicit type this compiler cannot build a column for is refused, not quietly replaced by the inferred one. Falling back would make the escape hatch fail open: the entity states one storage type, the compiler builds another, and the disagreement first shows up as a value written to the wrong kind of column rather than as a rejection naming the annotation. The fall-through that did this was invisible for as long as it was: no fixture entity declared columnType: at all, so neither the honouring nor the refusal had ever run.

Both failures carry create_column.failed. A caller that has already built the column node — [_createParameter] is the only one — cannot reach either, because the same column resolved once already.

List<String> _splitQuerySentence(String qs)

Splits [qs] into tokens: words, separators, and whole string literals.

Quoting is why this is a hand-written scan rather than the regex-and-split it replaced. That version inserted spaces around every ,()=<>, collapsed runs of whitespace and split on the result — with no notion of a quoted region, so a literal was only writable if it contained none of those characters and no space. title = 'in progress, phase (2)' became eight tokens, the first of them 'in, and the failure that came back named a column ['in]: a fragment the author never wrote, raised by the annotation analyzer rather than as a query-syntax error.

A quoted region is returned as one token with its quotes still on, so the literal branch of [_buildExpression] recognises it the same way it always has, and so a token that merely looks like a keyword or a column name cannot be mistaken for one — by, order and and are all found by scanning this list.

An apostrophe inside a literal is written the SQL way, by doubling it. The doubling is left in the token here and undone by [_decodeStringLiteral], so a token still reads back as it was written when it appears in an error message.

static Map<String, Set<_SentenceOption>> _permittedOptions

Which options each kind of sentence permits.

The declaration, not a detail: a kind permits what is listed here and refuses everything else by name, so a new kind is a new row rather than a search for the conditions that mention the existing ones. Listing what is permitted rather than what is refused is the direction that fails safe — an option added to [_SentenceOption] is refused by every kind until one opts in, where a refusal list would let it through everywhere.

Private, because a Set<_SentenceOption> is not something a caller could do anything with. The table a reader needs is in doc/object_persistence.md, and query_sentence_options_test.dart asserts the compiler against that table rather than against this one — a test reading this map would agree with it by construction.

static Map<Type, _CompiledColumnType> _compiledColumnTypes

Every spelling a compiled column type may be written with, on either of the two routes into [_compiledColumnType].

One map for both routes rather than one per route. A field cannot be declared with a TomDb… box — those name SQL types, not Dart values — so the declared-type vocabulary is a strict subset of the explicit one, and splitting the map would buy nothing but a second thing to keep in step. The extra keys are unreachable on the declared route, not wrong on it.

static Set<String> _reservedInOperandPosition

The grammar's words, which are never an operand.

Reaching a branch below is how a word becomes an operator; reaching this set is how one that did not becomes a diagnosis. Every branch that claims one of these needs a lookahead — IS NULL, IS NOT IN, NOT LIKE — so a word whose partner is missing or wrong declines every branch and arrives in operand position, where the only remaining reading is "column name". That reading is always wrong and always plausible: find by title is was answered by the annotation analyzer with "No column match field [is] found. Must be a variable and must have @TomDbColumn annotation", sending the author to look for a field they never wrote, for a sentence that merely stops one token early.

The set is the same construction as the TRUE/FALSE branches and [_separatorCharacters], and carries the same cost: a column actually named is or and no longer resolves. SQL reserves these words too, the sentence language has no quoting for identifiers, and @TomDbColumn(name: ...) already renames such a field. The alternative — resolve the column first and fall back to the diagnosis — would make which error you get depend on the entity's field list, so the same malformed sentence would be reported two ways in two entities.

AND and OR are here although the outer loop is what joins predicates: this expression parser is entered per operand, so a sentence like find by title = and presents one in operand position without the outer loop ever seeing it.

static Set<String> _twoCharacterOperators

The two-character operators, matched before the single-character ones so <= is one token rather than < followed by =. This is the whole vocabulary [_buildExpression] recognises; anything else made of these characters splits into singles and is refused there by name.

static String _decodeStringLiteral(String token)

The value a quoted [token] stands for: the quotes removed and each doubled apostrophe folded back to one.

The fold belongs here rather than in the dialect, which does the opposite job — [TomStandardSqlDialect.text] escapes ' to '' on the way out. class _ScalarLiteral

class _ScalarLiteral

One kind of scalar value a query sentence can spell inline, as opposed to binding it — find by priority > 3, find by due = 2026-07-05.

The five kinds are recognised by shape alone, and their shapes nest: every datetime literal contains a date and a time, every date contains digits, and a bare digit test matches any token that merely contains one. So two rules keep them all reachable, and both are load-bearing —

  • every [pattern] is anchored, so a token matches a kind only by being

that kind entirely rather than by containing one somewhere; and _scalarLiterals is ordered most specific first*, so the datetime is tested before the date it contains and the date before its digits.

Drop either and the later kinds become unreachable: the token is claimed by a broader rule that then rejects it for having the wrong type.

enum _CompiledColumnType

enum _CompiledColumnType

The SQL type a named column is compiled as.

Interposed between an entity's annotations and the two nodes a predicate builds from them — the column and the parameter bound against it — so that the two cannot answer the same question differently. They did: _createColumn honoured an explicit @TomDbColumn(columnType: ...) and _createParameter read only the declared Dart type, so an entity using that escape hatch produced a column of one type and a parameter of another. The two meet at a cast, so the disagreement surfaced as a bare TypeError — outside the exception family this module documents, and naming neither the column nor the annotation that caused it.

Both dispatches are switch expressions over this enum, so they are exhaustiveness-checked: a type family added here fails to compile until both are extended. That is the property worth having, because the three previous defects in this file were all one dispatch of a set being missed — double was absent from three of them at once.

Deliberately not [TomSqlTypeFamily]. That answers a neighbouring but different question — how a value is stored, folding in isJson and the TomDbColumn<,> type arguments — and it resolves an explicit columnType: naming a bare Dart type differently from this compiler. Sharing the vocabulary without sharing the resolution would suggest an agreement that does not hold.

enum _SentenceOption

enum _SentenceOption

One thing a query sentence can carry besides its predicate.

Three are written before by (distinct, the row cap, the skip) and one after the predicate (order by …), but they are one vocabulary: each is parsed once for every sentence, and each kind of sentence then either permits it or refuses it by name.

Naming them is what makes that one question instead of several. A rule written per kind, in a condition of its own, is a rule a fifth kind has to remember to state — and an option no condition happens to mention is accepted and then dropped, which changes what a query returns while reading as though it had not.

[refusalKey] and [reason] are what a kind that does not permit this option says. One pair per option rather than per (kind, option) pair, because exactly one kind refuses each of them today; a second refuser would need a reason of its own, which query_sentence_options_test.dart asserts by checking every kind against every option.

typedef _ComparisonFactory

typedef _ComparisonFactory = TomOperator<TomDbBool> Function<T>(TomOperator<T>, TomOperator<T>)

A two-operand comparison node factory: [TomQueryBuilder.eq], [TomQueryBuilder.neq], [TomQueryBuilder.lt], [TomQueryBuilder.lte], [TomQueryBuilder.gt] and [TomQueryBuilder.gte] all have this shape.

Naming it is what lets a single dispatch over the operand's SQL type serve all six operators. Without it each operator needs its own copy of the switch, and a type added to one is silently missing from the other five — which is exactly how double came to be unsupported.
