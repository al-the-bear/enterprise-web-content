class TomCountResult

class TomCountResult

Result holder for a COUNT(*) query: a single [count] field populated by the row mapper. Reflectable so the data source can materialise it.

It is a plain reflected holder (no @TomDbTable), so the row mapper fills it by field name: the COUNT(*) AS count projection names its column count, which matches this field. That name is the entire binding, and it is checked nowhere — rename [count], or project the count under a different alias, and the mapper finds no column for the field, leaves it at its default 0, and every count reports an empty table instead of failing.

class TomFileRepository

abstract class TomFileRepository<T extends Object, K>

The subset of a repository the file surfaces need: load a row, and move the bytes of one of its @TomFileReference columns.

Split out of [TomRepository] rather than folded into it because it is what the HTTP file endpoint depends on, and an endpoint that depended on the full SQL repository could only ever be exercised against a database. Every method here is already implemented by [TomSqlDatasourceRepository]; naming them as a contract costs nothing and makes the endpoint's requirement explicit — five methods, not a persistence stack.

class TomRepository

abstract class TomRepository<T extends Object, K>

The persistence contract for an entity [T] keyed by [K].

Modelled on Spring Data's CrudRepository: it offers id-based CRUD ([save], [findById], [delete], …) plus three query styles — a parsed Spring-style query sentence (findByQuerySentence and friends), a built TomQuery object ([findByQuery] / [deleteByQuery] / [countByQuery]), and a raw SQL string ([executeQueryString]).

Paging and sorting. Every read that can return more than one row takes an optional [TomPageRequest]: an offset, a row limit, and an ordered list of (field, direction) sort terms. The result is the window itself — a plain List<T> — and the total comes from the matching count method, which applies the same row scope, so page metadata never reports rows the principal may not see. A caller that does not page passes nothing and gets exactly the behaviour it had before.

class TomRepositoryException

class TomRepositoryException extends TomServerException

Raised when a repository operation cannot complete: the entity's data source was never registered, a primary-key lookup matched more than one row, a COUNT(*) returned other than one row, a row written by [TomRepository.save] could not be read back, or [TomRepository.delete] was handed an entity that was never persisted.

All but the last are server faults — a broken registration or a database that contradicts its own schema — so [TomServerException.clientThrow] defaults to false and the message is kept off the wire; the key is what a caller matches on and what the endpoints pipeline logs.

The delete of an unsaved entity is the exception, and sets clientThrow explicitly. It is raised for something the caller did rather than something the deployment did, and its message describes only the argument it was handed — so masking it would tell a caller nothing about a mistake it is the only party able to fix.

It sits beside the repository rather than in the module's other exception files because those describe inputs the repository rejects ([TomQuerySyntaxException], [TomColumnAuthorizationException], [TomDataScopeException]); this one describes the repository's own preconditions failing — including, in the delete case, the precondition that there is a persisted row to address at all.

class TomSqlDatasourceRepository

abstract class TomSqlDatasourceRepository<T extends Object, K> extends TomRepository<T, K> with TomQueryBuilder implements TomFileRepository<T, K>

SQL-datasource implementation of [TomRepository].

On construction it resolves the entity's persistence metadata via [TomAnnotationAnalyzer] (table, primary-key column, columns), looks up the named [TomDataSourceInfo], and builds a [TomQuerySentenceCompiler] for the query types. CRUD methods compile/cache prepared statements and render them through the active [sqlDialect]; the [TomQueryBuilder] mixin supplies the expression-tree factories. Concrete drivers (e.g. [MariadbRepository]) subclass this and override [sqlDialect].

Future<TomDataScopePredicate?> _resolveScope({bool forWrite = false})

Resolves the row-scope predicate (C-3) for the current-zone principal, or null when the entity declares no @TomDbScope or its resolver opts out.

The predicate is bound (<field> IN (:__tomscope_0, …)), so a principal's allowed values ride the prepared-statement protocol as positional parameters — never concatenated into the SQL (C-7). Because the number of allowed values (and thus placeholders) varies per principal, a scoped read path prepares a fresh statement rather than reusing a cached one.

A scope kind registered asynchronously resolves through [TomDataScope.buildAsync] — the union/OR path that folds ownership and share-mode delegations (resolved from another database) into the visible id-set; every other kind takes the synchronous single-IN path. The method is async so the union path can await its cross-database resolution; the sync path completes synchronously via the returned already-completed future.

[forWrite] selects the (possibly narrower) set the principal may modify rather than the set it may see — the difference the grant-driven resource scope draws between a read grant and a full one. A scope kind that registers no write resolver writes exactly what it reads, so every other kind is unaffected.

Future<void> _assertRowWritable(K id)

Asserts the current principal may write the row keyed by [id] under the entity's @TomDbScope (C-3 write enforcement). A no-op when the entity declares no scope; otherwise a scoped read must find the row — an out-of-scope (or absent) row raises [TomDataScopeAuthorizationException].

The guard reuses the exact scoped read predicate the read paths apply (via [_selectById]), so a principal cannot update or delete a row it could not itself read, and the scope values ride the prepared-statement protocol as bound parameters (C-7). Modelling it as a scoped visibility read — not an atomic … WHERE id = ? AND <scope> with a zero-rows-affected test — deliberately sidesteps the MariaDB quirk that an UPDATE which changes no value reports zero affected rows, which would otherwise reject a legitimate in-scope no-op write. A missing row and an out-of-scope row are reported identically, so existence is not leaked across the scope boundary.

The read it performs is resolved forWrite, so a scope kind that grades its values measures the row against the writable set: a row the principal may only read is reported here exactly as an invisible one is — as not writable.

Future<void> _assertIdsWritable(Iterable<K> ids)

Asserts every id in [ids] is writable under the entity's @TomDbScope before a bulk delete. A no-op when the entity declares no scope; otherwise a scoped existence check must see all of them — if any is out of scope (or absent) it raises [TomDataScopeAuthorizationException]. Reuses the scoped [existsById] so the same bound-parameter predicate governs the check and the reads — resolved against the writable set.

Future<void> _assertInsertWritable(T entity)

Asserts the current principal may create [entity] under the entity's @TomDbScope: its scope-field value must be one the principal is allowed (C-3 write enforcement for inserts). A no-op when the entity declares no scope or its resolver opts out; an out-of-scope value raises [TomDataScopeAuthorizationException]. Without this a principal could create a row scoped to a value it cannot itself read (e.g. owned by someone else), silently bypassing the read scope.

A scope on the primary key is a no-op here: a fresh insert has no id yet, so there is no scope-field value to check — insert authorization for such entities is enforced at the service layer (the caller must hold a create grant on the parent). Applying the read scope to a null/unassigned id would reject every legitimate insert. Note this is a property of the column, not of the resolver being async: a grant-driven scope on a resource_key column carries its value on the incoming entity and is checked here like any other, which is what stops a principal from creating a row under a resource key it holds no full grant on.

The check resolves the writable value set, so a read-graded value is rejected for an insert exactly as an ungranted one is.

Future<T> saveFile(T entity, String fieldName, Stream<List<int>> bytes, {String? mediaType, String? fileName})

Uploads [bytes] to the store behind the file-reference column [fieldName], writes the resulting key into [entity], and saves the row.

Returns the stored entity, exactly as [save] does. When the column already held a key, the superseded blob is deleted by [save] itself, so replacing a file leaves nothing behind.

The order — upload, then save — is the one whose failure mode is survivable. Saving first would leave a row pointing at a key that reads back not_found: a dangling reference, visible to users and repairable only by hand. Uploading first can at worst leave an orphaned blob, which nothing references and a sweep can collect; and even that is cleaned up here when the save throws.

Stream<List<int>> openFile(K id, String fieldName, {TomBlobRange? range})

Streams the file held by the file-reference column [fieldName] of the row with primary key [id], or [range] of it.

[range] is passed to the store, which serves it natively where the backend can seek. Both authorization gates run first and unchanged: a range is a narrower read of the same bytes, never a way to reach bytes a whole read would refuse.

Reads the row through [findById], so the entity's row scope (C-3) applies unchanged: a row the principal may not see is simply not found. A column the principal may not read (C-4) raises [TomColumnAuthorizationException] rather than reporting an absent file, and a row whose column holds no key raises storage.file_reference .no_file — the caller asked for a file that is not there, which is a different answer from an empty one.

Future<TomStoredBlob?> describeFile(K id, String fieldName)

The descriptor of the file held by [fieldName] on row [id] — its media type, size and original name — or null when the row holds no key.

The metadata read that precedes a download: a caller needs the Content-Type and Content-Length before it starts streaming. Gated identically to [openFile].

Future<T> clearFile(T entity, String fieldName)

Clears the file-reference column [fieldName] on [entity] and saves the row, deleting the blob it referenced.

Expressed as a save of a nulled column rather than as its own delete path, so the orphan collection, the audit record and both authorization gates are the ones every other write goes through.

The per-row C-4 grade is checked here for the same reason [saveFile] checks it: [save] resolves the column column-wide, which is not the answer for a column with a [TomRowColumnAuthorization] resolver. Without this a principal graded read — allowed to download the file and nothing else — could delete it, which is the most destructive of the three writes.

Future<void> _discardBlob(TomBlobStore store, String key)

Deletes [key] from [store], logging rather than raising on failure.

Every caller has already completed the operation the user asked for — the row was updated, the row was deleted, the save was rolled back. A store that will not delete leaves bytes behind, which is a housekeeping problem; raising would report a completed operation as failed, which is a correctness problem. The key is logged so a sweep can find what was left.

List<(TomColumnInformation, String)> _supersededFiles(T? baseline, Map<String, Object?> written)

The (column, key) pairs whose blobs an update has orphaned: file columns that cascade, whose [baseline] value is a key, and whose newly [written] value differs from it.

Measured against the value actually written rather than the row read back: a C-4 masked column reads back as null, which would otherwise look like the file having been removed and would delete a live blob. A column absent from [written] — a read-only one — was not changed by this save and so orphans nothing.

The write counterpart of [_runPrepared], which returns rows and therefore cannot answer "how many did that touch": a DELETE returns no rows, and its count is per-execution state on the statement handle. Q _compileSentenceAs<Q extends TomQuery>(String querySentence, String key, String verb)

Compiles a caller-supplied [querySentence] and checks that it is the kind of query [Q] the calling method can actually run, raising [TomQuerySyntaxException] under [key] when it is not.

The sentence's verb selects the compiled type — find by … yields a [TomSelect], count by … a [TomCount], delete by … a [TomDelete] — so handing find by … to a counting method is a caller mistake, and a mistake in the sentence, which is why it reuses the compiler's own [TomQuerySyntaxException] rather than a repository error. [verb] names the verb the method expects, so the message says what to write instead.

A bare cast would surface a raw TypeError naming internal query classes: unclassified, unlocalisable, and outside the module's exception family.

void _assertGroupedColumnsReadable(TomGroupedSelect query)

Rejects a grouped query that touches a column the principal may not see (C-4).

The row-returning paths mask such a column — they null it out of each returned entity. A grouped query cannot: by the time the rows exist the column has already been collapsed into a group key or folded into an aggregate, so nulling the result would not undo the leak (COUNT(*) per masked group still discloses the masked values' distribution). The only sound enforcement is therefore to refuse the query outright, and to do so before it reaches the database.

static bool isUnsavedKey(Object? primaryKey)

Whether [primaryKey] marks an entity that has not yet been persisted, so [save] should INSERT rather than UPDATE.

Two unsaved conventions are honoured: a nullable surrogate key is null before its first persist, and a non-nullable int key uses a negative sentinel (the id >= 0 convention TomResourceGrant and friends rely on).

static K2? readPrimaryKey<K2>(Object? raw)

Reads an entity's primary-key value as a nullable [K2].

A not-yet-persisted entity with a nullable surrogate key (int?) carries null, which [isUnsavedKey] is explicitly designed to accept. Casting straight to a non-nullable K (e.g. int) threw Null is not a subtype of int on every insert of such an entity, defeating the very check that gates INSERT vs UPDATE — so the read must tolerate null. Negative-sentinel int keys arrive non-null and are handled by [isUnsavedKey] all the same.

static (String, List<String>) buildInsertStatement(String table, List<TomColumnInformation> columns)

Builds the INSERT statement and its ordered bind-parameter names for [table] over the writable [columns] (the caller filters out read-only columns such as an auto-increment primary key).

Each value binds through a :declaredName placeholder, and the parameter list is those declared names in column order — matching the :name -> ? substitution and positional binding prepareStatement performs from [TomLiteralSelect.getParameters].

static (String, List<String>) buildUpdateStatement(String table, List<TomColumnInformation> columns, TomColumnInformation primaryKey)

Builds the UPDATE ... SET ... WHERE pk = :pk statement and its ordered bind-parameter names for [table] over the writable [columns], keyed on [primaryKey].

The SET clause assigns each column by its mapped column name; the trailing WHERE scopes the update to the single row by the primary key (its placeholder name and bind name is the pk's declared name, appended last). Without that clause the statement would rewrite every row.

static List<String> _extractPlaceholderNames(String sql)

Extracts :name placeholder names from [sql] in textual order (repeats included), so a raw statement can be prepared and its values bound positionally in the order the ? slots appear.

Delegates to the shared, quote-aware [SqlPlaceholderScan.extractNames] so this extraction and [MariaDbDatasource.toPositionalStatement]'s positional rewrite tokenise identically — including skipping a :name-looking substring inside an inlined string literal.
