class TomBaseServerConfiguration

abstract class TomBaseServerConfiguration

Reflected base class for a server's configuration.

Subclasses declare typed fields (port, TLS material, handlers, logging, …); the reflection layer fills them from the merged configuration sources in the constructor. The defaults below are sensible for local development — notably [certificateChain] / [privateKey] hold a throwaway self-signed localhost pair that MUST be overridden in production.

Sources are merged by [getDefaultValues] with later sources overriding earlier ones: configuration resources, then the OS environment, then a .env file, then command-line arguments (which win).

The JWT fields ([jwtRsaPubKey] / [jwtRsaPrivKey] / [jwtSharedSecretKey]) are the server's signing key material, read by [installJwtSigning] — which a boot calls once, after the runtime environment is selected and before anything mints or verifies a token. A field left null falls back to the framework's bundled sample key, which is permitted in a development or test environment and refused anywhere else. The rest of a signing configuration — algorithm, issuer, audience, expiry — is supplied in code, because there are no configuration keys for those.

Constructors

TomBaseServerConfiguration.new(List<String> args)

Creates the configuration, resolving and applying values from all sources (see [getDefaultValues]) for the given [args].

[args] is assigned to the field of the same name after [setValues], so the record of the invocation survives a merged key that happens to be spelled args. Both are last for a reason: [setValues] runs first because a subclass's constructor body must see the resolved fields, and the args assignment runs after it because the invocation is the meaning this field promises.

The instance also registers itself as the isolate's active configuration, which is what [tomAppId] resolves through. Registering the object rather than reading [appId] out of it here is the point: the subclass constructor body has not run yet, so there is no value to read — only an object that will have one.

For the same reason it installs a resolver over [tomAppId] as the kernel's remote-log sender rather than a copy of it. A remote log collector names its per-client files after the sender, so without this every application reports the kernel's default — and several servers of one deployment, which is exactly when a collector is worth running, write into one file set distinguished only by isolate name. The closure is installed here because this is the one place that already says "this isolate's application is me", and it is idempotent: a second configuration in the same isolate installs an equivalent closure over the same getter.

A field an application marked [TomRequiredField] is checked here too, by [assertRequiredSettings], with the merged map and before the instance registers itself: a configuration that refuses to start must not become the isolate's active one on its way out.

It applies the kernel's protection settings from [args] too ([TomResourceKeyProtection.applyArguments]), so tom.protection=false or tom.protection.json=false on a server's command line switches the authorization system or one tier of it off. A misspelt setting throws before anything else is configured: a server that believed a tier off while it was on — or the reverse — is worse than one that does not start.

Properties

String appId

The application's own name — what this server calls itself in a log, a diagnostic, or anywhere else several servers meet.

It is an ordinary configuration key, so the merge can supply it (appId in a resource file, the environment, .env, or appId=… on the command line). A server that has a fixed name states it in its constructor body instead, and one that wants both states it the way [port] does, so the configured value wins: 

MyConfiguration(super.args) {
  if (appId.isEmpty) appId = 'billing';
}

Whichever way it is set, [tomAppId] reports it process-wide; nothing else needs to publish it.

List<String> args

The command-line arguments this configuration was built from.

The one derived field on this class: every other field answers "what was I told", this one answers "how was I invoked". It is not a configuration key — the constructor assigns it from its own parameter after [setValues] has run, so a merged key spelled args cannot displace the real invocation. Such a key is still merged and still visible in [getDefaultValues]'s result; it just does not land here.

Note that a merged args key whose value is not a List<String> — an args=x argument parses to a String — still fails inside [setValues] before this assignment is reached. That is deliberate: the message names the field and the offending value, which is the right answer for a configuration that set a key it should not have.

This may hold a secret. The command line is one of the out-of-band channels a deployment uses to supply [smtpPassword], [smsApiKey] and the rest, so the invocation recorded here can contain them verbatim. Log or serialize individual fields, never this list.

String serverHeader

The Server response header. Empty (the default) sends none.

Applied to the bound [HttpServer] after it is listening, so it names the deployment, not a route. An empty string is the "say nothing" value rather than a header with no value: [TomServer.start] translates it to null, which is what leaves the header off the wire. Naming the product and version here tells every client — and every scanner — what is running, so a deployment that would rather not say leaves this as it is.

bool autoCompress

Whether the bound [HttpServer] compresses responses it judges compressible.

true by default, and only ever turned on by [TomServer.start] — the flag gates an assignment, so setting this false leaves the socket at Dart's own default rather than actively disabling compression. Turn it off where a proxy in front of the server already compresses, or where response bodies are encrypted or already compressed and the pass would only cost CPU.

String poweredByHeader

The X-Powered-By response header. Defaults to "tom"; empty sends none.

Passed to shelf_io.serve, so unlike [serverHeader] it is fixed when the socket is bound. Empty is again the "say nothing" value, translated to null before the bind.

bool noSsl

Whether to bind a plain HTTP socket instead of a TLS one.

false by default, which is the safe direction: a deployment gets TLS unless it asks not to. When true, [TomServer.start] builds no [SecurityContext] at all and [certificateChain] / [privateKey] are never read — which is the supported way to run behind a TLS-terminating proxy, and the only honest way to run without a certificate. Reading [TomServer.securityContext] afterwards reports what was built; this field reports what was asked for.

bool listenToAnyIP

Whether to bind every interface, overriding [host].

Read after [host], so true wins: [TomServer.start] resolves the listen address from [host] (or [InternetAddress.anyIPv4] when it is empty) and then replaces it with anyIPv4 if this is set. So it is not "also listen on any IP" — it is "ignore whatever host was configured", which is the setting a container image wants when the host it inherited from a configuration file names an address that does not exist inside the container.

int port

HTTP bind port. 0 is the "unconfigured" sentinel: [setValues] (config / env / port=) overwrites it when a port is supplied, otherwise a subclass constructor — which runs after the base constructor's [setValues] call — applies its own default via if (port == 0) port = …. A literal default here (e.g. 8080) would defeat that guard, since the field would never be 0 for the subclass to detect "no port configured".

Either command-line spelling reaches it: a key is the argument text before the first = with its leading dashes stripped, so port=8080 and --port=8080 are one argument naming this field (see doc/cmdline.md).

String certificateChain

The PEM-encoded TLS certificate chain [TomServer.start] binds with, unless [noSsl] is set.

The default is a throwaway self-signed localhost pair committed to this repository, and its private key is public. It exists so a development machine can speak HTTPS without a certificate authority. Nothing refuses to start when a deployment leaves it in place, so overriding this and [privateKey] together is the deployment's responsibility — a server still serving this chain in production is authenticating itself with a key anyone can read.

Supplied as PEM text rather than a path, which is what lets a container inject it through the environment; the bytes are handed to [SecurityContext.useCertificateChainBytes] unparsed, so a malformed value fails at bind time and not before.

String privateKey

The PEM-encoded TLS private key for [certificateChain]. A credential: handle it exactly as the marked settings below are handled.

The default is the private half of the checked-in self-signed pair and is therefore public. See [certificateChain]: the two are overridden together or not at all, since a chain without its matching key binds nothing.

Never log this field, and never log [args], which may carry it. The bytes are handed to [SecurityContext.usePrivateKeyBytes] unparsed.

It carries a different wording from the marked settings on purpose. That marker is a controlled one: doc/configuration.md tabulates the four out-of-band blocks a deployment supplies — JWT signing, server self-login, outbound mail, outbound SMS — and a test holds the marked fields and that table to each other, so a field marked without a row there fails. TLS material has no row: it is documented by the limitation naming the checked-in pair. The difference is about which document owes a row, not about how carefully this value is handled.

String? jwtRsaPubKey

PEM of the RSA public key that encrypts the payload section of an issued token; read by [installJwtSigning].

Null means "not configured", and every one of the three JWT fields means that by being null rather than by holding a sentinel: a default that looked like a key could not be told apart from a key, which is how a server came to sign with a published passphrase and report nothing.

Environment name: JWT_RSA_PUB_KEY (see [getDefaultValues]).

String? jwtRsaPrivKey

PEM of the RSA private key that decrypts the payload section; the counterpart of [jwtRsaPubKey] and secret-bearing.

Environment name: JWT_RSA_PRIV_KEY.

String? jwtSharedSecretKey

Passphrase of the HMAC key that signs an issued token, and the one setting two servers must agree on to trust each other's tokens.

The auth server that issues and the application server that verifies share this value and nothing else; set it in one only and the second rejects the first's tokens. Secret-bearing: whoever holds it can mint a token this deployment accepts.

Environment name: JWT_SHARED_SECRET_KEY.

String? authServerLoginUri

Absolute URI of the auth server's login endpoint, e.g. https://auth.example.com/auth/login.

Not secret, but deployment-specific: it belongs in the deployed config tree / environment, not in a spec (codespecs_mapping.md §5.16, CE-CF). null or blank disables server self-login.

String? serviceAccountName

The login name of this deployment's service account.

null or blank disables server self-login.

String? serviceAccountCredential

The service account's secret — secret-bearing per codespecs_mapping.md §5.16.

Its declaration lives here (so the shape and the source key are known); its value is never authored. It is supplied out-of-band at deploy time through the ordinary CE-CF precedence chain — OS environment, .env, or command line — and must never be written into a spec or a checked-in configuration tree, the same rule that governs [privateKey] and the JWT keys above.

null or blank disables server self-login.

String? serviceAccountOrganization

Organization presented with the deployment's own login; null for a single-tenant deployment.

String? serviceAccountApplication

Application the deployment logs into; null when the auth server does not scope service logins by application.

String? serviceAccountProcess

Process (sub-context of [serviceAccountApplication]) the deployment logs into; null when unscoped.

String? serviceAccountClient

Client identifier the deployment's own login originates from; null when the auth server does not scope service logins by client.

String? smtpHost

The mail server's host name; null or blank means this deployment sends no mail.

Deployment-specific but not secret, like [authServerLoginUri] (codespecs_mapping.md §5.16, CE-CF).

int smtpPort

The mail server's port. 0 is the "unconfigured" sentinel — the same convention as [port] — and lets the transport pick the default that goes with [smtpSecurity] (25, 587 or 465) rather than forcing every deployment to restate a number the protocol already implies.

String smtpSecurity

How the connection is secured: none, startTls or implicitTls.

Defaults to startTls, which is both the common case on port 587 and the safe one: an unrecognised value falls back to it too, because failing closed on a typo is the only acceptable direction for a setting that decides whether a password crosses the network in the clear.

String? smtpUsername

The login name presented to the mail server; null or blank for an unauthenticated relay.

String? smtpPassword

The mail server password — secret-bearing per codespecs_mapping.md §5.16.

Its declaration lives here (so the shape and the source key are known); its value is never authored. It is supplied out-of-band at deploy time through the ordinary CE-CF precedence chain — OS environment, .env, or command line — and must never be written into a spec or a checked-in configuration tree, the same rule that governs [serviceAccountCredential], [privateKey] and the JWT keys above.

Supplying [smtpUsername] without this value is rejected when the settings are built, so the omission surfaces at startup naming the setting rather than as a 535 on the first notification.

String? smtpFromAddress

The address mail is sent from when a message does not name its own.

Most relays require the envelope sender to be an address they are authorised to send for, so this is effectively mandatory for any deployment that actually sends.

String? smtpFromName

The display name shown beside [smtpFromAddress]; null to send the bare address.

String smtpClientName

The name announced in EHLO.

Some relays check that it resolves. localhost is accepted by most and is the honest answer for a server that has no public name.

bool smtpAllowInsecureCertificate

Whether to accept a mail server certificate that does not validate.

false, and it should stay that way in any deployment. It exists because self-signed certificates are common on internal relays, and a developer who cannot turn this on will set [smtpSecurity] to none instead — which is strictly worse, since it sends [smtpPassword] in the clear.

String? smsEndpoint

The gateway's submit URL; null or blank means this deployment sends no SMS.

Deployment-specific but not secret, like [smtpHost] (codespecs_mapping.md §5.16, CE-CF). Must be http or https; anything else is rejected when the settings are built, so a typo surfaces at startup rather than as an unroutable request at 03:00.

String? smsApiKey

The gateway credential — secret-bearing per codespecs_mapping.md §5.16.

Its declaration lives here; its value is never authored. Supplied out-of-band at deploy time through the ordinary CE-CF precedence chain, exactly as [smtpPassword] is.

String? smsApiSecret

The second half of a two-part gateway credential — secret-bearing.

Required only by [smsAuthScheme] basic, where [smsApiKey] is the user and this is the password. Gateways that authenticate with a single bearer token leave it unset.

String? smsSenderId

The sender shown to the recipient — a short code, a long number, or an alphanumeric sender id where the destination country permits one.

A message may override it through [TomMessage.metadata]; this is the default for the ones that do not.

String smsAuthScheme

How the credential is presented: none, bearer or basic.

Defaults to bearer, and an unrecognised value falls back to it. That fallback is safe in a way [smtpSecurity]'s is not — the worst outcome is a 401 from the gateway, not a credential sent in the clear — but it is still the setting to check first when a gateway rejects every request.

Gateways that want the key in the payload rather than in a header use none here and name the field on the protocol.

int smsTimeoutSeconds

How long to wait for the gateway before treating the attempt as deferred.

A timeout is transient: the message may well have been accepted, and the only honest answer is to retry and let the message id deduplicate.

int smsMaxSegments

The most segments a single message may occupy, or 0 for no cap.

Three is roughly a paragraph. The cap exists because segmentation is invisible at composition time — a template that gains one sentence, or a parameter that arrives with an umlaut in it, can quietly triple the cost of every message the deployment sends. Over the cap fails permanently at send: a message too long now is too long on the retry.

String host

The bind host. Empty (the default) makes [TomServer.start] listen on [InternetAddress.anyIPv4]; set a concrete host to bind a specific address. The default must stay a genuine address or the empty string; a placeholder such as "t" or "0" binds nothing.

int isolateCount

How many worker isolates the deployment runs. Defaults to 10.

The framework reads it for one decision only: a count above 1 binds the socket with shared: true, so several isolates can accept on the same port. Actually starting the isolates is the application's boot step — TomWorkerPool.withSize(configuration.isolateCount, …) — which is why a deployment that raises this without also sizing its pool from it gets a shared socket and one listener.

0 is meaningful: a boot that reads it takes it as "no pool, serve from the main isolate", and the socket is then bound unshared.

FutureOr<Response> Function(Request) Function(FutureOr<Response> Function(Request))?? authenticationMiddleware

Replaces the authentication layer of [TomServer.start]'s pipeline.

null (the default) installs [tomDefaultAuthenticationMiddleware], which is what reads the bearer token and publishes the principal into the request zone. A replacement takes over that whole responsibility: everything downstream — authorization, delegation, audit attribution — reads the principal this layer established, so a middleware that publishes none leaves the pipeline running as nobody rather than failing.

Supply one to authenticate against something this package does not model. Wrapping rather than replacing is usually what is wanted, and shelf's Middleware composes, so a custom layer can call the default and add to what it produced.

Response? Function(Request, Object, StackTrace)?? errorHandler

Replaces the server's default error response.

null (the default) leaves [TomServer.errorHandler] in place, which renders [tomErrorEnvelope] as a 500 with x-tom-error: true and a JSON content type. Installed at two pipeline layers — the inner one below authentication, and the outer one when [authenticationErrorHandler] is null — so a single handler here covers both unless the two are separated deliberately.

Returning null from the handler rethrows the original error rather than answering, which is the way to handle some failures and leave the rest to shelf. The error and its stack trace are already logged before the handler is called, so a handler that only wants to log has nothing to add.

A handler that puts a message in its body must read it through TomServerException.clientMessage, not from defaultUserMessage. The clientThrow flag is the thrower's statement about its own text, and five types in the package set it false because their messages describe server internals — an unreachable data source, a failed audit write, a misconfigured identity provider. The default handler is safe by construction because [tomErrorEnvelope] carries no message at all; a handler that adds one takes the obligation on.

Response? Function(Request, Object, StackTrace)?? authenticationErrorHandler

Replaces the error response for failures raised at or above the authentication layer.

Falls back to [errorHandler] when null, which is the default, so the two differ only where a deployment wants them to. Separating them is worth it when an authentication failure should answer differently from an application one — a 401 with a WWW-Authenticate challenge rather than the 500 envelope, say — since this layer sits outside the authentication middleware and therefore sees what it throws.

FutureOr<Response> Function(Request)?? preExecutionHandler

A handler offered the request before the router, in a shelf [Cascade].

null (the default) leaves the router alone. A cascade tries each handler in turn and takes the first response that is not a 404, so this one answers or steps aside: return a response to serve it, or a 404 to let the router handle the request as usual. It is not middleware — it cannot see or alter what the router returns, and it runs inside the pipeline, so the principal and the request context are already established.

Serving a fixed asset or a redirect that must not reach the router is the case for it.

FutureOr<Response> Function(Request)?? postExecutionHandler

A handler offered the request after the router, in the same [Cascade].

Reached only when the router answers 404, which is what "after" means here: it is a fallback, not a post-processing step, and it never sees the router's response. Use it for a catch-all — a single-page-application index, a custom not-found body — and use [loggingMiddleware] or a [Middleware] of your own when the response itself has to be inspected or changed.

FutureOr<Response> Function(Request) Function(FutureOr<Response> Function(Request)) loggingMiddleware

The middleware that emits the per-request access-log line.

Installed as the innermost layer of [TomServer.start]'s pipeline, so it sees the response the router produced. The default, [tomLoggingMiddleware], emits one line per request but only when the request's [TomRequestLogInfo.shouldBeLogged] is set and it has not already been logged.

Shelf's own logRequests() is the obvious alternative and drops in unchanged — it is a Middleware of the same shape and adds request timing, which the default does not report: 

loggingMiddleware = logRequests(
  logger: (String s, bool error) =>
      error ? tomLog.error(s) : tomLog.info(s),
);

It is not the default because it reads nothing from the request context, so it can honour neither guard. The consequential one is shouldBeLogged: the endpoint pipeline copies each endpoint's logRequests flag onto it, which is how TomHealthService keeps a /health probe arriving every few seconds out of the log. Substituting shelf's middleware silently re-enables the line for every endpoint that opted out. hasBeenLogged likewise stops being honoured, so a retried or re-entered request logs once per pass.

It also logs the error path, which this layer deliberately does not: it sits inside _handleError, which already logs the error and its stack trace, so shelf's middleware reports every failed request twice.

Choose it when timing matters more than the opt-out — a load test, or a deployment with no suppressed endpoints — and expect health-probe noise and doubled error reports.

bool isolateLogging

Whether the deployment moves logging into an isolate of its own.

Read by the application's boot, not by the framework: the step it gates is TomIsolateLogging.startIsolatedLogging, which a main calls once in the main isolate. Declared here so it arrives through the same merge as every other setting rather than being read from the environment by hand.

true by default. Isolated logging keeps formatting and writing off the request path, which matters most for a worker pool, where every isolate would otherwise write to the same sink; the cost is that a log line is posted to another isolate, so a process that dies abruptly can lose the last of them.

String logLevelExceptions

Per-logger log-level overrides, as name1=level1,name2=level2.

Not a level for exceptions. It is the pattern TomLogger.setLogLevelExceptions parses, where each entry raises or lowers the level for one logger name against the global [logLevel] — the "exception" is to the global setting, not an error. MyClass=DEBUG turns one class up while the rest of the deployment stays at INFO.

Empty (the default) sets no override. An unparseable pattern is logged and otherwise ignored, so a typo here loses the overrides silently rather than stopping the boot. Applied by the application's boot alongside [logLevel]; the framework only carries the value.

String logLevel

The global log level, by name: TRACE, DEBUG, TRAFFIC, INFO, WARN, STATUS, ERROR, SEVERE, FATAL, or one of the aggregate names (ALL, DEVELOPMENT, EXTENDED, ERRORS, PRODUCTION, STILL, SILENT, OFF).

Empty (the default) leaves the logger at whatever it already had, so a deployment that says nothing does not get silence. An unrecognised name is reported as an error and the level is left alone.

Applied by the application's boot — tomLog.setLogLevelByName(...) — and not by the framework, which is why it takes effect at the point that call is reached: everything logged earlier in the boot, this class's own merge included, is emitted at the previous level.

Environment name: LOG_LEVEL (see [getDefaultValues]).

String databaseMigrationsDirectory

The directory TomDbMigrations.migrateDatabases reads, relative to the working directory unless absolute.

Defaults to ./database_migrations, which is where every sample keeps them — and since the path is relative, a server started from anywhere but its package root finds no migrations rather than failing to find the directory. Migration is the application's boot step, so nothing in the framework reads this; it is declared here so the path is configurable per deployment through the same merge as the rest.

The directory holds one subdirectory per datasource name, which is what ties a migration set to the datasource key it belongs to.

Methods

bool usesDevelopmentTlsMaterial()

Whether either half of the TLS material is still the checked-in development pair.

Either half, not both, because the two halves fail differently and both are worth hearing about. A default [privateKey] means the server authenticates itself with a key published in this repository, which is the danger this getter exists for. A default [certificateChain] beside an overridden key is a different fault with the same remedy: the pair does not match, so the socket fails to bind — and saying so before the bind is cheaper than reading the error afterwards.

Compared against [developmentCertificateChain] and [developmentPrivateKey], which are the very constants the fields default to, so the check cannot drift from what it checks.

It says nothing about whether TLS is served — [noSsl] answers that, and a plaintext server carrying the default pair is not doing anything wrong. [TomServer.warnOnDevelopmentTlsMaterial] puts the two questions together. A method rather than a getter, and on this class that is a distinction the documentation rests on: the Properties table of api_summary_configuration.md is the list of knobs a deployment sets, held to the class's fields by a census, and a computed answer standing among them would blur the two.

void setValues(Map<String, Object?> values)

Assigns the merged configuration [values] onto this instance.

Implemented by the generated reflection for the concrete subclass; each known field is set from the matching key in [values].

Implement it with the shared tomReflectionInfo, not with a TomReflectionInfo(strictUnknownFields: true). Strictness turns a key naming no field into reflection.set.unknown_field, which is the right setting for a map whose two ends are both yours — and [values] is not that map. [getDefaultValues] merges the entire process environment into it, in both the SCREAMING_SNAKE_CASE spelling and the field spelling [TomArgs.resolveEnvironmentNames] derives from it, so a configuration resolved on an ordinary developer machine arrives here carrying PATH, path, HOME, home and eighty or so of their neighbours. A strict converter would refuse the first of them and no server would start.

The cost is the one strictness exists to remove: a key misspelled in a configuration file is dropped in silence and the field keeps its default. Catching that needs the check applied to the configuration layer alone, before the environment is merged over it — a narrower question than this method is in a position to ask.

void assertRequiredSettings(Map<String, Object?> values)

Throws when a field marked [TomRequiredField] was supplied by no source.

Called by the constructor with the map [getDefaultValues] merged, which is the only place the question can be asked: the answer is "did any source name this setting", and no single source knows. Binding cannot report it — an unsupplied setting leaves the field at its initialiser, which reads exactly like a setting nobody required, so the failure would otherwise surface much later as a connection to localhost:0 or an empty application id.

Nothing on this class carries the annotation, and nothing should: every field here has a documented default, and a field a constructor falls back for is not required. An application marks its own: 

@tomReflector
class BillingConfiguration extends TomBaseServerConfiguration {
  @TomRequiredField()
  String dbUrl = '';

  BillingConfiguration(super.args);
}

Every missing setting is named at once, in declaration order, so a deployment fixes them in one pass rather than one restart at a time. A key present with a null value counts as missing — a .env line DB_URL= names the setting without giving it one — while an explicitly empty command-line value (dbUrl=) counts as supplied. That is the distinction the conversion table draws deliberately; see [TomReflectionInfo.missingRequiredFields].

Public and separate from the constructor so a configuration composed some other way — a test, a tool that merges its own sources — can ask the same question of the same map.

A configuration with no mirrors is not checked. The annotation is read through reflection, so a subclass that implements [setValues] by hand instead of through the generator has none to read, and this method has nothing to report rather than a failure to report. That is a supported shape — a test or a tool composing a configuration without codegen — and it is the same class of object for which setValues was already the subclass's own affair. A server whose setValues is generated is reflected by construction, so the check is in force wherever the framework binds the fields.

Static

static String developmentCertificateChain

The PEM certificate chain [certificateChain] defaults to: a throwaway self-signed localhost pair committed to this repository.

Named rather than written inline so that [usesDevelopmentTlsMaterial] compares against the very text the field defaults to. A fingerprint or a copy would be a second statement of the same value, and the check would go quiet the day the two drifted apart.

static String developmentPrivateKey

The PEM private key [privateKey] defaults to, and the reason [usesDevelopmentTlsMaterial] exists: it is published, in this repository, so a server serving it authenticates itself with a key anyone can read.

static Map<String, Object?> getDefaultValues(List<String> args)

Builds the merged value map used to populate a configuration instance.

Starts from a deep copy of the active provider's [TomServerConfigResourceProvider.resources] and overlays, in increasing precedence: the OS environment, a .env file (./.env), then the parsed [args]. Command-line arguments therefore win. The copy is essential: the merges below mutate their first argument in place, so merging into the provider's own resources would permanently inject the environment, the .env file and the CLI args into the process-wide provider. [deepCopyJsonTree] is the kernel's primitive for exactly this; a shallow Map.from would leave every nested subtree shared and defeat the copy.

Environment names

Both environment sources pass through [TomArgs.resolveEnvironmentNames], so a variable written SCREAMING_SNAKE_CASE also arrives under the lowerCamelCase field name it spells: JWT_SHARED_SECRET_KEY sets [jwtSharedSecretKey], LOG_LEVEL sets [logLevel], PORT sets [port]. The verbatim key is kept as well, and a variable already spelled as the field wins over its screaming twin.

Resolution happens per source, not on the merged result, so a resolved name inherits the precedence of the source it came from — a PORT in the OS environment still loses to a port= argument.

The command line is deliberately left out of it. An argument names its field directly — port=9081, or --port=9081, since TomArgs strips a key's leading dashes (see doc/cmdline.md) — so there is no naming convention to reconcile, and accepting a SCREAMING_SNAKE_CASE argument as well would widen the surface without gaining a source.

class TomServerConfigResourceProvider

class TomServerConfigResourceProvider

Holds the resolved configuration tree and answers property lookups for [TomConfig].

A single provider is shared process-wide through [getServerConfig]; install a populated one at startup with [setServerConfigProvider] or by setting the static [loader]. Keys may be dotted paths into the nested [resources] map (resolved via the kernel's tree walker).

A dotted key is tried as a path first and as a literal top-level key only if the walk fails, so server.port reads the same value whether it was written nested under server: or flat as server.port:. Where a tree carries both, the path wins and the flat key is unreachable — never merged and never reported. Use one spelling per key.

Methods

bool exists(String s)

Whether property [s] exists, as a dotted tree path or a top-level key.

A property configured explicitly as null exists: [getObjectFromTree] resolves it rather than throwing, so the tree leg returns true for it. That is the point of the distinction — a deliberately cleared setting is configured, and [TomConfig] must see it as configured so it does not silently substitute a default the operator was overriding.

Object? get(String s)

Returns property [s] (dotted path or top-level key).

Gate on [exists] first. This method is total — it never throws, and it never answers null for a key the tree does not hold — so it cannot, by itself, report a key nobody configured. An unknown key resolves to the key string [s]; [exists] is what separates that from a value. [TomConfig] gates, and a caller reading through it inherits the gate.

That is the contract rather than a gap, and the reason is the pair of answers it keeps apart. null means the property is present and explicitly cleared; the key string means unknown. Answering null for both would collapse them, and the distinction is the one [exists] was built to preserve: a cleared setting is configured, and [TomConfig] must see it as configured so it does not substitute the default the operator was overriding. Throwing instead would cost the other half — a read that cannot fail is what lets a caller walk a tree of optional settings without a try at every step.

The fallback is indistinguishable from a configured value that equals its own key, which is the price and is why the gate is [exists] rather than a test on the value. The cost of forgetting it is the one this API cannot remove: a missing host reads back as the host name host, and the failure surfaces at connect time rather than at lookup. Every read in this package is gated, and configuration_test.dart fails on one that is not.

Static

static TomServerConfigResourceProvider? _configProvider
static Map<String, dynamic> Function()?? loader

Optional factory for the default provider's [resources]. When set, it is invoked the first time [getServerConfig] lazily creates a provider.

It is reachable only before a provider exists. The call is in the default constructor, which [getServerConfig] runs on its creating access, so once [setServerConfigProvider] has installed anything this hook can never fire — setting it afterwards is silently inert. Use [TomServerConfigResourceProvider.load] from that point on; it defers the same build, scoped to one provider instead of standing as a process-wide default.

static void setServerConfigProvider(TomServerConfigResourceProvider provider)

Installs [provider] as the process-wide configuration source.

static TomServerConfigResourceProvider getServerConfig()

Returns the active provider, creating a default one (using [loader] if set) on first access.

The provider created here when [loader] is unset is a placeholder: it holds nothing, and nobody asked for it. It is returned rather than refused, so a direct exists/get still answers, but it is marked (see [isUnconfiguredPlaceholder]) and [TomConfig] refuses to resolve against it — a property that resolves before its configuration exists is the ordering mistake, and taking the placeholder's answer hides it.
