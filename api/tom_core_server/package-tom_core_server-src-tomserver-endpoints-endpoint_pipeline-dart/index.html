class TomEndpointHandler

class TomEndpointHandler

Serves one endpoint: binds a reflected service [method] to a route and runs the per-request pipeline.

For each request [handleMethodCall] answers CORS preflight, enforces access ([checkAccess] / [checkAutomaticAccess]), materialises the method's parameters from the request (principal/token from the zone, the request object, path/query params, JSON body, request or execution context), optionally wraps the call in a transaction, invokes the method by reflection, and converts the result (or any error, via the endpoint's [TomErrorHandler]) into a shelf Response.

final bool declaresNoResult

Whether this endpoint's declaration promises the caller no result, so that the response body is empty whatever the invocation completes with.

Future<void> does not erase the value it completes with, and Dart lets an implementation narrow the return type: a method declared Future<void> whose body tail-calls one returning Future<int> — every delete endpoint forwarding to [TomRepository.deleteById] does — hands the pipeline an int while every static type between the two says there is nothing there. The value cannot be recognised once it arrives, so the declaration is asked instead.

Read off [TomMethodMetadata.methodMirror] — the declaration the @TomEndpoint annotation sits on — rather than off [method], the implementation's. They differ exactly when the implementation narrows, and the annotated one is both the wider of the two and the contract: the client's typed proxy is generated from it and has nowhere to put a body.

A reflector without reflectedTypeCapability cannot answer, and then the endpoint keeps the ordinary treatment — an unrenderable result is a failure there, which is the right answer for a genuinely unrenderable one.

Object _requirePrimitive(Type type, String raw, {required String parameter, required String source})

Binds [raw] — a URL value from [source] — to the primitive [type] of the parameter called [parameter], or refuses the request.

Reached only when [isBindablePrimitive] has already answered true, so a null from the coercion means exactly one thing: the caller sent a value this parameter cannot take. That is a statement about the request, and the client is the party who can fix it — which is why it leaves as a named exception carrying the parameter, the type and the offending value rather than falling through to the remaining strategies. Falling through ends with the parameter unbound and the request refused by unbindable_parameter, a message that names neither the value nor the fact that it was nearly right.

Future<void> enforceAccess()

Enforces this endpoint's access rule for the principal in the current zone, auditing and throwing on a denial.

Shared by every endpoint kind — the HTTP pipeline and the WebSocket handshake alike — because "may this caller reach this endpoint?" is the same question regardless of what happens after the answer is yes. A socket that authorized itself separately would be one place for the policy to drift out of step.

Future<List<Object>> bindParameters(Request req, {Map<Type, Object> extraByType = const {}})

Materialises the endpoint method's positional arguments from [req].

Each parameter is resolved by the first binding strategy that succeeds: a value supplied by the caller in [extraByType], the zone's [TomPrincipal] / [TomClientJwtToken], the request object itself, the request context (by type or by name), a primitive path or query value, the execution context, the decoded multipart/form-data body (whole form or a single file part), and finally the request DTO built from the JSON or form body folded together with the URL parameters.

[extraByType] is how an endpoint kind contributes a value the generic strategies cannot know about — a WebSocket endpoint passes the [TomWebSocketConnection] this way. It is consulted first, so a kind-owned value is never shadowed.

Shared by [handleMethodCall] and [handleWebSocketCall]: the two differ in what they do with the invocation, not in how the handler's parameters are found.

List<Object> _toPositionalArguments(List<Object> slots)

Turns the one-slot-per-parameter list built by [bindParameters] into the argument list [InstanceMirror.invoke] is called with, or throws naming the parameter that makes the call impossible.

Exactly one shortening is legitimate: dropping trailing optionals, which is how Dart applies their defaults. Every other unfilled slot is refused, because there is no way to express it — an omission anywhere else silently moves later arguments into earlier parameters, and where the types happen to line up the method is invoked successfully with the wrong values in it. A named exception identifying the parameter is the alternative to that: "wrong number of arguments" points at the generated call site, this points at the declaration that cannot be satisfied.

Future<Response> handleMethodCall(Request req)

Runs the full request pipeline for this endpoint and returns the response.

Handles preflight, access control ([enforceAccess]), reflection-based parameter binding ([bindParameters]), optional transaction wrapping, method invocation, and result/error conversion (see the class doc).

A WebSocket endpoint takes the sibling path, [handleWebSocketCall], which shares the first two stages and replaces the rest with a socket lifetime.

Future<Response> _handleMethodCallInScope(Request req)
Future<Response> handleWebSocketCall(Request req)

Serves a WebSocket handshake for this endpoint and runs the handler for the lifetime of the accepted connection.

The first two stages are the HTTP pipeline's own — [enforceAccess] and [bindParameters] — and run before the upgrade, so an unauthorized or unbindable call is refused as an ordinary HTTP error rather than as a socket that opens and immediately dies. What replaces the rest of the pipeline is the socket's lifetime: the handler is invoked once, with the live [TomWebSocketConnection] among its arguments, and the socket is closed when it returns.

A transaction is deliberately not offered here — see the mounting check in createRoutesForEndpoint.

Future<void> _serveSocket(String reqId, Request req, String callName, TomWebSocketConnection connection, List<Object> positionalArguments)

Invokes the socket handler and closes the connection when it returns.

Runs inside the captured request zone (see [handleWebSocketCall]), so the handler sees the same principal and execution context an HTTP handler would.

bool checkAccess(TomPrincipal? principal)

Decides whether [principal] may call this endpoint from its resolved [TomAccessControl] — the handler-side override if present, otherwise the contract-declared policy (G-API-3) — falling back to the global protection default when neither declares an access rule.

bool checkAutomaticAccess(bool accessCheck)

Second-chance access check via resource-key protection, over the pair of keys [automaticProtectionKeys] names. Takes the prior [accessCheck] and returns the possibly-upgraded decision.

The rule is: holding the container key grants every member of it, unless the principal also holds the negated member key -<member>; otherwise only the member key itself grants. A principal holding neither is left with the decision it arrived with — enforceAccess only consults this after the ordinary check has already refused, so this can raise a refusal to a grant but never invents one of its own.

Note the polarity of [TomResourceKeyProtection.isProtected]: it answers "the principal lacks this key". Every key in the list, -<member> included, is something the principal holds — the minus is part of the name of a revocation, not a negation of the test. Which is why a * grant never covers a - key ([TomAccessControlInformation.holdsResourceKey]): a principal granted every container is not thereby issued every revocation.

Nothing is granted while resource keys are not enforced ([TomResourceKeyProtection.globalSettingProtectionDefault] off). There, isProtected answers "held" for every key there is, so a second chance taken from it would overturn every refusal the ordinary check made — a role requirement included — and asking about -<member> would report every revocation as issued. With no grants in force there is nothing to grant from, and the prior decision stands.

static bool isBindablePrimitive(Type type)

Whether [type] is a primitive this module binds from a raw URL string.

The question [coercePrimitiveParameter]'s answer cannot carry. That method returns null for two conditions that are different answers — a Request parameter, which is not a primitive at all and should fall through to the next binding strategy, and ?count=abc on an int, which is a client error — and a single null cannot express both. Asked first, this separates them: past it, a null means the value did not parse.

Kept as a predicate rather than folded into the coercion's return type because the coercion is a pure function with other callers and tests of its own, and the binding loop is the one place that has to tell the two cases apart.

static bool? _coerceBool(String raw)

[raw] as a bool, or null when it is no spelling of either.

Case-insensitive: TRUE, True and true are one word written three ways, and a caller who capitalises is not making a different statement.

static Object? coercePrimitiveParameter(Type type, String raw)

Coerces a raw URL string (a matched path variable or a query-string value) into the method parameter's primitive [type], or returns null when [type] is not a bindable primitive (so the caller falls through to the other binding strategies).

Such values always arrive as strings, so the numeric and boolean forms are parsed; a value that will not parse also yields null. The two nulls mean different things and are told apart by asking [isBindablePrimitive] first — which is what the binding loop does, and what makes a malformed value a named refusal rather than a parameter that quietly goes unbound.

bool is the reason that matters. It was raw == 'true', which is total: every other spelling — 1, yes, on, TRUE — produced false, so ?active=TRUE meant the opposite of what the caller wrote and nothing could notice. A number at least answers null for nonsense. So the accepted spellings are a closed, case-insensitive set ([_trueSpellings] / [_falseSpellings]) and anything outside it is unparsable, which is now a refusal the caller is told about.

static void injectPathParameters(Map<String, dynamic> jsonBodyData, Request req, TomEndpoint<Object, Object> endpoint)

Folds the request's URL path parameters into [jsonBodyData] under the request-DTO field names declared by [endpoint].urlParameterMapping.

Each captured path parameter (shelf route capture, e.g. id from /items/{id}) is written under its mapped field name — or, when the mapping has no entry for it, under its own capture name (identity). This is what lets a typed request DTO receive /items/{id} as request.id (or request.itemId with a {'id': 'itemId'} mapping) without a bare-String handler parameter (G-API-2). Called immediately before the DTO is instantiated from the folded map.

Pure and side-effect-free apart from mutating [jsonBodyData], so it is unit-testable without a live router (like [coercePrimitiveParameter]).

static void injectQueryParameters(Map<String, dynamic> jsonBodyData, Request req, TomEndpoint<Object, Object> endpoint, {Set<String> declaredParameterNames = const {}})

Folds the request's query-string parameters into [jsonBodyData] under the request-DTO field names declared by [endpoint].urlParameterMapping.

Only query parameters that the mapping names explicitly are folded — unlike [injectPathParameters], there is no identity fallback. A path capture is part of the route and therefore part of the endpoint's own declaration, so binding it by its own name is safe; a query string is whatever a caller chose to append, so an identity fallback would let any caller write any field of the request DTO of any endpoint. Requiring the mapping makes query binding opt-in per contract and per parameter, and leaves every existing endpoint's behaviour unchanged.

This is what lets a redirect target — GET /oauth/callback?code=…&state=…, which a browser navigates to with no body at all — arrive as a typed DTO rather than a handful of bare String parameters (G-API-2). It is also where a provider's snake_cased spelling (error_description) is translated into the Dart field name, so the wire convention stops at the contract.

Called before [injectPathParameters], so a path capture of the same mapped name still wins: the route is the stronger statement.

A parameter the mapping does not name is dropped, and the drop is logged at debug. Dropping is the opt-in working as designed; the silence was a separate choice, and the expensive one. A client sending ?status=open to an endpoint that never mapped status gets a 200 computed as though it had not been sent, and nothing anywhere says so — the endpoint author sees a working request and the caller sees an ignored filter. Debug is the level the decision names: it is findable by someone who goes looking, without failing a request or filling an ordinary log with the tracking parameters (utm_source, gclid) that every public URL collects.

The names are logged; the values never are. A query string is where ?code=…&state=… arrives on an OAuth callback, and a log at a level people leave on in development is the last place a credential should reach. The name alone is the whole diagnosis anyway: what the author needs is that status was sent and not bound.

[declaredParameterNames] are the handler method's own parameter names, and they are excluded from the report. The mapping is not the only way a query value reaches a handler: a bare primitive parameter binds from the query string by its own name (GET /projects?workspaceId= → String workspaceId), several strategies earlier. An endpoint that declares one and takes a request DTO would otherwise have the bound parameter reported as dropped on every request — a diagnostic that cries wolf on the documented case is worse than none, because it teaches its reader to skip the line that matters.

Pure and side-effect-free apart from mutating [jsonBodyData] and that log line, so it is unit-testable without a live router (like [coercePrimitiveParameter]).

static void injectFormFields(Map<String, dynamic> jsonBodyData, TomMultipartForm form, TomEndpoint<Object, Object> endpoint)

Folds the text parts of a decoded multipart/form-data body into [jsonBodyData], so the request DTO is built from a form exactly as it is built from a JSON body.

[TomEndpoint.formFields] decides which parts are folded, and its two states mean genuinely different things:

  • empty — fold every text part. A request body is the endpoint's own

contract, just as a JSON body is, and a JSON body is not filtered field-by-field either. Nothing is gained by making the ordinary case restate the DTO's field list. non-empty* — an allow-list: only the named parts are folded. This is for the endpoint whose form is filled in by something it does not control (a payment provider's callback, a third-party webhook posting a form), where the sender may add fields at will and only the declared ones should reach the DTO.

Note the asymmetry with [injectQueryParameters], which binds only what the mapping names. It is the same reasoning read in the other direction: a query string is appended by whoever typed the URL, whereas a body is what the endpoint asked for. Where that stops being true, formFields is the way to say so.

File parts are not folded — see [TomFormFile], which binds as a method parameter, because an arbitrary object cannot travel through a JSON map into a reflected DTO.

Called before [injectQueryParameters] and [injectPathParameters], so a URL value of the same name still wins: the route is the stronger statement, and a form field cannot override the row it is posted to.

Pure and side-effect-free apart from mutating [jsonBodyData], so it is unit-testable without a live router (like [coercePrimitiveParameter]).

static Map<String, dynamic> decodeJsonObjectBody(String body, ClassMirror<dynamic> parameterMirror)

Decodes a request body that is required to be a JSON object, or throws a named endpoint exception.

Both failure modes are one answer to the client — send a JSON object — so both carry the same key rather than the bare FormatException / TypeError a raw jsonDecode(...) as Map produced. That key is worth distinguishing from the neighbouring parameter_instantiation_failed: this one says the bytes never were a field map, that one says they were and the DTO refused a value inside them. A client can act differently on each, which is the whole reason for naming them separately.

static Response accessDeniedResponse()

The response a denied caller receives: a bare 404, indistinguishable from a route that does not exist.

A denial says nothing. The alternative — 403, which says "this exists and you may not have it" — hands an unauthorized caller a working oracle: walk the id space, read the statuses, and the ids that answer 403 are the rows that exist. That is a disclosure the caller was refused the data for, delivered by the refusal itself. The resource-key arm makes it concrete, because there the id is the thing being protected, but the contract arm leaks the same way at the level of the route: a 403 on /admin/users tells an anonymous prober that this deployment has an admin API and that the endpoint is spelled that way.

So the body carries no [tomErrorEnvelope] and no error key either. An envelope naming access_denied on a 404 would undo the whole of it in one header — the status would say "nothing here" and the body would say "something here, and you may not have it".

The diagnosis is not lost, it moves to where it belongs. The denial is audited unconditionally just above, with the principal, the endpoint and the outcome, and the exception's message reaches the server log. An operator asking "why did this caller get a 404" has a record; the caller does not.

Not routed through [TomEndpoint.errorHandler], and that is deliberate. Those hooks exist for errors of the invocation, and a handler written for one — mapping a domain exception to a 409, say — would be handed a security decision it was not written for. A deployment that genuinely wants 403 states it by returning one, not by inheriting a handler.

static String _socketShape(String lead, Stopwatch open, TomWebSocketConnection connection)

[lead], followed by how long the socket was open and what crossed it.

One renderer for both closing entries, so the success and failure records of a conversation are read the same way. Seconds to one decimal rather than a Duration: an auditor scans these, and 3.4s and 3600.0s sort and compare by eye where 0:00:03.412000 does not.

class TomEndpointRouting

class TomEndpointRouting

Builds the shelf [Router] for the application by reflecting over annotated service/API classes and mounting one route per endpoint method.

[scanClasses] partitions the reflected classes into service interfaces, API implementations, and components; [initializeRouter] resolves each service's instance (via [TomComponentReference], bean lookup, or a matching component class) and mounts its endpoint methods. The mounted handlers and a [TomEndpointRouteKey]→[TomEndpointRoutingInfo] map are exposed statically, read-only, for diagnostics.

Constructors

Methods

TomClassScanResult scanClasses()

Reflects over the annotated classes and partitions them into service interfaces, API implementations, and components. Throws if a class carries both @TomApiImplementation and @tomService.

void registerFrameworkApis()

Registers the API contracts the framework itself ships an implementation of, so the router can resolve them without the application registering anything.

A registry-based handler is mounted by looking its contract up in [tomRemoteApis], and the lookup throws when the contract is absent. For an application's API that is right: the contract and the handler are both the application's, and a handler whose contract was never registered is a bootstrap the application got wrong. For the framework's own it would not be: [TomUserPreferencesServer] is exported from the barrel, so it is reflected — and therefore scanned — in every deployment, whether or not that deployment has any interest in preferences. Leaving the registration to the application would mean every server that forgot one line failed to start, for an endpoint it never asked for.

Registering is idempotent (the registry is keyed by API id), so repeated router initialisations — which the test suite does per case — cost nothing and cannot double-mount.

List<TomMethodMetadata> getClassMethodMetadata(ClassMirror<dynamic> classMirror)

Collects, for each endpoint-annotated method of [classMirror], the merged [TomMethodMetadata] (endpoint, access control, transaction, and remote-API tags). Throws on conflicting/duplicate tags or a missing @TomApiImplementation for an API-endpoint method.

Access control follows G-API-3 (C-12): a handler-side TomAccessControl annotation is a local override and wins; when the handler declares none, the endpoint's contract-declared policy (TomApiEndpoint.access from the registry) is extracted, so a registry-based handler is gated without restating the policy inline.

Object? findServiceInstance(List<ClassMirror<dynamic>> componentClasses, ClassMirror<dynamic> serviceType, Object? serviceInstance)

Fallback resolution for an interface-based service: finds a component class that extends or implements [serviceType] and returns its bean, otherwise returns the passed-in [serviceInstance].

A component with no registered bean is constructed here (see [instantiateComponent]) rather than left unresolved, and a resolved instance is never overwritten by a later, unresolvable candidate.

Object? instantiateComponent(ClassMirror<dynamic> componentType)

Constructs [componentType] through its no-argument constructor and registers it as the bean for its type, or returns null when it cannot be built that way.

The framework ships services of its own — the health check, the file endpoint — and a library that adds one must not force every existing application to register a bean it has never heard of. A @tomComponent that needs no arguments is fully described by its own declaration, so building it is not a guess. Anything with a real constructor still belongs to the application, and stays unresolved here.

The instance is registered so that the router and any later TomBean.getBeanByType see the same object; an application that registers its own bean first is never overridden, because this only runs when the lookup came back empty.

static List<TomEndpointHandler> handlers

Every endpoint handler mounted during the last [initializeRouter] run.

A read-only view of the live list, not a copy: a diagnostics caller reading it after a later mount sees that mount, and reading it costs nothing. add, clear and the rest throw [UnsupportedError].

The mutation path is deliberately not here. What is served is decided by what the reflector holds and what [initializeRouter] mounts from it, and a caller that could append to this list would be describing a route nothing serves, or — worse — removing the record of one that is still being served. Both make the table's readers wrong about the process they are reporting on. A test that needs an empty table calls [resetRoutes].

static Map<({String method, String uri}), TomEndpointRoutingInfo> routingInfo

Mounted routes for diagnostics, one entry per route and HTTP method.

A read-only view, for the reason [handlers] is one.

See [TomEndpointRouteKey] for why the method is part of the key. An endpoint declaring three methods contributes three entries sharing one handler; two endpoints splitting a path between them contribute one entry each, and remain distinguishable.

Only the methods an endpoint declares are listed. Every route also gets an automatic OPTIONS registration for CORS preflight, which is framework plumbing rather than part of the endpoint's surface: recording it would double the table with entries that say nothing an operator does not already know holds for every route.

static void resetRoutes()

Forgets every mounted route, so the next mount starts from an empty table.

[initializeRouter] calls it, which is what makes [handlers] answer for the last run rather than for every run since the process started — it builds a fresh [Router], so the table describing that router is fresh too.

It is public because a test that mounts routes directly, without a router, needs the same fresh start; there is no other caller. The table is process-wide rather than per-router, which is what lets a diagnostics endpoint report on a server it does not hold, and is the reason two routers in one process would share one table — a shape nothing in this framework builds.

static String shelfRoutePath(String uri)

Translates a Tom route template into the shelf_router path syntax.

Tom (and OpenAPI) write path variables as {name}; shelf_router matches them as <name> and treats {name} as a literal path segment. So a route mounted with the raw template (/items/{id}/field-states) silently never matches a real request (/items/1/field-states) — the only symptom is a 404 "Route not found". Every {name} is rewritten to <name>; a route with no variables is returned unchanged. The captured variable keeps its name, so the pipeline binds it from Request.params by that name.

class _UnboundParameter

class _UnboundParameter

Occupies the slot of a parameter no binding strategy could fill.

A positional argument list cannot express "absent" — leaving a parameter out does not leave it unset, it shortens the list and moves everything after it one place to the left. So binding fills one slot per declared parameter and marks the ones it could not resolve, and the shape of the call is decided afterwards, when the whole picture is visible. Only then is it knowable whether an unfilled slot is a trailing optional (droppable) or a hole (not).

typedef TomEndpointRouteKey

typedef TomEndpointRouteKey = ({String method, String uri})

Identifies one mounted route: a path template and the HTTP method it was mounted for.

The method belongs in the key because a path alone does not identify a route. One endpoint may answer several methods, and — legally — two endpoints may divide the methods of a single path between them, so a table keyed by path holds one entry where several routes are mounted and silently reports whichever was written last.

[uri] is the route as declared (/items/{id}), not the shelf_router translation of it, so a caller can look an entry up with the string it wrote in the annotation. [method] is the HTTP method's uppercase wire name (TomHttpMethod.name) rather than the [TomHttpMethod] instance, because TomHttpMethod does not define value equality — two instances naming the same method are only interchangeable as map keys while both are the canonical constants, which is a precondition a diagnostic API should not impose on its callers.
