Where a rendered export is kept when it is stored rather than streamed.

codespecs_mapping.md §5.28 lets a report name one of three delivery channels. Two of them — apiResponse and email — consume the renderer's byte stream and keep nothing; the third, fileExport, has to put the document somewhere and hand back a reference to it. This library is that somewhere.

Why a four-method interface and not the persistence layer's blob API

This is deliberately not a general file store. It is the narrowest interface an export needs — put a stream under a key, read it back, ask whether it is there, delete it — with no directories to list, no metadata to update, no partial reads. It was written before the framework's general blob storage (file_storage/) existed, on the reasoning that guessing the shape of an API someone else is designing produces two APIs that nearly match.

That storage now exists, and the adaptation turned out to be exactly what was predicted: [TomBlobExportStore] — one class, four delegating methods — puts every blob backend (filesystem, database, S3, or an application's own) behind this interface, and nothing that renders or delivers an export changed. The two backends below remain because an export module that can run with no storage configured at all is worth the hundred lines.

Why streams on both sides

The same reason the renderers produce one: an export large enough to be worth storing is large enough that holding it and its copy at once is the failure. [TomExportStore.store] takes the renderer's stream directly, so a result flows from the database to the disk without ever being whole in memory.

class TomDirectoryExportStore

class TomDirectoryExportStore extends TomExportStore

An export store over a directory tree on the local filesystem.

The default backend, and the one that needs no infrastructure: a mounted volume, a container's writable layer, a developer's ztmp. Keys become paths beneath [root], so 2026/07/sales.xlsx is a file two directories down — which makes the stored exports browsable with ls, and date partitioning a matter of how the caller spells the key.

Constructors

TomDirectoryExportStore.new(Directory root)

Creates a store rooted at [root], without touching the filesystem.

[root] is created by the first [store] call, together with whatever directories that call's key names — one create(recursive: true) covers both, so a store is configured long before it is a directory. The three read paths do not create it: [open] on a missing root is export.store.not_found, and [exists] and [delete] answer false. Asking a store whether it holds something is a question, and a question should not leave a directory behind.

Deferring the creation is what makes a store safe to configure at startup: a constructor cannot await, so creating the root here would mean a blocking createSync on a path that may be a slow mount, throwing out of a field initialiser on a store the application may never write to. It also means the root is created again if it goes away — a remounted volume, a reaped tmpfs — where a store that made it once would report itself configured and fail every write after.

class TomExportStore

abstract class TomExportStore

Stores and retrieves rendered exports by key.

Why the public methods are final

A backend implements [doStore], [doOpen], [doExists], [doDelete] and — when it can — [doDeletePrefix]; the public methods are this class's own and wrap them. That indirection buys two guarantees no backend can forget:

  • Every key is validated, so a backend written later — or by an

application — cannot be handed a directory traversal. - Every failure arrives as a [TomExportException] carrying the key [TomExportStoreOperation] names for the operation that failed. A backend touches a filesystem, an S3 client or a database driver, each with an exception vocabulary of its own; without this, which exception a caller has to catch would depend on which backend is configured.

Leaving either to the backends is what makes them differ: a guarantee every implementor must remember is one some implementor does not.

Why there is no listing

Store, open, exists, delete, delete-a-prefix — and nothing that walks the key space. That is not an omission waiting to be filled. A listing is a paginated call over an object store and a scan over a blob table, and neither answers what a retention pass actually needs to know: which export, rendered for whom, is now old enough to go.

The enumeration belongs to the deployment. [TomStoredExport] is a row — key, media type, size, time — and a system that stores exports for later retrieval keeps one per export anyway, next to the tenant and the user that storage has no business holding. Retention is then a query over those rows and a [deletePrefix] per partition, which works on every backend rather than on the ones that can enumerate. example/export/export_retention.dart is that pass, run against a store that can reclaim by prefix and one that cannot.

Future<TomStoredExport> store({required String key, required Stream<List<int>> bytes, required String mediaType})

Writes [bytes] under [key], replacing anything already there.

A failed write leaves nothing readable under [key] — a truncated export is indistinguishable from a complete one to whoever downloads it next, which is the one outcome worse than a failure that is reported.

Throws [TomExportException] (export.store.invalid_key) for a key that is not relative, or (export.store.write_failed) when the write fails.

Stream<List<int>> open(String key)

Reads the export stored under [key].

Throws [TomExportException] (export.store.not_found) when the key holds nothing: a caller reading an export it has a reference to and finding it gone has hit a real fault — an expiry it did not expect, a store it is not pointed at — and an empty stream would disguise that as an empty file. A read that fails for any other reason is export.store.read_failed.

A transfer that breaks partway still delivers the chunks that arrived, and then fails — the same contract [TomBlobStore.get] states, for the same reason and by the same means. Stated here too because the two are only coincidentally the same code: a reader of this method has no cause to go looking at the other module for what this one promises.

Future<bool> exists(String key)

Whether [key] currently holds an export.

Throws [TomExportException] (export.store.probe_failed) when storage could not answer — which is not the same as answering false.

Future<bool> delete(String key)

Deletes [key], returning whether anything was there to delete.

Throws [TomExportException] (export.store.delete_failed) when the deletion itself fails; a key that held nothing is false, not an error.

Future<int> deletePrefix(String prefix)

Deletes every export whose key lies under [prefix], returning how many went.

The prefix is matched by key segment, never by characters. 2026/07 removes 2026/07 and everything beneath it, and never 2026/070 — a string prefix that can reach a sibling is an ordinary convenience everywhere except in a delete, where it is how a month's retention takes the next month with it.

This is the reclaim primitive the day partitioning [TomExportService.keyFor] writes exists for: a retention pass deletes 2026/07/08 rather than enumerating what is under it. When it runs is the deployment's — a scheduled purge belongs in the back-office tier, on the same scheduled-work machinery as its other nightly passes, not in this module.

Throws [TomExportException] (export.store.prefix_delete_unsupported) on a store that cannot enumerate, naming the backend. A store that answered 0 instead would make "the purge found nothing" and "this backend cannot purge" the same answer, and the deployment would learn the difference from a disk filling up.

An empty prefix is refused (export.store.invalid_key): it names every export there is, and a delete whose argument came from a configuration value that turned out to be empty should not empty the store.

Future<int> doDeletePrefix(String prefix)

Deletes everything under [prefix]. Implemented by backends that declare [supportsPrefixDelete]; called by [deletePrefix].

[prefix] has already been validated and is non-empty. The default throws, so a backend that claims the capability and forgets the implementation fails loudly rather than reporting an empty purge.

Future<TomStoredExport> doStore({required String key, required Stream<List<int>> bytes, required String mediaType})

Writes [bytes] under [key]. Implemented by backends; called by [store].

[key] has already been validated. A failure may be thrown in whatever vocabulary the backend has — [store] translates it — but a backend that has a better key than export.store.write_failed for the failure should throw a [TomExportException] carrying it, which passes through untouched.

A chunk from [bytes] is borrowed for the duration of the await: consume or copy it before asking for the next, and do not retain it. A renderer refilling one scratch buffer per chunk is ordinary, and a backend that kept the list would store that buffer's last state once per chunk.

Stream<List<int>> doOpen(String key)

Reads [key]. Implemented by backends; called by [open].

Throws [TomExportException] (export.store.not_found) when the key holds nothing — the one error a backend must raise itself, because only it knows the difference between absent and unreadable.

Each chunk belongs to the caller: writable, and aliased with nothing the backend keeps. A backend reading from a file or a blob has this already; one holding its exports in memory must copy. Both halves are load-bearing — yielding an internal buffer lets a consumer decoding in place edit the stored export, while yielding an unmodifiable view would make that consumer throw on the backend the tests use and work on every backend they deploy to.

Deletes [key]. Implemented by backends; called by [delete].

static String validateKey(String key)

Validates a storage key and returns it.

Keys are relative, slash-separated, and made of unreserved characters. The rule exists because the obvious backend maps keys onto paths, and a key of ../../etc/passwd would then be a directory traversal handed to whatever built the key from a report name. Validating centrally means every backend gets the check, including ones written later.

The rule is [TomBlobStore.isValidKey] — one definition, so an export key and a file-reference key cannot drift apart and a key that passes here is storable by any blob backend. Only the error is this module's own, because a caller catching export.store.invalid_key should keep catching it.

class TomMemoryExportStore

class TomMemoryExportStore extends TomExportStore

An export store that keeps its contents in memory.

For tests, and for the development server that should not leave files behind. It buffers whole exports by definition, so it is the one place in this module where that is acceptable — and the reason it is not the default.

Holding the bytes rather than reading them off a disk makes it the only backend that could hand a caller a reference into its own state, so it is the only one that has to copy on purpose: a chunk it yields is the reader's own, and a chunk streamed into it is copied before the next is asked for. Both are what [TomExportStore.doOpen] and [TomExportStore.doStore] require of any backend — stated here because here they cost something.

class TomStoredExport

class TomStoredExport

A stored export: what was written, where, and how big it turned out.

Returned by [TomExportStore.store] rather than assembled by the caller — [byteCount] is only known once the stream has drained, and it is the field a caller most often needs next (a Content-Length, a quota check, a log line).

Constructors

TomStoredExport.new({required String key, required String mediaType, required int byteCount, required DateTime storedAt, Uri? location})

Creates a stored-export descriptor.

[storedAt] is normalised to UTC for the same reason [TomStoredBlob] does it, and this type needed it more: the directory and memory backends stamp DateTime.now() while the blob-backed one forwards the blob's own stamp, so without normalising here the three backends of one interface would have disagreed with each other about the zone.

enum TomExportStoreOperation

enum TomExportStoreOperation

The five things a store does, and how each one reports a failure.

The keys are named here rather than spelled at each throw site so that the same failure of the same operation carries the same key whichever backend is configured — which is the entire promise [TomExportStore] makes by being an interface at all.

Values

write

Writing an export: [TomExportStore.store].

read

Reading one back: [TomExportStore.open].

probe

Asking whether one is there: [TomExportStore.exists].

delete

Removing one: [TomExportStore.delete].

deletePrefix

Removing a whole partition: [TomExportStore.deletePrefix].
