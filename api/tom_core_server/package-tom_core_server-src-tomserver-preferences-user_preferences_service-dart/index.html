package:tom_core_server/src/tomserver/preferences/user_preferences_service.dart

import 'package:tom_core_server/src/tomserver/preferences/user_preferences_service.dart';

The server-side store for per-principal preferences (C-13): typed reads and writes of [TomUserPreference] rows for the caller.

Why a service rather than a repository

[TomUserPreferenceRepository] persists rows; this persists values. Every consumer of a preference wants a String timezone or a reflected settings object, not a row carrying JSON text plus a type name — and if each of them did the encode/decode itself, each would decide independently whether a DateTime is written local or UTC and whether a mismatched read is an error or a coercion. [TomUserPreferenceCodec] makes that decision once; this service is what makes the codec unavoidable.

The caller is the zone, not an argument

[get] and [set] take no principal. They read the one in the request zone — the same principal @TomDbScope(field: 'principal_id', scope: 'owner') resolves against — so the value a handler stores and the row the repository permits it to store can never disagree. An API that took a principal would invite a handler to pass one it read off the request, which is precisely the parameter the endpoints deliberately do not have.

[getFor] is the exception, and exists for one reason: the authentication path needs a preference before a request zone exists. It installs the principal and delegates, so even that path reaches the same scoped query.

Why the lookups name the principal anyway

The scope already confines every statement to the caller, so FIND BY preference_key = :key would be correct in a request. The queries below still say principal_id = :principalId because [TomDataScope.runUnscoped] exists: inside an administrative bypass the scope deliberately filters nothing, and a lookup that relied on it would then find — and [set] would then overwrite — some other principal's row. Naming the principal keeps the lookup meaning "mine" under every scope state. It is not a second copy of the authorization: the scope still decides what may be written, and it is the scope that rejects an attempt to write elsewhere.

class TomUserPreferences

class TomUserPreferences

Typed access to the calling principal's server-stored preferences.

Installed as a bean so an application can substitute its own implementation (a caching one, a read-only one) without any consumer changing: 

TomBean.withType(TomUserPreferences, TomUserPreferences(TomUserPreferenceRepository()));
final timezone = await TomUserPreferences.resolve()?.get<String>(
  TomUserPreferenceKeys.timezone,
);

Every key is checked on the way in

[read], [get], [set], [setEncoded] and [remove] all reject a key that does not satisfy [TomUserPreferenceKeys] with a [TomUserPreferenceKeyException] (preferences.key.invalid), which the endpoints map to a 400. Here the check is not a redundant second guard on something the client already refused: the endpoints read the key off the request URL, so on this side it is untrusted input — and a key wider than preference_key would otherwise be stored truncated, silently merging two preferences into one row.

Each of them checks it first, before the caller is resolved from the zone. A bad key is the one fault the caller can see from the call site, so it is the one worth reporting when the ambient state is unusable too; the reverse ordering answers "no principal" to a call that was malformed anyway.

Methods

Future<List<TomUserPreferenceDto>> all([TomPageRequest? page])

Every preference of the calling principal, ordered by key.

That order is the contract's, not this store's preference: [TomUserPreferencesApiService.listPreferences] states it for every implementation, so tom_core_flutter's device store answers in the same sequence and an application holding either one reads the same list.

The order by is not decoration. Without it the answer is whatever order the storage engine finds convenient, and that changes as the table is rewritten, as rows are deleted and reinserted, or as the planner picks a different index — so a caller that renders the list, or diffs two of them, would see the sequence shift under it for reasons that have nothing to do with the data. The clause is what lets this method's answer be described at all: "whatever order storage happens to use" is not an order a caller can rely on, however stable it looks in practice.

The key is the ordering column rather than, say, updated_at, because it is the one column that is unique per caller and never changes while the preference exists: rewriting a value must not move it in the list. It is also free — uq_tom_user_preference (principal_id, preference_key) already covers WHERE principal_id = ? ORDER BY preference_key, so the rows come back in order off the index rather than through a sort. [page] windows the answer, and is for a server-internal caller — a migration walking one principal's settings, an admin tool, a job that reads in batches. The wire has no equivalent, and deliberately: see [TomUserPreferencesApiService.listPreferences] and doc/preferences.md §The Store Is Bounded.

A window is only meaningful over a defined order, and this one has it already — the ORDER BY above is the contract's, so page 2 is the rows after page 1 rather than whatever the engine returned second.

Future<TomUserPreferenceDto?> read(String key)

The calling principal's preference stored under [key], or null when it has never been written.

Future<T?> get<T extends Object>(String key)

The calling principal's preference stored under [key], decoded as a [T].

null when the preference does not exist. Throws a [TomUserPreferenceCodecException] when it exists but was written as a different type — see [TomUserPreferenceCodec.decode].

Future<T> getOr<T extends Object>(String key, T fallback)

[get], with [fallback] for a preference that has never been written.

A type mismatch still throws: an unwritten preference is an ordinary state that a default answers, while a preference stored as the wrong type is a bug, and silently answering [fallback] would hide it.

Future<TomUserPreferenceDto> set<T extends Object>(String key, T value)

Writes [value] as the calling principal's preference under [key], replacing any previous value, and returns the stored DTO.

Scalars and DateTimes are written by [TomUserPreferenceCodec]; anything else must be a @tomReflector class, which is what makes a preference a typed object rather than a stringly-typed blob.

async for the encoding step, which can throw: every other failure of this service arrives as a rejected future, and one method that throws synchronously instead would be caught by a try the caller wrote around the await and missed by everything else.

Future<TomUserPreferenceDto> setEncoded(String key, {required String valueType, required String valueJson})

[set], for a value that arrives already encoded.

The endpoint's write path: a request carries [valueType] and [valueJson] as text, so there is no Dart value to take the type from. The pair is validated before it is stored ([TomUserPreferenceCodec.validateEncoded]), because a mismatch written here is one every later read of the key — on every device — would fail on.

Future<TomUserPreferenceDto> _write(String key, String valueType, String valueJson)

Upserts the calling principal's row under [key].

A write that would add a key is refused once the principal holds [tomUserPreferencesMaxPerPrincipal] preferences; a write that replaces one is never refused for the count. The count is read before the insert, so two inserts racing for the last place can both pass and leave the caller one or two over. That is accepted: the ceiling exists to keep the list small, not to be exact, and an insert that overshoots it leaves the principal able only to replace and delete until it is back under.

Future<bool> remove(String key)

Deletes the calling principal's preference under [key].

Answers whether a row was removed, so a caller can tell "deleted" from "was never there" without a second read.

Future<int> clear()

Deletes every preference of the calling principal, and answers how many rows went.

The operation an account reset performs, and it is one statement rather than a loop over [all] and [remove] for the reason the device store gives for its own clear: a loop that fails half way leaves a state nobody asked for, and here that state is shared across every device the user owns. A single DELETE either happens or does not.

Idempotent and unconditional: a principal holding nothing is cleared, and answers 0. There is no filter, because a partial clear is [remove] repeated.

Names the principal in the predicate for the reason [_rowFor] does: under [TomDataScope.runUnscoped] the scope filters nothing, and a bulk delete that relied on it would be everyone's.

Future<T?> getFor<T extends Object>(TomPrincipal principal, String key)

[get], for a [principal] that is not the one in the current zone.

For the authentication path, which needs a user's stored preference at a point where the request zone carries no principal yet — the principal only exists once the credentials have been accepted. Installing it and delegating keeps that path on the same scoped query as every other read, instead of giving login its own unscoped lookup.

Future<void> _requireRoomFor(TomPrincipal principal, String key)

Throws unless [principal] holds fewer than [tomUserPreferencesMaxPerPrincipal] preferences, so that one more may be added under [key].

Counted with the principal named, for the reason [_rowFor] names it: under [TomDataScope.runUnscoped] the scope filters nothing, and a count that relied on it would be everyone's.

Future<TomUserPreference?> _rowFor(TomPrincipal principal, String key)

[principal]'s row under [key], or null.

Takes both already settled — every caller is a public method that validated the key and resolved the principal on entry. The principal is a parameter rather than a second read of the zone so that each operation reads it exactly once: [_write] needs it for itself (a row being inserted has no id to copy one from), and a helper that resolved it again would leave the write path with two lookups whose second could no longer fail.

TomPrincipal _requirePrincipal()

The principal in the current zone.

Throws rather than returning null: without a principal there is no row to read and no owner to write, and the alternative — an unowned row — is one the scope would reject on the next read anyway, having already been stored.

Static

static TomUserPreferences? resolve()

The installed [TomUserPreferences] bean, or null when none is registered.

null rather than a throw, because a preference is optional by nature: a deployment that has not created tom_user_preference should fall back to whatever the caller used before, not fail.
