The framework's HTTP file endpoint: the server half of the file-transfer wire contract the kernel's TomHttpFileTransferClient speaks.

The two halves of file storage live in different packages. The server owns the store — blob backends, @TomFileReference columns and the four repository methods saveFile / openFile / describeFile / clearFile. The kernel owns the client — POST/GET/HEAD/DELETE on <baseUri>/<slot>, the JSON descriptor, the x-tom-file headers. This class is the handler between them, and that handler is the same in every application: map a slot to an entity and a file column, stream the request body into saveFile, stream openFile back out, answer HEAD from describeFile, clearFile on DELETE. Which is why it lives here, once, rather than in every application that serves a file.

The slot is derived, not declared

A slot is <table>/<id>/<column>, and both names come from annotations the entity already carries: @TomDbTable.table and the column's mapped name. No application-supplied mapping table exists, so there is no second copy of the entity name, the column name or the store name to go stale — renaming a column moves the slot with it, and a column that no longer exists fails at registration rather than at request time.

Exposure is default-closed

Reflection can see every file column; it publishes none of them. A column is reachable over HTTP only when its @TomFileReference says exposed: true. Whether a file may be fetched over HTTP is an authorization decision, so it is declared next to the column it exposes.

What exposure decides is which column a slot names — never whether the caller may have it. That stays where it already is: the row scope (C-3) and column grade (C-4) the repository enforces on every one of these calls, and the endpoint access check the surrounding pipeline runs before the handler is entered. A file endpoint is not a hole in the C-grade model.

Wiring it up

One line per entity, naming the repository and nothing else — T and K come from the repository's own type arguments: 

TomFileSlots.register(documentRepository); // TomFileRepository<Document, int>
TomBean.withType(TomFileServer, TomFileServer());

The client then addresses it with no knowledge of any of the above:

final client = TomHttpFileTransferClient(
  baseUri: Uri.parse('http://localhost:8080/files'),
);
await client.upload(slot: 'document/42/attachment', source: source);

static bool _matches(String? header, String? digest)

Whether [header] lists an entity tag matching [digest].

* matches anything that exists, which is what it means in If-None-Match. Otherwise each comma-separated tag is compared to the strong tag this endpoint writes; a W/ prefix is accepted because the weak comparison is the one If-None-Match specifies, and a cache is entitled to send back a tag it weakened.

A file with no digest matches nothing: it has no validator, so a conditional request against it cannot be satisfied and the bytes are served.

static TomBlobRange? _rangeOf(String? header, int byteCount)

The single byte range [header] asks for, or null for no usable one.

Deliberately lenient: an unparsable header, a unit other than bytes, or more than one range answers null, and the caller then serves the whole file with a 200. RFC 9110 permits exactly that, and it is the right trade here — a multipart/byteranges body is a second wire format for a case no browser needs, and refusing a header we merely do not understand would break a download that would otherwise have worked.

The three forms: bytes=500-999 is [500, 1000), bytes=500- runs to the end, and the suffix form bytes=-500 means the last 500 bytes. [byteCount] is taken because the suffix form cannot be resolved without it — it counts backwards from an end this header never names.

bytes=-0 asks for the last nothing, which the RFC calls unsatisfiable; it comes back as a range starting at [byteCount], which [TomBlobRange.clampedTo] then reports as such. That keeps "the caller asked for something impossible" (416) apart from "this header says nothing I understand" (200 and the whole file), which are different answers.

static Stream<List<int>> _inCurrentZone(Stream<List<int>> Function() open)

[open]'s stream, opened and consumed in the zone this is called from.

A response body is lazy: the handler returns a stream and shelf hands it to the socket, so nothing is read until the request has already returned and the zone the authentication middleware established — the one holding the [TomPrincipal] — is no longer current. For a file that is not an implementation detail. openFile is a scoped read, and a @TomDbScope predicate resolves its principal from the zone; subscribed outside the request it finds none, filters the row away, and raises row_not_found after the 200 and its headers are on the wire. The caller is left with a truncated body and a status code that says the opposite of what happened.

So the subscription is made where the request still is. The controller defers [open] until something listens, then runs both the call and the listen inside the captured zone, which is what the async generator behind openFile captures in turn. Pause, resume and cancel are forwarded so backpressure still reaches the store — buffering the file to sidestep the zone would trade this bug for a worse one.

class TomFileService

abstract class TomFileService

The file-transfer service interface, mounted by the endpoints pipeline.

One method for all four verbs: the wire contract addresses a single resource and varies only the method, and splitting it into four handlers would mean four copies of the slot resolution that has to be identical across them.

Constructors

TomFileService.new()

Methods

Future<Response> file(Request request)

POST/GET/HEAD/DELETE on /files/{entity}/{id}/{column}.

consumes is deliberately not JSON: the pipeline reads a request body into a string only for a JSON endpoint, so declaring octet-stream is what leaves the upload stream intact all the way to the blob store.

[TomAuthenticatedAccess] because the endpoint's other protections cannot stand in for it. The row scope (C-3) and the column grade (C-4) are both principal-relative: they answer "which rows, which columns", never "whether there is a caller at all". An entity that declares no @TomDbScope filters nothing and an ungraded column refuses nothing, so without this an exposed file column on an ordinary entity would be world-readable and world-writable. An application that genuinely wants anonymous file access declares its own [TomFileService] component with a different [TomAccessControl] — a handler-side annotation is a local override (G-API-3) — rather than every application inheriting the open case by default.

class TomFileSlot

abstract class TomFileSlot

One addressable file column: everything [TomFileEndpoint] needs to serve <table>/<id>/<column>, with the entity and key types already bound.

The endpoint is not generic and cannot be — a URL carries strings, and the entity type behind a slot is only known once the application registers its repository. This interface is where the generics stop: [TomFileSlots] stores slots as TomFileSlot, and each one closes over the <T, K> it was registered with.

class TomFileSlots

class TomFileSlots

The registry of HTTP-reachable file columns, keyed by table and column name.

Registration is per repository, not per column: the repository is the only thing an application has to name, because it already carries the entity type, the key type and — through the entity's annotations — the table name, the column names and the blob store. Anything else would be a restatement, and a restatement is what drifts.

Its lifetime is the isolate's, and that is a bootstrap requirement

The registry is a process-wide static, and Dart isolates do not share statics — so it is really one registry per isolate. An application that serves from several isolates must run its [register] calls in each of them, which is what a server bootstrap already does: the registration sits in the start-up path every isolate runs, beside the bean wiring and the data-source configuration, not in a main() one isolate reaches and the others do not.

Static rather than owned state because the alternative buys nothing here. The registry is written once at start-up and read on every file request; a bean-scoped one would make the lifetime the server's rather than the process's, which is the same lifetime in every deployment this framework builds, at the cost of threading a dependency through [TomFileEndpoint], TomFormFileStorage and every call site of [resolve].

What the static does cost is a silent failure mode: an isolate that never ran the registration answers every file request with "no such slot", which is indistinguishable from a column that is deliberately closed. [resolve] removes it — see there.

static void register<T extends Object, K>(TomFileRepository<T, K> repository)

Registers every exposed @TomFileReference column of [T].

Fails loudly and at wire-up time when the entity is not mapped, exposes no file column, or would produce an ambiguous slot. That is the trade the reflection-derived design buys: the failures a hand-written mapping table would have shown at request time show here instead.

Call this in the start-up path every isolate runs. The registry it writes to is a static, and statics are per isolate, so a registration that happens in one isolate is invisible to every other one — see the class documentation. Registering twice in one isolate is refused (file_endpoint.duplicate_slot), so a bootstrap that runs once per isolate is both the requirement and the only thing that works.

static void _assertUnambiguous(String table, List<TomColumnInformation> fileColumns)

Rejects a set of file columns in which a slot name would be ambiguous.

Checked across all file columns of the entity, not just the exposed ones, because the repository resolves a field by its declared name or its mapped column name. A column named secret with another column mapped to the column name secret would let the exposed one address the closed one — an exposure by accident, which is exactly what the default-closed rule exists to prevent.

static TomFileSlot? resolve(String table, String column)

The slot serving <table>/<column>, or null when none is exposed.

A non-exposed column is indistinguishable from a non-existent one here, and that is the intent: the endpoint answers both with a plain 404 rather than telling a caller which columns exist but are closed to them.

An empty registry is the one case that does not get that answer. It means no slot was registered in this isolate at all, which a file request arriving here says somebody expected one — and the two readings of "no such slot" are then a closed column and a bootstrap that did not run, which no caller and no operator can tell apart from a 404. So it is refused by name and logged, and the request fails as the server fault it is.

The trigger is deliberately "a file request arrived and the registry is empty", not "the registry is empty": a deployment that exposes no file columns is not misconfigured, it simply has no caller asking, and it never reaches this.

static void reset()

Forgets every registration.

Exists for tests, which build a fresh registry per case; an application registers once per isolate at startup and never calls this. A test that resets while another test's slots are live deregisters them too — they share the isolate, and the registry is the isolate's.

extension TomFormFileStorage

extension TomFormFileStorage on TomFormFile

Stores a file that arrived as one part of a multipart/form-data request.

This is the join between the two upload shapes, and it is deliberately thin: a form part reaches the blob store through the same [TomFileSlot] the raw-body endpoint uses, so exposure ([TomFileReference.exposed]), the row scope (C-3) and the column grade (C-4) all apply to it unchanged. There is one route from bytes to storage; multipart only changes how the bytes get to the handler.

The call is the handler's, not the pipeline's, and that ordering is load-bearing: on a create the row does not exist while the request body is being read, so the id the slot is addressed by is only known once the handler has saved the entity. 

final saved = await documents.save(request.toDocument());
await attachment.storeIn('document', 'attachment', '${saved.id}');
