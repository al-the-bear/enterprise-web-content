Second factors that are delivered: a one-time code sent to an address or a number the user already controls.

The part of the contract TOTP never reached

[TomTotp2FAService] proved that the adaptor contract works, but it proved only half of it. TOTP re-derives its answer from a shared secret, so it stores nothing in [Tom2FAChallengeSpec.verificationData] — and that map is the contract's central design decision. It is the reason a challenge is split in two: [Tom2FAChallengeSpec.clientData] travels in the interim token's public claims, [Tom2FAChallengeSpec.verificationData] in its encrypted section, so an adaptor can remember something across the two passes that the holder of the token must not learn.

A delivered code is precisely that shape, and the first mechanism here to need it. The server generates the code, sends it away, and must recognise it again on pass 2 — while the client, which carries the interim token from one pass to the other, must not be able to read the answer out of what it is carrying. So [verificationData] holds a salted hash of the code and never the code itself, and pass 2 re-hashes the submission and compares.

What the two channels share, and what they do not

Everything except the channel. Code generation, hashing, the constant-time compare, masking, the enrolment begin/confirm shape and the delivery-failure rule are identical for a mailed code and a texted one, and live once in [TomDeliveredCode2FAService]. A subclass supplies four things: its mechanism key, where the destination is on the user record, how to mask a destination for display, and how to hand a rendered message to its channel.

Why delivery is synchronous, and why that is not a violation

Every other message in the framework goes through [TomMessageOutbox], for good reasons: durable retry, backoff, one-delivery-per-message. A one-time code is the case those reasons do not apply to. Its value expires with the challenge — ten minutes — while the outbox's retry budget is measured in tens of minutes, so a code delivered on the third attempt is a code that arrives after the prompt it answers has gone. Retry does not rescue this message; it only hides that the first attempt failed.

And the failure must not be hidden. A user staring at a code prompt for a code that was never sent has no way to tell that from a slow relay, and the login has already told them a code is on its way. So delivery goes through [TomTemplatedMessageService.deliverNow], which surfaces the transport's own failure, and an undelivered code fails the challenge with login.error.2fa.delivery-failed — the adaptor contract permits a throw exactly when verification "could not be performed", and a challenge nobody received is that.

The retry a delivered code actually wants is the user pressing resend, which issues a fresh challenge with a fresh code — not a redelivery of a stale one.

Enrolment is the proof of control

For TOTP, enrolment hands the user a secret. Here there is no secret to hand over: the address is already on the user record. What enrolment establishes is that the person logging in can read what is sent there — so [TomDeliveredCode2FAService.beginEnrolment] sends a code to the claimed destination and [TomDeliveredCode2FAService.confirmEnrolment] refuses to yield an enrolment until it comes back. The confirmed destination is then stored as the enrolment's [Tom2FAEnrolment.secretData], and challenges prefer it over the record — a proven address outranks an asserted one.

class TomDeliveredCode2FAService

abstract class TomDeliveredCode2FAService<S extends Object> implements Tom2FAService, Tom2FAEnrolmentSupport, Tom2FAPrerequisite

The mechanism shape shared by every second factor that sends a code somewhere.

Subclasses supply the channel; everything else — generating the code, sealing it into [Tom2FAChallengeSpec.verificationData], recognising it again, and the enrolment round trip that proves the destination — is here, once.

Instances are constructed by [Tom2FARegistry] through reflection, so a subclass needs a no-argument constructor and must resolve its collaborators (the messaging service, the enrolment store) at call time rather than in its constructor.

[S] is the delivery service the channel sends through, named as a type parameter so [requireDeliveryService] hands the subclass its own service back without a cast. It is also what makes this mechanism shape a [Tom2FAPrerequisite]: a code mechanism with nothing to send through cannot be offered, and that has to be answerable at registration rather than discovered at the challenge.

String? destinationOnRecord(Tom2FAContext context)

The destination this channel would reach [context]'s user at according to the user record — the mail address, the mobile number — or null when the record names none.

Distinct from [resolveDestination], which prefers a confirmed enrolment. This is the asserted address; enrolment is what turns it into a proven one.

String maskDestination(String destination)

[destination] reduced to what is safe to show a caller who has not yet proved anything.

Shown on the code prompt so a user with two mail addresses knows which inbox to open — and shown to whoever holds the interim token, which is why it is a mask and not the address.

S? resolveDeliveryService()

The service this adaptor sends through, or null when the deployment installed none.

Resolved per call rather than held, for the reason the class dartdoc gives: the adaptor is constructed by the registry before a deployment has necessarily finished installing its beans, so a service captured in a field would be captured as null and stay that way.

S requireDeliveryService()

The delivery service, or a [Tom2FAException] naming what is missing.

Reached only when the prerequisite was bypassed — an adaptor registered by hand, or a service uninstalled after the scan. A wiring fault either way, which is why it is a [Tom2FAException]: not client-throwable, so the caller learns only that the login failed while the operator gets a logged, named cause.

Future<void> deliver(Tom2FAContext context, {required String destination, required String code, required String templateKey, required Duration validity})

Sends [code] to [destination] through this adaptor's channel.

Must complete only when the message has actually been handed to a transport that accepted it, and must throw otherwise — the whole delivery-failure rule rests on this being synchronous. [templateKey] names the resource template to render; the code and the challenge's lifetime are supplied as parameters, never as literal text.

Future<Tom2FAChallengeSpec> issueChallenge(Tom2FAContext context) override
Future<bool> verifySubmission(Tom2FAContext context, Tom2FASubmission submission) override
Future<String?> resolveDestination(Tom2FAContext context)

The destination a challenge should be sent to: the confirmed one from the enrolment store, else the one on the user record.

The ordering matters and is the same as [TomTotp2FAService]'s. A user who has proved control of an address must be challenged at that address even if the record has since been edited — an attacker who can change a profile field must not thereby redirect the second factor. And a deployment that has installed a store but not yet run an enrolment campaign keeps working, because the record still answers.

Falling back to the record is deliberate rather than lax: it is the address the deployment already trusts for account recovery, and refusing to use it would lock out every user of a system that has not enrolled anybody yet. What enrolment adds is proof, and where proof exists it wins.

Future<Tom2FAEnrolmentOffer> beginEnrolment(Tom2FAContext context) override
Future<Tom2FAEnrolment> confirmEnrolment(Tom2FAContext context, Tom2FAEnrolmentOffer offer, String submitted) override
Future<void> deliverOrFail(Tom2FAContext context, {required String destination, required String code, required String templateKey, required Duration validity})

Calls [deliver] and turns any failure into a login the user can understand.

Two kinds of failure pass through unchanged, because both are already classified and re-labelling them would lose the classification:

  • [TomLoginException] — a subclass that already decided how this login

fails knows more than this wrapper does; - [Tom2FAException] — a wiring fault (no messaging service installed, no gateway configured), which has a different owner and a different fix from a relay that is down. Reported as a delivery failure it would send whoever is on call to the mail logs of a relay that was never asked.

Everything else becomes login.error.2fa.delivery-failed, logged, with the original cause attached: the operator needs the relay's own words, and the user needs to be told the code is not coming rather than to wait for it. Either way the challenge is not issued, which is the part that matters.

TomTextLocale? localeFor(Tom2FAContext context)

The locale a delivered message should be rendered in.

The principal's own preference first ([TomTextLocale.fromPrincipal] already prefers the stored language over the device's), then the login attempt's client locale, then null — which lets the bundle set apply its default in one place instead of every adaptor inventing 'en'.

The context's locale comes from the login request, so it is read leniently: a country a client cannot have sent legitimately costs the country, not the delivery.

Map<String, Object?> templateParameters(Tom2FAContext context, {required String code, required Duration validity})

The template parameters every delivered code message may use.

Supplied whether or not a given template mentions them: an unreferenced parameter costs nothing, whereas a template that wants the user's first name and finds no parameter renders a visible {firstname}.

static String maskedDestinationKey

The key the masked destination is filed under in [Tom2FAChallengeSpec.clientData] and [Tom2FAEnrolmentOffer.clientData].

static String digitsKey

The key the code's length is filed under in the client payload, so a UI can size its input without hard-coding this mechanism's policy.

static int saltBytes

How many bytes of salt a sealed code carries.

Sixteen: enough that two challenges never share a salt, so a table of hashes of every six-digit code cannot be precomputed once and reused. The value being protected is small — a million possibilities — which is exactly why the salt matters more here than it would for a password.

static String generateNumericCode(int digits)

A fresh decimal code of [digits] digits, drawn from the framework's CSPRNG.

[RsaKeyHelper.getSecureRandom] rather than dart:math's Random(), whose output is predictable from a handful of observations — and a predictable one-time code is worse than no second factor, because it is trusted.

Rejection-sampled rather than reduced modulo ten: byte % 10 would make the digits 0–5 slightly likelier than 6–9, and while that bias is small it is free to remove.

static Map<String, Object?> sealCode(String code)

[code] reduced to a salt and a hash — the only form of it that may travel.

The map is what goes into [Tom2FAChallengeSpec.verificationData] and [Tom2FAEnrolmentOffer.enrolmentData]. Both are carried in an encrypted token section, so the hash is defence in depth rather than the only defence; it is here because a six-digit code is brute-forceable in microseconds by anyone who does obtain the plaintext, and the encryption is one key compromise away from being no defence at all.

static bool matchesSealedCode(Map<String, Object?> sealed, String submitted)

Whether [submitted] is the code [sealed] was built from.

false — never a throw — for a malformed or absent seal: a token that lost its verification blob is an ordinary thing to meet, and the login's answer to it is the same as its answer to a wrong code.

static List<int> _digest(List<int> salt, String code)

SHA-256 over the salt followed by the code.

Salt first so that the code's bytes cannot be shifted into the salt's position by a code of a different length — the length-extension shape that makes hash(code + salt) and hash(salt + code) different propositions.

static bool constantTimeEquals(String a, String b)

Compares two strings without leaking, through timing, how much of the submission was right.

The same shape as [TomTotp2FAService]'s private one. Public here because two adaptors and their tests use it, and a second private copy is exactly the duplication that lets one of them quietly become a ==.

class TomEmailCode2FAService

class TomEmailCode2FAService extends TomDeliveredCode2FAService<TomEmailService>

A one-time code delivered by email.

Registered as mechanism 'email', so a principal whose [TomPrincipal.twoFactorType] is 'email' — or a [Tom2FAPolicy] that permits it — is challenged with a code sent to their address. 

TomBean.withType(TomEmailService, TomEmailService(outbox: outbox, texts: texts));
// The template the code arrives in:
//   email.two_factor_code.subject: "Your {application} sign-in code"
//   email.two_factor_code.text:    "Your code is {code}. It expires in {minutes} minutes."

The address comes from the user's confirmed 'email' enrolment, falling back to [TomUser.email].

static String maskEmailAddress(String address)

The domain is kept whole and the local part is reduced to its ends. That is the convention every large provider uses, and it is the right trade: the domain is what tells a user which of their inboxes to open, while the local part is the half that identifies them.

A value with no @ is masked as an opaque string rather than rejected — this runs on data the deployment supplied, and a challenge prompt is not the place to discover that a directory holds a malformed address.

class TomSmsCode2FAService

class TomSmsCode2FAService extends TomDeliveredCode2FAService<TomSmsService>

A one-time code delivered by SMS.

Registered as mechanism 'sms'. The number comes from the user's confirmed 'sms' enrolment, falling back to [TomUser.mobile] and then [TomUser.phone] — the same order [TomSmsRequest.toPrincipal] uses, so a code and a notification reach the same handset. 

TomBean.withType(TomSmsService, TomSmsService(outbox: outbox, texts: texts));
//   sms.two_factor_code.text: "{code} is your {application} code."

The default validity is shorter than the mailed code's: an SMS arrives in seconds, and a one-time code should live no longer than it needs to.

static String maskPhoneNumber(String number)

+41791234567 as +*******4567.

The last four digits are kept — the part a user recognises as their own — and every earlier digit is replaced. Non-digits are preserved so a number keeps the shape it was stored in, which is what makes +41 79 … and 0041 79 … still look like the same handset to the person reading the prompt.
