import 'package:tom_core_server/src/tomserver/authentication/oauth_flow.dart';

The authorization-code + PKCE handshake (C-9): everything between "the user pressed Sign in with …" and "here is who they are".

This library knows about OAuth and nothing about logging in. It produces a [TomExternalIdentity] — an issuer, a subject and some claims — and stops. Turning that into a session is [TomOAuthAuthenticationService]'s job, and issuing tokens for it is [TomAuthenticationServer]'s; the separation is the module's central decision (see readme.md).

What actually protects the flow

Three things, and it is worth being precise about which does what, because they are often described as if they were one:

  • state ties the redirect to the browser that started the flow. It is

server-issued, single-use ([TomOAuthStateStore.consume]) and TTL-bounded, so a code replayed into a different pending flow finds nothing to complete. This is the CSRF defence. PKCE ties the code exchange to the client that started the flow. The verifier never leaves the server, and an attacker holding a stolen code cannot exchange it without one. This is the code-interception defence. The registered redirect_uri keeps the code from being delivered to the attacker in the first place — which is why it is configuration and not a request parameter ([TomOAuthProviderConfig.redirectUri]).

Each covers a case the others do not, which is why all three are present and none is optional-by-default.

Why the ID token's signature is not verified

[TomOAuthFlow] reads the claims out of an id_token without checking its signature, and this is deliberate rather than pending. The token arrives as the response body of a TLS-authenticated, server-to-server POST that this server made to the provider's configured token endpoint, using its client credentials. OIDC Core §3.1.3.7 explicitly allows TLS server validation in place of signature checking for exactly that case: there is no untrusted party between the issuer and the reader, so the signature would be verifying a channel that is already authenticated.

The claims that are checked are the ones TLS does not cover: iss must be the configured issuer and aud must contain the configured client id, so a token minted for some other relying party cannot be presented here.

This reasoning stops holding the moment an ID token is accepted from anywhere else — a front-channel redirect, a client-supplied parameter, a cached copy. Nothing in this module does that, and nothing added to it may.

Freshness is checked, and is a separate question

The argument above is about authenticity: who minted this token, and could anyone have substituted it in transit. It says nothing about freshness, and the two do not follow from one another — a token can be unquestionably the issuer's and hours out of date. So exp is verified, and nbf when the provider sends one, against [TomOAuthProviderConfig.clockSkew] (one minute by default).

It is checked even though, on this back channel, a stale token would mean the provider is misbehaving rather than that anyone is attacking. Two reasons. exp is the one claim that costs nothing to verify and is the standard's own requirement of a relying party; and the moment an ID token reaches this code from a second source — which the section above forbids but cannot enforce — an unchecked expiry stops being a shortcut and becomes a replay hole. The skew tolerance is what keeps the check from turning ordinary clock drift into a failed login.

A token with no exp at all is refused rather than treated as unbounded: OIDC Core §2 requires the claim, so its absence is a non-conformant provider, and reading "cannot check" as "check passed" would make the verification true only of providers that chose to cooperate.

iat is deliberately not turned into a rejection. It answers "how long ago was this minted", which is only a refusal once a deployment states a maximum age — a policy this module does not hold, and one the provider has already expressed on its own terms as exp. An OIDC max_age / auth_time policy is the natural place for that decision, and it is a different decision from this one.

class TomOAuthAuthorizationState

class TomOAuthAuthorizationState

A pending authorization: everything the server must remember between sending a user to a provider and the provider sending them back.

The login context is here rather than reconstructed at the callback because the callback is a plain browser navigation and carries none of it: no client id, no locale, no organization, no timezone. Capturing it when the flow starts is what makes an externally-authenticated session come out in exactly the organization and locale the login began in.

class TomOAuthExchange

class TomOAuthExchange

A completed code exchange: which provider it was against, who that provider says this is, and which pending flow it completes.

Constructors

const TomOAuthExchange.new(TomExternalIdentity identity, TomOAuthAuthorizationState pending, {required TomOAuthProviderConfig provider, TomOAuthTokenGrant? tokens})

Pairs an identity with the flow it completes and the provider it came from.

Properties

final TomExternalIdentity identity

The identity the provider asserted.

final TomOAuthAuthorizationState pending

The pending record this exchange consumed — the login context the session must be issued in.

final TomOAuthProviderConfig provider

The provider this exchange was completed against.

Carried rather than re-derived, because a login makes several decisions out of provider configuration — whether to provision, whether to retain the grant — at points far enough apart that two of them could resolve to different providers and disagree about which login this was. Resolution happens once, here, at the only moment the answer is not in question: the pending record names the provider the flow began with, and this exchange is that flow's conclusion.

Deriving it again downstream from [identity] would not be equivalent. [TomExternalIdentity.issuer] is copied from this provider's configuration, so it identifies the IdP and not the registration — and two registrations may share an issuer, which is how a deployment offers one IdP under two scope sets or two client registrations.

final TomOAuthTokenGrant? tokens

What the provider's token endpoint returned, or null when it returned no usable access token.

Surfaced always, and retained only on request. The grant is already in memory for the duration of this request — the flow needed it to reach the claims — so handing it over costs nothing and lengthens nothing, and it is what makes the framework's "keeps nothing by default" position usable rather than merely restrictive: a deployment with its own credential vault can take the grant here and never touch [TomOAuthTokenStore]. What it must not do is start a second authorization flow to obtain what this one already had.

Whether the framework itself keeps a copy is [TomOAuthProviderConfig.storeTokens], and that decision is made after the login succeeds — not here.

Completes a flow: spends the pending record, exchanges [code] and answers who the provider says this is.

Throws when [state] is unknown, expired or already spent — the three cases are deliberately indistinguishable to a caller, because telling them apart tells an attacker whether a handle was ever valid.

Future<TomOAuthTokenGrant> refreshGrant({required String providerId, required TomOAuthTokenGrant grant})

Exchanges [grant]'s refresh token for a fresh one at [providerId].

This is not a login. It consults no [TomAuthenticationService], asks no 2FA policy, touches no session and produces no principal — it is one HTTP call to a token endpoint on behalf of a user who consented some time ago. Reusing the login path here is the drift the C-9 seam exists to prevent: the login path's job is to decide who someone is, and a background job refreshing a calendar token has already had that decided for it.

Throws when the grant carries no refresh token — the caller cannot recover by retrying and must send the user through consent again, which is a different action, not a slower one.

Future<bool> revokeGrant({required String providerId, required TomOAuthTokenGrant grant})

Revokes [grant] at [providerId]'s revocation endpoint (RFC 7009).

Answers true when the provider was asked and did not refuse, and false when there was nothing to ask — the provider configures no revocationEndpoint, or the grant carries no token. The two are different facts and a caller acts on them differently: nothing-to-ask is the ordinary shape of a deployment whose provider publishes no such endpoint, while a refusal is worth an operator's attention.

The refresh token is what is revoked when there is one. Revoking it ends the chain: an access token outlives it by minutes, where a refresh token outlives a disconnect by months. The access token is the fallback for a grant that never carried a refresh token at all.

RFC 7009 specifies an empty 200 for success and for a token the provider does not recognise, which is what makes revoking a grant this deployment may not have minted harmless. This transport sees bodies rather than statuses, so an empty body is read as that success, and a body that decodes to an object carrying error is read as the refusal it is.

Throws [TomOAuthException] (oauth.flow.revocation_rejected) on a refusal, and lets a transport failure out as it comes. Callers that must not fail for either — [TomExternalIdentityStore.unlink] is the one in this module — catch around it; see [revokeGrantsFor].

Future<TomOAuthTokenGrant?> accessTokenFor({required String providerId, required String subject, Duration minimumValidity = const Duration(seconds: 30), TomOAuthTokenStore? store})

A live access token for (issuer, subject) at [providerId], refreshing it when it is within [minimumValidity] of expiry.

The method an application actually calls before reaching a provider's API, and the reason [refreshGrant] alone would not have been enough: "is this still valid, and if not, renew it and remember the renewal" is three steps that every caller would otherwise write, and the caller that writes them wrong writes back nothing — so every call refreshes, and the provider's rate limiter eventually says so.

Answers null when nothing is held for the identity, when the held grant has expired and cannot be refreshed, or when no [TomOAuthTokenStore] is installed at all — the deployment's cue to send the user through consent.

A grant found expired and unrefreshable is deleted, not merely reported as null. It can never mint another token, so it is not a credential this deployment holds — it is a fact about the past, and a credential store is the wrong home for one. Leaving it would make the store grow without bound, make every later call repeat the same read for the same answer, and leave an operator unable to tell a dead row from a live but idle one. The module already takes this position where it is most visible: [TomExternalIdentityStore.unlink] deletes the grant with the link. Nothing is lost that is wanted — the identity link still records that this user once consented, and a deployment that wants a history of consent wants the audit module, not a table of unusable secrets.

A rejected refresh is deliberately not purged, and the contrast is the point: a provider answering invalid_grant during an outage is not proof the grant is dead, and destroying a credential a retry would have used is worse than keeping one that is stale. That path throws instead, because a provider rejecting a refresh token it issued is an event an operator needs to see rather than an empty answer a job retries forever.

A grant that declares no expiry is never expired and so is never purged: the provider said nothing about a lifetime, and guessing one would throw away a working token.

Future<Map<String, Object?>> _exchangeCode(TomOAuthProviderConfig provider, TomOAuthAuthorizationState pending, String code)

The authorization-code exchange.

Future<Map<String, Object?>> _postTokenRequest(TomOAuthProviderConfig provider, Map<String, String> form, String what)

One call to the provider's token endpoint, with client authentication.

Shared by the code exchange and the refresh because the two differ only in their form: the endpoint, the client_secret_basic header and the error-shaped-200 handling are identical, and a second copy of them is a second place for the client secret to be presented differently. [what] names the grant this call performs, and appears in both failures — which is the difference between a five-minute and a one-hour investigation when a provider answers 200 with an HTML error page, or rejects a refresh and the log says "code exchange".

Future<Map<String, Object?>> _claimsFor(TomOAuthProviderConfig provider, Map<String, Object?> tokens)

The user's claims: from the id_token when the provider is OIDC, otherwise from the configured user-info endpoint.

void _verifyIdTokenClaims(TomOAuthProviderConfig provider, Map<String, Object?> claims)

Checks the claims TLS does not cover — see the library documentation for why these and not the signature.

Two independent questions. Who minted this is answered by iss and aud; is it still valid is answered by exp and nbf, both read against [TomOAuthProviderConfig.clockSkew]. The argument that lets the signature go unchecked is about authenticity over an already-authenticated channel and says nothing whatever about freshness, so freshness is checked on its own terms.

iat is read by nobody here, deliberately. It answers "how long ago was this minted", which becomes a rejection only once a deployment states a maximum age — a policy this module does not hold, and one the provider has already expressed in its own terms as exp.

void _verifyIdTokenFreshness(TomOAuthProviderConfig provider, Map<String, Object?> claims)

Checks that the token is inside its own validity window.

A missing exp refuses rather than passing: OIDC Core §2 makes the claim required, so its absence is a non-conformant provider and not a token that never expires. Treating "cannot check" as "check passed" would leave the verification true only of providers that happened to cooperate.

DateTime? _numericDate(TomOAuthProviderConfig provider, Map<String, Object?> claims, String name)

The claim [name] as a NumericDate (RFC 7519 §2), or null when absent.

A numeric string is accepted as well as a number, because providers stringify these often enough that refusing the spelling would be refusing a perfectly good token. Anything else throws: a exp of "tomorrow" cannot be compared, and silently ignoring it would skip the check.

Static

static Future<int> revokeGrantsFor({required String issuer, required String subject, TomOAuthProviders? providers, TomOAuthTokenStore? tokenStore, TomOAuthTokenTransport? transport})

Revokes whatever is held for (issuer, subject) at every configured registration of that issuer, and never throws.

What [TomExternalIdentityStore.unlink] calls, which is why it cannot fail: refusing to unlink because a provider is unreachable would leave the deployment holding the credential it was just told to drop — the opposite of what pressing disconnect asked for. So every failure is logged and the deletion proceeds, and the honest reading of the result is best effort.

Every registration sharing the issuer is asked. Two registrations against one IdP is a shape this module supports, and the token store is keyed by issuer rather than by registration — so which client credentials minted a grant is not recorded. Asking all of them is what makes the revocation reliable, and costs nothing: RFC 7009 makes a token the provider does not recognise a success.

Answers how many registrations accepted the revocation.

static Map<String, Object?> decodeIdTokenClaims(String idToken)

The claims of a JWT, without verifying its signature.

Public because a test asserting the flow's behaviour needs to build the same shape the provider sends, and because the reasoning for not verifying (see the library documentation) is a property of where the token came from, which only the caller knows. Never call it on a token that did not arrive over an authenticated back channel.

static Map<String, Object?> _decodeJsonObject(String body, String what)

Decodes [body] as a JSON object, naming [what] in the failure.

A provider that answers 200 with an HTML error page is common enough that "unexpected character" from jsonDecode is a real diagnosis problem; naming which response failed is the difference between a five-minute and a one-hour investigation.

class TomOAuthMemoryStateStore

class TomOAuthMemoryStateStore implements TomOAuthStateStore

An in-process [TomOAuthStateStore] with a time-to-live.

Expiry is enforced on read rather than by a timer: a record that is never read never needs to be evicted correctly, and a background timer in a library is a thing every embedding process then has to shut down. class TomOAuthPkce

class TomOAuthPkce

A PKCE verifier / challenge pair (RFC 7636).

The verifier is the secret the server keeps; the challenge is its SHA-256 digest, which is what travels to the provider. Only S256 is produced — plain is in the RFC for clients that cannot hash, which a Dart server on the back channel is not.

class TomOAuthStateStore

abstract class TomOAuthStateStore

Where pending authorizations live between the redirect out and the redirect back.

An interface because the right store depends on the deployment: a single process is served by [TomOAuthMemoryStateStore], while a load-balanced pair needs a shared one (the redirect can land on either node) and would back this with the cache or a table.

[peek] and [consume] are separate operations on purpose. The endpoint needs the login context to build its authentication message, and the authentication service needs the PKCE verifier and must spend the record — so the record is read twice and consumed exactly once, and the single-use guarantee lives in one method rather than in each caller's discipline.

class TomOAuthTokenTransport

abstract class TomOAuthTokenTransport

The one place this module speaks HTTP to a provider.

A seam, and the reason the whole flow is testable: a stub provider implements these two calls and every other line — the PKCE check, the state check, the claim mapping, the account linking, the token issuance — runs exactly as it does in production. A flow that called http.post inline could only be tested against a real provider, which means it would be tested by hand, once.
