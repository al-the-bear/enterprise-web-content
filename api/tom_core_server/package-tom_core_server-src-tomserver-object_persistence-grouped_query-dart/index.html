Aggregation and grouping for the typed query layer.

The rest of the query surface describes rows: a [TomSelect] projects an entity's columns and a predicate filters them. This module adds the second shape a relational store offers — groups: rows collapsed by one or more key columns, with an aggregate value computed per group.

Three pieces make that expressible:

  • [TomAggregate] and its concrete nodes ([CountAll], [Count], [Sum], [Avg],

[Min], [Max]) are ordinary [TomOperator]s, so they compose with the existing predicates and render through the active dialect rather than through any driver-specific string. - [TomGroupedSelect] is the compiled sentence: a SELECT that carries the group columns, the aggregate projection, the row predicate (WHERE) and the group predicate (HAVING) as separate, typed parts. - [TomGroupedRow] is the result shape. A grouped query does not return entities — its rows are group-key plus aggregate-value tuples whose shape is decided by the query, not by any entity class — so it gets its own typed holder instead of being forced into the entity type.

Everything stays inside the typed tree on purpose. A raw-SQL escape hatch (the [TomLiteralSelect] shape) would defeat the point: a generated repository has to emit these queries deterministically from a specification, and raw SQL is neither checkable nor portable across dialects.

class Sum

class Sum<T> extends TomAggregate<TomDbDouble, double>

SUM(<value>) — the total of [value] across the group.

The result is a double regardless of the operand's type. SQL widens a sum to an exact-numeric type (MariaDB returns DECIMAL for an integer column), which does not round-trip through Dart's int; widening once, here, keeps the value type predictable instead of dialect-dependent.

class TomAggregate

abstract class TomAggregate<R, V> extends TomOperator<R>

An aggregate function applied to a group: COUNT(*), SUM(t.amount), MAX(t.created), …

[R] is the SQL type of the result (so the node composes with the typed predicates — Sum yields a TomOperator<TomDbDouble> that gt accepts), and [V] is the Dart type the value materialises as, which [read] returns and the result mapper uses to pull the column out of a driver row.

Every aggregate carries an [alias]: a grouped query's result columns are named, because unlike an entity projection there is no column metadata to map them back by. The alias is how [TomGroupedRow] finds the value again.

class TomGroupedRow

class TomGroupedRow

One row of a grouped query's result: the group-key values plus the aggregate values, each under the alias the query projected it as.

This is deliberately not an entity. A grouped row's shape is decided by the query — which columns it grouped by and which aggregates it asked for — so there is no entity class it could be mapped onto, and forcing one would mean inventing a holder per query shape.

Values are read through the typed accessors, which coerce the driver's representation to the declared Dart type: a driver may hand back an exact numeric (SUM/AVG are DECIMAL in MariaDB) or a text form depending on the protocol in use, and the caller should not have to care which.

DateTime? dateTimeValue(String alias)

The value under [alias] as a UTC DateTime.

The module has one convention for an instant and this is a read path like any other: a DATETIME column carries no zone, so its text taken at face value is this node's wall clock rather than the moment the writing node stored. parseSqlInstant is the reading half everywhere else — the reflected entity mapper, [TomDbDateTime.of], and the driver's own grouped projection, which is what normally fills this map — so it is the reading half here too. A second answer in the one place a caller builds a row by hand would be the module disagreeing with itself, silently and by exactly the machine's UTC offset. See datasources/sql_instant.dart.

A value that is already a DateTime is relabelled rather than reparsed: toUtc names the same moment, so a row built by hand from a local value answers what a row built by the driver would.

class TomGroupedSelect

class TomGroupedSelect extends TomGeneratedQuery

A SELECT … GROUP BY … over the entity types: the group-key columns and the aggregate projection, filtered by a row predicate (WHERE) and a group predicate (HAVING).

It sits beside [TomSelect] and [TomCount] as a third compiled sentence rather than as an option on the select, because its result is a different shape: [TomGroupedRow]s, not entities. The two predicates stay separate all the way down to the dialect for the same reason they are separate in SQL — WHERE filters rows before aggregation, HAVING filters groups after it, and ANDing them together would change the meaning of both.

The projection is fully named: each group column is projected as its declared field name and each aggregate as its alias, which is what lets the result mapper build a [TomGroupedRow] without any entity metadata.

Constructors

TomGroupedSelect.new(List<Type> types, {required TomOperator<TomDbBool> query, List<DbCol<dynamic>> groupBy = const [], required List<TomAggregate<dynamic, dynamic>> aggregates, TomOperator<TomDbBool>? having, List<String> orderBy = const [], bool ascending = true, List<TomSortField>? sort, int top = 0, int offset = 0})

Builds a grouped select over [types].

[query] is the row predicate, [groupBy] the key columns, [aggregates] the projected aggregates, [having] the optional group predicate. The ordering (sort, or the orderBy/ascending shorthand) names projection aliases (a group column's declared name or an aggregate's alias), not arbitrary entity fields — ordering a grouped result by an ungrouped column is not meaningful.

Throws [TomQuerySyntaxException] when no aggregate is given, when two projections share an alias, when a group column's type cannot be materialised, or when a sort term is not a projection alias.

Rejects a HAVING that filters on a bare column which is neither a group key nor inside an aggregate.

Such a predicate is not meaningful — the column has many values within a group and no rule for picking one — and databases differ on whether they reject it or silently pick an arbitrary row. Catching it here makes the behaviour the same on every dialect.
