The convergence guard for the tables the framework owns.

TomSchemaConvergenceCheck proves that an application's migration chain builds the shape its entity model declares. The framework's own tables — the job queue, the lease table, the roll call, the blob pair, the audit trail — are not entities, so they sat outside that guard. This is the same comparison pointed at them.

What "one declaration" means here

Each framework table is declared once, as a [TomFrameworkTable]. This file relates that declaration to the three other places its columns could otherwise be spelled independently:

  • [verifyChain] — against the shipped reference migration a deployment

applies when the migration module owns the schema, rather than letting the store create it. The two must build the same table or a migrated deployment and a self-provisioning one diverge. [verifyRowTypes] — against the reflected row types the data source's mapper materialises. A row type is the other half of every SELECT: it names the columns the statement projected. Binding it to the descriptor is what makes a rename in the descriptor, left unmade in the statement, a compile-free but test-caught failure. [verifyLive] — against a provisioned database, read from information_schema. The only one of the three that can catch a schema that was applied once and edited by hand afterwards, and therefore the only one that needs a server; it is tagged db wherever it is used.

Why the model is replayed rather than translated

[modelOf] does not walk a descriptor's columns and classify their SQL types. It renders the descriptor's CREATE TABLE and replays it through [TomSchemaDdlReader] — the very reader the migration side uses. A second classifier would be a second opinion about what TINYINT(1) means, and two opinions that agree today are two opinions that can diverge; one parser cannot disagree with itself.

TomSchemaConvergenceReport verifyChain({required String datasource, required String schema, required Iterable<TomFrameworkTable> tables, required List<TomMigrationArtifact> chain})

Checks [tables] against the migration [chain] that also builds them.

The chain is filtered down to the descriptors' tables before the diff, so a chain that legitimately creates other tables — an application's own, or the migration engine's version table — does not produce a warning per table. What is being asked here is only "does the chain build these correctly".

List<TomSchemaDivergence> verifyRowTypes(TomFrameworkTable table, Iterable<Type> rowTypes)

Checks that every column [rowTypes] map is one [table] declares.

This is the guard on the half of a statement a generated column list cannot cover. A SELECT names columns and a row type maps them; if the descriptor renames a column and the mapper is not changed with it, the projection still compiles and still type-checks — it simply returns nothing at runtime, on whichever path happens to use it.

The asymmetry is deliberate. A column a row type maps but the table does not declare is an error: the projection cannot work. A column the table declares that no row type maps is a warning: a row type may legitimately project a subset, and several do — TomBlobChunkRow reads only chunk_data, TomAuditHeadRow only the two values that recover a chain head.

A String field is exempt from the type comparison, and that is not a loophole. The MariaDB driver decodes every column value into a Dart String before the mapper sees it, so a String field is the driver's raw form and claims nothing about the column's SQL type — the scheduling row types read their DATETIME(6) columns as text on purpose, and parse them with parseSqlInstant. A field of any other type is a coercion claim, and is checked.

Future<TomSchemaConvergenceReport> verifyLive(TomDataSource datasource, Iterable<TomFrameworkTable> tables, {String datasourceName = 'live', String schema = 'DATABASE()'})

Checks [tables] against the schema [datasource] is actually connected to.

Needs a server, which is why it is separate from [verifyChain] rather than folded into it — but it is the only variant that can catch the case neither of the others can: a database whose schema was applied correctly once and then edited outside the migration chain.

DATABASE() rather than a configured schema name, so the check asks the connection what it is connected to instead of being told, and cannot be pointed at the wrong schema by a stale setting.

function frameworkOwnedTables

List<TomFrameworkTable> frameworkOwnedTables({String jobRun = defaultJobRunTable, String lease = defaultLeaseTable, String schedulerNode = defaultSchedulerNodeTable, String blobManifest = defaultBlobManifestTable, String blobChunk = defaultBlobChunkTable, String auditTrail = defaultAuditTrailTable, String oauthState = defaultOAuthStateTable, String deliveryReport = defaultDeliveryReportTable})

Every table the framework owns, at the names it uses when nothing overrides them.

The list exists so "all of them" is a thing that can be named. A deployment that renames a table passes the corresponding argument; one that does not — which is nearly all of them — gets the shipped set. Without this, each caller would assemble its own list, and a table added to the framework later would be checked wherever someone remembered to add it.

The direction of the dependency is deliberate: this module reaches into scheduling/, file_storage/, audit/, authentication/ and messaging/ for their descriptors, and none of them reaches back. A deployment can run the scheduler without ever loading a migration.
