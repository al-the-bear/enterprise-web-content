The tabular shape that export renderers consume.

This is the input half of the export capability: a title, one or more [TomTabularSection]s, and — inside each section — typed [TomTabularColumn]s over a stream of [TomTabularRow]s.

Why a stream of rows and not a list

An export exists precisely for the results too large to hand back inline. A List<TomTabularRow> would put the whole result in memory before the first byte of output was produced, which defeats the purpose: the caller would need enough heap for the rows and the rendered document at once. So a section carries Stream<TomTabularRow> and every renderer pulls it.

The stream is single-subscription and consumed once. A renderer reads it exactly once, in order. Rendering the same result twice — or in two formats — requires a result whose sections can produce a fresh stream; build one per render rather than sharing.

Why cells are positional

Rows are the one thing there are many of, so their representation is the one that matters. A Map<String, Object?> per row allocates a hash table and re-stores every column name for every row; a List<Object?> parallel to the section's columns allocates one list. At a million rows that difference is the whole memory budget. [TomTabularRow.fromMap] exists for the callers who naturally hold keyed values — a TomGroupedRow, a JSON map — and it does the ordering once, against the section's declared columns.

Why this type and not the CE-RP envelope

The CodeSpecs report-result envelope (codespecs_mapping.md §5.28) is a tom_core_codespecs gap class: named by the mapping, not written. This type is deliberately the minimal tabular shape those renderers actually need, so the rendering capability is useful now — any endpoint returning rows can export — and so that when the envelope lands it is adapted to this shape rather than the renderers being rewritten.

The one thing codespecs_mapping.md §5.28 names that is not here is charts (series and axes). Two of the three output formats cannot express a chart at all, so a chart model would be a field that only the PDF renderer ever read. When charts are specified they belong beside this type, not inside it — and they wait on the same envelope, because a chart is a projection of a report result rather than of a tabular one, so its shape follows from the envelope's.

Nothing here anticipates them, deliberately: no chart field, no capability flag beside [TomTabularRenderer.streamsRows], no way for a renderer to declare that it cannot draw one. Each would be a declaration about a shape that does not exist yet — the same mistake as the model itself, one layer down. An application that needs charts sooner registers a renderer that draws them through [TomExportFormats], which the module neither knows about nor has to. ## Why there are two ways to build a section

[TomTabularSection.ofRows] / [TomTabularSection.ofMaps] make the caller declare its columns and project each row onto them. For an export of entities that projection restates what @TomDbColumn already declares, and the two then drift in both directions: a column added to the entity never reaches the export, and a type changed on the entity leaves cells being formatted under a stale [TomColumnType].

[TomTabularSection.ofEntities] / [TomTabularResult.fromEntities] derive the columns from the reflected entity instead, so there is one declaration and nothing to keep in step. They are bounded on purpose — see [TomTabularSection.ofEntities] — and the explicit route remains for everything they cannot express.

Properties

final String name

The machine-facing key: the query alias or map key this column reads.

final String label

The human-facing header text.

final TomColumnType type

The value type every cell in this column must hold.

final int? width

How wide this column should be, in characters, or null to be sized by its [type] and [label].

The unit is a character, in every format, and that is the whole of the contract. It is the unit a caller can actually reason about — "a product name runs to about 24 characters" is a fact about the data, true of the spreadsheet and the printed page alike — and it is the unit OOXML already uses, so a spreadsheet column is written out at exactly this number.

It is not a proportion. A proportion cannot be stated in a spreadsheet at all, because a sheet has no total width to be a proportion of; reading the same number both ways is what made width: 24 mean "about 24 characters" in XLSX and "twenty-four times every other column" in PDF, and left the module's own example printing one column across seven eighths of the page while Amount broke into four pieces down the margin.

A page does have a fixed total, so the PDF renderer cannot give a column its literal 24 characters and stay on the paper. What it honours instead is the ratio of these widths, which is the closest a fixed page can come to an absolute request, and which degrades evenly instead of starving one column to feed another.

Must be at least 1 when given: 0 hides the column in a spreadsheet and collapses it on a page, which is never what a width was meant to say.

Creates a row from cell values in column order.

The list is stored as given rather than copied — a renderer reads a row once and drops it, so the copy would buy nothing and cost an allocation per row. Callers must not mutate a list after handing it over.

Creates a row by reading [values] in the order [columns] declares.

A missing key yields null — an absent value and an explicit null render identically, so distinguishing them would be a difference no output can carry. A key in [values] that no column names is ignored: sections routinely project a subset of what a query returned.

The convenience for the small case — a summary table, a test fixture — where streaming buys nothing. Large results should build the stream directly so they are never fully resident.

factory TomTabularSection.ofMaps(List<TomTabularColumn> columns, Stream<Map<String, Object?>> rows, {String? title})

Creates a section over keyed maps, ordering each by [columns].

The adapter for anything that hands back values by name — a TomGroupedRow's values, decoded JSON, a driver's row map.

The caller declares the columns; they are never inferred from the rows. Inferring them would mean reading the first row to learn the shape, and a first row is the worst available witness: a null cell declares nothing, so the column would be typed by whichever row happened to arrive first and every later row formatted under that guess. It is also unavailable — a section's columns must exist before its stream is subscribed, so inference would make this the one constructor in the family that has to be awaited. The same argument governs widths: [TomTabularColumn.effectiveWidth] falls back to the schema and never measures the rows, because XLSX is written a row at a time and cannot measure them either. A caller that wants its columns derived rather than written out has [ofEntities], which reads them from @TomDbColumn — a declaration, ordered and named and typed, rather than a sample.

static TomTabularSection ofEntities<T>(Stream<T> rows, {String? title, List<String>? include, Set<String> exclude = const {}, Map<String, String> titles = const {}, bool includeFileReferences = false})

Creates a section whose columns are derived from the reflected entity [T], and whose rows are read off each entity by reflection.

The "these entities, these columns" case — the majority of exports, and the one a declarative report definition can express without a hand-written projection. Every @TomDbColumn field of [T] becomes a column, named by its declared field name, typed by [TomColumnType] derived from its declared type, and labelled by [titles] or by the field name. 

TomTabularSection.ofEntities<Task>(taskStream, title: 'Open tasks')

What this is not for

An export of a join or of an aggregate is not one entity: its columns come from several types or from expressions no type declares. Those keep the explicit route ([ofRows] / [ofMaps]), and so does anything needing a computed or reformatted column — a storage key turned into a download URL, say, which this cannot produce because the public URL of a file is a routing decision the export module does not know.

Two kinds of column that are not exported

  • Redacted fields. @TomAudited(redact: …) names the fields whose

values must not exist in a second place at all. An export is a second place, and answering that question differently here would defeat the declaration; they are dropped, and naming one in [include] throws. - File references. A @TomFileReference column holds an internal storage key, not content — a spreadsheet of them is a small leak and is useless to the reader either way. Dropped by default; pass [includeFileReferences] to export the keys to an audience that has a use for them.

Selecting and naming

[include], when given, selects the columns and their order; [exclude] removes columns; both are keyed by declared field name, matching how the audit trail keys its own image — the database column name is a mapping detail a spec author should not have to know. A name in [include], [exclude] or [titles] that no field carries throws rather than being ignored: a typo that silently drops a column is exactly the drift this constructor exists to remove. [include] narrows the exportable set and never widens it, so it cannot be used to reach a redacted or (unless [includeFileReferences] is set) a file-reference column.

static TomColumnType columnTypeOf(TomColumnInformation column)

The cell type for [column], from the type family its annotations declare.

[TomAnnotationAnalyzer.familyOf] describes how the value is stored; a cell holds the Dart value the getter returns, and the two diverge — a JSON column is text in the database and a Map in Dart, and an explicit TomDbType box can disagree with the field it annotates. So a family maps to a column type only when the declared Dart type can actually inhabit it; otherwise the column is [TomColumnType.text], which every renderer formats through tomFormatCellAsText.

Reusing [TomColumnType.dartType] for that test is what keeps this a rule rather than a second type table to maintain beside the first.

enum TomColumnType

enum TomColumnType

The value types a tabular column may hold.

This set is not chosen freshly — it is the set the query layer already produces. TomGroupedRow maps exactly int, double, String, bool and DateTime, so an aggregate result adapts to a column type without a lossy conversion, and a renderer never meets a value it has no rule for.

Values

integer

A whole number; rendered unquoted, right-aligned, as an XLSX number.

decimal

A fractional number; rendered unquoted, right-aligned, as an XLSX number.

text

Free text; the only type that needs quoting and escaping.

boolean

A truth value; rendered as true/false, as an XLSX boolean.

timestamp

A point in time; rendered ISO-8601, as an XLSX date serial.

Constructors

const TomColumnType.new(Type dartType, int naturalWidth)

Creates a column type bound to the Dart type it accepts.

Properties

final Type dartType

The Dart type a cell of this column must hold (or null).

final int naturalWidth

How wide a cell of this type renders, in characters.

Measured against what this package actually emits rather than against the type's theoretical range: [timestamp] is 23 because that is the length of 2026-07-01T00:00:00.000, and [boolean] is 5 because false is. The two numeric widths are the only estimates — an int can reach 20 digits and a double's toString can run longer still, but a column of those is a count, an id or an amount, and sizing every numeric column for its worst case would waste the page on the reports that do not have one.

This is what a column with no [TomTabularColumn.width] is laid out at, so adding a type here means deciding its width — which is why it is a constructor argument and not a defaulted switch somewhere else.
