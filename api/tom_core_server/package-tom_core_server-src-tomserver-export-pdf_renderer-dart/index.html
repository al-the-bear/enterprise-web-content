import 'package:tom_core_server/src/tomserver/export/pdf_renderer.dart';

PDF rendering: the format a person reads, and the one that cannot stream.

Why a package here and not for the other two

package:pdf (Apache-2.0, 3.13.0 — see doc/export.md for the recorded evaluation) is adopted. CSV and XLSX were hand-written because what those formats need from an export is small and fully specified; PDF is the opposite. Paginating a table means knowing how wide a string is in a given font at a given size, which means font metrics, line breaking, and a layout pass that can split a row across a page boundary. That is the whole hard part of a PDF writer, none of it is specific to this package, and writing it again would be exactly the format-encoder work this package declines to own.

The dependency is pure Dart with no native or Flutter part, so it is usable from a plain server isolate.

Why this renderer does not stream

A PDF ends with a cross-reference table of byte offsets into everything before it, so no conforming writer can emit the first page before the last object is placed. On top of that, how many pages there are — a number the footer prints on the first of them — is only known once every row has been laid out. Both facts point the same way, and neither is a property of the library: PDF is a random-access document format, and rendering one costs memory proportional to the result.

[TomTabularRenderer.streamsRows] is therefore false here, and this renderer states its limits rather than discovering them:

  • [rowLimit] caps how many rows it will accept, and it fails rather

than truncating. A silently shortened report is a wrong report that looks right; an error names the limit and points at CSV or XLSX, which have no such ceiling. - [maxPages] raises package:pdf's own 20-page default, which exists for invoices and would reject any real report.

Text outside Latin-1

The default is the PDF base-14 Helvetica, which no file has to embed but which can only encode WinAnsi. A result containing Greek, Cyrillic or CJK text needs a real font: build a [pw.ThemeData] over an embedded TTF and pass it as [theme]. This is left to the application because a Unicode font is a megabyte-scale asset and which one is right is a deployment's decision, not the framework's.

The default announces itself, and that is not a leak

package:pdf prints Helvetica has no Unicode support … as it builds each document, and the same for Helvetica-Bold, because a bold header draws on a second base-14 face. Three things are worth knowing before treating that as log noise to be fixed.

It is not a logger call, so it cannot be silenced the way a logger can: it is a bare print inside an assert in PdfType1Font.create. There is no level to raise and no scope to narrow, and the only interception point is the enclosing [Zone]'s print handler — which would mean string-matching the library's own message, and would swallow every other print the render makes, including the application's. This renderer does not try.

It is also easy to get wrong in a way that looks right. The font is created while the page is laid out, inside addPage, not while the document is serialised — so a zone wrapped around document.save(), which is where one would naturally put it, suppresses nothing at all. A suppression has to enclose the whole build, which widens exactly the blast radius that made it a bad idea.

Sitting inside an assert is also why it cannot reach a deployment. Assertions are compiled out of a dart compile exe binary and of dart run without --enable-asserts, so the line appears in test runs and in explicitly assert-enabled runs, and nowhere else. It is a developer diagnostic delivered by the only channel a package has before an application has configured a logger.

And it stops for the reason it exists: pass a [theme] carrying an embedded font and no base-14 face is ever created, so nothing warns. Suppressing it any other way would be suppressing the answer to a question this module has already decided on purpose.

test/export_test.dart pins both halves — that the diagnostic is emitted once per face under assertions, and that a production-shaped run of the example is silent — because this paragraph is a claim about someone else's library and would otherwise rot without anyone noticing.

Properties

final PdfPageFormat pageFormat

The paper size. A4 by default; use [PdfPageFormat.letter] for US output.

final PageOrientation orientation

Portrait or landscape.

Worth setting to landscape from about eight columns on: the column count a table can carry legibly is what decides this, and only the caller knows how wide its columns really are.

final int rowLimit

The largest number of rows, across all sections, this renderer accepts.

Exceeding it throws a [TomExportException] on the output stream. The default is chosen to be well inside a server's heap while being far more than anyone reads on paper.

final int maxPages

The page ceiling handed to package:pdf, whose own default is 20.

final double baseFontSize

The body text size in points. Header text is one point larger and bold.

final ThemeData? theme

An optional theme, typically supplying an embedded Unicode font.

Supplying one is also the only way to stop package:pdf's base-14 diagnostic, because it stops the base-14 font from being created at all — see The default announces itself in this library's documentation for why that is the only way, and why the line never reaches a deployment.

final bool compress

Whether to deflate the document's object streams.

Set false to produce a PDF whose text is readable in a hex dump — useful when debugging output, and what the tests use to assert content.

Widget _table(_RenderedSection rendered)

One section as a bordered table with a repeating header row.

Columns are laid out by flex, not intrinsically. An intrinsic width is the width of the longest cell, so one row holding a long free-text value would push the table past the page edge and clip every other column; flex makes the text wrap instead.

The flex factors are the columns' [TomTabularColumn.effectiveWidth]s — character counts, the same numbers a spreadsheet is written at. A page's total width is fixed, so the counts cannot be honoured literally; what survives the fit is their ratio, and the ratio is what a reader sees. A column asking for 24 characters beside one asking for 12 gets twice the room whatever the paper size, which is the most of an absolute request a page can keep.

The characters are deliberately not converted to points first. The conversion is a single factor applied to every column, and flex is scale invariant, so it would cancel exactly — arithmetic that changes no output and implies a precision this has no way to deliver.

What matters far more than the unit is that an unhinted column gets a factor of its own. It used to get 1, against hints in the twenties, and the module's own example is what that looked like: product at 24 took seven eighths of the table and Amount came down the remaining strip as A, m, ou, nt.
