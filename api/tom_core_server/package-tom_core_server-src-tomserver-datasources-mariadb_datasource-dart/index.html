class MariaDbDatasource

class MariaDbDatasource implements TomDataSource

A MariaDB / MySQL [TomDataSource] driver (registered for the "mariadb" type).

Connection settings ([username], [password], [host], [port], [databaseName], [timeOut]) are filled from the configuration map by reflection in [initialize], which then opens the [connection]. The driver implements the full data-source surface — [prepareStatement], [executeQuery] (with reflection-based row→object mapping), [executeCommand] — and participates in transactions via plain START TRANSACTION / COMMIT / ROLLBACK (see [MariaDbXADatasource] for the XA variant).

Connection lifecycle

A data source is opened explicitly, and never by the statement that wants to run. Opening it means either [initialize], which binds the settings and connects, or setting the connection fields and calling [connect] — the two forms the package documents. Every execution entry point ([prepareStatement], [executeQuery], [executeCommand]) then requires an open connection and throws a [MariadbDatasourceException] if it is reached before one exists, so all three behave the same way on the same data source.

Opening on demand is not offered because it could not work: [connect] binds [host], [port] and the credentials, and until they are configured it would dial :-1 — turning "never opened" into "the database is unreachable".

A link that was opened and has since dropped is a separate case, and is re-opened automatically: the settings are known, so every entry point reconnects and carries on.

[close] releases the link and lets go of it, which puts the data source back to not-open: a closed data source refuses statements exactly as one that was never opened does, rather than being silently re-opened by the next one to arrive. Deliberate teardown is not a dropped link. [isOperational] and [connected] report the current state, and [toString] distinguishes the two ways of holding no connection — closed from never opened — because they point at different faults.

Maps the driver's [qResult] onto a list of [T], choosing between the five row shapes this driver understands.

This is the module's central decision, and which branch a result takes is determined entirely by what [resultType] (or [T]) declares:

1. a grouped row, when [groupedProjection] is non-null — there is no class to reflect, so the query's own projection supplies the types; 2. a table-less [TomClass], bound by observable member name; 3. an annotated [TomClass], bound by @TomDbColumn name; 4. a plain reflected holder with no @TomDbTable, bound by declared field name — the shape an aggregate query lands on; 5. an annotated entity, bound by its persistent column list.

It is public, and takes the driver's result set rather than a connection, because nothing here needs a server: every branch reads column text the protocol has already decoded. Only a @TomReference column reaches back to the database, and only after a row's own columns are set. Keeping the mapping reachable without a live server is what lets the row-shape decision be tested in the ordinary run rather than only in the db-tagged one.

Closes the connection and lets go of it.

[connection] is cleared whatever the link's state was, so that a closed data source reads as closed rather than as one holding a dead connection. That distinction is load-bearing: [_openConnection] repairs a dropped link, and a closed data source that still carried one would be silently re-opened by the next statement — resurrecting, on the shutdown path, a connection nothing would ever close again.

A data source that was never opened has nothing to release, so closing it changes nothing and leaves it reading as never opened.

String getParticipantId() override

The database this source speaks to, not the object speaking to it.

Two instances configured for one database therefore answer the same id, which is deliberate: a transaction wants the resource enlisted once. What it does not permit is both of them enlisting — they are two connections with two transactions of their own, and only one of them can be the transaction's. TomTransaction.registerParticipant refuses the second with …duplicate_id rather than dropping it, because a dropped connection's writes are neither committed with the transaction nor rolled back with it.

A deployment that genuinely needs two enlistments against one database — two XA branches, say — gives the second source a distinct databaseName, host or port, or overrides this.

Future<BigInt> _lifecycle(String command)

Issues one of the transaction's own statements — START TRANSACTION, COMMIT, ROLLBACK, the XA verbs — without passing admission.

They belong to the connection's owner by definition, and admission would either enlist them in the very transaction they are starting or make them wait for a release only they can bring about. Routed through [executeCommand] rather than around it, so there stays one way a command reaches the connection.

Future<void> _admit()

Enlists this data source in the current transaction, at the point of use.

Called before every statement — [_openConnection] and a prepared statement's execute both route through here — so a data source used inside a running transaction joins it without any call site asking. That is what makes @TomTransactional mean anything: the pipeline opens and concludes the transaction, and it cannot know which data sources the endpoint will touch.

Three cases, in order:

  • the connection already belongs to the current transaction — admitted;
  • it belongs to another — wait for [_released], then look again;
  • it is free, and a transaction is running — take it and enlist. A

participant that cannot start its transaction fails the statement that triggered the enlistment (registerParticipant raises): a statement that ran outside the transaction it was meant to join is the defect this exists to remove.

Enlisting runs [startTransaction], which claims the connection (_claimConnection) and issues its statement without coming back here.

The waiting has a cost worth naming: work that the owning transaction itself waits on, issued from a zone that does not carry it (a TomTransactionManager.runInTransactionScope nested inside it), waits on its own transaction for good. Nothing in the framework does that.

Future<void> _claimConnection(TomTransaction transaction)

Takes the connection for [transaction], waiting while another holds it.

Called by [startTransaction] — whoever enlisted this data source, the point of use or an explicit registerParticipant — so the connection has exactly one owner from its START TRANSACTION to its release. A second transaction reaching a busy data source therefore waits its turn rather than being refused: two requests that each open a transaction are ordinary traffic, not a programming error.

void _releaseConnection()

Hands the connection back, waking every statement waiting in [_admit].

Never _refuseNestedTransaction([String? transactionId])

Refuses a transaction that would nest inside one already running.

Shared by both lifecycles so the refusal cannot drift apart again — it is one programming error, reported one way, whichever data source hits it. [transactionId] names the branch already open where there is one; the plain lifecycle tracks a flag rather than an id, so it has nothing to name and omits the parameter.

Thrown rather than reported as false, and in front of the try that turns a failed statement into false, because the two are not the same kind of event. A START TRANSACTION the database refuses is a failure the caller may retry or route around; a second start on a busy data source is the caller's own mistake, and no retry fixes it. Carrying that distinction is the whole reason for the module's own exception type: a caller that catches Exception to handle connection trouble would otherwise swallow this too, and never learn it has a bug.

Future<bool> startTransaction(TomTransaction transaction) override

Opens the connection's transaction, read-only when [transaction] is.

START TRANSACTION READ ONLY is what makes the flag mean something: the server refuses every write on this connection until the transaction ends, with ER_CANT_EXECUTE_IN_READ_ONLY_TRANSACTION. The coordinator cannot enforce it — it has no idea what a write is — so the resource that can is the only place it can be enforced, and a flag declared on an endpoint and enforced nowhere is a statement of intent a reader will take for a guarantee.

Future<bool> endTransaction() override

Ends this participant's part of a transaction by releasing the connection to whatever is waiting for it; always succeeds.

A one-phase START TRANSACTION / COMMIT has no prepare step, so there is no statement to issue — the XA lifecycle's XA END + XA PREPARE has no plain equivalent (see [MariaDbXADatasource.endTransaction]). [commit] and [rollback] clear the in-transaction flag themselves; what is left is the connection's ownership (see _admit), and this is where it ends, because the coordinator calls this on every participant after either conclusion.

Reporting true is not a formality. The coordinator ands every participant's result into the outcome, so a false here would fail a transaction that had in fact completed.

Future<bool> prepare() override

Phase one for a resource that has no phase one: always true.

A plain START TRANSACTION / COMMIT has no statement that makes the commit certain without performing it, so there is nothing to issue here and nothing this data source can promise beyond what the connection is already doing. Its COMMIT can still fail.

That is the cost of enlisting it beside a two-phase participant, and it is worth naming: the transaction is atomic unless this participant's commit fails, at which point the peers that prepared have already committed. A deployment that needs the full guarantee across two databases uses [MariaDbXADatasource] for both.

Future<bool> commit() override
Future<bool> rollback() override

Undoes the connection's transaction, reporting whether it was undone.

A false here is the outcome that needs a human: the statements this connection issued are neither committed nor rolled back. The coordinator puts this data source in [TomTransactionResult.failed] and reports the transaction as [TomTransactionOutcome.rolledBackWithFailures]; before the result carried it, a failed rollback returned the same true as a clean one and the error log was the entire record.

static void _refuseMultipleStatements(String command, String operation)

The open connection to run [operation] on, re-opening a dropped link first.

This is the one place the lifecycle rule stated in the class dartdoc is implemented, so that every execution entry point observes the same rule rather than each carrying its own guard.

A [connection] of null means the data source is not open — never opened, or closed — and that is refused rather than repaired. Neither case is one a statement should quietly fix. Opening a never-opened data source here could not even work: [connect] binds [host], [port] and the credentials, which arrive only from [initialize] or a direct assignment, so before either it would dial :-1 — reporting an unreachable database where the truth is an unconfigured one, and sending the reader to the network for a configuration bug. Re-opening a closed one could work, and that is precisely why it must not happen by accident: it would resurrect a data source the application deliberately let go.

A link that was opened and has since dropped is the one case that is repaired: the settings are known, the caller never asked for the loss, and reconnecting is exactly what it wants.

[operation] names the calling entry point and is carried in the thrown exception's parameters alongside the state that refused it, so a log identifies both which call ran too early and which of the two faults it met. Refuses [command] when it holds more than one statement.

mysql_client completes a call on the first reply it reads and never checks whether more follow, so every reply after the first stays on the wire and is read by the next call on this connection — which is then answered by its predecessor's reply, and so on for the connection's life. Nothing reports it: a query comes back empty, an XA COMMIT returns before the server has committed, and an error in any statement after the first is never raised. So one call carries one statement, and the check runs before the connection is touched. A script is split first, with [TomSqlLexer.splitStatements] — which is what the migration adaptor does.

A terminating ;, and a ; inside a literal, quoted identifier or comment, are not separators; the lexer is quote- and comment-aware.

static (String, List<String>) toPositionalStatement(String namedSql)

Translates the generated :name [namedSql] into the positional ? form the MySQL binary protocol binds, returning the rewritten SQL and the placeholder names in the exact left-to-right order the ? slots appear.

Delegates to the shared, quote-aware [SqlPlaceholderScan.toPositional] so the datasource and [TomSqlDatasourceRepository]'s name extraction stay in lock-step. A whole-identifier scan in occurrence order — not a per-name replaceAll(":$p", "?") — is essential: replaceAll corrupts a placeholder that is a prefix of another (:id vs :idx → ?x) and collapses a repeated name to a single slot, desynchronising every following bind value. The scan is also string-literal aware, so a :name-looking substring inside an inlined literal ('x:y') is not mistaken for a slot.

static B _readTemporal<B extends TomDbType<dynamic>>(ResultSetRow row, String field, B Function(String?) read)

Reads [field]'s text through [read] — one of the TomDbDateTime, TomDbDate and TomDbTime of factories — and refuses what it cannot.

Those factories parse with the public parseSql… functions, which keep Dart's parse contract and throw a [FormatException]. That is the right answer for a caller parsing text it chose; a stored row is not that. It is data from outside the process, so an unreadable value is a failure of the read, and it is reported the way the numeric readers report theirs — keyed, naming the column and the value, with the parser's exception as the root. Unconverted, the FormatException crossed the endpoints pipeline unclassified: no key, no clientThrow, no column.

The key names what the column failed to be: not_a_date for a DATE holding a timestamp, not_a_time for a TIME holding an interval, not_an_instant for a DATETIME holding neither.

static Iterable<ResultSetRow> _rowsOf(IResultSet result)

The rows of [result], each marked when [result] came over the binary protocol, so the temporal readers can repair what the driver renders there (see [_repairBinaryTemporalText]).

Every loop that maps a row goes through this rather than result.rows: a row read without the mark is read as text-protocol text, and for a binary row that is the defect this exists to prevent.

static String? _repairBinaryTemporalText(String? text)

Restores the six-digit fraction of a temporal value the driver rendered from the binary protocol.

Over the binary protocol mysql_client builds a DATETIME's text itself, and writes the microsecond field as a bare integer: 91 371 µs becomes .91371, which every parser reads as 0.91371 s. So every instant whose fraction is under a tenth of a second came back up to 0.9 s late — one value in ten, with nothing failing. Over the text protocol the server formats the value, with exactly the column's precision, so the same digits there mean what they say; that is why the repair applies only to rows [_rowsOf] marked, and why it cannot be done from the text alone: a binary .5 is 5 µs and a text .5 from a DATETIME(1) is 500 000 µs.

Anything that is not <date> <time>.<digits> is returned unchanged, null included.

static double? _readDouble(ResultSetRow row, String field)

Reads [field] from [row] as a Dart double.

This is the only place that knows how this driver yields a double, and it exists because typedColByName<double> cannot be trusted to widen. mysql_client converts a column to double only from a fixed whitelist of protocol types — TINY, SHORT, LONG, LONGLONG, INT24, FLOAT, DOUBLE (mysql_column_type.dart). DECIMAL/NEWDECIMAL (246) is in neither that list nor the int one, so asking the driver for a double there throws MySQLProtocolException instead of widening.

That matters far beyond aggregates. DECIMAL is the correct SQL type for money — exact where DOUBLE is approximate — so an ordinary business entity hits this on its first select. SUM/AVG over an integer column return NEWDECIMAL too, so an aggregate reaches it even where no column is declared DECIMAL at all.

Reading the raw text and parsing it here loses nothing: the driver's own conversion starts from exactly this text (the whitelist is a gate, not a decoder), and it reports DECIMAL as best-matching Dart String. The exact text form ("1234.56", "43.0000") parses losslessly.

static int? _readInt(ResultSetRow row, String field)

Reads [field] from [row] as a Dart int.

The int whitelist has the same NEWDECIMAL gap as the double one, and an int-declared field over a DECIMAL column is not automatically a modelling error: DECIMAL(n,0) is an exact integer type, and wide identifiers and counters are routinely declared that way. Rejecting the read for being DECIMAL would therefore break a legitimate mapping.

What must not happen is a silent truncation. Reading DECIMAL(10,2) into an int and quietly dropping the cents turns a modelling mistake into wrong money that no test would notice, so this encodes the decision rather than leaving it to the driver: an exact integral value is read, and a value with a fractional part is refused by name. Neither outcome is the driver's raw MySQLProtocolException, which said only that a conversion was unavailable and never which column it was reading.

The datasource binds port to an int field, but application config may express the port either as an int or as a string — e.g. an environment substitution (port: ${DB_PORT:3306}) always yields a string. class MariaDbXADatasource

class MariaDbXADatasource extends MariaDbDatasource

A MariaDB [TomDataSource] that uses XA (distributed) transactions (registered for the "mariadb_xa" type).

It inherits all connection and execution behaviour from [MariaDbDatasource] but overrides the transaction lifecycle to issue XA START / XA END + XA PREPARE / XA COMMIT / XA ROLLBACK against a per-transaction branch id, so this data source can take part in a two-phase commit across multiple resources.

The lifecycle maps onto the coordinator's two phases exactly: [prepare] issues XA END + XA PREPARE, [commit] issues XA COMMIT, [rollback] issues XA ROLLBACK (preceded by XA END when the branch is still active), and [endTransaction] has nothing to do. That is what makes this data source able to keep the promise the phase asks for: a prepared branch commits.

The branch id doubles as the in-transaction guard: [startTransaction] throws while one is set rather than opening a nested branch. Every exit therefore clears it except a failing [prepare], which hands it on to [rollback] — a veto is answered by rolling every participant back, this one included, and [rollback] needs the branch to name. An exit that forgets locks this data source out of every later transaction for good, and the caller cannot recover by rolling back, because the branch it would have to name never began.

String? _txId
bool _ended

Whether the branch has been XA ENDed — it is IDLE or PREPARED rather than ACTIVE.

XA END is legal exactly once, on an ACTIVE branch, and a rollback has to know which side of it the branch is on: XA ROLLBACK is refused on an ACTIVE branch — XAER_RMFAIL: The command cannot be executed when global transaction is in the ACTIVE state — and XA END is refused on an IDLE or PREPARED one. A rollback can arrive in any of the three states: before [prepare] ran, after its XA END succeeded and its XA PREPARE did not, or after a prepare succeeded and the commit did not.

Methods

String _newBranchId()

A new branch id: <database>@<host>:<port>_<process>_<time>_<counter>.

Bounded and unique, in that order of necessity. MariaDB refuses a gtrid over [maxBranchIdBytes] as a syntax error, so a branch id built from the coordinates as written makes every XA transaction fail to start the moment a real hostname or database name is long enough. The unique tail is always kept whole and the readable head is what gets truncated: a shortened name still tells an operator reading XA RECOVER whose branch it is, while a shortened tail could name two branches alike. The tail is unique across processes (a random tag) as well as within one (the time plus a counter). Characters outside [A-Za-z0-9_.@:-] become _, which keeps the id single-byte and safe to quote.

Future<bool> startTransaction(TomTransaction transaction) override

Opens an XA branch. A read-only [transaction] cannot be honoured here.

XA START has no READ ONLY form in MariaDB or MySQL, so this data source cannot ask the server to refuse writes the way its one-phase sibling does. Reported rather than ignored: a deployment that declared @TomTransactional(isReadOnly: true) and reads nothing anywhere would otherwise believe the branch was protected.

Future<bool> endTransaction() override

Ends this participant's part of the transaction: it issues no statement and releases the connection, exactly as its one-phase sibling's does.

Every XA statement belongs to a phase the coordinator decides something with, and this method is called after the decision — so a statement placed here could not influence the outcome it is part of. XA END and XA PREPARE are [prepare]'s; XA COMMIT is [commit]'s.

Reporting true is not a formality. The coordinator ands every participant's result into the outcome, so a false here would fail a transaction that had in fact completed.

Future<bool> prepare() override

Phase one: XA END then XA PREPARE against this branch, as two calls.

Two calls, not one command: the driver reads only the first reply of a multi-statement command (see _refuseMultipleStatements), and a PREPARE's reply left on the wire is what a later XA COMMIT would then return on — before the server had committed.

This is the statement XA exists for. A prepared branch is one the server has undertaken to be able to commit — it survives a restart, and nothing but XA COMMIT or XA ROLLBACK can resolve it — which is exactly the promise the coordinator's prepare phase asks every participant for.

A failure here keeps _txId, and that is the opposite of every other exit. The coordinator answers a veto by rolling every participant back, this one included, and [rollback] needs the branch to name; clearing it would send XA ROLLBACK null and leave the real branch behind. [rollback] clears it in its finally, so the data source is not wedged either way.

Future<bool> commit() override

Phase two: XA COMMIT against the prepared branch.

Reached only once every participant has prepared, so the branch here is always a prepared one and this call is the promise being kept. A failure is an in-doubt branch rather than a veto: the coordinator reports the transaction as partially committed and does not roll anybody back, because peers have already committed. The branch is left set and prepared so that an operator — or a later XA RECOVER — has something to name.

static int? normalizeGeneratedId(BigInt rawLastInsertId)

Normalises a driver-reported last-insert id into a generated key: the driver reports 0 when a statement generated no AUTO_INCREMENT value (e.g. an UPDATE, or an INSERT into a table without one), and a real AUTO_INCREMENT value is never 0 — so 0 maps to null ("no generated key") and every other value passes through as an int.

static List<Object?> buildPositionalParameters(List<String> parameterList, Map<String, Object?>? params)

Maps the named [params] onto the positional bind list its [parameterList] expects, in placeholder order.

Values are taken raw — a Dart null stays null (so it binds SQL NULL), a String keeps its exact characters (no surrounding quotes), an int/double/DateTime keeps its native value. They must not be rendered through the SQL-literal renderer (objectOp), which would double-encode them over the binary protocol — a null would bind the text "NULL" and a string would carry literal quote characters.

A [TomDbType] box is the one value that is not bound raw: it is the SQL representation a column's toDbConverter produces (e.g. an enum mapped to a TomDbString), and the driver only understands primitives. Binding the box directly would marshal it through its toString() — "TomDbType TomDbString full" — which the server rejects (an ENUM column truncates it to '', error 1265). Unwrapping the box to its primitive here keeps that kernel→driver translation at the single data-source boundary that owns it. Returns an empty list when [params] is null.

class MariadbPreparedStatementException

class MariadbPreparedStatementException extends TomServerException

Thrown when a MariaDB prepared statement failed with no live link to have run on, signalling that a single reconnect-and-retry may recover it.

The type carries the whole signal: [MariadbPreparedStatement.execute] catches this and nothing else, so raising it is the decision to retry. Which failures qualify is settled by isLostConnectionFailure.

function _toBindParams

Map<String, dynamic>? _toBindParams(Map<String, dynamic>? params)

Marshals a whole named-parameter map through [_toBindValue].

Both statement paths need this and only one of them used to have it. The prepared-statement path marshals positionally through [MariadbPreparedStatement.buildPositionalParameters]; executeQuery and executeCommand handed their map to the driver untouched, so a hand-written store binding a DateTime or a bool got the driver's own encoding rather than this one — a local wall-clock reading in a column read back as UTC, and the string 'false' in an integer column. That is why the scheduling, audit and OAuth-state stores render every instant with sqlInstant before binding it: they were routing around this hole rather than choosing to. Marshalling here makes the boundary one boundary, whichever path a statement takes.

function _toBindValue

Object? _toBindValue(Object? value)

Marshals one bind [value] into a driver primitive: a [TomDbType] box is unwrapped to the Dart value it holds; a Dart bool becomes its MariaDB integer encoding; a [TomZonedDate] becomes its DATE text and a [TomZonedTime] its TIME text; any other [DateTime] becomes its UTC DATETIME(6) text; every other value is bound as-is.

MariaDB has no native boolean type — BOOLEAN is an alias for TINYINT(1) stored as 1/0. The driver serializes a bound Dart bool as the string 'true'/'false', which the server rejects for an integer column ("Incorrect integer value: 'false'", error 1366). Translating bool→int here keeps that kernel→driver mapping at the single data-source boundary that already owns the [TomDbType] unwrap.

MariaDB has no zone-aware DATETIME either, and the driver serializes a bound [DateTime] through its toString() — which for a UTC instant ends in Z. The server rejects the suffix ("Incorrect datetime value: '2000-01-01 00:00:00.000Z'", error 1292), so a DateTime must reach the driver with no zone designator — DateTime.utc(...) is the ordinary case, not an exotic one.

Rendered through [sqlInstant] rather than converted with toLocal(). toLocal() also produces an acceptable suffix-less value and round-trips on the node that wrote it, which is why it stood for a while — but what it stores is that node's wall clock, so two servers of one cluster leave different characters in the column for the same moment and each reads the other's rows off by the difference in their offsets. [sqlInstant] writes the instant, identically everywhere, and TomDbDateTime.of reads it back as UTC. Callers keep whichever flag they like on their own DateTime; only what reaches the driver is normalised.
