SMTP delivery: the settings, the conversation, and the failure classification that drives every retry decision downstream.

Why the transport is written here rather than taken from a package

The protocol surface a server actually needs is small — greet, optionally upgrade to TLS, optionally authenticate, address, transfer — and the part that matters most for a reliable mailer is not the wire format at all but the classification of what comes back. A dependency that returns "it failed" without saying whether the failure is worth repeating pushes the hardest decision back onto the caller, which is where mailers go wrong. Owning the conversation is what lets [TomSmtpTransport] map every reply code to a retry judgement once, in one place, and document why.

The classification rule

SMTP's reply codes carry the answer in their first digit, and the standard means it:

CodeMeaningJudgement
2xxacceptedsuccess
3xxsend moreintermediate, never final
4xxtransient negative — "not now"retry
5xxpermanent negative — "no"do not retry

The two exceptions are deliberate and documented at their call sites: authentication failures (535) are permanent as the RFC says but are the single most common misconfiguration, so the message names the setting; and a socket that dies mid-conversation is transient regardless of what code preceded it, because no answer at all is not a refusal.

class TomSmtpConnection

abstract class TomSmtpConnection

The socket half of an SMTP conversation.

An interface rather than a concrete socket so the protocol logic in [TomSmtpTransport] is testable end to end without a mail server: every branch above — a missing STARTTLS, a rejected credential, a partially refused recipient list, a 4xx deferral — is reachable against a scripted fake, and none of them is conveniently reachable against a real relay.

class TomSmtpTransport

class TomSmtpTransport extends TomMessageTransport

Delivers [TomMessageChannel.email] over SMTP.

One connection per message. That is the right default for a server whose mail is occasional — a pooled connection to a relay that closes idle sockets is a source of failures that only appear under light load — and the cost is one handshake per notification, which the outbox is already absorbing asynchronously.

final TomMimeEncoder encoder

Renders the message document.

Injectable so a test can pin the boundaries and the date — and so a deployment that must sign its mail can, without forking the transport: a subclass overriding [TomMimeEncoder.encode] to prepend a DKIM-Signature header to super.encode(message) is the whole seam.

It is needed because this transport writes the document to the socket exactly as the encoder produced it. A deployment relying on that relies on its relay to sign, which is fine for a provider relay and is a requirement to state for one sending directly to destination MX hosts: unsigned mail is accepted and then filed as spam, so nothing here can ever report that it happened. See doc/messaging.md.

enum TomSmtpSecurity

enum TomSmtpSecurity

How the connection to the mail server is secured.

Values

Plain TCP, no encryption. For a mail relay reachable only over a trusted network — anything else sends the credential in the clear.

Plain TCP upgraded with STARTTLS after the greeting. The usual choice on port 587.

TLS from the first byte ("SMTPS"). The usual choice on port 465.

function _quietly

Future<void> _quietly(String stage, Future<void> Function() action)

Runs [action], writing any failure down instead of raising it.

The policy is the same wherever this is used: the outcome that matters is already decided, and an error while tidying up afterwards must not be allowed to contradict it. A relay that drops the socket instead of answering QUIT has not un-delivered the message it accepted on the 250, and reporting a failure there would produce a duplicate on the retry.

Swallowing is not the same as discarding. A relay that consistently errors on QUIT, or a TLS socket that never shuts down cleanly, is invisible until someone reads a packet capture — so the error is logged at debug, where it costs nothing until somebody goes looking.

[stage] names where the failure happened. These lines are read long after the fact, when the reader has no idea which half of a teardown produced them, so "an error was ignored" on its own is barely better than silence.
