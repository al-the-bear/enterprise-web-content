The shared pending-authorization store: one row per flow in progress, in the database the application already has.

Why the in-process store is not enough

An authorization-code flow is two HTTP requests, and the second one is a redirect the provider issues to the user's browser. It lands wherever the load balancer sends it. On a single node that is always the node that began the flow; behind a load balancer it is a coin flip, and a callback that lands on the wrong node finds no pending record and fails with oauth.flow.unknown_state — the same key an expired handle and a replayed one produce. The symptom is "external login works, but only sometimes, and the log says replay attack". Restarting a node does the same thing to every flow in progress.

So the record has to live somewhere both halves of the deployment can see, and in practice that is the database every node is already talking to. This is the same move TomSqlJobStore and TomSqlLeaseLock make for the scheduler, and it is deliberately the same shape: one [TomFrameworkTable] declaration, created on first use or by a shipped migration, with the database — never the application — arbitrating the races.

Completing a flow is one statement

DELETE FROM tom_oauth_state
 WHERE state = :state AND expires_at > :now
RETURNING state, provider_id, ...

The single-use guarantee is that statement. Two callbacks racing the same handle both reach the DELETE; exactly one of them gets a row back and the other gets an empty result, because the row can only be deleted once. A read-then-delete would look equivalent and is not: both readers would see the record, and the replay the state exists to defeat would succeed once for each racer.

When the answer to the completion is lost

[TomSqlJobStore] re-reads its row when a claim's acknowledgement never arrives, because the claim mutates the row and the truth is still there to be read. Nothing analogous is possible here: if the DELETE committed and the answer was lost, the record — including the PKCE verifier the exchange needs — is gone, so there is nothing to recover and no way to complete the flow. The ambiguity therefore resolves the only way it can, and fortunately the conservative way: the exception propagates, the login fails, and the user presses the button again. The cost of failing closed here is one retry; the row is already gone, so a replay cannot succeed either.

Expiry

A deletion predicate on the statements, plus a swept-on-write bound. Of the two shapes a relational store can take, this is the one that needs neither a background timer (which every embedding process would then have to shut down) nor a scheduled job (which makes correctness depend on a scheduler being configured — and the scheduler is exactly the subsystem a deployment may not be running):

  • every read and the completion carry AND expires_at > :now, so an expired

record is never selected. It does not have to be deleted first to behave like an unknown one, which is what keeps the three failure cases indistinguishable to a caller; [store] deletes expired rows before writing, so a deployment that keeps starting flows nobody finishes cannot grow the table without bound. The sweep is throttled to [sweepInterval] because it is bookkeeping, not correctness — the predicate above already makes an unswept row invisible, so sweeping on every* login would buy nothing and cost a delete per login.

This mirrors [TomOAuthMemoryStateStore], which enforces its TTL on read and sweeps on write for the same reasons. Two stores behind one interface should not have two different theories of when a record dies.

The PKCE verifier is stored as written, and not encrypted

The row is a credential at rest and is treated as one, so the decision is stated rather than defaulted into.

What the verifier is. A single-use, TTL-bounded nonce that proves the party redeeming an authorization code is the party that requested it. On its own it authorises nothing: without the code — which the provider delivers only to the registered redirect_uri, over the back channel — it is a random string. PKCE's threat model (RFC 7636 §1) is an attacker who intercepts the code; the verifier is this server's answer to that attacker, not a long-lived secret of its own.

What encrypting the column would buy. Protection against someone who can read this table but not the process's key material — a stolen backup, a replica, a query log. That is a real threat and the reason encryption is worth asking about. It is not the threat that decides this one, because an attacker with that access to this database also has the identity provider's client secret, the JWT signing keys and every issued session — the verifier is the least of what they hold, and encrypting it alone would be security theatre pointed at the smallest item in the blast radius.

What it would cost. The framework has no column-encryption facility. One would have to be invented here, in an OAuth store — the wrong place for a data-source concern — and every deployment would then carry a key whose loss silently breaks external login. A wrong key is indistinguishable from an expired handle at the only point it is read.

What is done instead, which bounds the exposure to the flow's own lifetime rather than merely obscuring it:

  • the row is deleted by the completion, not marked spent, so a finished

flow leaves no verifier behind at all; an abandoned flow's row survives at most its TTL before the sweep removes it; the column is VARCHAR, so it never reaches an off-page overflow segment that a DELETE leaves readable.

A deployment whose regulator requires the value encrypted at rest has two answers that do not need this class to change: encrypt the tablespace, or install its own [TomOAuthStateStore]. The seam exists precisely so this decision does not have to be the framework's for everyone.

Time

Instants are stored as DATETIME(6) in UTC and read back through String columns — see datasources/sql_instant.dart for why the driver makes that necessary.

class TomOAuthStateRow

class TomOAuthStateRow

One pending-authorization row, as the mapper materialises it.

The instants are String fields rather than DateTime ones on purpose: the MariaDB driver builds a DATETIME with DateTime.parse, which yields a local DateTime that compares unequal to the UTC value that was written. Carrying the text and converting with parseSqlInstant makes the round trip exact.

expires_at is mapped even though [TomSqlOAuthStateStore] does not read it back, because the framework-schema guard treats an unmapped column as a finding worth reporting and this one is genuinely projected by SELECT <columnList>.

class TomOAuthStateStoreSettings

class TomOAuthStateStoreSettings

The configured choice of pending-authorization store.

Read from the same oauth: block as the provider set, because the two are one deployment decision: turning on external login and deciding where its half-finished flows live are read together, in one place, by whoever writes the configuration. 

oauth:
  stateStore:
    type: sql          # memory (default) | sql
    datasource: main
    table: tom_oauth_state
    timeToLiveSeconds: 600
    createSchema: true
  providers:
    google: { ... }

Absent, the answer is [TomOAuthStateStoreType.memory], so a single-node deployment behaves exactly as it did before this store existed and nothing has to be configured to keep it that way.

class TomSqlOAuthStateStore

class TomSqlOAuthStateStore implements TomOAuthStateStore

A [TomOAuthStateStore] whose pending authorizations are rows in a [TomDataSource].

Constructors

TomSqlOAuthStateStore.new(TomDataSource datasource, {String table = defaultOAuthStateTable, bool createSchema = true, Duration timeToLive = const Duration(minutes: 10), Duration sweepInterval = const Duration(minutes: 1)})

Creates a store over [datasource].

[table] names the pending-authorization table. With [createSchema] left true the table is created on first use, which is what a test or a self-provisioning deployment wants; set it false when the schema is owned by the migration module and the application's database user may not run DDL.

[timeToLive] is measured from [TomOAuthAuthorizationState.createdAt], the same as [TomOAuthMemoryStateStore] measures its own — the two stores implement one contract and must not disagree about when a record dies.

[sweepInterval] bounds how often [store] prunes expired rows. It is a cost control and nothing else: expiry is enforced by the expires_at predicate on every read, so a row the sweep has not reached yet is already invisible.

factory TomSqlOAuthStateStore.named(String datasourceName, {String table = defaultOAuthStateTable, bool createSchema = true, Duration timeToLive = const Duration(minutes: 10), Duration sweepInterval = const Duration(minutes: 1)})

Creates a store over the registered data source named [datasourceName].

Throws a [TomServerException] keyed oauth.state_store.unknown_datasource when no such data source is registered — a configuration error far better caught at start-up than on the first login. The base class rather than a subtype is deliberate; [TomServerException] says why.

Future<int> purgeExpired([DateTime? now])

Deletes every record whose deadline has passed, answering how many went.

Called by [store] on the [sweepInterval] cadence, and exposed so a deployment that would rather prune from a scheduled job — or an operator cleaning up after an outage — can drive it directly. It affects no behaviour: an expired row is already invisible to [peek] and [consume].

This is the only place the expiry predicate is written. The throttled sweep comes through here rather than issuing its own copy, so what the background prune deletes and what an operator's prune deletes cannot come apart. [now] exists for that caller: it prunes against the instant it stamped its throttle with, not a second reading of the clock.

Future<void> deleteAll()

Empties the table.

For provisioning and for tests that need a known-empty state — the same reason [TomSqlJobStore.deleteAll] exists.

Future<void> _sweep()

Prunes expired rows through [purgeExpired], at most once per [sweepInterval].

All this adds to [purgeExpired] is the throttle and a discarded row count; the statement is deliberately not repeated here. Two copies of one predicate is the duplication that drifts, and a store whose background sweep and whose explicit purge disagreed about what "expired" meant would leave rows behind that no purge removes, with nothing failing to say so.

The sweep's own instant is passed on, so the deadline the delete tests against is the one the throttle was stamped with rather than a second reading of the clock. The stamp precedes the await for the usual reason: two [store] calls interleaving here must not both get past the throttle.

Values

[TomOAuthMemoryStateStore] — a map in one process. The default, and correct for every deployment that is one process.

[TomSqlOAuthStateStore] — a table every node can see. What a load-balanced deployment needs, because the provider's redirect lands on whichever node the balancer picks.
