Server self-login — the deployment authenticates as itself against the auth server and installs the resulting principal as [TomServerPrincipal.current].

A deployed server is a principal like any other client: it presents a service credential, receives a token pair, and the token reconstructs a [TomPrincipal] whose entitlements are the feature grants of this deployment. Those grants then cap every user's grants — the min(user, server) meet in TomAccessControl (kernel, access_controls.dart).

Unconfigured is the default, and it is silent

Every server built before server-as-principal existed has no service credential configured, and must keep working byte-for-byte as it did. So [TomServerSelfLogin.loginAndInstall] returns false and installs nothing when the configuration is incomplete — it does not throw, does not log an error, and leaves [TomServerPrincipal] empty so access evaluation degrades to the user's grant alone. Only a configured deployment that then fails to log in is an error, and that one is loud.

Why a transport seam

The login is one JSON POST. Putting it behind [TomServiceLoginTransport] keeps the credential handling, the response parsing and the principal reconstruction testable without a live auth server, and lets a deployment whose auth server speaks a different dialect swap the one HTTP call rather than reimplement the flow.

static Duration globalSettingRenewalLead

How long before a session expires the next login is attempted.

Long enough that a slow auth server does not leave the deployment briefly capping at an expired principal, short enough that the extra logins are noise rather than load.

How soon a failed renewal is tried again.

Sooner than the lead, because the session is now closer to expiry than it was when the attempt was scheduled, and the reason a renewal fails is usually a brief one.

Reached when a session's whole life is shorter than the lead — legitimate for a deployment issuing very short service tokens, and a busy-wait without the clamp.

static Future<TomServerSession> logIn(TomServiceCredential credential, {TomServiceLoginTransport transport = const TomHttpServiceLoginTransport(), bool decryptTokens = true})

Logs in with [credential] and returns the deployment's [TomPrincipal].

[decryptTokens] controls whether the authorization token's encrypted section is unwrapped locally; it must be true for a deployment whose entitlements travel in the encrypted claims, which is the normal case for a server that holds the RSA private key.

Throws [TomServerSelfLoginException] when the auth server refuses, when the response is not the expected shape, or when a token it carried cannot be decoded into a principal.

static Future<bool> loginAndInstall(TomBaseServerConfiguration config, {TomServiceLoginTransport transport = const TomHttpServiceLoginTransport(), bool decryptTokens = true, bool renew = true})

Logs the deployment in from [config] and installs the principal into [TomServerPrincipal]; returns whether a principal was installed.

Returns false — silently, having changed nothing — when the deployment did not configure self-login. That is the GUARD this whole feature stands on: an unconfigured deployment behaves exactly as it did before server-as-principal existed. A configured deployment that cannot log in throws [TomServerSelfLoginException]; that is a misconfiguration the operator must see, not a state to degrade into, because degrading would silently widen access.

TomServer.start() calls this itself, before it binds the socket, so a deployment that starts its server the ordinary way needs no call here. Call it directly only when the principal must be installed without a TomServer — a worker isolate or a scheduled job that talks to the same capped services but serves no HTTP.

static void stopRenewal()

Cancels any scheduled renewal, leaving the installed principal in place.

Not a way to drop the principal, and there is deliberately no such call here: clearing it widens access, since an uncapped deployment caps nobody. A shutdown stops the loop; it does not un-cap the server on its way out.

static Future<bool> renewNow()

Logs in again with the credential [loginAndInstall] used, and installs the result; returns whether it succeeded.

The renewal the timer performs, callable directly — a deployment that knows its entitlements have changed need not wait for the lead time.

A failure keeps the principal it has. The old cap may be stale, and a stale cap is still a cap; dropping it would widen every user's access at the moment the auth server became unreachable, which is exactly when widening is least defensible. So a failure is logged, the principal stands, and another attempt is scheduled.

static Duration renewalDelayFor(DateTime expiresAt, {DateTime? now, Duration? lead})

How long to wait before renewing a session that expires at [expiresAt].

One [lead] before expiry, clamped to [minimumRenewalDelay] so a session shorter than the lead — or one already past — schedules a prompt attempt rather than a negative delay.

Public and pure because it is the part worth checking: the arithmetic has three edges (comfortable, too short, already past) and a timer is a poor place to discover which one was taken.

static (String, String) _readTokens(String body, TomServiceCredential credential)

Extracts the (authentication, authorization) token pair from a login response body.

Two spellings are accepted because two are in the field: the kernel's [TomAuthenticationResult] serialises authenticationToken / authorizationToken, while application login DTOs commonly shorten these to authToken / authzToken. Accepting both here is cheaper than forcing every auth server to re-shape a response it already publishes to its clients — and the two names are unambiguous, so nothing is guessed.

When only one token is present it is used for both roles, matching [TomBearerAuthentication.convertTokenPayloadToPrincipal]'s own fallback.

class TomServerSelfLoginException

class TomServerSelfLoginException extends TomServerException

Raised when a configured deployment fails to log itself in.

Never raised for an unconfigured deployment — that path returns false instead (see [TomServerSelfLogin.loginAndInstall]).

Constructors

TomServerSelfLoginException.new(String key, String defaultUserMessage, {TomServerCallError? serverCallError, Object? rootException})

Creates the exception.

[serverCallError] carries the kernel's account of the outbound HTTP call when the failure came from one — the status, the body, the underlying exception. Without it the only record of why the auth server could not be reached is whatever the message interpolated, which is a string an operator has to read rather than a value anything can branch on. It never reaches a client: this type masks its message, and tomErrorEnvelope does not serialise the field at all.

Written out rather than using super. parameters because the super(...) call is explicit — it hard-wires clientThrow: false, which is the point of the type — and Dart allows only one of the two forms.

class TomServerSession

class TomServerSession

What a self-login produced: the deployment's principal, and how long the tokens that carry it are good for.

The expiry is here rather than inferred by the caller because it is the one fact renewal is scheduled against, and a caller that had to dig it out of a token would be re-implementing the decode this class already did.

Constructors

const TomServerSession.new({required TomPrincipal principal, required DateTime expiresAt})

Creates a session.

Properties

final TomPrincipal principal

The deployment, as a principal.

final DateTime expiresAt

When the session stops being good.

The earlier of the two tokens' expiries, because the session is only as good as its shorter half — a still-valid authentication token beside an expired authorization token is a principal whose grants have lapsed, which is the half that does the capping.

Never absent: a session is built only from live tokens, and a token with no exp is not live — [TomBearerAuthentication.checkTokenLifetime] refuses it, and [TomServerSelfLogin.logIn] reports that as server.selflogin.bad_token. So every installed session has a deadline to schedule its renewal against.

Methods

String toRequestBody()

The login request body, shaped as the kernel's [TomAuthenticationMessage].

Written by hand rather than through reflection so the credential never passes through a general-purpose serialiser that might log or cache it.

The identity fields come from this credential; the three locale fields do not, because a deployment has no locale to assert. It is a process, not a device: there is no browser to read a language from, no operator present to have a country, and its own clock is UTC. So it sends [TomAuthenticationMessage]'s defaults — which is what "no locale" is already spelled as in this framework, XX being the ISO 3166-1 user-assigned code the kernel uses for "none".

They are read from the message type rather than restated here. Writing the body by hand buys the credential its isolation and costs exactly one thing: nothing otherwise keeps it agreeing with the type it claims to be shaped as. Three literals would have been a second copy of the kernel's defaults, correct on the day they were written and silently stale the day the kernel moved one.

Static

static TomServiceCredential? fromConfiguration(TomBaseServerConfiguration config)

Reads the credential out of [config], or returns null when the deployment did not configure server self-login.

"Did not configure" means any of the three required values ([TomBaseServerConfiguration.authServerLoginUri], [TomBaseServerConfiguration.serviceAccountName], [TomBaseServerConfiguration.serviceAccountCredential]) is absent or blank, or the URI does not parse. null is the supported, silent default — see the library doc. A partially configured deployment is treated the same way deliberately: half a credential cannot authenticate, and failing loudly at startup for a value the operator may be mid-way through rolling out is worse than running uncapped. [TomServerSelfLogin.loginAndInstall] logs the skip at info level so the state is visible.

"Blank" includes whitespace for all three, the credential included: an unsubstituted ${SERVICE_CREDENTIAL} leaves whitespace behind in some templating setups, and a whitespace credential read literally would pass this test and buy a login that cannot succeed -- reported as a rejected credential rather than a missing one, which is the harder of the two to diagnose because the redaction policy hides the value that would have explained it.

The trim decides whether one was configured and nothing else: the value is carried through as written. A secret is opaque, so if the auth server expects a trailing space then that space has to reach it, and reshaping it here would turn a correct deployment into the same undiagnosable rejected login, inverted. TomSmtpSettings.fromConfiguration splits the analogous smtpPassword the same way.
