The CE-DB ↔ CE-MG convergence check: proof that a schema's migration chain builds exactly the shape its entity model declares.

The two halves of a persistence specification are written independently. The entity model (@TomDbTable / @TomDbColumn) says the schema has a shape; the migration chain under <databaseMigrationsDirectory>/<datasource>/<schema>/ independently builds one. Nothing in the type system relates them — and the migration filenames, which decide the order that chain is replayed in, are one of the few string surfaces deliberately left untyped. This check is their only guard.

It runs with no database: the expected side comes from reflection, the actual side from replaying the chain's DDL text ([TomSchemaDdlReader]). That is a requirement, not an optimisation — a check that needs a live server cannot gate code generation.

class TomEntitySchemaReader

class TomEntitySchemaReader

Derives the expected schema — the shape the entity model declares.

This is the half of the check that reads @TomDbTable / @TomDbColumn through [TomAnnotationAnalyzer] and reduces it to the same [TomSchemaModel] the DDL side produces, so the diff compares one vocabulary only.

What the entity model can and cannot say

The comparison scope is bounded by what the annotations actually declare, and that boundary is deliberate rather than provisional:

  • Compared — table existence, column existence, column type family

([TomSqlTypeFamily]), and the primary key. Not compared, because the entity model does not declare it — column length and precision (VARCHAR(255) vs VARCHAR(64)), defaults, AUTO_INCREMENT, unique keys, secondary indexes, foreign keys, charset, collation and engine. Not compared, because the entity side carries no usable signal — nullability. Every mapped Dart field is nullable so an unsaved record can exist, and [TomColumnInformation.declaredType] erases nullability anyway (int? arrives as int). The DDL side still parses nullability into [TomSchemaColumn.nullable], so a future entity-side declaration can switch the comparison on without re-parsing anything. Out of scope entirely* — seed data, generated columns, partitioning and stored routines.

static ({List<TomSchemaDivergence> divergences, TomSchemaModel schema}) read(Iterable<Type> entityTypes)

Reduces [entityTypes] to the schema shape they declare, together with any contradiction within the entity model itself.

Two entities mapping to the same table name is not an error — a table may legitimately be read through more than one projection — so their columns are merged, and the table's origin names the first entity that declared it.

They must agree on the primary key, though, because a table has exactly one. The first entity to declare a table fixes its key; a later entity on the same table whose key differs (compared by [_sameKey], the same tolerance the diff applies to the DDL side) yields a [TomSchemaDivergenceKind.conflictingEntityPrimaryKey] and leaves the first declarer's key in place.

Keeping the first key is what makes the reported [TomSchemaTable.origin] and the reported key describe the same entity. The alternatives are worse: letting the last entity win — which is what this did before — is a silent overwrite whose outcome depends on the caller's iteration order, and merging the two keys into a union would put a key in the model that neither entity declares, so every downstream comparison would run against a shape nobody wrote and report a second, invented divergence against the DDL.

The verdict is therefore order-independent — both orders report the contradiction — while which key survives follows the origin by design.

static List<String> primaryKeyOf(TomTypePersistenceInfo info)

The primary-key column names [info] declares, in declaration order.

@TomEntityId is the primary signal and supports a composite key. When no field carries it, [TomDbTable.idColumn] is used, and failing that [TomDbTable.primaryKeyField] — resolved through the column mapping, since it names a field and the DDL side knows only columns.

class TomSchemaConvergenceCheck

class TomSchemaConvergenceCheck

The named CodeSpecs validator check that proves CE-DB and CE-MG agree.

Using it

[checkAll] walks a whole <databaseMigrationsDirectory> tree and returns one report per <datasource>/<schema> pair; [checkSchema] does a single pair. [verify] is the pure core: hand it an already-read chain and the entity types, and it computes the report with no I/O at all.

Everything here is synchronous, and says so

No database is opened and none needs to exist; the only I/O is reading a handful of migration files, which this module does synchronously throughout. So these methods block, and their signatures admit it — across the module a Future means a database is involved ([TomDbMigrations.migrateDatabases], [TomDbMigrator.applyMigration], [TomFrameworkSchemaCheck.verifyLive]) and nothing else does.

The honesty is not cosmetic. A future that is already complete before the first await tells a caller the file walk is off the event loop when it is not — which is exactly wrong for a check that runs at startup. Worse, it makes the missing-directory refusal ignorable: a caller who omits the await gets a value that reads as success, and the exception arrives later as an unhandled rejection nothing is watching. That is the vacuous pass [TomDbMigrations.requireMigrationsDirectory] exists to prevent. Thrown from the call itself, it cannot be dropped.

Ordering

The chain is ordered and environment-filtered through [TomDbMigrations.orderMigrationNames] and [TomDbMigrations.selectForEnvironment] — the very functions the engine uses — so the replay order is the applied order by construction rather than by a second implementation that could drift. This check reads that model; it does not change it.

List<TomSchemaConvergenceReport> checkAll(String migrationsDirectory, {Iterable<Type>? entityTypes})

Checks every <datasource>/<schema> pair under [migrationsDirectory].

[entityTypes] defaults to every @TomDbTable type known to tomReflector. A datasource directory with several schemas whose entities declare no [TomDbTable.schema] yields an [TomSchemaDivergenceKind.ambiguousEntitySchema] error rather than an arbitrary attribution.

A [migrationsDirectory] that does not exist throws [TomDbMigrationException] via [TomDbMigrations.requireMigrationsDirectory] — the same refusal the engine gives the same path. An empty report list would be indistinguishable, at every call site, from "every pair converged", so a mistyped path would read as a clean bill of health. An existing but empty tree is a different thing and still yields no reports: there is genuinely nothing to check.

TomSchemaConvergenceReport checkSchema(String migrationsDirectory, String datasource, String schema, {Iterable<Type>? entityTypes})

Checks the single pair [datasource] / [schema] under [migrationsDirectory].

[migrationsDirectory] is the tree root and must exist, exactly as it must for [checkAll] — the two take the same argument and cannot hold different opinions about it. The pair below it need not: a schema directory that was never created reads as an empty chain, which the report renders as every entity missing from the migrations. That is a finding, and producing findings is what this check is for.

List<TomMigrationArtifact> readChain(String schemaDirectory)

Reads the migration artifacts of one schema directory in applied order.

Files are collected, parsed, ordered by numeric version and filtered for [environment] exactly as the engine does; a malformed name throws [TomDbMigrationException] from the shared parser, and two files whose basenames collide throw from the shared collector ([TomDbMigrations.collectMigrationFiles]) — because a tree the engine would reject is a defect the check must not paper over.

A [schemaDirectory] that does not exist is the one absence this module does not treat as an error. It is content below a root that was already proven to exist, and an empty chain is the honest reading of it: [verify] then reports every entity as missing from the migrations, which localises the problem far better than an exception would. Contrast [checkAll] and [TomDbMigrations.migrateDatabases], where the absent directory is the root — an input, not content.

TomSchemaConvergenceReport verify({required String datasource, required String schema, required List<TomMigrationArtifact> chain, required Iterable<Type> entityTypes, bool reportUnschemedEntitiesAsAmbiguous = false})

Computes the report for one pair — the pure core, with no I/O.

[reportUnschemedEntitiesAsAmbiguous] is set by [checkAll] when the datasource has more than one schema directory; a caller naming a single pair has already resolved the attribution itself.

List<TomSchemaDivergence> diff(TomSchemaModel expected, TomSchemaModel actual)

Diffs the [expected] declared schema against the [actual] built one.

Public because it is the comparison itself, and the framework-owned tables are compared by the same rules through a different pair of sources — see framework_convergence.dart. Two diffs over one vocabulary would be two tolerance policies, and a schema that passes one and fails the other is a schema nobody can act on.

enum TomSchemaDivergenceKind

enum TomSchemaDivergenceKind

What kind of disagreement a [TomSchemaDivergence] reports.

Values

missingTable

The entity model declares a table the migration chain never creates.

unexpectedTable

The chain creates a table no entity maps to.

A warning, not an error: version-tracking tables, join tables and tables read only through raw SQL legitimately have no entity.

missingColumn

The entity model declares a column the chain never adds to the table.

unmappedColumn

The chain creates a column the entity does not map.

A warning: an entity may deliberately project a subset of its table.

columnTypeMismatch

Both sides have the column, in incompatible type families.

primaryKeyMismatch

The two sides disagree on which columns form the primary key.

conflictingEntityPrimaryKey

Two entities map to the same table but declare different primary keys.

A contradiction within the entity model, reported before the migration chain is consulted at all: a table has exactly one primary key, so two projections of it cannot each be right. Distinct from [primaryKeyMismatch], which is the entity model disagreeing with the chain — the two have different culprits and different fixes, and reporting this one as that would send the reader to the migration scripts to correct something no migration script did.

chainError

A statement in the chain could not be replayed — the actual side of the comparison is incomplete, so everything downstream of it is unreliable.

ambiguousEntitySchema

An entity declares no [TomDbTable.schema] in a datasource that has more than one schema directory, so which schema it belongs to is unknowable.

function _sameKey

bool _sameKey(List<String> a, List<String> b)

Whether two primary keys are the same key.

Compared as case-insensitive sets. The entity model orders a composite key by field declaration order, which carries no intent, so reporting a reordering as a disagreement would be a false positive on a key that is in fact correct.

One function, because every primary-key comparison in the module runs through it — entity against entity in [TomEntitySchemaReader.read], entity against replayed DDL in [TomSchemaConvergenceCheck.diff]. Two tolerance policies would let a key pass one comparison and fail the other, which is a key nobody can act on.
