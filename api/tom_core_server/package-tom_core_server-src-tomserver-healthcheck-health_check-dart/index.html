class TomHealthAnalyzer

abstract class TomHealthAnalyzer

Analyzer for customizing health check responses.

Extend this class to implement custom health check logic such as: - Database connectivity checks - External service availability - Memory/resource usage checks - Custom application health metrics

Example

class MyHealthAnalyzer extends TomHealthAnalyzer {
  @override
  Future<TomHealthStatus> analyzeHealth() async {
    final dbOk = await checkDatabaseConnection();
    final cacheOk = await checkCacheService();
    if (dbOk && cacheOk) {
      return const TomHealthStatus.healthy();
    }
    return TomHealthStatus.unhealthy('db=$dbOk, cache=$cacheOk');
  }
}

// Install globally before the server starts. A dependency check belongs on
// readiness: a database being down is a reason to stop receiving traffic
// and not a reason for the process to be restarted.
TomHealthServer.installReadinessAnalyzer(MyHealthAnalyzer());

Future<TomHealthStatus> analyzeHealth()

Analyzes the health of the server.

Returns the verdict a probe acts on and the message a person reads.

It is awaited under [TomHealthServer.healthTimeout], and a timeout or a thrown exception becomes an unhealthy verdict naming what happened — so an analyzer cannot stop a probe from answering. An analyzer that touches anything remote should still impose its own, shorter deadline: the framework's can only say that the check did not answer, while the analyzer's own can say which dependency was slow, and it is the only one that stops the work rather than the waiting.

class TomHealthServer

class TomHealthServer implements TomHealthService

Default implementation of [TomHealthService].

Delegates each route to its own analyzer — [livenessAnalyzer] for /health, [readinessAnalyzer] for /ready — and turns the verdict it gets back into the response. Install a custom [TomHealthAnalyzer] on either before server startup to add real checks.

static Duration defaultHealthTimeout

The deadline a process starts with: five seconds.

Long enough that a real dependency check — a SELECT 1 over an established pool, a cache PING — answers well inside it, and short enough to beat the OS connect timeout that is the failure it exists for.

It only fires if the probe's own timeout is longer. Kubernetes defaults timeoutSeconds to 1, so a deployment that wants this deadline to be the one that answers has to raise it — see doc/healthcheck.md.

static void installLivenessAnalyzer(TomHealthAnalyzer analyzer)

Installs [analyzer] as the process-wide liveness analyzer, logging the replacement at info.

Read-only storage with one installing function, rather than an assignable field, because installation is the whole of the module's configuration and it happens through a process-wide global. A bare public static can be replaced by anything in the process at any moment — including after the server is serving — and an assignment leaves no trace, so a deployment answering a probe with the wrong analyzer has nothing to read. The log line, naming the outgoing and incoming runtime types, is that trace.

It is not sealed after startup, and deliberately: the analyzer has to be replaceable before the bean context exists, which is what rules out making it a bean, and the framework has no way to know when a given deployment has finished installing. A seal nothing can call is dead code; a visible late installation is the boundary that can actually be enforced.

static void installReadinessAnalyzer(TomHealthAnalyzer analyzer)

Installs [analyzer] as the process-wide readiness analyzer, logging the replacement at info. See [installLivenessAnalyzer] for why installation goes through a function.

static void installHealthTimeout(Duration timeout)

Installs [timeout] as the process-wide deadline for both probes, logging the replacement at info.

Throws ArgumentError on a zero or negative duration, which would make every probe answer "timed out" before its analyzer ran — a health endpoint that is wrong in the safe-looking direction, since 503 on liveness is a restart.

It goes through a function for the same reason the analyzers do: it is a process-wide global, and a deadline silently shortened by something else in the process is a probe failure with nothing to read. See [installLivenessAnalyzer].

static void resetHealthChecks()

Puts the module's process-wide state back the way a fresh process starts it: a fresh [TomDefaultHealthAnalyzer] on each probe, and the deadline at [defaultHealthTimeout].

The supported spelling for a test or an example that configured the module and wants the process back the way it found it. Each probe gets its own analyzer instance, which is the state a fresh process starts in.

It logs like any other installation, because it is one: a reset that went unrecorded would be the one replacement the log could not account for.

static Future<TomHealthStatus> verdictOf(TomHealthAnalyzer analyzer, String probe)

Runs [analyzer] under the [healthTimeout] deadline and turns every way it can fail to produce a verdict into one.

Public so a deployment adding a probe route of its own gets the deadline and the failure handling rather than a second, thinner spelling of them. [probe] names the check in the message a person reads.

The deadline is the point. analyzeHealth is async precisely so a SELECT 1 and a cache PING can be awaited, and a TCP connection to a host that has dropped off the network does not fail fast — it waits for the OS connect timeout, which on Linux is over two minutes. Awaited without a deadline, the probe returns nothing at all for that window, so an orchestrator sees a probe timeout rather than a degraded body and restarts a process whose only problem was a slow dependency. "I could not determine my health within $healthTimeout" is a worse answer than a real verdict and a far better one than no answer.

A thrown analyzer is caught for the same reason, and it is the nearer failure. The analyzer this module is written for issues a SELECT 1 through the datasource, and a datasource that is down throws rather than hangs — so an exception, not a timeout, is the realistic first encounter with a broken dependency. Letting it out replaces the plain-text answer with the pipeline's error envelope, a 500 carrying JSON, which is a different response shape from the one every probe was configured to read; and on liveness a 500 is a restart. The exception's text becomes the body instead, so the cause is still on the wire — nothing is swallowed, it is answered.

The catch takes the synchronous throw too: an analyzeHealth that is not async and raises before returning a future never reaches [Future.timeout], so the call itself is inside the guarded block.

A timed-out analyzer is not cancelled: Future.timeout stops the waiting, not the work, and Dart has no way to abort a future in flight. An analyzer that hangs on every probe therefore accumulates pending futures at probe frequency, which is one more reason for an analyzer that touches anything remote to carry its own, shorter deadline.

static Response responseFor(TomHealthStatus status)

The HTTP response one [status] is served as.

Public and static so a deployment writing a health endpoint of its own — a third route, a different path — answers with the same shape rather than a second spelling of it.

The content type is set here because a handler returning a Response bypasses the endpoint's produces, and a probe log full of application/octet-stream is a small confusion nobody needs to earn.

class TomHealthService

abstract class TomHealthService

Health check service interface for server health monitoring.

Declares the two endpoints container orchestration tools (Docker, Kubernetes, Cloud Run, every load balancer) expect. Both answer the installed analyzer's message verbatim — "OK" is the [TomDefaultHealthAnalyzer]'s answer, not a constant of the endpoint — with the status code carrying the verdict: 200 for [TomHealthVerdict.healthy], 503 for [TomHealthVerdict.unhealthy].

Which is what makes an ordinary probe correct. A load balancer's default check reads the status code and nothing else, as does a Kubernetes httpGet probe unless the deployment adds a body matcher. A probe that wants the reason still reads the body, which is where it has always been.

Two routes, because the two questions have opposite consequences

GET /health is liveness — am I running — and a failure restarts the process. GET /ready is readiness — can I serve traffic — and a failure takes it out of the load balancer and leaves it alone. One route cannot answer both: "the container started but its database is unreachable" is ready-false with live-true, and a single verdict forces a deployment to pick which consequence it wants. Answering unhealthy there restarts a pod that would have recovered, in a loop, because restarting does not bring the database back; answering healthy sends it traffic it cannot serve.

So the split is by what the check touches: a liveness analyzer looks at the process — is the event loop turning, is a critical isolate still there — and a readiness analyzer looks at what the process needs — the pool, the cache, the downstream API. A dependency being down is a reason to stop receiving traffic and not a reason to be killed.

A route per question rather than one route with a ?probe= parameter: query parameters on a health check are awkward to configure in several orchestrators, and a single route stays a single point of failure for both answers.

Neither route can fail to answer

Both run their analyzer through [TomHealthServer.verdictOf], so an analyzer that hangs, that throws, or that returns a future completing with an error produces an unhealthy verdict carrying the reason rather than an exception. That matters for the response shape as much as for the status: an exception leaving the handler becomes the endpoint pipeline's error envelope — a 500 with a JSON body — which is not what a probe configured against a plain-text route reads, and on liveness a 500 is a restart. The endpoint whose job is to report failure is the last one that should fail to respond because something failed.

Methods

Future<Response> health()

The GET /health endpoint — liveness: a plain-text status string, with the status code carrying the verdict. Marked @TomPublicAccess (no authentication) and logRequests: false so probe traffic does not flood the logs.

Returns a shelf [Response] rather than a String, because the status is part of the answer and a String has nowhere to put it. That is the pipeline's documented escape hatch — a handler that knows its whole response returns one — and it is used here rather than inventing a directive in endpoint_results.dart because one caller is not a pattern: TomRedirect exists for the case where the body is implied by the intent, and here the handler is holding both facts already.

Never completes with an error: whatever the analyzer does becomes a verdict — see "Neither route can fail to answer" above and [TomHealthServer.verdictOf].

Future<Response> ready()

The GET /ready endpoint — readiness: the same shape as [health], answered by [TomHealthServer.readinessAnalyzer].

/ready rather than /health/ready: a sub-path of the liveness route reads as a refinement of it, and these are two questions rather than one asked in more detail. It is also the path the platforms' own examples use, which is the path an operator will try first.

Never completes with an error, for the same reason [health] does not.

class TomHealthStatus

class TomHealthStatus

What an analyzer concluded: a verdict a probe can act on, and a message a human can read.

The two are separate because they are different facts. Encoding both into one string — "OK" meaning healthy and anything else meaning not — is what forces every consumer to parse, makes a typo in an analyzer a wrong verdict, and leaves an orchestrator no way to act without a body matcher.

Constructors

const TomHealthStatus.healthy([String message = 'OK'])

A healthy verdict, with an optional [message].

The default message is OK because that is what a human reading a probe log expects to see, and because an empty body makes a curl look broken.

const TomHealthStatus.unhealthy(String message)

An unhealthy verdict, with a [message] saying what failed.

The message is required here and optional above: an unhealthy answer that does not say why is the one a person is reading at three in the morning.

enum TomHealthVerdict

enum TomHealthVerdict

Whether a deployment should be sent traffic.

Two values, and deliberately not three. HTTP offers a probe exactly two answers — send me traffic, or do not — so a third verdict would either map to one of those two, making a distinction no probe can act on, or invent a status code no orchestrator reads. The gradation belongs in [TomHealthStatus.message], which is free-form and is where "degraded: cache=false, db=true" says what a number cannot.

Values

healthy

Everything the analyzer checked answered. HTTP 200.

unhealthy

Something the analyzer checked did not. HTTP 503, which is what takes a pod out of a load balancer and what a default probe already understands.
