Where audit records go, and how long they stay there (CE-LG).

The sink is deliberately a separate concern from the trail that produces records. Deployments differ in what they are obliged to keep and for how long — a test wants the last few entries in memory, a regulated production server wants years of append-only files, a bank wants a WORM appliance — and none of that should reach the code that emits the records.

Why not just write to the log

The kernel's logging subsystem rotates by size, drops by level, and is expected to be truncated by an operator who needs disk back. Every one of those is correct for diagnostics and fatal for an audit trail: a trail with a hole in it cannot be distinguished from a trail that was tampered with, so a trail that permits holes proves nothing. The sinks here therefore append only, rotate by moving aside rather than truncating, and chain each entry to its predecessor by hash.

The hash chain

Each written entry carries the hash of the previous entry, and its own hash covers both that link and its own content. An entry that is edited, removed or reordered after the fact breaks the chain at that point and at every point after it, which [verifyAuditChain] reports.

This is tamper-evidence, not tamper-proofing. Someone with write access to the files and the algorithm can rewrite the whole chain from the point of the edit onwards. Making that impossible needs an external anchor — a countersigning service, a WORM volume, periodic publication of the head hash — which is a deployment decision rather than a framework one. What the chain buys unconditionally is that a partial edit, which is what accident and casual malice both produce, cannot go unnoticed.

class TomAuditEntry

class TomAuditEntry

A [TomAuditRecord] together with its position in the hash chain.

The entry — not the record — is what a sink stores, because the chain link only means anything in the context of a particular sink's sequence. The same record written to two sinks legitimately has two different hashes.

Every field is required. Nothing here is defaulted, because a default does not produce a vague entry — it produces a specific accusation about a record nobody touched, and an investigation that starts from the wrong finding goes somewhere else entirely:

  • A guessed index guesses the entry's position, which is precisely what

anchor verification is built on — it would turn a truncated trail into a merely short one. - A defaulted hash reads back as an entry whose stored hash does not match its contents, which [verifyAuditChain] reports as content changed after writing: the signature of an edited record. - A defaulted previousHash claims the entry began a chain. Mid-chain that is a link mismatch — an entry was removed or reordered here — and at the head it is not a finding at all: the entry is self-consistent against the link it was handed, so damage verifies as health.

The hashes are also refused when present but empty, since the empty string was the old default and an empty hash is not a short hash but an absent one. The unnamed constructor cannot enforce any of this — it is const — so this factory is where storage that has been damaged, hand-edited or written by something other than [toJson] is turned away. That is what lets [parseAuditLines] promise that a line it cannot read is reported rather than silently reinterpreted.

Stored rather than inferred from the entry's offset in whatever the reader happens to hold, because retention makes those two different numbers. Once a prefix has been pruned, an offset says where an entry sits in the surviving suffix; the index still says where it sat in the chain. Anchor verification is a claim about a position ([TomAuditAnchor.entryCount]), so without this a pruned prefix and a rewritten one look alike — and a check that reports tampering on every retention pass is one operators learn to ignore.

Deliberately outside the hashed payload: [hashOf] covers the link and the record, so adding the index neither changes existing digests nor lets a renumbering forge one.

class TomAuditSink

abstract class TomAuditSink implements TomClosable

Where a [TomAuditRecord] is persisted.

[write] is expected to fail when it cannot store the record. The trail is fail-closed — an action whose audit record could not be stored is not allowed to look like it succeeded — so a sink that swallows its own storage errors defeats the guarantee for everything above it. Failing means completing the returned future with an error, in every case; see [write].

Reading a trail back is deliberately not part of this interface

A sink is a writer. [write], [headHash], [entryCount] and [close] are the whole of what a caller may do to an arbitrary sink; reading entries back, or verifying them, is not among them. That is a decision rather than an oversight, and this paragraph exists because an omission nobody wrote down reads like one.

Each implementation exposes its own read-back instead, in the shape its storage actually has: [TomMemoryAuditSink.verify] and [TomFileAuditSink.readAll] / [TomFileAuditSink.verify] are synchronous because the entries are already in memory or in a local file, while TomSqlAuditSink.readAll / TomSqlAuditSink.verify are asynchronous because they are a query. Hoisting those onto one signature would have to pick the asynchronous shape for all three, and would advertise readAll() on a trail table of ten million rows as though it were a reasonable thing to call.

Nothing is lost by leaving it out, because the analysis is already storage-neutral: [verifyAuditChain], verifyAgainstAnchor and filterAuditEntries take a List<TomAuditEntry>, not a sink. An operator reads the trail back the way that particular storage is read — they know which one they deployed — and hands the entries to the same checker or the same filter whichever sink produced them.

What is uniform is the pair an anchor needs. [headHash] and [entryCount] are on this interface precisely because [TomAuditAnchor.of] must work against whatever sink happens to be installed without knowing its concrete type; that is the one cross-sink read the module performs, and it is served.

Querying a trail — by actor, target, outcome or time window — is TomAuditQuery, and it stays off this interface by the same argument. The question is storage-neutral and is a value; answering it is not. A sink whose entries are already in memory is filtered where it stands, with filterAuditEntries over the entries it hands back; the relational sink pushes the filter into the database instead, because the indexes that make the question cheap are in the table and reading ten million rows to discard all but five is not a query. One signature over both would have to promise the asynchronous shape everywhere and would hide that difference, which is the difference a deployment needs to see.

Future<TomAuditEntry> write(TomAuditRecord record)

Persists [record], returning the entry as stored.

Every failure arrives through the returned future, including the ones an implementation can see before it has done any work — a closed sink, a rejected record, a misconfiguration. Implementations should mark this method async rather than raise from the synchronous part of the body: async puts the rule in the declaration, where a guard added later inherits it, instead of in each guard, where it has to be remembered.

The rule matters because the return type is what a caller protects against. sink.write(r).catchError(...), Future.wait([...]) and an unawaited write with a .then(onError:) are all complete handling of a future's failure and none of them is inside a try. A method that can also throw before the future exists makes each of them a coin flip on which failure occurred, and the one that escapes escapes on whatever stack was running — which for a fail-closed trail is the audited action dying of an error it thought it had handled, rather than being told its record was not stored.

Future<void> close() override

Waits for every queued record to be stored, then closes.

Nothing enqueued before the call is lost: the close completes once those records are stored, so a shutdown that awaits it — this is [TomClosable]'s method, and a registered sink is awaited within its phase's budget — has a complete trail behind it.

A record written after the call is refused — its write future completes with audit.sink.closed — rather than dropped or written anyway. The queue has to stop growing for the drain to have a point to reach while a caller keeps writing, and refusing is the only honest way to stop it. Writing anyway means a sink that is closed is still writing. Dropping means an audited action reports success with no entry behind it, which is the one outcome a fail-closed trail exists to prevent. Refusing tells the caller, and the caller is the code that knows whether the action can still be allowed to stand.

Idempotent: every call is handed the same close, so each caller that awaits it waits for the one drain.

class TomFileAuditSink

class TomFileAuditSink implements TomAuditSink

An append-only JSON-Lines file sink with age- and count-based retention.

There is one file per UTC day, named audit-<yyyy-mm-dd>.jsonl, and it is rotated when it exceeds [maxFileBytes]; a rotated file is renamed to audit-<yyyy-mm-dd>-<n>.jsonl and never rewritten. Retention deletes whole files that are older than [retention] or that exceed [maxFiles] — deleting a whole file, on a boundary the chain records, is auditable in a way that trimming lines out of a live file is not.

Retention here is automatic: the sink applies it itself whenever it opens a file, so a deployment that sets the two arguments has nothing left to schedule. TomSqlAuditSink is the other way round — it retains nothing unless the deployment schedules purgeBefore or purgeToMaxEntries — and the asymmetry is deliberate rather than an omission on either side. This sink owns its directory and may delete in it; a trail table is pruned with a DELETE grant the serving credential should not have. See that class for the scheduling side of it.

UTC, not the host's calendar, because every [TomAuditRecord] timestamp is UTC: a file named from local time disagrees with its own contents on any host that is not on UTC, so an operator grepping a reported day reads the wrong file. It also makes a day boundary the same instant on every node writing into the same directory.

Rotation sequence numbers are monotonic for the sink's lifetime and never reused, including after retention has deleted the file that held one. A scheme that reissued the lowest free number would let a newly rotated file take an older file's name, and file order — which is the order entries are read back in — would stop matching write order.

The chain continues across files: the first entry of a new file links to the last entry of the previous one. So retention leaves a verifiable suffix rather than a set of unrelated fragments, and the missing prefix is visible as such.

void _discardBrokenHandle()

Drops the file handle after a failed write, and consumes its error.

Two reasons, and neither is tidiness.

Dropping it is what lets the sink recover. _ensureOpen returns early while a handle exists, so a handle kept after a failed write is consulted by every later record — which would go on failing against the dead handle long after the operator fixed the directory it died on, and with a Bad state: StreamSink is closed in place of the filesystem error that says what is actually wrong. A transient storage fault would become a permanent one, silently, in the component whose whole purpose is to still be recording when things go wrong.

Closing it is what keeps the failure inside the future it was reported on. openWrite is lazy, so a path that cannot be opened fails the flush above — which becomes the caller's write_failed — and the handle's own completion, which nobody listens to. That second copy of an already-reported failure surfaces as an unhandled asynchronous error in the zone that called [write], so a caller who handled the failure exactly as documented still gets an uncaught error for it.

The close is ignored rather than awaited: waiting would make one caller's failure delay the next caller's write, and there is nothing to learn from it — the error it carries is the one being thrown on the line below.

Future<void> _ensureOpen({required int additionalBytes})

Ensures the file for today's UTC day is open with room for [additionalBytes].

Two things send the sink to a different file, and they are not the same event. Overflow rotates: the day is not finished, so the file is moved aside under the next sequence number and reopened under the same name. A UTC day boundary does not rotate: the outgoing file is complete, and the new day simply gets its own name. Renaming a finished day would spend a rotation number on a file nothing overflowed and leave a day with rotated parts and no live file — a shape that otherwise only ever means "this day filled up".

Both fall out of one rule, which is why there is one rotation site rather than one per reason: reopen whenever the file that should be open is not the one that is, and rotate only if the file being opened is already too full to take the record. A new day's file is empty, so it is never rotated; a full day's file is, every time. An earlier version rotated on the way out as well, which was redundant when the day was unchanged and wrong when it was not.

The target is recomputed on every call, not only when the byte cap bites. Consulting the day only on overflow is what made "one file per day" false for any trail quiet enough to stay under the cap: the sink went on appending to the file named after the day of its first write, for weeks.

Closing the outgoing file is awaited: rotation renames the file out from under the sink, and a rename racing an unflushed buffer is how a rotation loses the last entries it was supposed to preserve.

void _rotate()

Moves the current file aside under the next rotation sequence number.

Renaming rather than truncating is the whole point: the bytes already written are never touched again, so rotation cannot lose or alter an entry the way a size-capped log rotation legitimately does.

The sequence only ever advances. Reusing a number freed by retention would give a newly rotated file the name of an older one, and the trail would then read back out of write order — which the chain reports as a break, indistinguishable from tampering.

void _applyRetention()

Deletes whole files that fall outside [retention] or [maxFiles].

The age comparison is deliberately left on a local DateTime, unlike the file naming above, and it is worth saying why so the point is not "fixed" into a change that alters nothing. [DateTime.difference] compares instants, not calendar fields: both operands here come from real instants — the clock and the file's mtime — so the elapsed time it returns is exact in any zone, and unchanged by a DST shift landing inside the window. The SDK's DST caveat applies to constructing local DateTimes from wall-clock components, which retention never does. A ten-year window measured this way really is ten years.

({int entryCount, String hash}) _recoverHead()

Reads the last chain hash and position from the newest existing file.

A restart that began a fresh chain would present every pre-restart entry as unverifiable, which is indistinguishable from tampering — so the head is recovered rather than reset. The count is recovered from the same entry for the same reason: restarting the numbering would make every anchor taken before the restart point at the wrong entry.

String _utcDay()

Today's date in UTC, as yyyy-mm-dd — the day a file is named for.

UTC because that is the calendar the entries themselves are on: [TomAuditRecord] coerces every timestamp to UTC. Naming the file from the host's local calendar instead put a record stamped 2026-08-12T01:00Z into audit-2026-08-11.jsonl on any host west of UTC, so a file's name disagreed with its own contents and an operator grepping a reported day read the wrong file — or, at a month boundary, none. It also made the name depend on where the process happened to run, which is precisely the kind of dependency an audit trail is not allowed to have.

Future<void> close() override

Waits for the queued records to be written, then flushes and closes the file.

The drain awaits _queue rather than the individual write futures because _queue is the tail of the chain: awaiting it means every record enqueued before this call has run. It swallows nothing — _queue already absorbs write errors so one failure cannot wedge the sink, and each error was delivered to its own caller through the future write returned.

The sink is closed to new records first, and only then waited on. That order is what gives the drain a fixed point to reach: a caller writing in a loop would otherwise keep extending the queue for as long as the close waited on it. With nothing left to write, nothing can reopen the file once it is closed.

function verifyAuditChain

TomAuditChainVerification verifyAuditChain(Iterable<TomAuditEntry> entries, {String startHash = tomAuditGenesisHash})

Checks that [entries] form an unbroken chain from [startHash].

Three distinct failures are reported, because they mean different things: a self-inconsistent entry says this record was edited; a broken link says an entry was removed, inserted or reordered here; and a jump in [TomAuditEntry.index] says the chain was renumbered.

The index check is not redundant. The index sits outside the hashed payload — deliberately, so that adding it did not invalidate every existing digest — which means it is the one field an attacker can rewrite without breaking a single hash. Left unchecked, renumbering would silently slide the window that [verifyAgainstAnchor] compares against, and an anchored position could be made to point at a different entry.
