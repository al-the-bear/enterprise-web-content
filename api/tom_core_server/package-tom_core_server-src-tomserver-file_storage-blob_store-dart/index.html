import 'package:tom_core_server/src/tomserver/file_storage/blob_store.dart';

The blob-storage contract: bytes under a key, put and got as streams.

This is the framework's general file/blob storage — the capability the export module's deliberately narrow TomExportStore was written to be adapted onto, and the server half of a persisted entity's file-reference column (a column that holds a storage key rather than the bytes).

Why streams on both sides, and not Uint8List

A blob worth storing separately from its row is a blob large enough that holding it — and the copy the next layer makes of it — is the failure. Every method here therefore speaks in Stream<List<int>>: a 400 MB upload flows from the socket into the backend without ever being whole in memory, and a download flows back out the same way. A convenience that buffers is easy to write at a call site that knows its blobs are small ([TomBlobStore.getBytes] is that convenience); a streaming API cannot be recovered from a buffering one.

Why four operations and no directory

Put, get, describe, delete. There is no list, no rename, no partial read, no metadata update — not because they are hard, but because nothing in the framework needs them and every one of them constrains the backends. list in particular is the expensive lie: it is a cheap readdir on a filesystem and a paginated, eventually-consistent API call on an object store, and an interface that promises it invites callers to build on the filesystem's version of it.

Keys are hierarchical by spelling (2026/07/invoice.pdf), so partitioning is available without the store having to model directories.

Why a failed write must leave nothing

A truncated blob is indistinguishable from a complete one to whoever downloads it next. Every backend here therefore commits atomically — filesystem by writing a sibling .part and renaming, database by writing chunks and only then the manifest row, S3 by aborting an incomplete multipart upload. A [TomBlobStore.put] that throws has left the key holding either its previous content or nothing at all.

Why every failure arrives as a storage error

The faults that stop a store come from the layer underneath it and speak that layer's language: a FileSystemException, a driver error, an HTTP status. A backend that lets those through makes the caller's error handling depend on which backend it was configured with, and slips past every on TomServerException between it and the request boundary.

So a failure is translated into one of [TomBlobStoreOperation]'s keys, keeping the original as rootException. The module's own answers — not_found, invalid_key, missing_chunk, same_key — pass through untranslated, because callers branch on them.

The translation is [TomBlobStore]'s own, not each backend's: a backend implements doPut, doGet, doDescribe, doDelete and the public methods wrap them. The same wrapper is what validates the key, so both obligations hold for every backend including ones written later — see [TomBlobStore]'s "Why the public methods are final".

class TomBlobDigest

The running SHA-256 of a blob, fed chunk by chunk as it is stored.

A backend hashes on the pass it is already making — a file write, a chunk insert, a part upload — so the digest costs no extra read. Public because [TomStoredBlob.digest] is a promise every backend has to keep, including one an application writes, and a promise the framework does not make easy to keep is one that gets broken.

class TomBlobRange

class TomBlobRange

A half-open byte range of a stored blob: [start] inclusive, [endExclusive] exclusive.

Half-open because that is what File.openRead and List.sublist take, and the backends are where this ends up. HTTP's Range is inclusive-at-both-ends and a suffix form (bytes=-500) has no start at all; both are resolved against the blob's known size before they reach here, by whoever read the header. This type is the resolved one, so a backend never has to reason about a range it cannot check.

Both ends are checked at construction rather than at the backend, so every store refuses the same nonsense the same way — the same reason key validation sits on [TomBlobStore] and not in each do*.

Constructors

TomBlobRange.new(int start, [int? endExclusive])

A range from [start] up to but not including [endExclusive].

[endExclusive] null means to the end of the blob, which is the form a bytes=500- header takes and the only one that needs no size to resolve.

Throws [TomStorageException] (storage.blob.invalid_range) for a negative start or an end at or before it. An empty range is refused rather than answered with an empty stream: a zero-length read is a caller's arithmetic going wrong, and an empty body is how that mistake reaches a user as a corrupt download.

class TomBlobStore

abstract class TomBlobStore

Stores and retrieves blobs by key.

Implemented by [TomMemoryBlobStore], TomDirectoryBlobStore, TomDatabaseBlobStore and TomS3BlobStore; an application registers its own with TomBlobStoreInfo.registerBackend.

Why the public methods are final

A backend implements [doPut], [doGet], [doDescribe] and [doDelete], and optionally sharpens [doExists], [doGetRange], [doCopy] and [doMove], each of which is concrete and built from the four; the public methods are this class's own and wrap them. That indirection buys two guarantees no backend can forget:

  • Every key is validated, on reads as well as writes, so a key that is

refused is refused the same way whichever backend is configured — and a backend written later, or by an application, cannot be handed a directory traversal. - Every failure arrives as a [TomStorageException] carrying the error key [TomBlobStoreOperation] names for the operation that failed, so a caller catches one type rather than a socket exception here and a database exception there.

Both properties were previously left to each backend to honour, and each backend honoured a different subset of them: three of the four validated on put alone, so get('../escape') answered invalid_key on a directory store and not_found on a memory one — the wrong error, and for a caller branching on the two, the wrong branch.

Future<TomStoredBlob> put({required String key, required Stream<List<int>> bytes, String mediaType = TomStoredBlob.defaultMediaType, String? fileName})

Writes [bytes] under [key], replacing anything already there.

Returns the descriptor of what was written — notably [TomStoredBlob .byteCount], which is not known until the stream drains.

A failure must leave nothing readable under [key] beyond what was there before: implementations commit atomically or not at all.

A chunk arriving from [bytes] is borrowed for the duration of the await: an implementation must consume or copy it before asking for the next one, and must not retain it. A producer refilling one scratch buffer per chunk is the ordinary shape of an encoder, and a store that kept the list would record that buffer's last state once per chunk.

Stream<List<int>> get(String key, {TomBlobRange? range})

Reads the blob stored under [key].

Throws a [TomStorageException] (storage.blob.not_found) when the key holds nothing: a caller reading a blob it holds a reference to and finding it gone has hit a real fault — an expiry it did not expect, a store it is not pointed at — and an empty stream would disguise that as an empty file.

Each chunk belongs to the caller: writable, and not aliased with anything the store keeps. The backends that read from a file, a row or a socket get this for free — the memory backend is the only one that has to choose, and it copies. Both halves are load-bearing. Handing back an internal buffer lets a consumer decoding in place edit the stored blob; handing back an unmodifiable view would instead make that same consumer throw on the backend the tests run on and succeed on every other, which is the worse trade.

A transfer that breaks partway still delivers the chunks that arrived, and then fails. Both halves are the contract. A consumer that has already written the first megabytes to a file can truncate what it has; one handed nothing at all cannot tell a broken download from an empty object. That is why the failure is translated around the forwarding rather than by draining the backend's stream first: buffering here would be invisible to anyone reading a small blob, and would quietly turn every interrupted download into an empty one.

Future<TomStoredBlob?> describe(String key)

The descriptor for [key], or null when it holds nothing.

The one read that is allowed to answer "nothing" without throwing, because asking what is there is a different question from asking for it.

Future<int> deletePrefix(String prefix)

Deletes every blob whose key lies under [prefix], returning how many went.

The reclaim primitive, and the only part of retention this module owns. What to keep and how long are a deployment's decisions, taken against its own record of what it stored; this is the one operation that record cannot assemble from the outside, because deleting a partition key by key is a call per blob and a prefix delete is a call per partition.

The prefix is matched by key segment, never by characters. 2026/07 removes 2026/07 and everything beneath it, and never 2026/070 — a string prefix that can reach a sibling is an ordinary convenience everywhere except in a delete, where it is how a month's retention takes the next month with it.

Throws [TomStorageException] (storage.blob.prefix_delete_unsupported) on a backend that cannot, naming it. A backend that answered 0 instead would make "the purge found nothing" and "this backend cannot purge" the same answer, and the deployment would learn the difference from a disk filling up.

An empty prefix is refused (storage.blob.invalid_key): it names every blob there is, and a delete whose argument came from a configuration value that turned out empty should not empty the store.

Future<TomStoredBlob> copy(String fromKey, String toKey)

Copies the blob at [fromKey] to [toKey], returning the new descriptor.

A relocation is an ordinary thing to want: the documented pattern for expiry is a date-prefixed key, so re-partitioning happens, and without this it means pulling every byte through the server and pushing it back.

Anything already at [toKey] is replaced, as it is by [put] — the same rule, because a copy is a write and a second one about overwriting would be a rule to remember. The media type and file name travel with the bytes: a copy that lost its Content-Type would be served as application/octet-stream and download as a file nothing opens.

Throws [TomStorageException] (storage.blob.not_found) when [fromKey] holds nothing, (storage.blob.invalid_key) for a key outside the grammar, (storage.blob.same_key) when the two are equal, and (storage.blob.copy_failed) when the backend fails.

Future<TomStoredBlob> move(String fromKey, String toKey)

Moves the blob at [fromKey] to [toKey], returning the new descriptor.

The source is gone when this returns. Ordering is the whole contract: the destination is committed before the source is removed, so an interrupted move leaves the blob readable under both keys rather than under neither. The residue of a failed move is a duplicate, which a retry converges on; the residue of the other order is a deletion.

Same replacement rule, same errors as [copy], under storage.blob.move_failed.

Future<bool> delete(String key)

Deletes [key], returning whether anything was there to delete.

Exact on a backend that can delete conditionally, best-effort on an object store. A filesystem, a map and a manifest row all answer the two questions — did it exist, and is it gone — in one operation, so their boolean is a fact. S3's DELETE answers 204 whether or not the object was there, so [TomS3BlobStore] asks separately with a HEAD and another caller can create or remove the key between the two. Two concurrent deletes of one key can therefore both answer true there, and a delete racing a put can answer false having removed nothing that the put then writes.

The window only misleads a caller that is already racing itself, which is why the exact answer is kept rather than dropped for a void that no backend could get wrong: a boolean that is a fact on three backends and a recent observation on the fourth is more useful than no answer anywhere. A caller that must not race holds a lock of its own; nothing in a storage API can supply one.

Future<bool> exists(String key)

Whether [key] currently holds a blob.

Future<TomStoredBlob> doPut({required String key, required Stream<List<int>> bytes, String mediaType = TomStoredBlob.defaultMediaType, String? fileName})

Writes a validated [key]. Implemented by backends; called by [put].

A backend that fails part-way through cleans up and lets the failure out: [put] names the operation. Throwing a [TomStorageException] by hand is for the cases where the backend knows something the wrapper cannot.

Stream<List<int>> doGet(String key)

Reads a validated [key]. Implemented by backends; called by [get].

Stream<List<int>> doGetRange(String key, TomBlobRange range)

Reads [range] of a validated [key]. Called by [get] when one is given.

Defined in terms of [doGet] so a backend implements one read path, not two — the same arrangement as [doExists] over [doDescribe]. Override it when the backend can seek, which is every backend shipped here: a file opens at an offset, a chunked row set skips whole rows, and S3 takes a Range header. The default reads from zero and discards everything before the range, stopping once the range is served — correct, and costing the prefix, which for a seek near the end of a large blob is the whole thing.

Putting the discarding here rather than in the caller is the point. A download endpoint honouring HTTP Range needs a range read from every backend, and writing the fallback at the endpoint would mean the S3 backend's native capability were unreachable through the interface.

A range that runs past the end of the blob yields what there is rather than failing: [get] cannot know the size without a second lookup, and the caller that does know — the endpoint — has already refused an unsatisfiable one with [TomBlobRange.clampedTo].

Future<TomStoredBlob> doCopy(String fromKey, String toKey)

Copies a validated [fromKey] to a validated [toKey]. Called by [copy].

Concrete, and a stream round trip: read the source, write it to the destination. Override it wherever the backend can do it without the bytes leaving — which is every backend shipped here, because each has a native answer: a filesystem copy, a map entry, an INSERT that shares the chunks, an x-amz-copy-source header.

A concrete default is right here in a way it would not be for a listing. The cost of this one is not misleading — a stream round trip is exactly as expensive as it looks — whereas a default list would hide a paginated scan behind a method that reads like a map lookup.

Future<TomStoredBlob> doMove(String fromKey, String toKey)

Moves a validated [fromKey] to a validated [toKey]. Called by [move].

Concrete, and defined as a copy followed by a delete — in that order, so an interruption leaves a duplicate rather than a hole. Override it where the backend can rename: a filesystem does, and a manifest row's key is a column to update.

Static

static int maxKeyLength

The longest key any backend accepts.

512 is comfortably under the shortest limit in play (S3 allows 1024 bytes; a filesystem path component 255) while being longer than any key a sane prefix scheme produces. Bounding it here means the database backend can declare a fixed-width indexed column and the filesystem backend cannot be handed a name the OS will reject.

static String auxiliaryMarker

A character no valid key can contain, for backends that keep bookkeeping files alongside the blobs themselves.

A backend storing blobs as files needs somewhere to put what a filesystem will not hold — a metadata sidecar, the partial a write is staged in — and the obvious naming, <key>.meta, is a trap: . is an ordinary key character and only the segments . and .. are reserved, so a.meta is a key a caller may legitimately choose. Two callers picking ordinary keys then destroy each other's data, neither having done anything wrong.

Suffixing with this marker instead makes the bookkeeping unaddressable: [isValidKey] admits [A-Za-z0-9._/-] and nothing else, so no key that reaches a backend can name a file suffixed with it. ~ is legal in a filename everywhere this runs — POSIX reserves only /, Windows only <>:"/\|?* — and is the conventional mark of an auxiliary file.

It lives on the contract rather than in a backend because it is a fact about [isValidKey], which is defined here and shared by every store including TomExportStore. The suffixes are each backend's own storage layout and stay with the backend; only the guarantee that they cannot be spelled is common.

static RegExp _keyPattern
static RegExp _unsafeSegmentCharacters

What [sanitiseKeySegment] replaces: [_keyPattern]'s character class negated, minus the separator — a segment may not contain one even though a key may. Kept adjacent so the one deliberate difference between the two is visible rather than inferred.

static Set<String> passThroughErrorKeys

The error keys that reach a caller as the backend raised them.

Everything a store can go wrong at is reported under one of the four [TomBlobStoreOperation] keys, whichever backend is configured. These four are the exceptions, and they are exceptions because they are answers rather than failures: the key held nothing, the key was not a key, the deployment's prefix leaves no room for one, the blob's chunks do not add up. A caller branches on them — TomBlobExportStore on not_found, the file endpoint on its 404 — so translating them would turn a decision the caller can make into a failure it can only report.

Every one is raised by code every backend shares, or by a rule every backend is held to, so none of them tells a caller which backend it got. That is the test for membership, not "the module happens to raise it": invalid_key_prefix is raised inside the S3 backend as well as by [validateKeyPrefix], and belongs here because the limit it enforces is [maxKeyLength] — the rule every backend obeys — rather than S3's own.

The list is closed on purpose, and that is the whole of the module's backend-independence claim. A TomStorageException a backend raises under any other key is wrapped like any other fault, so a caller switching on error.key sees the same key whether the deployment is configured with the S3 backend, the directory backend or one the application wrote. The backend's own exception survives as rootException: still in the log, still carrying its status and code, no longer part of the contract a caller is written against.

static String _differentKey(TomBlobStoreOperation operation, String fromKey, String toKey)

[toKey] validated, and refused when it is [fromKey].

Copying a key onto itself has no meaning worth guessing at, and the obvious implementation — read it, write it back — is a truncation on any backend whose write is not atomic. S3 refuses it outright without a metadata directive. So it is one error rather than four behaviours.

static bool isValidKey(String key)

Whether [key] is a well-formed storage key.

The single definition of the key grammar, exposed as a predicate so that every surface with its own error vocabulary — [validateKey] here, TomExportStore.validateKey in the export module — can enforce the same rule while throwing its own exception type.

Keys are relative, slash-separated, and made of unreserved characters. The rule exists because the obvious backend maps keys onto paths, and a key of ../../etc/passwd would then be a directory traversal handed to whatever built the key from a user-supplied file name.

static String sanitiseKeySegment(String name, {String fallback = 'file'})

[name] rewritten into one key segment, so that a human-chosen name can become a key rather than merely be tested against the grammar.

It lives beside [isValidKey] because the two are one grammar spelled twice, and a sanitiser that drifts from its own validator produces the worst outcome available: output that is refused by the check it was written to satisfy. sanitiseKeySegment(x) is a valid key for every [name] short enough to be one — asserted over the code-unit range in export_test.dart, not merely intended.

One segment, never two. / and \ are replaced like any other disallowed character, so a name cannot contribute path structure. Whatever builds a key decides its shape; a name is only ever a part of it. That is also what defuses ../../etc/passwd — not by refusing it, but by leaving it nothing to traverse with.

Length is the one fault it does not repair. A name over [maxKeyLength] comes back over [maxKeyLength] and [validateKey] refuses it. Truncating would silently give two different names the same key, and the second write would replace the first with nothing reported anywhere — a refusal the caller can see is strictly better than a collision it cannot.

[fallback] is returned when nothing usable survives — an empty name, whitespace, or one of the two segments the grammar reserves. It must itself be a valid key.

static bool isValidKeyPrefix(String? keyPrefix)

Whether [keyPrefix] is usable as a key namespace.

A prefix is not a separate notion from a key: it is joined to one as "$keyPrefix/$key", so it must satisfy [isValidKey] itself or the join produces something no backend accepts. null and '' both mean no namespace — a configured store leaves the setting unset, an unconfigured one defaults it to empty, and neither should have to say so twice.

A trailing slash is deliberately not a second accepted spelling: the join supplies the separator, so exports/ would yield exports//sales.csv, which the grammar rejects for the doubled slash.

Length is the one clause this cannot settle — a prefix and a key may each be within [maxKeyLength] and still exceed it once joined, which depends on a key that has not arrived yet. So the obligation belongs to whoever performs the join, and every site that performs one discharges it: those that join above a store hand the result to [validateKey] and get it for free, and TomS3BlobStore, which joins below that boundary — the prefix goes straight into a signed URI — checks the length itself.

static String validateKey(String key)

Validates [key] and returns it, throwing storage.blob.invalid_key when it does not satisfy [isValidKey].

static String? validateKeyPrefix(String? keyPrefix)

Validates [keyPrefix] and returns it, throwing storage.blob.invalid_key_prefix when it does not satisfy [isValidKeyPrefix].

A distinct error key from [validateKey], because the two faults call for different actions: a bad key is a caller's mistake, a bad prefix is a deployment's. The parameter is named keyPrefix and carries the prefix itself rather than a key derived from it — the derived key is one the caller never wrote, and naming it sends the reader to the wrong place.

static TomStorageException notFound(String key)

The error raised when [key] holds nothing — one spelling, so a caller can match on the key string and every backend agrees on it.

static TomStorageException _asStorageException(TomBlobStoreOperation operation, String key, Object error, StackTrace stack)

[error] restated as the storage failure of [operation] on [key].

The original is kept as rootException rather than summarised into the message: the caller needs a key it can branch on, and whoever reads the log needs the errno that actually explains it.

static Future<T> _translating<T>(TomBlobStoreOperation operation, String key, Future<T> Function() body)

Runs [body], reporting any infrastructure failure as [operation] on [key].

A [TomStorageException] passes through only when its key is one of [passThroughErrorKeys], which is the clause that makes this safe to wrap a whole method in without also making the caller's error handling depend on which backend the deployment configured.

Matched on the key rather than on the type. The type is what every backend's own failures are raised as too, so catching it let storage.s3.request_failed and its siblings past the translation the module exists to perform — for the same fault, a caller heard one key on S3 and another on the directory backend.

Private, because the wrapping is now the contract's own job rather than something a backend opts into: a helper a backend may call is a helper a backend may forget, which is the state this replaced.

class TomMemoryBlobStore

class TomMemoryBlobStore extends TomBlobStore

A store that keeps its contents in memory.

For tests, and for a development server that should not leave files behind. It buffers whole blobs by definition, so it is the one place in this module where that is acceptable — and the reason it is not the default.

Because it holds the bytes instead of reading them back off a disk or a bucket, it is the only backend that can accidentally share a buffer with a caller, in either direction. So it is the only one that copies on purpose: what [get] yields is the reader's own, and what [put] is streamed is copied before the next chunk is asked for. [TomBlobStore] requires both of every backend; they are noted here because here they are a choice.

class TomStoredBlob

class TomStoredBlob

What a stored blob is: its key, what it contains, how big it turned out.

Returned by [TomBlobStore.put] rather than assembled by the caller — [byteCount] is only known once the stream has drained, and it is the field a caller most often needs next (a Content-Length, a quota check, a log line).

Constructors

TomStoredBlob.new({required String key, required String mediaType, required int byteCount, required DateTime storedAt, String digest = unknownDigest, String? fileName, Uri? location})

Creates a stored-blob descriptor.

[storedAt] is normalised to UTC here rather than at each construction site, which is what makes the zone a property of the type: a backend added later cannot forget it, and there is one place to read the rule. Every backend sources the value locally — DateTime.now() on three of them, the filesystem's stat.modified on the fourth — so without this a descriptor written in Berlin and read in Denver disagreed with itself by the offset. TomAuditAnchor and TomOAuthTokens normalise the same way.

Properties

The key the blob is stored under.

The number of bytes stored.

final Uri? location

A backend-specific address — a file: URI, an object-store URL.

Useful to a human chasing a blob down; never the thing to read it back with. [TomBlobStore.get] takes the [key], because only the store knows how its keys map to addresses.

final String digest

The lowercase hex SHA-256 of the stored bytes, or [unknownDigest].

Every blob written through [TomBlobStore.put] has one, whichever backend is configured: the hash is computed while the bytes stream past, on a pass the backend is making anyway, and recorded beside the media type and the file name. That is what makes it something a caller can build on — an integrity check after a transfer, a deduplication key before one, an ETag a download endpoint can serve.

It is [unknownDigest] for a blob this framework did not write: a file dropped into a directory store's tree by hand, an object already in a bucket the store was pointed at. Those have no recorded media type either and fall back to [defaultMediaType]; the digest's counterpart is a named empty string rather than null, so that "not recorded" cannot be confused with the digest of zero bytes — which is a real, well-known value. [hasDigest] is the question to ask.

enum TomBlobStoreOperation

enum TomBlobStoreOperation

What a store was doing when its infrastructure refused.

Storage faults come from somewhere else — a full disk, a denied permission, a bucket that answered 500 — and arrive as that layer's own exception type: a FileSystemException, a MySqlException, a socket error. Letting those reach the caller means a pipeline that catches [TomServerException] does not catch storage at all, and a caller that wants to distinguish what failed has to know which backend it was configured with.

So each backend translates, and this enum is the vocabulary it translates into: four operations, one error key and one user-facing message each, spelled once so every backend agrees. It mirrors TomExportStoreOperation in the export module deliberately — the same four questions are being asked of the same kinds of infrastructure, and two different answers for one fault would be an accident of which module the caller came through.

The division is by what the caller asked for, not by which call threw: [read] is "give me the bytes", [probe] is "tell me about the blob" ([TomBlobStore.describe] and [TomBlobStore.exists]), and a sidecar that cannot be read during a describe is therefore a [probe] failure even though a file read is what failed.

Values

write

Storing bytes under a key.

read

Reading a blob's bytes back.

probe

Asking what is stored under a key, or whether anything is.

delete

Removing what a key holds.

copy

Putting what one key holds under a second one as well.

move

Moving what one key holds to another.

deletePrefix

Removing everything under a key prefix.
