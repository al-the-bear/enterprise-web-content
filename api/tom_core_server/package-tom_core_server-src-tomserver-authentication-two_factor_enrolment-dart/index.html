Which second factors a user has actually set up — the store behind "choose a method".

Why this exists

[Tom2FARegistry.availableMethods] answers what could be used here. It is a property of the deployment, identical for every user. The question a login actually has to answer is narrower and per-user: what has this user set up? Before this library there was no answer at all — the only enrolment state was [TomTotp2FAService.globalSettingSecretResolver], a single hook that spoke for exactly one mechanism and had no notion of "several", "primary" or "none yet".

That gap is not cosmetic. "Has this user enrolled a second factor?" is the condition a forced-enrolment flow branches on; "which of the user's factors do we challenge?" is the choice the login offers; and neither is expressible as one nullable secret.

The shape

  • [Tom2FAEnrolment] — one set-up factor: the mechanism, a stable id, a

displayable [Tom2FAEnrolment.hint], when it was enrolled, whether it is the user's default, and the mechanism's own opaque [Tom2FAEnrolment.secretData]. - [Tom2FAEnrolmentStore] — read/write access to a principal's enrolments; [Tom2FAEnrolmentStore.resolve] finds the installed one (G-DI-3). - [TomMemory2FAEnrolmentStore] — for tests and for a deployment that has not provisioned a database yet. - [TomPersistent2FAEnrolmentStore] over [TomUserTwoFactorEnrolment] — the real one, through the ordinary CRUD repository, with secret_data encrypted at rest.

Why this is a separate library from two_factor.dart

The two import each other: the adaptor contract needs the store to resolve a user's secret, and an enrolment is described in terms of a [Tom2FAContext]. Dart permits the cycle, and the alternative — a third library holding just the context — would split the 2FA flow across three files to avoid an import graph nobody reads. The split that is worth making is the one here: the mechanism contract has no dependency on persistence annotations or a datasource, and this library does, so a deployment that never persists an enrolment does not pay for the repository.

class Tom2FAEnrolment

class Tom2FAEnrolment

One second factor a user has set up.

A value, not a row: the memory store and the persistent store hand back the same type, so nothing above them can tell which is installed. That is what lets the login flow be tested without a database and run against one unchanged.

Constructors

Tom2FAEnrolment.new({required String type, required String enrolmentId, String hint = '', DateTime? enrolledAt, bool isPrimary = false, Map<String, Object?> secretData = const {}})

Records one enrolled factor.

[enrolledAt] defaults to now and is normalised to UTC — the value crosses a database boundary, and a local-time timestamp read back on a server in another zone is silently wrong.

Properties

final String type

The mechanism key this enrolment is for — the same value [Tom2FARegistry.lookup] resolves.

final String enrolmentId

Identifies this enrolment among the user's others, stably across logins.

Chosen by whatever performed the enrolment (a device id, a uuid), not by the store: the client that offers "remove this authenticator" needs a handle it can quote back, and a surrogate database key would tie that handle to one storage implementation.

final String hint

A short displayable clue distinguishing this enrolment from the user's others — a masked phone number, a device name.

Deliberately not resource-keyed, unlike everything on [Tom2FAMethodDescriptor]: a hint is user data, not interface text. There is no locale in which 'iPhone 14' or '•••• 4417' should read differently, and routing it through a resource bundle would only invite a missing-key placeholder where the user expects to recognise their own device.

final DateTime enrolledAt

When the user set this factor up (UTC).

final bool isPrimary

Whether this is the factor to challenge when the user expresses no choice.

At most one of a user's enrolments should carry it; the store does not enforce that, because the flow's fallback — first enrolment in the list — is well-defined either way, and a uniqueness rule that can be violated by a concurrent write would fail a login rather than merely pick oddly.

final Map<String, Object?> secretData

The mechanism's own state for this enrolment: a TOTP shared secret, a phone number, a credential id. Opaque to everything but the adaptor that wrote it.

Treated as secret in full, not per key: the store encrypts the whole map, because a mechanism added later must not be able to leak by filing something sensitive under a key the store had not been told about.

class Tom2FAEnrolmentOffer

class Tom2FAEnrolmentOffer

What an adaptor produces when asked to begin setting a factor up — the enrolment counterpart of [Tom2FAChallengeSpec].

The same split, for the same reason: [clientData] is what the user must be given (for TOTP the base32 secret and the otpauth:// URI behind the QR code, for SMS the number a code was sent to), [enrolmentData] is what only the server may see. Confirmation checks the typed code against [enrolmentData], never against [clientData] — the latter travels in public claims, and a confirmation that trusted it would let a client enrol a secret of its own choosing and call it confirmed.

For TOTP the secret appears in both, deliberately: in [clientData] because handing it to the user is the entire point of enrolment, and in [enrolmentData] because the server must confirm against a copy the user's browser could not have edited on the way past.

Carried between [Tom2FAEnrolmentSupport.beginEnrolment] and [Tom2FAEnrolmentSupport.confirmEnrolment] in the interim token — see [Tom2FAEnrolmentClaims] — so enrolment is as stateless as verification and any instance can finish what another started. Nothing is written to the [Tom2FAEnrolmentStore] until confirmation succeeds.

class Tom2FAEnrolmentState

class Tom2FAEnrolmentState

An enrolment in flight, as carried by an interim login token.

The counterpart of [Tom2FAChallenge] for the other thing a login can owe. Where a challenge says "answer this", a state says "you have no factor yet; here is what you may set up, and here is how far you have got".

It has two shapes, and the difference is [offer]:

  • offered ([offer] is null) — the login has branched into enrolment and

the user has been handed [offeredTypes] to choose from. Nothing mechanism- specific exists yet. - begun ([offer] is non-null) — a mechanism was chosen, the adaptor generated its material, and the user must now type back a confirmation. [expiresAt] and the attempt counter bound that window.

[offeredTypes] survives into the begun shape on purpose: a user who scanned nothing and wants a different method must be able to go back without restarting the login, and the list they may go back to is the one the server offered — not one the client remembers.

Methods

bool isExpired([DateTime? now])

Whether the confirmation window has closed as of [now] (default: the current instant).

A null [expiresAt] means two different things in the two shapes, and the answer differs accordingly. In the offered shape there is no window to close, so this is false. In the begun shape the deadline is the only thing that stops a generated secret being confirmable forever, so its absence is not "no limit" but a state that should never have been built — and the safe reading of a window that was never opened is that no instant is inside it.

[fromClaims] rejects such a token outright rather than relying on this, so in practice a begun state always has a deadline. This is the backstop for the paths that construct one directly.

Tom2FAEnrolmentState withConsumedAttempt()

This state with one more confirmation attempt consumed.

Tom2FAEnrolmentState withOffer(Tom2FAEnrolmentOffer chosen, {DateTime? now})

This state advanced to the begun shape with [chosen]'s material.

The attempt counter restarts: the attempts an offer allows belong to that offer, and choosing a different mechanism is a different offer.

Map<String, Object?> toClaims()

Projects this state onto the interim token's public claims (see [Tom2FAEnrolmentClaims]).

The mechanism-specific claims appear only in the begun shape, so a client cannot mistake an offer list for a pending confirmation.

String toString() override

Names the state without printing the offer's payloads — they carry the secret being enrolled, and this value reaches log lines.

Static

static Tom2FAEnrolmentState? fromClaims(Map<String, dynamic>? payload, [Map<String, dynamic>? secretData])

Reads a state back from a token's public [payload] and its decrypted [secretData], or returns null when the token carries no enrolment.

Defensive throughout, for the reason [Tom2FAChallenge.fromClaims] is: the input arrived from outside the process. A payload that claims a pending enrolment but carries an unreadable offer yields the offered shape rather than a half-built confirmation — the user is asked to choose again, which is the only safe reading.

An unreadable expiry on a begun enrolment is the one thing this method refuses outright, with login.error.2fa.enrolment-offer-invalid. Degrading it the way an unreadable offer degrades is not available: the offer travels in the token's encrypted half and so is authentic, while the deadline travels in the public payload, which nothing on the bearer path verifies. Reading a missing deadline as "no deadline" would therefore let a client delete one claim and hold a confirmable secret indefinitely, and inventing one from the offer's own validity would let it renew the window on every request. Refusing costs an honest user a restarted enrolment; the alternatives cost a credential nobody is watching.

Every boolean claim is read with [Tom2FAClaims.isTrue], the same rule the kernel's [Tom2FAPendingEnrolment.fromClaims] applies. The two decode the same claims from the same token — one to drive the UI, one to authorise the enrolment passes — so a disagreement about what skippable means would show up as a skip button that the server then refuses. They agree on the deadline too, by the same argument and with the same effect: the kernel returns null (it has no error channel and only has to decline to render a panel), this one throws (it must fail the pass).

Throws [TomLoginException] with login.error.2fa.enrolment-offer-invalid when a begun enrolment's expiry claim is absent or is not a parsable instant.

class Tom2FAEnrolmentStore

abstract class Tom2FAEnrolmentStore

Where a principal's set-up second factors live.

Reads and writes only. Deciding whether a factor is owed is [Tom2FAPolicy]'s, issuing and verifying one is [Tom2FAService]'s; a store that also decided would make the two answerable in two places.

Every method takes a [Tom2FAContext] rather than a bare principal id for the same reason the adaptors do: a deployment writing its own store sees the whole attempt — client, organization, locale — and one handed only an id could not. What the shipped stores actually file rows under is narrower, and is [principalKeyOf]'s to state.

Future<void> store(Tom2FAContext context, Tom2FAEnrolment enrolment)

Records [enrolment], replacing any existing one with the same [Tom2FAEnrolment.enrolmentId] for this principal.

Upsert rather than insert: re-running an enrolment is how a user replaces a lost authenticator, and making that path an error would leave the user with a factor they cannot use and cannot overwrite.

Future<void> remove(Tom2FAContext context, String enrolmentId)

Removes this principal's enrolment with [enrolmentId]; removing one that is not there is a no-op, not an error.

Static

static Tom2FAEnrolmentStore? resolve()

The store this deployment installed, or null.

Nullable with no default, unlike [Tom2FAPolicy.resolve]: a policy has a meaningful "challenge the mechanism" fallback, whereas a fallback store would be an empty one — and an empty store is indistinguishable from this user has enrolled nothing, which is exactly the answer callers must not be given wrongly. null says "no store here, ask the legacy hook"; an empty list says "asked, and this user has none".

Uses [TomBean.getBeanByType] because not installed is an ordinary case; the resolving handle would throw.

static String principalKeyOf(Tom2FAContext context)

The storage key for the principal in [context] — the principal id, and nothing else.

One place, so the memory store and the persistent store agree on what "this user" means and a test written against one is meaningful for the other.

The organization is deliberately not part of it. [TomPrincipal.id] is unique across the deployment rather than within a tenant, so it already names one person; adding the organization would split that person's factors across the tenants they log into, so the same authenticator would have to be enrolled once per organization. Every framework table that files rows per principal rests on the same premise and carries no tenant column — tom_principal_resource_grant, tom_external_identity, and this module's own tom_user_two_factor_enrolment, keyed (principal_id, enrolment_id).

A deployment that allocates principal ids per tenant has broken that premise framework-wide and not merely here; its answer is its own [Tom2FAEnrolmentStore], which is handed the whole context and may key rows however it needs. That is also why this being static costs nothing: it is the key the two shipped stores share, not a hook the contract imposes on an implementation.

class Tom2FAEnrolmentSupport

abstract class Tom2FAEnrolmentSupport

What a mechanism implements when a user can set it up — the third question, asked only of the mechanisms that have an answer.

Why this is not on [Tom2FAService]

[Tom2FAService] asks two questions and says so: issue a challenge, verify a submission. Enrolment is a third, and not every mechanism has one — a hardware token an administrator provisions, or a mechanism backed by a corporate directory, is acquired entirely outside the framework and has nothing to offer here. Widening the base contract would force those adaptors to implement a method whose only honest body is a throw, and every caller to treat that throw as a normal outcome. A separate interface makes "can this be enrolled?" an is check that [Tom2FARegistry.enrollableMethods] answers for the whole registry at once.

Why confirmation is not optional

The pair is begin then confirm, and nothing is stored in between. Storing an unconfirmed secret locks the user out of their own account whenever the QR scan silently failed: the server believes a factor is enrolled, the authenticator holds nothing, and the next login demands a code that cannot be produced. Making the user type back a derived code proves the secret arrived before it is allowed to become a login requirement.

Implementations must be stateless between the two calls, for the same reason [Tom2FAService] must be: they may run on different instances. Everything the confirmation needs travels in the [Tom2FAEnrolmentOffer].

Future<Tom2FAEnrolmentOffer> beginEnrolment(Tom2FAContext context)

Begins setting this mechanism up for [context]'s principal: generates whatever the factor needs and returns it as an offer.

Nothing is persisted. Throws [TomLoginException] when this user cannot enrol this mechanism at all (no phone number on file, a quota reached).

Future<Tom2FAEnrolment> confirmEnrolment(Tom2FAContext context, Tom2FAEnrolmentOffer offer, String submitted)

Confirms [offer] against what the user typed back, returning the enrolment to store.

Returns only on success — the return type is non-nullable precisely so that "an enrolment came back" cannot mean anything but "confirmed". A wrong [submitted] throws [TomLoginException]; the caller may re-offer the same offer until [Tom2FAEnrolmentOffer.attemptsAllowed] is spent.

Implementations must derive the expected answer from [Tom2FAEnrolmentOffer.enrolmentData] and never from [Tom2FAEnrolmentOffer.clientData].

class TomPersistent2FAEnrolmentStore

class TomPersistent2FAEnrolmentStore implements Tom2FAEnrolmentStore

A [Tom2FAEnrolmentStore] over tom_user_two_factor_enrolment, with the mechanism's secret encrypted at rest.

The encryption scheme, and why this one

[Tom2FAEnrolment.secretData] is JSON-encoded and then passed through [TomJwtConfiguration.encrypt] — RSA-OAEP (SHA-1 MGF1, PointyCastle's OAEPEncoding(RSAEngine())), block-chained so a map of any size is safe, base64-wrapped for a TEXT column. Reading it back is the inverse through [TomJwtConfiguration.decrypt], with the RSA private key.

A TOTP shared secret is a credential: anyone holding it can generate the user's codes forever, so a readable tom_user_two_factor_enrolment is a complete 2FA bypass and a database backup is a bearer token. Storing it in the clear would make the second factor security theatre against exactly the attacker it exists to stop — the one who already reached the database.

The scheme is [TomJwtConfiguration]'s and not a new one because that is the framework's existing at-rest/in-transit asymmetric primitive: it is what the authorization token's encrypted claims section already uses, so a deployment that has provisioned real keys has provisioned these keys, and one that has not gets the same loud dummy-key warning here as everywhere else. A second, 2FA-only cipher would mean a second key to rotate and a second place to get it wrong.

[cipher] is a constructor argument so a deployment can hand this store a different key pair from its token configuration — enrolment secrets are long-lived where a signing key is rotated often, and a deployment that wants them decoupled should not have to fork the store to get it. Unset, it follows [TomJwtConfiguration.defaultSignConfiguration] at call time, so installing production keys after boot is obeyed.

A row that cannot be decrypted — written under a key that has since been rotated away — yields an empty map rather than throwing. Throwing would instead fail the whole login, including the user's other, perfectly good factors.

class TomUserTwoFactorEnrolment

class TomUserTwoFactorEnrolment

The persisted form of one [Tom2FAEnrolment] — a row of tom_user_two_factor_enrolment.

Mapped through the ordinary object-persistence annotations, like every other framework table that has an entity ([TomPrincipalResourceGrant], [TomPrincipalDelegation]): a second persistence path for one table would have to reimplement binding, row mapping and the audit hook, and would drift.

[secretData] is not a column. What is stored is [secretDataCipher] — the JSON of the map, encrypted; see [TomPersistent2FAEnrolmentStore] for the scheme and why.

Static

static String createTableSql

The DDL this entity expects, reproduced verbatim by the framework migration so the two cannot drift — test/reference_migrations_test.dart fails if they do.

(principal_id, enrolment_id) is unique because that pair is the enrolment's identity — the upsert in [TomPersistent2FAEnrolmentStore.store] relies on there being at most one row to find, and a duplicate would make which secret answers a login depend on row order.
