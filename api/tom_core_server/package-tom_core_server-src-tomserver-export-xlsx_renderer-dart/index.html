XLSX rendering: one worksheet per section, written straight to the wire.

An .xlsx file is a ZIP archive of XML parts. That happens to be the one office format that can be produced front-to-back without ever holding the document, which is why it — and not PDF — is the rich format that keeps [TomTabularRenderer.streamsRows] true.

Why no XLSX package

package:excel (MIT, 4.0.6) was evaluated and not adopted, for two independent reasons:

1. It buffers everything. Its model is Excel.createExcel(), sheet.appendRow(...) per row, then excel.encode() returning the whole file as bytes. Both the workbook object graph and the encoded archive are resident at once — the failure this module exists to prevent. 2. It pins xml <7.0.0. package:pdf moves to xml ^7 at 3.13.0, so depending on both would freeze the PDF renderer at 3.12.x indefinitely.

The alternative was not "write a spreadsheet format". The hard parts of XLSX — a formula engine, styles, charts, shared strings, the reading side — are exactly the parts an export does not use. What is left is a fixed set of small XML parts — six, plus one per sheet, plus one more when the result carries metadata — and a ZIP container, and the ZIP compression itself is dart:io's ZLibEncoder. So this renderer takes no dependency at all.

Where the title and the metadata go

Both land in the package's document properties rather than in a cell: [TomTabularResult.title] as dc:title in docProps/core.xml, and [TomTabularResult.metadata] as user-defined properties in docProps/custom.xml. That is the same choice the PDF renderer makes when it passes the title to the document's info dictionary — with the difference that the PDF also prints both, because a page has somewhere to print them and a sheet does not.

A header block above the table was the alternative and is the wrong answer here: it would push the header row down by however many metadata entries there happened to be, so a consumer reading the sheet as a table would find its columns at a row number that varies with the metadata. A spreadsheet's value is that it is machine-readable; the properties carry the context without spending that.

How it streams

Two techniques, both standard, together remove every reason to buffer:

  • Inline strings (t="inlineStr") rather than a shared-strings table. A

shared-strings table must be written before the sheets that index into it, which means knowing every string in the document before emitting the first row. Inline strings cost some size and save the entire result. - ZIP data descriptors (general-purpose bit 3). A local file header normally carries the entry's CRC and sizes, which are unknown until the entry is finished. Bit 3 says "the three values follow the data instead", so each part is written as it is compressed. Every mainstream reader, Excel included, supports this.

The result: peak memory is one row of XML plus the deflate window, regardless of how many rows there are.

class TomXlsxRenderer

Creates an XLSX renderer.

Properties

final int compressionLevel

The deflate level, 0 (store) to 9 (smallest).

6 is zlib's default and the right trade for tabular XML, which compresses roughly ten to one. 0 is worth choosing only when the consumer is a program on the same machine and the CPU matters more than the bytes.

final int maxRowsPerSheet

The most rows one worksheet may hold, header included.

Defaults to Excel's own limit since the 2007 format, and it is Excel's rather than this writer's: a sheet past it renders perfectly here and is refused by the reader. Checked while the rows stream, so a result that will not fit fails on the row that crosses the line rather than at the reader an hour later.

Lower it for a consumer with a tighter limit of its own. Raising it produces a file Excel will not open, which is the caller's to decide in the same way [TomPdfRenderer.rowLimit] is.

final int maxColumnsPerSheet

The most columns one worksheet may hold — Excel's limit, as above.

Checked before any row is written, because a section's columns are known up front and a refusal that waited for the stream would have spent the query first.

final int maxPartBytes

The largest value the archive's 32-bit size and offset fields can hold.

Every size and offset this writer emits is 32-bit and ZIP64 — the extension that widens them — is not written. A part or an archive past this would wrap silently: the fields would hold the value modulo 4 GiB, the reader would believe them, and the result is a corrupt workbook produced by a run that reported success. The module's stated purpose is the export too large to hold in memory, so this is a ceiling a real report reaches rather than a theoretical one.

So it is checked as the bytes go past and the render fails at the ceiling, which is what [TomPdfRenderer] does with its own. Emitting ZIP64 instead is the other honest answer and a larger one: it changes the local header, the data descriptor, the central directory and the end-of-central-directory record, and every reader that has to accept them.

A parameter so that the refusal can be reached in a test without producing four gigabytes; a deployment has no reason to change it.

static String _coreProperties(String title)

The core properties part, carrying the result title as dc:title.

It deliberately carries no dcterms:created or dcterms:modified. Those are the two fields a real authoring tool always writes, and writing either would make the same result render to different bytes on two runs — the property the zeroed MS-DOS timestamps in [_ZipStreamWriter._localHeader] exist to preserve. An export has no author and no edit history; it has a title, and that is what it says.

static List<MapEntry<String, String>> _customPropertyEntries(Map<String, String> metadata)

The metadata entries that can become custom properties, escaped.

An entry whose name escapes to nothing — empty, or made only of control characters XML cannot carry — is dropped rather than written. A custom property with an empty name is what makes Excel declare the file corrupt, and the same trade is made here as in [_escapeXml]: losing one entry of context beats a workbook that will not open.

static String _customProperties(List<MapEntry<String, String>> entries)

The custom properties part: one user-defined property per metadata entry.

fmtid is the format id OOXML reserves for user-defined properties, and pid numbers them from 2 — 0 and 1 are reserved by the underlying property-set format, and a property claiming either is rejected.

class _ZipStreamWriter

class _ZipStreamWriter

Uint8List _localHeader(List<int> nameBytes)

The local file header for [nameBytes], with sizes deferred to bit 3.

The MS-DOS timestamp fields are written as zero on purpose. A real modification time would make the same result render to two different byte sequences on two runs, which breaks the cheapest possible test — compare the bytes — and any caching keyed on a content hash. Readers show the entries as dated 1980-01-01; nothing depends on it.

function _escapeXml

String _escapeXml(String text)

Escapes [text] for XML character data, dropping characters XML cannot carry.

Control characters below 0x20 (other than tab, newline and carriage return) are not representable in XML 1.0 at all — not even as a numeric reference — so they are removed rather than escaped. They reach an export from binary data mis-stored in a text column, and a workbook that will not open is a worse answer than a cell missing a byte no one can see.
