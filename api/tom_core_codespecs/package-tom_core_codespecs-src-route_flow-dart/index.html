class TomRouteRegistry

class TomRouteRegistry

The route registry and screen-flow model a CodeSpec's @CsRoute / @CsScreenFlow (CE-NV) is built on.

*Why this is a gap (codespecs_mapping.md §5.11, verdict gap). The tom_flutter_ui substrate (TomPageRoute in widgets/navigation/) is a bare MaterialPageRoute subclass: it knows how to push a screen but carries no route id and belongs to no registry. The framework therefore assumes route uniqueness without anywhere to check it — two screens can claim the same name and nothing notices until runtime. CodeSpecs needs the two things the substrate has no home for: (a) a route-id registry that makes uniqueness and dangling references checkable at generation time, and (b) a screen-flow model in which an action's target is conditional on its [TomFlowOutcome] and a form's placement is authored as replace-or-popup. So it lands here as a concrete tom_core-family class — never an abstract `Cs base (the framework carries annotations only, codespecs_mapping.md` §1.1).

A CodeSpec @CsRoute graph is a [TomRouteRegistry]. CE-NV is a client part (codespecs_mapping.md §4.2), so the registry lives in the client project of the three-project output trio.

enum TomFlowOutcome

enum TomFlowOutcome

The outcome of an action, which selects the navigation target (codespecs_mapping.md §5.11).

Navigation is action-triggered and conditional on the outcome: one action reaches different screens depending on how it ended, so the outcome set is part of the flow vocabulary rather than a runtime detail.

Values

success

The action completed.

error

The action failed with a processing error.

validationError

The action was rejected by validation.
