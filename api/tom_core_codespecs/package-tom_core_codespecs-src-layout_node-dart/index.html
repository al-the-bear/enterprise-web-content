class TomLayoutModel

class TomLayoutModel

The two-layer layout holder a CodeSpec's @CsLayout (CE-LO) is built on.

*Why this is a gap (codespecs_mapping.md §5.2/§5.12/§5.22, verdict gap). The tom_flutter_ui substrate (AclComponent in advanced_container_layout/) is a rendering leaf: it holds a live Widget child and its own alignment flags, so it describes one already-built widget tree. CodeSpecs needs the layer above that — an authorable, serializable layout description in which (a) placement references elements by stable id instead of embedding them, and (b) a generated [base] tree and an authored [overrides] layer are kept separate so regeneration does not destroy manual layout work. tom_flutter_ui has no such base/override layering and no id-addressed delta grammar, so the model lands here as a concrete tom_core-family class — never an abstract `Cs base (the framework carries annotations only, codespecs_mapping.md` §1.1).

A CodeSpec @CsLayout class is a [TomLayoutModel]. CE-LO is a client part (codespecs_mapping.md §4.2), so the layout lives in the client project of the three-project output trio.

List<String> reconcileWarnings()

Every delta that does not resolve against the current [base] tree.

Three things can be wrong with a delta after the base is regenerated, and all three are reported rather than silently applied or silently dropped:

  • an id that resolves to nothing — the node the delta addressed is

gone from the regenerated tree; - an id that resolves to the wrong kind of node — the id survived but now names a container where the delta needs a slot, or the other way round; - a delta that names no new parent where its operation requires one.

The second is what the closed delta grammar exists for. An id that vanished is conspicuous; an id a regeneration re-used for a different kind of node still resolves, so without this check the delta goes on applying and quietly means something other than what was authored.

Each operation requires the kind its own documentation states: [TomLayoutDeltaOp.setContainerProp] and [TomLayoutDeltaOp.removeContainer] address a container, [TomLayoutDeltaOp.setSlotHint] a slot, and [TomLayoutDeltaOp.reparent] moves a node of either kind. A new parent is always a container, because only a container owns children.

[TomLayoutDeltaOp.insertContainer] is the one operation whose target is not required to exist — the delta creates it. It is required not to exist already: a [TomLayoutNode.nodeId] is unique across the tree, so an insert whose id the regenerated base has since taken is the same drift seen from the other side.

Nothing is dropped. The list is advice to whoever regenerated the base; the deltas stay exactly as authored, because the author is the one who can decide what a warning means.

class TomLayoutNode

abstract sealed class TomLayoutNode

A node in the generated base layout tree — either a [TomLayoutContainerNode] or a [TomLayoutSlotNode].

Sealed so the two-layer reconcile can exhaustively distinguish containers (which own children and can be inserted/removed) from slots (which reference an element and can only be hinted).

Constructors

TomLayoutNode.new({String nodeId = ''})

Creates a layout node with the given stable [nodeId].

Properties

String nodeId

Stable identifier of this node, unique across the whole layout tree.

Override deltas address nodes by this id, so it must survive regeneration of the base tree — that stability is what lets manual layout outlive model changes.

class TomLayoutSlotNode

class TomLayoutSlotNode extends TomLayoutNode

A leaf node that places an element which is defined elsewhere.

The slot carries [referencedId] — the id of the field, action or component — and never the element's definition. That is the semantics↔layout split of codespecs_mapping.md §5.2: what an element is is authored once in the semantic model; where it sits is authored here, so re-arranging a screen cannot silently change a field's meaning, validation or binding.

enum TomLayoutContainerKind

enum TomLayoutContainerKind

The closed set of layout containers a CodeSpec may author (codespecs_mapping.md §5.22).

The set is closed on purpose: a generated layout must be renderable by every target platform, so a container kind exists here only when all targets can express it. Adding a kind is a deliberate authored act on the catalogue, not a per-spec escape hatch.

Values

row

Horizontal sequence.

column

Vertical sequence.

wrap

Horizontal sequence that wraps onto further lines.

stack

Overlapping children painted back to front.

flex

Proportional sequence driven by per-child flex factors.

grid

Two-dimensional cell arrangement.

padding

Insets around a single child.

align

Positions a single child within the available space.

sizedBox

Constrains a single child to fixed dimensions.

enum TomLayoutDeltaOp

enum TomLayoutDeltaOp

The closed grammar of override deltas in the authored layer (codespecs_mapping.md §5.22).

Every manual layout adjustment is expressed as one of these five operations against a stable node id. Keeping the grammar closed is what makes the authored layer reconcilable: each delta can be checked against a regenerated base tree, which an opaque "hand-edited layout file" could not.

Values

reparent

Move an existing node under a different parent.

setContainerProp

Set a property on an existing container node.

setSlotHint

Set a layout hint (flex, span, alignment) on an existing slot.

insertContainer

Add a container that the generated base does not contain.

removeContainer

Drop a container the generated base contains (its children reparent to the removed container's parent).
