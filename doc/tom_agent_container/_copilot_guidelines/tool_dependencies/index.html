CRITICAL: All Tools Must Be Based on tom_build_base

Every CLI tool in the workspace MUST be built on tom_build_base. This package provides the foundation that all tools share:

  • CLI argument parsing (CliArgParser, isHelpCommand, isVersionCommand)
  • Version display (BuildkitVersionInfo via generated version.versioner.dart)
  • Process execution (ProcessRunner)
  • Workspace navigation and project discovery
  • Logger infrastructure (ToolLogger)
  • Macro expansion (expandMacros)
  • Help text generation (getToolHelpHeader)

If a tool needs functionality that tom_build_base doesn't yet provide, add it to tom_build_base first, publish it, then use it in the tool. Never implement shared CLI infrastructure directly in a tool — it belongs in tom_build_base.

All tools depend on tom_build_base via pub.dev (not path dependencies). When making changes to tom_build_base:

1. Publish tom_build_base to pub.dev first 2. Run dart pub upgrade tom_build_base in each dependent tool project 3. Recompile the tools to pick up changes

See _copilot_guidelines/dart/project_republishing.md for the complete workflow.

CRITICAL: No Temporary Downstream Implementations

If functionality belongs to tom_build_base, do not add temporary or stopgap implementations in downstream tools.

Mandatory sequence:

1. Modify tom_build_base. 2. Test it with a test tool created inside tom_build_base (or an existing one there). 3. Republish tom_build_base. 4. Update the tom_build_base version in all tools based on tom_build_base. 5. Run tests in all tools based on tom_build_base.

Applies at minimum to tom_build_kit, tom_test_kit, and tom_issue_kit, and to any other tool that depends on tom_build_base.

Version Checking

All tools support version, -version, and --version. If a tool does not support version checking, report it as a bug. 

# Check any tool version
buildkit --version
tom --version
dcli --version
testkit --version

Check If Rebuild Needed

Compare tool version with source project version:

# Get tool version
buildkit --version

# Check source pubspec.yaml version
cat tom_ai/basics/tom_build_kit/pubspec.yaml | grep "^version:"

If source version is newer, rebuild is needed.

Rebuilding Tools

Standard Rebuild Command

For development builds (local platform only):

buildkit -R --project <project-name> :pubupdate :versioner :compiler --targets darwin-arm64
  • -R - Workspace root mode (scan from workspace root, no need to cd into project folder)
  • --project - Specify project name(s), comma-separated
  • :pubupdate - Update pub dependencies
  • :versioner - Increment build number, generate version.versioner.dart
  • :compiler - Compile the binary
  • --targets - Target platform (use current platform for dev builds)

Important: The :versioner step is required because: 1. It increments the build number 2. It generates version.versioner.dart (compilation fails if missing)

Tools Requiring D4rtgen

The tom and dcli tools require bridge generation before compiling:

buildkit -R --project tom,dcli :pubupdate :versioner :d4rtgen :compiler --targets darwin-arm64

Bootstrapping Buildkit

Buildkit requires manual compilation for initial setup. After that, it can compile itself.

Initial bootstrap (when buildkit doesn't exist):

cd tom_ai/basics/tom_build_kit
dart pub get
dart compile exe bin/buildkit.dart -o ~/.tom/bin/darwin-arm64/buildkit
chmod +x ~/.tom/bin/darwin-arm64/buildkit

Self-compile (after buildkit exists):

buildkit -R --project buildkit :pubupdate :versioner :compiler --targets darwin-arm64

Other Tools

Standard tools without special requirements:

# testkit
buildkit -R --project testkit :pubupdate :versioner :compiler --targets darwin-arm64

# issuekit
buildkit -R --project issuekit :pubupdate :versioner :compiler --targets darwin-arm64

# d4rtgen
buildkit -R --project d4rtgen :pubupdate :versioner :compiler --targets darwin-arm64

# astgen
buildkit -R --project astgen :pubupdate :versioner :compiler --targets darwin-arm64

Publishing Workflow

When a pub.dev dependency needs updates, Copilot must perform these steps manually:

1. Bump version in pubspec.yaml 2. Update CHANGELOG.md with changes 3. Update README.md if API changed 4. Run tests: dart test 5. Dry run: dart pub publish --dry-run 6. Publish: dart pub publish 7. Update dependent projects to use new version 8. Run dart pub get in dependent projects

Note: There is currently no full tool support for the complete cycle of republishing dependencies and updating pubspec.yaml files in dependent projects. This must be done manually.

Checking for Updates

Before building tools, check if pub.dev dependencies need updates:

# Check if local changes exist in published packages
cd tom_ai/basics/tom_build_base
git status
git log --oneline -5

# Compare with pub.dev version
dart pub outdated

Build Order

Buildkit can calculate the correct build order automatically. However, when pub.dev dependencies need updating, the full cycle is:

1. Identify changed pub.dev packages 2. Republish in dependency order (tom_basics → tom_build_base → etc.) 3. Update pubspec.yaml in dependent projects 4. Run buildkit to compile tools

For simple tool rebuilds (no pub.dev changes):

# Rebuild all tools
buildkit -R --project buildkit :pubupdate :versioner :compiler --targets darwin-arm64
buildkit -R --project testkit,issuekit,astgen,d4rtgen :pubupdate :versioner :compiler --targets darwin-arm64
buildkit -R --project tom,dcli :pubupdate :versioner :d4rtgen :compiler --targets darwin-arm64
