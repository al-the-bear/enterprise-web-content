Maintaining the tom_d4rt ↔ tom_d4rt_ast mirror

tom_d4rt/lib/src/… and tom_d4rt_ast/lib/src/runtime/… hold the same interpreter twice: once against the analyzer's AST, once against the zero-dependency mirror AST in tom_ast_model. A fix to one is incomplete until it lands in the other.

The only practical way to check that it did is to diff the two files. That check is the reason for everything on this page — anything that fills the diff with noise does not merely make the check unpleasant, it makes it stop happening.

The mirrored file pairs

tom_d4rt/lib/src/ and tom_d4rt_ast/lib/src/runtime/ mirror each other wholesale, not file by file. Every .dart file under the first has a twin at the same relative path under the second, except for the handful each line needs alone — the analyzer front end (d4rt_base.dart, module_loader.dart, scope_frame.dart and three more) and the bundle front end (d4rt_runner.dart, ast_module_loader.dart, ast_bundle.dart and the conditional utils/file_access/ trio).

Do not read a file list from this page. Two guards derive the set from the trees and name every exception with a reason — tom_d4rt/test/scd183_mirror_source_sync_test.dart for everything outside stdlib/, scd49_stdlib_twin_sync_test.dart for stdlib/ itself. A list written here would be a third copy that nothing checks, and the count in it would be wrong within a week.

How much actually differs, measured rather than assumed

The received wisdom was that the stdlib pairs diff cleanly and the runtime files "genuinely differ, so a diff there is read for shape, not for equality". The first half is right. The second is true of five files and false of the rest:

identical in code, once the twin's SFoo is read as Foo 23 of 31 shared non-stdlib files
one recordable region apart 3 — bridge/bridged_enum.dart , bridge/bridged_types.dart , environment.dart
structurally different throughout 5 — interpreter_visitor.dart , callable.dart , runtime_types.dart , declaration_visitor.dart , introspection.dart

The normalisation that makes the first row true is not a convenience. The quest architecture states that tom_ast_model mirrors the analyzer AST's STRUCTURE 1:1; rewriting SFoo to Foo is that claim made executable, and 23 files satisfy it exactly.

The model does not mirror the analyzer's accessor NAMES, and that is decided (SCE235): it says isNot for notOperator != null, name for lexeme, and so on, and its identifier name is nullable. Those spellings are a second normalisation, accessorVocabulary in tom_d4rt/test/mirror_normalisation.dart, which the per-body guard (scd199) applies to both trees. If you add a model accessor that renames an analyzer member, add its row there. Otherwise every body that uses it silently leaves the checked set and joins the recorded divergences.

Mirroring a stdlib change: the tool, not a sed loop

For stdlib/, where the rewrite is mechanical, use tom_d4rt/tool/mirror_stdlib.dart from the tom_d4rt package root: 

dart run tool/mirror_stdlib.dart                 # check: report, write nothing
dart run tool/mirror_stdlib.dart --write         # mirror what it safely can
dart run tool/mirror_stdlib.dart --write core/set.dart

It rewrites the imports and writes a twin file only when doing so loses nothing: never a file SCD49 pins as deliberately different (it reads SCD49's list rather than keeping its own), never a twin whose comments differ from the reference's — those it names for a hand port — and nothing at all when either tree is missing. It refuses any path outside stdlib/: the files there are the five that differ throughout, and a tool that helps with the easy files and not with those is the habit this replaces. The hand-typed loop it replaces once overwrote io/process.dart. SCD49 is still the authority; run it after writing.

The five in the last row diverge because the mirror AST has no parent pointer (so the twin reconstructs one) and because its node accessors differ (node.name.lexeme against node.name?.name ?? '').

That last row overstates them, and the overstatement is dangerous. The file-level comparison trims the common prefix and suffix to quote a divergence, so ONE early difference leaves every token after it inside the residue — interpreter_visitor.dart reads as "99 % of tokens differ" and is exempted whole. Compare the same trees member by member, with the same normalisation, and the picture is different:

shared member bodies across the 31 files726
identical after normalising618 (85 %)
divergent, in 7 files108
files that are 100 % body-identical24 of 31
the worst file, interpreter_visitor.dart77 of 134 bodies identical

So three questions are asked of these pairs, not two, and each is asked where it can be true:

  • Code identity where the two copies can be the same file (F-SCD183-2).
  • Member-set parity everywhere, including the five — "the same fix landed in

both" is first a claim about what a file DECLARES (F-SCD183-5). This is what catches the mirror rule's usual failure: a helper added to one tree only. - Per-body agreement everywhere, which is what catches its other failure: a one-line disagreement INSIDE a member both trees declare. visitPropertyAccess returned the wrapper's runtimeType in tom_d4rt and the native object's in the twin for as long as both files existed, with both suites green throughout, because a wholesale _structural exemption is exactly where such a line is invisible. scd199_mirror_body_agreement_test.dart pins the 108 bodies that really do disagree, by the SHAPE of their disagreement — so a change mirrored into both trees stays silent and a change made to one fires.

The front end is a mirror too, and this page used to omit it

tom_d4rt_exec is not the interpreter — it is the layer that parses with the analyzer and hands a mirror AST to tom_d4rt_ast. Two of its files nevertheless mirror tom_d4rt files of the same name, and they hold the two places a consumer can silently lose behaviour the interpreter provides:

tom_d4rttom_d4rt_execWhat lives there
lib/src/d4rt_base.dart lib/src/d4rt_base.dart the host boundary: whether an SDK-shaped error reaches the caller as itself
lib/src/module_loader.dart lib/src/module_loader.dart bridged-class registration: whether a bridge's source URI reaches the environment

Both drifted for months and neither tree could see it (scd10_aicx). The mirroring rule named the interpreter pair, which was in sync throughout; these files are in the consumer, so tom_d4rt_ast's own suites cannot exercise them, and exec's suite was pinned eleven minors behind. The catch-alls lost SCB10 — every SDK-shaped error came back as RuntimeD4rtException('Unexpected error: …') — and registration computed sourceUri, used it for logging, and never passed it on, so tcca19's ambiguity detection never fired.

"exec delegates to the runner" is true of only ONE of its two execution paths, and the exception is the part worth carrying. D4rt there is a facade: executeBundle delegates, while the classic execute() carries its own _executeInEnvironment, because it runs against the analyzer front end's ModuleLoader rather than a pre-resolved bundle. So the execution seam exists in three copies — tom_d4rt, tom_d4rt_ast, and tom_d4rt_exec — and a fix landed at that seam has to land three times. The rule as stated above names two of them.

scd74_aido found this while adding onUncaughtError: wiring the hook to the runner alone would have produced an API that fires for executeBundle and silently does not for execute. tom_d4rt_exec/test/scd74_hook_covers_both_paths_test.dart keeps one case per path for that reason, and neither can stand in for the other.

A byte diff does not work here: two of exec's paths delegate or parse differently and the file is about a thousand lines shorter, so everything differs. tom_d4rt_exec/test/front_end_parity_test.dart (F-SCD10-1..4) compares vocabulary instead — the error types and guard helpers each file names in code, and the named arguments each passes at mirrored call sites — with comments stripped, because one of these files explains the other's exception in a comment. Legitimate differences are recorded with their reason and re-checked, so a delegation that stops delegating fails rather than keeping its exemption.

The SDK floor is load-bearing, and not for the reason it looks like

dart format has two output styles and chooses between them by language version: the pre-3.7 style, and the tall style from 3.7 (one argument per line, trailing commas, block-like indentation). The language version comes from the enclosing package's environment.sdk lower bound, resolved through .dart_tool/package_config.json — not from anything in the file itself.

So two packages holding byte-identical source will format it two different ways if their floors straddle 3.7. The result is a mirror diff of thousands of lines of pure re-wrapping, with any real divergence buried inside it.

Every package in the mirror therefore declares a floor at or above 3.7, and all three trees are kept formatted. Once that holds, dart format is idempotent and running it is harmless — which is the whole point: the alternative is a rule that everyone has to remember at the moment they reach for a reflex command.

tom_d4rt_ast/test/scc26_format_alignment_test.dart enforces this. It fails if any mirrored package drops its floor below 3.7, or if either tree is left unformatted.

If you must lower a floor

Don't, unless a consumer genuinely needs it — and check first whether the declared floor is even reachable. A package whose dependencies force a higher SDK cannot resolve at its own declared lower bound; the declared value is then a promise nothing can honour, and lowering it further buys nothing at all.

If a lower floor is truly required, the mirror invariant has to be re-established some other way before the change lands, and the guard test updated to say so.

Proving a reformat is inert

git diff -w cannot do this. It ignores whitespace within a line, but the tall style splits lines, and a moved line boundary still reads as a change. A reformat therefore looks enormous under -w while being entirely empty.

Compare the token stream instead: strip all whitespace, and — for files that still differ — strip commas as well, since a trailing comma is pure formatting punctuation in Dart. A file that matches only after the comma pass changed nothing but comma placement. A file that differs even then contains a real edit.

What actually checks the mirror, and where it runs

The rules on this page are enforced by tests, and none of those tests lives in both trees. They are REPO-WIDE GUARDS: their subject is the pair, or the whole repository, rather than the package they sit in.

CheckLives inAsserts
scd49_stdlib_twin_sync_test.dart tom_d4rt the two stdlib trees are code-identical except at the points it records
sce219_mirror_stdlib_tool_test.dart tom_d4rt tool/mirror_stdlib.dart reports the real trees current, writes only lossless files, and refuses pinned files, twins with their own comments, a missing tree and paths outside stdlib/
scd183_mirror_source_sync_test.dart tom_d4rt the two trees agree OUTSIDE stdlib — code-identical where they can be, member-set-identical where they cannot, every exception named
scd199_mirror_body_agreement_test.dart tom_d4rt every member body the two trees share is identical, and each of the 108 that is not is pinned by the shape of its divergence
scd51_member_gap_parity_test.dart tom_d4rt the two trees' unreachable-member sets agree
scc26_format_alignment_test.dart tom_d4rt_ast every mirrored package is dart format clean — F-SCC26-3's subject is the SIBLING tree
scc45_resolution_guard_test.dart tom_d4rt_ast no package resolves a tom_* version behind one already cached
front_end_parity_test.dart tom_d4rt_exec exec's parsing front end stays in step with the pair
scd134_barrel_surface_parity_test.dart tom_d4rt the two barrels export the same public top-level names, and each place they do not is recorded with a reason

Each runs only when its own package's suite runs, so a session that edits one tree and tests only that tree checks none of the ones that live elsewhere. That is why the mirror rule is stated as "same commit": the guards cannot see a half-mirrored change until someone runs the package that holds them.

The full set spans six packages and is deliberately not listed anywhere, nor counted here — a hand-maintained list of it was found stale by a factor of nine, and a hand-maintained COUNT rots the same way for the same reason. Find them with 

grep -rn 'REPO-WIDE GUARD' */test

from the repo root; tom_d4rt/test/scd129_repo_wide_guard_index_test.dart fails if one arrives without the banner. The quest overview carries the standing gate.

The two barrels are part of the mirror

package:tom_d4rt/d4rt.dart and package:tom_d4rt_ast/runtime.dart are the two public faces of one interpreter, and they drift in a way no compiler catches: not as a broken build, but as a type a consumer RECEIVES and cannot NAME.

That is what SCD134 found. BridgedEnumDefinition.buildBridgedEnum() returns a BridgedEnum; Environment.getRuntimeType returns one for any native enum value; InterpreterVisitor.moduleLoader is a public field typed ModuleLoader. None of those three types was exported from tom_d4rt/d4rt.dart, so the only way to name one was import 'package:tom_d4rt/src/...' — the implementation import that implementation_imports exists to forbid. All three were exported by the twin, which is why the twin works as the oracle here.

When you add a public type, export it from the barrel of the tree you added it to, and check the other tree names it too. scd134_barrel_surface_parity_test .dart compares the sets on every tom_d4rt run and fails on any name only one side exports. It is not a formatting rule with a test attached — it is the only thing that sees this class of drift at all.

Where the two lines genuinely differ, record the divergence in that file's _divergences map with its side and its reason rather than widening the comparison. The reasons are the useful artefact: they separate "the AST line has no analyzer, so it has no source front end" from "this is a gap nobody noticed", and today the map holds both kinds, each named.

Two limits are deliberate and worth knowing before trusting a green run:

  • Members are not compared. bridgedLibraryUris exists on D4rtRunner with

no counterpart on D4rt, and nothing sees it. Top-level names only. - Cross-package re-exports are not followed. runtime.dart re-exports package:tom_ast_model/ast.dart; following it would add 188 S* types whose reference-line equivalent is package:analyzer, which is not re-exported either. The exemption is itself asserted, so a second one cannot appear silently — but names that live one package over (StaticResolver, opensLexicalFrame) show up as divergences and are recorded as such.

Commit discipline

  • Never bundle a formatting pass with a behaviour change. If both are needed,

the reformat is its own commit. Otherwise the next person reviewing a mirrored fix cannot tell the semantic hunks from the whitespace ones. - Fix lint fallout before the reformat, not after. Raising a language version or re-wrapping a line can make a lint start firing — curly_braces_in_flow_control_structures in particular, because the formatter splits a long braceless if onto two lines and the split is what trips it. Bracing those bodies first keeps the reformat commit free of semantic hunks. - Both packages need a version bump and a CHANGELOG entry for any commit that changes lib. The check is tom_d4rt/test/release_hygiene_test.dart, and it runs on its own in about three seconds — cd tom_d4rt && dart test test/release_hygiene_test.dart — so run it right after the lib commit rather than meeting it in the full suite a turn later. It reads committed history, so an unstaged bump does not clear it; the failure text says whether the bump still has to be written or only committed.

The FLUTTER twins have a mirror too, and it is bigger than any pair above

Everything above is about tom_d4rt ↔ tom_d4rt_ast. The two Flutter bridge packages carry their own, and it was the last one with no mechanism at all: lib/src/d4rt_runtime_registrations.dart is ~200 KB of hand-written interface proxies, present in both twins, edited by hand in both.

It had already bitten. SCD138 hand-applied the same 21-class change to both copies; a mistake in either would have been caught by nothing.

Characterise before mechanising — and the raw diff will mislead you. The work that filed this recorded "327 differing lines" and proposed building a derivation tool. 327 is a TEXT diff: comments, wrapping, import order. Compared as CODE — full-line comments stripped and the two package layouts normalised, which is what check_mirrored_sources.dart does for the interpreter pairs, along with the mirror rename (SAstNode read as AstNode) and the imports that supply the two ASTs — the real figure was 42 lines in three groups:

grouplinesverdict
the import prologue9structural
const on nine proxy constructors18drift
AutomaticKeepAliveClientMixin support 15 missing feature on the AST line

Two of the three were repaired rather than recorded, which is the point of measuring first — a baseline that records removable drift is a baseline nobody reads:

  • The const difference was MEASURED rather than assumed: adding const to

the AST twin's nine constructors analyzes clean. Drift. - AutomaticKeepAliveClientMixin was absent from the AST twin entirely, while 28 corpus scripts use it and the mixin is bridged on both lines. A script mixing it in "compiled" and was structurally absent at runtime. Ported.

What remains is the import prologue, and only that: the source twin imports one barrel, the AST twin reaches into src/ for D4, BridgedInstance, InterpreterVisitor, D4InterpretedProxy and RuntimeType, because package:tom_d4rt_ast/runtime.dart does not export them. That is a difference between the two PACKAGES' surfaces, not a copy that drifted — so a derivation tool would have to special-case it anyway, and a comparison that skips the prologue says the same thing without a generator to maintain.

tom_d4rt_flutter_ast/test/sce165_runtime_registrations_mirror_test.dart compares the two copies line for line below their prologues and runs from test/run_guard_tests.sh. Its sibling sce164_proxy_registry_parity_test.dart holds the narrower property that both twins register the same interface proxies and that every proxy class exposes its interpreted instance.

The twins' other shared files, for contrast. The four user bridges ARE derivable — they differ by one import line — and have a generator (sync_shared_user_bridges.dart) with a --check mode and a pre-commit refusal. The script corpus is not duplicated at all: both twins execute the one set that lives in tom_d4rt_flutter_ast. So the twins now have three mechanisms for three shapes of sharing, and the shape decides which: derive when one side is a function of the other, compare when neither is, share when the artefact can simply live once.

The test infrastructure is compared, not derived. Besides the 41 corpus drivers, whose assertions and skips are each twin's own, the twins carry 22 shared files in test/: runner scripts, the idle watchdog, the attribution and companion-app helpers, a handful of in-process guards, send_test_runner.dart, the READMEs. Measured as code (comments and directives stripped, whitespace collapsed), 16 are identical once four twin parameters are substituted:

parameterAST twinsource twin
companion app tom_d4rt_flutter_ast_app tom_d4rt_flutter_test_app
packages tom_d4rt_flutter_ast, tom_d4rt_ast tom_d4rt_flutter, tom_d4rt
HTTP port42474248
runner classes D4rtRunner, FlutterD4rt D4rt, SourceFlutterD4rt

A generator would overwrite each twin's comments, which describe its own variant and are right to differ, so none was built. The remaining six diverge by design: the READMEs are prose for their own readers, run_guard_tests.sh runs the pair's repo-wide guards only on the AST side, send_test_runner.dart regenerates and bundles on the AST side only, suspicious_rewrite_test.dart holds each twin's own verdicts, and scd133 / scd195 compile their probe through AstBundler first on the AST line.

tom_d4rt_flutter_ast/test/sce170_twin_test_infrastructure_test.dart holds all of it and runs from test/run_guard_tests.sh. It fails when a shared file is in neither list, when a derivable pair differs in code, when a divergent pair has converged, when a twin parameter is needed by no file, and when a derivable copy carries the OTHER twin's parameter.

That last check exists because identity cannot see it: a value copied verbatim from the other twin compares EQUAL. It is the defect the guard found on its first run. The AST twin's three profiler scripts read TOM_D4RT_TEST_TEST_PORT, the source twin's port variable, while the AST app binds TOM_D4RT_AST_TEST_PORT. Moving the AST app off a wedged port, which is what that variable is for, left the profiler probing the old one.

A divergence the mirror rule does NOT cover: what the warm parent holds

The mirror rule is about SOURCE. The two trees can hold identical code and still answer differently, because what a script can resolve depends on what is in the environment chain — and the two lines put different things there.

Measured 2026-09-22 (SCE151) against the same 18 bridge files on both sides, counting the bridged names reachable from the environment a script runs in:

script imports tom_d4rt_flutter (source) tom_d4rt_flutter_ast
nothing — enums0213
nothing — classes 84 2414
package:flutter/material.dart — enums151213
package:flutter/material.dart — classes18322426

It is not enum-specific, which is how it was first written down. D4rtRunner._registerDefsInto dumps the whole registry — enums, classes, function typedefs, library functions, variables, getters and setters — into the AST line's warm parent. The classes diverge harder than the enums do. On the AST line the import barely moves the numbers (2414 → 2426) because the baseline already holds everything; on the source line the import is what populates it (84 → 1832).

Do not "tighten the AST line" on the strength of the table above. The experiment was run: with the enum and class dumps disabled, the AST twin's base corpus goes from 926 / 1 / 1 to 851 / 1 / 25. Twenty-four scripts depend on it.

And they do not depend on it the way the table suggests. The failures are not scripts using an unimported name — they are

Undefined property or method 'views' on PlatformDispatcher. No bridge claims this type ...

for PlatformDispatcher, SemanticsFlag, DeviceGestureSettings, SpellOutStringAttribute and others: NATIVE VALUES returned from a bridged call, whose types no import ever named. Both twins resolve a native object through the same env-chain _bridgedClassesLookupByType walk — the code really is mirrored — so the baseline is not laxity about imports, it is the AST line's mechanism for bridging a transitively-reached type at all. The source line reaches those types through what material.dart's import registers; the AST line's per-import registration is narrower, and the baseline covers the gap.

So the divergence stands as a deliberate AST-line allowance, and the thing to carry away is which question it answers: "why does an unimported name resolve here and not there" has the same cause as "why can this line touch a type nobody imported", and only the second is load-bearing. Making the AST import path supply what the baseline supplies is a campaign with a 24-script blast radius, not a fix — measure it as one if it is ever attempted.
