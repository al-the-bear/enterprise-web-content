Appendix A1 · Four-state authorization deep dive

Appendix A1 of the Tom Core advanced-sample user guide — see the guide index.

Part 07 introduced the four-state model and named its moving parts. This appendix is the mechanical companion: the state lattice and its narrow/widen algebra, the exact five-layer resolution in TomField.resolveEffectiveAuth(), the closed-safe default as it actually falls out of the code, the full grant-matrix → per-field stamp → field data path, and a worked resolution trace of one field for each of the four roles. Where doc 07 says what, this appendix says exactly how, line by line.

The four states as a lattice

TomAuthState is a four-value enum declared most-to-least restrictive, and that declaration order is the algebra (the TomAuthState enum in tom_core_kernel/lib/src/tombase/security/tom_authorization.dart): 

none  <  disabled  <  read  <  full
 0        1            2       3      ← enum index

The ordering is load-bearing because two operations are defined directly on the index:

  • TomAuthState.narrow(other) → the more restrictive (lower index) of

the two. - TomAuthState.widen(other) → the less restrictive (higher index) of the two.

Three derived predicates read the same lattice: isVisible (!= none), showsContent (read || full), isInteractive (== full). So a field maps to a control by its resolved state alone — none collapses it, disabled greys it, read shows it read-only, full makes it editable — with no separate visibility flag to keep in sync.

Two facts follow from the lattice that the rest of the system relies on:

1. Composition by narrow can only ever lower a field's reach. Every resolution layer below combines by narrow, so a later layer is strictly a restriction — it can hide or read-only a field but never grant it. 2. The bottom of the lattice is the safe default. Because none is index 0, "we don't know" and "denied" are the same value, and any narrow against an unknown collapses to it. That is why the closed-safe default below is none rather than a separate sentinel.

Resolution order: the five layers

A field's effective state is computed by TomField.resolveEffectiveAuth() (tom_flutter_ui/lib/src/forms/tom_form.dart). The doc-comment and the CRITICAL note there make the contract explicit: all layers are evaluated; skipping one (group auth especially) is a severe bug. All five layers below live in that one method; each takes the running state and narrows it:

#LayerExpressionWhat it contributes
1 Resource-based TomAuthorization.resolveAuth(basePath) the field's own grade, keyed on its basePath
2 Group auth tomGroup!.applyMode(state) a TomAuthorizationGroup's collective ceiling/floor (AuthGroupMode)
3 Form narrow state.narrow(resolveAuth(formPath)) the form node's grade narrows every field (always narrow)
4 Per-field authorizer authorizer!.effectiveAuth(state) an explicit TomAuthorizer (e.g. TomAuthorizer.fixed)
5 UI-state controller uiStateController!.apply(state) a build-time TomUIStateController callback

Layer 1 seeds state; layers 2–5 each apply only if their hook is present, and each can only restrict. The sample does install a global adapter — AppResourceRoleAdapter, at login — but that adapter gates only <type>:<id> resource keys, so for a dotted basePath layer 1 still returns the permissive full. The grade a gradable item field renders at therefore comes from layer 4: the item detail screen stamps each gradable field with field.authorizer = TomAuthorizer.fixed(resourceState.narrow(grades[field.basePath] ?? TomAuthState.none)) (_ItemDetailScreenState._resolveForm in advanced_app_client/lib/screens/item_detail_screen.dart), where resourceState is the item's own resource-level ceiling — TomAuthorization.resolveAuth('item:<id>'), resolved through that same adapter. So for a graded item field the effective state is layer1(full).narrow(layer3(full)).narrow(layer4), which reduces to the layer-4 fixed grade: the server-resolved field grade, already capped by the resource ceiling. The admin user/role forms also add a layer 4 TomAuthorizer.fixed, there for create-vs-edit shaping rather than a server matrix (see doc 07).

> The skeleton called this "layers 1–4"; the live resolveEffectiveAuth has > five — the build-time TomUIStateController is the fifth. The sample's > forms exercise layers 3 and 4 (layer 1 stays permissive for every dotted field > path, since the installed adapter gates only resource keys); layers 2 and 5 are > framework capability the sample does not need.

Why basePath is the key

Layer 1 keys on basePath, and basePath is derived structurally when the field is constructed (the TomField constructor in tom_form.dart): scope = form!.basePath, then basePath = scope.isNotEmpty ? '$scope.$tomId' : tomId. Under TomScope.withScope('todo', …) with formId: 'item', the title field self-addresses as todo.item.title — byte-identical to the todo.item.title key the server grades. One scope alignment makes the field's authorization key equal the wire grade key with no translation (this is doc 07's headline; the full basePath convention is A2).

The closed-safe default, as it falls out of the code

"Ungraded ⇒ hidden" is enforced at three independent points, each defaulting to none, so no single omission can leak an editable control:

1. Ungranted resource key. The installed AppResourceRoleAdapter gates every <type>:<id> key through the framework registry; a key the principal holds no grant on resolves to none, so TomAuthorization.resolveAuth('item:<id>') returns none and the whole item's fields collapse. The kernel codec agrees — TomAuthStateCodec.fromStored(null) and fromStored('bogus') both return none (tom_core_server/test/graded_authorization_test.dart). 2. Missing role. The installed AppResourceRoleAdapter resolves an ungranted <type>:<id> resource key to none (app_resource_role_adapter.dart), and a roleName with no matching ProjectRole also yields none. So the item's resource ceiling is none whenever the principal holds no role on it — the item's fields collapse. 3. Client per-field narrow. The item screen stamps each gradable field with TomAuthorizer.fixed(resourceState.narrow(projectRoleFieldGrades[role][field.basePath] ?? TomAuthState.none)) (_ItemDetailScreenState._resolveForm in advanced_app_client/lib/screens/item_detail_screen.dart): a field with no grade in the shared row falls to none, and the narrow keeps it at or below the resource ceiling.

The same value at all three layers is what makes the lattice's "unknown = denied" property hold end-to-end.

The top of this path is server-folded resource access. Resource access (AppReadService.resourceRoles, reusing ResourceRoleResolver) answers "which objects may this principal touch, and as what role?" by folding the principal's C-5 ownership grants and C-6 share-mode delegations through the framework TomDelegationResolver into a flat resourceKey → roleName map, expanding each grant down its containment subtree item → list → project → workspace: an owner grant on the workspace surfaces on every contained item, else the strongest covering share wins (ProjectRole is declared owner, editor, commenter, viewer — most-to-least privileged, so the lowest index is strongest, in advanced_todo_domain/lib/src/enums.dart), else the key is absent (no access → closed/safe 404). That flat map is the only authorization payload the app read ships; the per-role field grades themselves live in the SHARED DOMAIN (projectRoleFieldGrades), so the client narrows the resource ceiling by them locally — no GradedFieldDto on the read. The server-side FieldGradeResolver (over RepositoryGrantStore, the framework grant/delegation stores plus RepositoryResourceContainmentStore — live; InMemory* seeded for tests) still resolves the per-field matrix, but only to enforce writes (below), which is what lets the socket-free suites reproduce the exact matrix on both sides.

Why a resource adapter plus a per-field narrow, and why the registry stays load-bearing

The installed AppResourceRoleAdapter gates only <type>:<id> resource keys (those containing :); any dotted path (login, board, dialogs, and the gradable todo.item.<field> keys alike) stays permissive (full) — the framework's no-adapter default for everything except the item's resource ceiling. The grade a gradable field renders at is the item's resource ceiling — layer 1 (TomAuthorization.resolveAuth(ResourceRoleKeys.item(id)), resolved through the registry via the adapter) — narrowed by the shared projectRoleFieldGrades[role] row and stamped at layer 4 by the per-field TomAuthorizer.fixed the item screen sets (_ItemDetailScreenState._resolveForm in advanced_app_client/lib/screens/item_detail_screen.dart). Two properties fall out:

PathResolves toWhy
a gradable leaf, principal holds a role resourceState.narrow(grade) (layer 4) TomAuthorizer.fixed(resourceState.narrow(grades[basePath]))
a gradable leaf, no role on the item none resource ceiling is none (adapter), and the narrow can only restrict — closed-safe
a gradable leaf absent from the shared row none (layer 4) grades[basePath] ?? TomAuthState.none — closed-safe
any non-gradable dotted field (login, board, dialogs) full the adapter leaves dotted paths permissive; no layer-4 stamp

This keeps the framework registry load-bearing: a principal with no role on the item resolves the resource ceiling to none, so every field collapses closed-safe without any per-field payload. Because every role's field grades sit at or below its resource ceiling, the narrow reproduces the field-grade matrix exactly. The alternative — shipping the per-field matrix over the wire and stamping it directly — is the obvious design and costs more than it looks: it makes the read payload grow with the matrix and puts a second authority on the client. Folding the read down to a flat resourceRoles map and narrowing the registry-resolved ceiling by the shared grades reaches the same closed-safe outcomes with no read-time matrix at all.

Worked role matrix

Take one field — assigneeId (todo.item.assigneeId) — and trace its effective state for each role, using the seeded field-grade rows (doc 07) and the resolution layers above. The item field carries one per-field authorizer (layer 4) and no group or controller; the dotted todo.item.assigneeId path stays at the adapter's permissive default at layers 1 and 3 (only the item:<id> resource key is gated). The per-field authorizer holds resourceState.narrow(grade), where resourceState is the item's ceiling and grade is projectRoleFieldGrades[role][todo.item.assigneeId]:

Role field grade todo.item.assigneeId resourceState (ceiling) resourceState.narrow(grade) renders as
owner full full full editable
editor read full read read-only
commenter read read read read-only
viewer read read read read-only

The editor row is the instructive one: it is the only row here where the narrow does something. An editor's resource-level ceiling is full — the registry collapses owner and editor — and it is the per-field grade alone that stops them reassigning the item. For commenter and viewer the ceiling already equals the grade, so the narrow is an identity; for the editor the two disagree, and the composition is what resolves them. Two other fields tell the rest of the story:

  • estimate is full / read / none / none for owner / editor / commenter /

viewer — the editor reads it, both commenter and viewer lose it entirely. This is what TC-30-02/04 assert (Part 12). - status is full / full / read / disabled — the matrix's only disabled cell, and the only place the fourth state is reachable from the seed. A viewer gets the status control rendered and inert, with no value in it: disabled is masked (showsContent is false), which is a stronger statement than read-and-greyed and is why the state exists separately at all.

Crucially the same rendering is re-checked server-side on write: AppWriteService._enforceFieldWrites requires every field a payload changes to be graded full for the caller's role (Part 10). The client's per-field stamps govern what the UI shows; the server independently governs what it accepts — a tampered client that renders assigneeId editable for a commenter still has its write rejected.
