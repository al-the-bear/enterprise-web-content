Testing & cross-tier integration

Part 12 of the Tom Core advanced-sample user guide — see the guide index.

Part 10 showed the secured servers and Part 11 the two clients that consume them. This part is how the whole sample proves itself: a layered test strategy that keeps the everyday suites fast and socket-free, plus one scripted run that boots the real stack end-to-end. The two ideas the guide rests on — server-delivered texts and authorization-driven field grades — are not described and trusted here, they are asserted: a sentinel suffix proves a label came from the server bundle, and a four-role matrix proves the same widget renders differently per principal. Part 13 then follows a single feature — file transfer — through every layer this part tests.

Test strategy across the eight packages

Each package carries its own suite, written against the layer it owns and against the seam directly below it — never against a live socket:

PackageWhat its suite proves
advanced_todo_domain the reflected entities round-trip and the enums/resource-key constants hold
advanced_todo_contracts the wire DTOs serialize/deserialize and the typed service interfaces match the registry
advanced_client_core the Flutter-free client core: auth/token storage, the shared transport, error normalisation (+ the live cross-tier, login and file-transfer scenarios, below)
advanced_auth_server the JWT issuer, the role gate, and the admin grant/assignment API against an in-process datasource
advanced_app_server the secured task API: the ownership-or-share resolver, the four-state field-grade resolver, the write enforcement, and the per-row column grade + file-column declarations behind the file slots
advanced_app_client the end-user widgets bound to the in-memory backend fake — the four-role render matrix, the sentinel render proof, the graded attachment field, and the two-pass second-factor sign-in
advanced_authadmin_client the admin console widgets against the in-memory admin fake — CRUD drafts, the login (credentials, the admin probe, and the second factor), the grant-matrix editor
advanced_ops_server the back-office jobs against stand-in stores — the retention scan, digest composition in two languages and its redelivery, the export projection, every declared schedule, and min(user, server) as a pair of runs; plus a live suite reading the audit trail and the exported bytes back out of app_db ( Part 14 )

The discipline that makes this work is the injected backend seam (Part 11): every client screen is written against an interface (AppBackend / AdminBackend), and the widget suites bind the seeded in-memory implementation. Because the fake mirrors the server's ownership + four-state model in process, the widget tests are deterministic by construction and never open a socket. The only place the real stack is exercised is advanced_client_core's live suites, each of which skips itself when the servers are unreachable so a plain unit run stays green.

Flutter tests need no concurrency flag

Run the client suites with a bare flutter test. It runs several suites at once by default — max(1, numberOfProcessors ~/ 2) — and these suites are safe that way.

The process-global state the tests install cannot leak between suites, because flutter test gives every suite file its own flutter_tester process: the TomTextResourceProvider bundle, the TomAuthorization adapter and the TomBearerAuthentication token store are per-process, so no two files can see each other's. Within a file the tests do share one process, which is why each widget test still installs its bundle/adapter in setUp and clears it in tearDown (TomAuthorization.reset) — but package:test never runs two tests from one file at the same time, so that discipline is about test order and is unaffected by how many suites run in parallel.

Nor is there anything outside the process to contend for. Every widget suite runs against the injected in-memory backend: no socket, no file, no database. The only suites that reach the real stack are advanced_client_core's live ones, and run_cross_tier_integration.sh invokes dart test one file per call, so those are serial by construction rather than by flag.

Two mechanisms are therefore deliberately absent, both settled by measurement rather than by argument:

  • No -j 1 in any recipe. There is nothing for it to protect, and it costs

roughly half the throughput. - No dart_test.yaml in the Flutter packages. Not because the file would be ignored — flutter test does honour its concurrency: key, and an explicit --concurrency=N still overrides it — but because there is no suite here whose concurrency needs pinning. The mechanism is real and stays available for a suite that ever acquires a shared external resource. tom_core_server/dart_test.yaml is the case that has one: its DB-backed suites share a single MariaDB schema, and it pins concurrency: 1 for that reason.

The sentinel-[srv] render proof

The guide's first headline rule is that UI texts are not hardcoded — they come from a server-delivered resource bundle keyed by basePath (Part 08). The render proof makes that falsifiable: a test installs a bundle whose every value carries a distinctive [srv] suffix, pumps the widget, and asserts the suffixed strings appear. A hardcoded label would render its own text and the find.textContaining('… [srv]') expectation would fail — so a green test is the proof the label resolved through the bundle.

It is applied at both the login and the bound-form layer, in both clients:

  • advanced_app_client/test/form_label_resolution_test.dart installs

'login.username.label': 'Username [srv]' (and the password/hint keys), pumps the login screen, and asserts the sentinels render (TC-10-01); a second group does the same for all seven todo.item.* field labels (TC-10-02). - advanced_app_client/test/item_detail_screen_test.dart folds the same proof into the bound detail form as TC-30-05: the owner opens the editor against a [srv]-suffixed field bundle and every field label resolves from it. - The admin console mirrors it — admin_login_form_test.dart's labels resolve from the adminLogin.* login bundle, not overrides case for the adminLogin.* keys, and advanced_authadmin_client/test/form_label_resolution_test.dart for the user/role/group draft forms (TC-10-U, TC-10-R, TC-10-G).

The four-role render matrix

The guide's second headline rule is that UI authorization is driven by the server's per-field grades, not by client policy (Part 07). The matrix proof is the heart of the sample: advanced_app_client/test/item_detail_screen_test.dart pushes the same ItemDetailScreen (the same bound TodoItemForm) four times, each as a different principal, and asserts the rendering differs purely because the session installed a different field matrix on the TomAuthorization singleton — the form holds no authorization state of its own (the regression guard for the per-field-authorizer removal):

TestPrincipal (role)What the matrix renders
TC-30-01 alice (owner) every gradable field is full — a complete editor with a Save
TC-30-02 val (viewer, shared in) read-only fields, a disabled status control, estimate hidden ( none → field collapses), no Save
TC-30-03 bob (editor) can save, but assigneeId is read ; editing the title and saving persists the title while the assignee stays put — the write-back carries only the editable fields
TC-30-04 val (commenter) both priority and estimate graded none (hidden), the rest read, no Save — distinct from the viewer matrix where priority stays visible

TC-30-03 is the one that also proves server-side enforcement matters: the client only sends the fields its grade renders editable, so the read-only assigneeId is never in the write-back — and the server's _enforceFieldWrites (Part 10) is the backstop for a client that ignores its grade.

The cross-tier integration runner

Every *_integration_test.dart in advanced_client_core/test/ runs against the real stack — five suites, all driven by the one script advanced_client_core/tool/run_cross_tier_integration.sh:

SuiteWhat only a live stack can show
cross_tier_integration_test.dart (TC-37-01…10) the two servers' authorization agreeing across the database boundary — including at the file endpoint and on an item's child collections
auth_client_integration_test.dart (TC-22-11…13) a real login, including the two-pass 2FA exchange and a mid-run enrolment
file_transfer_integration_test.dart (TC-FT-01…05) bytes moving through both blob stores, the closed/anonymous refusals, and a read-only column grade
app_api_client_integration_test.dart (TC-24-14) that the typed app client's base URI, routes and DTO decoding still agree with advanced_app_server
admin_api_client_integration_test.dart ( TC-25-14 , TC-25-15 ) the same for the typed admin client against the auth server's /admin/* , plus that a malformed id really is a 400 and not a 500

The last two are deliberately narrow. The three above them reach the clients only through a scenario, so when one breaks it cannot say whether the wire contract or the authorization logic stopped holding; these two answer that in one line of output.

TC-25-15 is the exception to that narrowness, and it is here rather than in a unit suite for a reason the others do not share. The status it asserts comes from a per-endpoint error handler declared on the @TomApiImplementation, so it holds only if that declaration survives reflection generation and the pipeline actually consults it — neither of which a socket-free test can show. Its unit counterpart proves the handler function returns a 400; only the live run proves the server calls it. A suite no script runs decays silently, which is why they run here rather than being left to a manual invocation.

The runner is one scripted command for the Phase-7 "scenario passes end-to-end" bar:

1. Fresh databases. docker compose down -v drops the old volume so the initdb seed re-applies, then brings up advanced-auth-db (:3307) and advanced-app-db (:3308) and waits for each container's docker health to report healthy. 2. Resolve dependencies once for the auth server, app server, and client core. 3. Start the servers in order — the auth server first (it mints tokens and owns the grant matrix), then the app server (it reads grants from auth_db and verifies the auth tokens). Each is started with exec dart run so the recorded PID is the server itself (cleanup actually stops it instead of orphaning a port-holding child). The waits are generous (~6 min) because dart run cold-compiles the reflection-bootstrapping server graph on first boot; a .dill snapshot is not viable (detached snapshots fail to initialise the generated reflection). 4. Run the three suites against the live stack and tear everything down via an EXIT trap that dumps the server logs on any non-zero exit.

The cross-tier scenario itself walks the three cross-tier authorization mechanisms:

  • An admin grant edit reaches the end-user's field matrix. The admin edits

the viewer role's todo.item.title grant through the auth server's PUT /admin/grants; a seeded viewer then re-reads the item's field states from the app server and sees the new grade — proving the app server resolves grades from the very rows the auth server's admin API writes (the app server's main datasource points at auth_db). The test posts the complete intended viewer row (only title flipped) and restores it in finally, so it leaves auth_db exactly as seeded and is re-runnable. - A share reveals a project to a second user. alice creates a project, bob cannot list it, alice shares it as editor, and bob then lists it — the ownership-or-share resolver in action over the live wire. - *An admin grant edit reaches the file endpoint (TC-37-09*). The same PUT /admin/grants narrows owner's grade on the item's attachment column from full to read; alice, who owns the item, keeps the download and is refused the upload; restoring the cell gives it back. The beat proves the grade governing bytes is the grant row an administrator already edits — not a file-specific permission model — and it is why file transfer belongs in this sample rather than in a framework example (Part 13).

The file-transfer suite is the one that cannot be faked at all: it asserts that a byte stream posted by a client lands in a blob store, that the row's key column is updated, and that a later GET hands the same bytes back — six layers agreeing at once (client → endpoint → repository → column grade → blob store → database). It also makes the three negative claims the feature exists to guarantee, one per refusal layer: a column that never said exposed is not addressable (asserted beside a reachable neighbour on the same row, by the same principal, so a 404 cannot be mistaken for an unreachable row); an unauthenticated caller is refused by the endpoint's own gate on both servers; and a principal whose column grade is read is served the complete bytes yet refused both the replace and the delete (TC-FT-05). Each test restores the slot it used, so the suite is re-runnable against the same databases.

Because the servers' host ports may be held by an unrelated service, the runner guards 8080/8081 with a preflight (assert_ports_free) and refuses to start rather than racing a stale process. When the servers are unreachable the tests call markTestSkipped rather than failing; under the runner the servers are guaranteed up, so the runner treats "All tests skipped" as a failure — only a real PASS from each of the three suites exits 0.

The global green gate

A change is done only when all three hold together:

1. dart analyze is clean in every package (zero errors, zero warnings). 2. Every suite is green under a plain dart test / flutter test. 3. Both runners exit 0 with "All tests passed!" against freshly booted infrastructure — the cross-tier runner over the whole stack, and advanced_ops_server/tool/run_ops_integration.sh over the databases alone.

Reaching this gate has so far surfaced and fixed ten real tom_core_server bugs: zone principal resolution, the nullable surrogate-key read, the MariaDB bool→1/0 bind, query-string parameter binding, pipeline error logging, a streamed download that lost its principal (a shelf response body is lazy, so the read ran outside the request zone), a file endpoint that declared no access policy at all — which, given that the framework's protection default is open, made every exposed file column world-readable — and then three DateTime defects the ops server reached first: a UTC timestamp MariaDB refused to bind, a timestamp column the query compiler declared untypeable, and an audit before-image that could not be JSON-encoded and so failed the mutation rather than the record.

The suites are not decoration; they were the instrument that found framework defects, including two security-relevant ones. The DateTime cluster is the sharper lesson: those three had survived the entire prior suite because no sample entity had ever happened to query, audit or bind a timestamp. A whole type's worth of behaviour was untested behind an accident of the domain model, and only a new kind of sample — one with a retention window and an audited purge — could reach it.
