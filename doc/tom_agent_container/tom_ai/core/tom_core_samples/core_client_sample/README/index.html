Tom Core — Client Sample (Todo)

A small but complete Flutter application built on the Tom Core client stack: tom_core_kernel for the observable/reflection/authorization model, tom_core_flutter for the client runtime, and tom_flutter_ui for bound forms. It is the consumer counterpart to core_server_sample — it shares the same domain (todo_domain) and the same four-state authorization matrix, so the two tiers tell one consistent story.

Where the sibling core_flutter_form_showcase is a feature tour — one cell per API — this sample is the opposite: a single, ordinary app (sign in, browse a list, edit a record) that wires those features together the way a real screen does. The interesting parts are not the widgets; they are the seams: how a form binds a reflected entity, how a role's authorization matrix turns into per-field render states, and how the backend is kept behind one interface so the app runs identically offline or against the live server.

> TL;DR — Run flutter run. Sign in as alice, bob or val (any > non-empty password). Browse the todo list, tap an item to edit it, and notice > how the same editor screen renders differently depending on who you are.

1. What you are looking at

The app has three screens and one job: edit todos under role-based field authorization.

ScreenFileTeaches
Login lib/screens/login_screen.dart A bound TomForm<LoginCredentials> driving an authentication call
List lib/screens/todo_lists_screen.dart Listing entities, navigation, the live-refresh action, logout
Detail lib/screens/todo_detail_screen.dart A bound TomForm<TodoItem> whose fields are gated by the session's TomAuthState matrix

The three demo accounts map onto the three roles the matrix grades:

AccountRoleWhat they can do
aliceownerEdit every field
bob member Cannot see priority; cannot change the assignee
val viewer Every graded field read-only; the done toggle renders disabled

That matrix is not invented here — it is the client-side twin of the grants core_server_sample seeds into tom_resource_grant via its [001]-todo_authz_grants.sql migration. Keeping the two in lock-step is what makes the four states render identically whether the app runs offline or talks to the server.

2. Running the sample

flutter create --empty --platforms=macos .   # once per machine; or linux, windows
flutter run

The sample ships no platform folders, and Flutter will not run a project on a platform it has no folder for — so the first run on a machine starts with the flutter create line, once. --empty matters: without it the command also writes a counter-app test/widget_test.dart pumping a MyApp this package does not have, and the suite stops compiling. It leaves lib/, pubspec.yaml and this README alone, and what it adds is gitignored. Web is not a target: the live client is built on dart:io's HttpClient.

On macOS the app is sandboxed and the generated macos/Runner/DebugProfile.entitlements allows incoming connections only; the offline default needs nothing more, but to reach a live server add <key>com.apple.security.network.client</key><true/> to that file first.

The app starts on the login screen against the in-memory backend (no server required). To exercise the live read path against a running core_server_sample: 

# 1. start the server sample (in its own folder)
dart run bin/server_start.dart        # serves http://localhost:8080

# 2. run the client with the live URL wired in
flutter run --dart-define=LIVE_SERVER_URL=http://localhost:8080

With LIVE_SERVER_URL set, the list screen gains a cloud-download action that pulls todos straight from the server's GET /todos. Without it, that action is hidden and everything runs in memory.

4. The backend seam: one interface, two implementations

The app is written against an abstract TodoApi (lib/api/todo_api.dart), never a concrete backend: 

abstract class TodoApi {
  Future<LoginResult> login(String username, String password);
  Future<List<TodoItem>> listItems();
  Future<TodoItem> saveItem(TodoItem item);
  Future<void> deleteItem(String id);
  Future<Map<String, TomAuthState>> fieldStates(String role);
}

Two things implement (or partially implement) the read side of that contract:

  • InMemoryTodoApi — the default. A fully working, seeded backend: three

users, three todos, and the grant matrix copied verbatim from the server's migration. It powers the offline app and every widget test, so the tests never touch a socket. - LiveTodoReadClient — an honest thin HTTP client over the server's three read-only endpoints (GET /health, GET /todos, GET /todos/field-states). Its JSON→entity mapping is factored into the pure functions parseTodos / parseFieldStates / parseAuthState, which are unit-tested against captured server responses.

Why two, rather than one HTTP backend? Because core_server_sample today exposes a read-only surface — it has no login or write endpoints. Pretending it did (by throwing UnimplementedError from a half-written HTTP TodoApi) would be dishonest and untestable. Instead the writes and login run in memory, the live reads run over the wire, and the boundary between them is deliberate. Swap the backend in exactly one place — main.dart — and the whole app follows.

5. The mental model: forms bind reflected entities

A Tom form is not a bag of controllers. It is a TomForm<T extends TomClass> whose field member names match the bound entity's field names, so binding is a reflection round-trip rather than hand-written copy code: 

@tomReflector
class TodoItemForm extends TomForm<TodoItem> {
  late final title = TomFormStringInput('title', '', form: this, /* … */);
  late final done  = TomFormBoolSwitch('done', false, form: this, /* … */);
  // …priority, assigneeId, description — each id matches a TodoItem field.
}

form.bind(todoItem) reads the entity's values into the fields through kernel reflection; form.save() writes them back the same way. No field-by-field plumbing, and adding a field to the entity is a one-line change to the form. The price is that both the entity and the form must be in the reflected graph — see the next section.

Validators are resources, not per-field closures (G-UI-7)

A field's validators are declared by name in the resource bundle, not hand-coded as one-off closures. Each validated field carries a <basePath>.validators entry — a comma-separated spec — that TomField resolves through the DI-swappable TomValidatorRegistry (built-ins required/email/minLength/maxLength/pattern/min/max, plus any the app registers). The login fields take the pure resource path: 

// app_texts.dart
'login.username.validators': 'required',
'login.password.validators': 'required',

// login_form.dart — no `validators:` argument at all
late final username = TomFormStringInput('username', '', form: this);

TomField merges code-supplied and resource-declared validators, so a field can have both. TodoItemForm.title is the illustration: required is declared as a resource (the framework built-in, naturally a resource), while an app-specific "no leading/trailing whitespace" rule — orthogonal to any built-in — stays in code, which is exactly when a code validator is the right tool: 

// app_texts.dart
'todo.item.title.validators': 'required',

// todo_item_form.dart
late final title = TomFormStringInput('title', '', form: this,
    authorizer: _authFor('title'), validators: [_noSurroundingSpace]);
// effective validators = [_noSurroundingSpace] (code) + [required] (resource)

Validation messages are resources too (G-RES-1). A failed validator emits an error.<name> key (error.required, and the code rule's error.titleWhitespace) that resolves from the same bundle — scoped <basePath>.error.<name> first, then global error.<name> — so no message string is ever hardcoded. test/ validator_resolution_test.dart (CCS-VAL-01…05) pins the resource-only path, the merge, and both resolved messages.

6. Bootstrap: reflection must come first

Three things happen in main.dart before runApp, in order:

void main() {
  initializeReflection();                                   // 1
  TomPlatformUtils.setCurrentPlatform(clientPlatformUtils); // 2
  TomTextResourceProvider.setAppResourceProvider(           // 3
    TomTextResourceProvider.from(appTexts),
  );
  runApp(TodoApp(session: AppSession(InMemoryTodoApi())));
}

1. Reflection. The forms bind reflected @tomReflector entities, so the field metadata must be registered before any form is constructed. 2. Platform. clientPlatformUtils (from tom_core_flutter) selects the Flutter platform implementation for kernel code that probes the runtime. 3. Resource provider. The appTexts bundle (lib/resources/app_texts.dart) is installed so every visible string — form-field labels/hints, screen copy, tooltips, errors, and enum display text — resolves through the singleton provider (G-RES-1). No widget carries hardcoded text.

Why one reflection seed for everything. The generated initializeReflection() assigns the reflection data (last writer wins), so exactly one seed's initializeReflection() may run per program. This app's seed (lib/reflection_seed.dart) is that one — and because the forms bind cross-package todo_domain entities (TodoItem, User) alongside the client-local LoginCredentials, the seed imports all of them so the generator emits one graph covering the lot. (todo_domain ships no seed of its own — a library carries none — so importing its barrel beside this seed is unambiguous.)

7. Four-state authorization, end to end

TomAuthState has four values, and each renders distinctly on a form field:

StateRender
fullFully interactive and editable
readShows its value but cannot be edited
disabledVisible but greyed out and non-interactive
noneHidden entirely — the field collapses to nothing

The flow is: role → matrix → per-field authorizer → render.

1. On login, AppSession.login calls api.fieldStates(role) and stores the resulting Map<String, TomAuthState> (keyed by the plain gradable-field resource keys — todo.item.title, todo.item.done, … — there is no *ResourceKeys catalogue class, G-RES-6). 2. The detail screen constructs the form inside the enclosing todo scope: TomScope.withScope(todoScopeId, () => TodoItemForm(session.fieldStates)). The form's own formId is the single segment item, and TomForm joins the two into the todo.item base path. A scope id must be one segment — the kernel refuses a dotted one, since 'todo.item' under no parent would render identically to the unrelated chain 'todo' → 'item', letting a scope named from data reach another scope's resources. 3. The form turns each entry into a TomAuthorizer.fixed(state) on the matching field: 

   // The field's own tomId composes both its label key and its grant key, from
   // the one key constant — so the two can never diverge. And that constant is
   // itself joined from the same two segments the framework joins
   // (`'$todoScopeId.$todoItemFormId'`), so it cannot drift from the basePath
   // the fields actually carry.
   TomAuthorizer _authFor(String tomId) =>
       TomAuthorizer.fixed(fieldStates['$todoItemKey.$tomId'] ?? TomAuthState.none);

   late final priority = TomFormStringDropdown(
     'priority', TodoPriority.medium.name,
     form: this, source: _prioritySource,
     authorizer: _authFor('priority'),
   );

4. tom_flutter_ui resolves the authorizer at build time and renders the field accordingly.

The payoff is in todo_detail_screen.dart: the same screen, with no conditionals, shows owner a full editor, hides priority from member (because their grant is none), and gives viewer read-only graded fields with a disabled done toggle. A graded field absent from the matrix degrades to none — the closed-safe default, matching the server's resolver — so an unconfigured grade hides the field rather than leaking an editable control.

Only fields that ask are graded. title, done, priority and assigneeId carry an authorizer that reads the matrix; description is declared without one, so the matrix never reaches it and it renders editable for every role, viewer included. That is deliberate — it is the sample's one ungraded field, the contrast that makes the graded ones visible — and it is pinned both ways: CCS-CRUD-07 renders it editable for the viewer, and CCS-FORM-05 shows an empty matrix hiding every graded field but not this one.

8. The login flow

LoginScreen owns a LoginForm bound to a fresh LoginCredentials. On submit: 

if (!await _form.save()) return;   // validation failed; fields show errors
await session.login(
  _credentials.username.get(),
  _credentials.password.get(),
);

save() writes the typed form fields back into the bound credentials through the reflection round-trip, then the values are handed to the session. A rejected login throws a TodoApiException, which the screen catches and shows inline without leaving the page. A successful login flips AppSession.isLoggedIn, and the app shell's ListenableBuilder swaps in the list screen.

9. The list and detail screens

TodoListsScreen loads items from session.api.listItems(), shows the role badge and logout, and opens the detail screen on tap (or via the + FAB for a new item). When it returns from a save it reloads.

TodoDetailScreen is where the authorization model is visible. It builds the gated TodoItemForm, renders the field widgets (_form.title.widget, …), and on Save calls _form.save() then session.api.saveItem(item). Because the form is constructed with the session's matrix, the screen needs no role logic of its own — the four states do the work.

Notifications and navigation: Tom presenter + Tom route (G-UI-1). Two touchpoints on TodoListsScreen go through Tom primitives rather than the raw Flutter mechanisms. The snackbar is shown with TomMessenger.showSnackBar(context, TomSnackBar(...)): TomMessenger is tom_flutter_ui's Tom-owned presenter, wrapping ScaffoldMessenger the same way the Tom widgets wrap their Flutter counterparts. The detail screen is opened with Navigator.of(context).push(TomPageRoute(...)): TomPageRoute captures the active TomScope at push time and re-enters it around the pushed screen's builder, so the screen constructs in the pushing scope rather than the Navigator's zone — closing the scope-propagation gap G-UI-6 warns about (a form's scope "is usually a Flutter route").

10. The live read path

LiveTodoReadClient is a deliberately small dart:io HttpClient over the server's read endpoints. The networking is trivial; the value is in keeping the mapping pure: 

List<TodoItem> parseTodos(List<Object?> body) { … }
Map<String, Map<String, TomAuthState>> parseFieldStates(Map<String, dynamic> body) { … }
TomAuthState parseAuthState(String? token) =>
    TodoFieldMatrixDto.parseState(token);

The bodies are the reflection-first wire DTOs declared in todo_domain (G-DTO): /todos is a JSON array of TodoItemDto, /todos/field-states a TodoFieldMatrixDto. Each parser deserializes through the kernel reflection path (dtoFromJson) and then projects into the observable form entity, so the client never hand-parses a field name the server chose — and an unrecognised grade token degrades to TomAuthState.none through the DTO's own closed-safe parseState.

Those functions are unit-tested against captured JSON with no socket in the test. The transport is tested too, without core_server_sample: the suite binds an HttpServer on the loopback interface and drives the client through an injected HttpClient — isHealthy() true only for {"status":"ok"}, both fetches hitting their paths, a non-200 raising an HttpException that names the path and the status, and close() closing the injected client. The base URL may be given with or without a trailing slash; the constructor drops it. The list screen's cloud-download action calls fetchTodos() and swaps the view to live data behind a "showing live server data (read-only)" banner — an honest demonstration of a real wire round-trip that never pretends the in-memory edits reach the server.

12. Reflection regeneration

reflection_seed.reflection.dart is generated and must not be hand-edited. Regenerate it only when a reflected signature changes (a form field added or renamed, or a bound entity's shape changes): 

./reflection_generation.sh

The script runs dart run tom_reflection_generator flag-free over lib/reflection_seed.dart (configured in build.yaml); the generator scans the current project only (framework default scan ., non-recursive). The generated file is large because reflecting a form necessarily reflects its field types — the same trade-off the verified tom_flutter_form_test accepts.

Being a Flutter GUI app, this sample has no headless example/ folder or run_all_examples.dart aggregator (those apply to pure-Dart samples like todo_domain and core_server_sample). The runnable entry point is the app itself — lib/main.dart — and this serial widget-test suite is its smoke test: it exercises every screen, form, and the four-state matrix end to end.

14. Deliberate limits and the full-stack successor

Two limits shape this sample, and both are teaching choices rather than unfinished work:

  • Login and writes are in-memory. core_server_sample exposes three GET

endpoints and nothing else, so there is no live login or persistence over the wire. The client models both with InMemoryTodoApi, behind TodoApi. - The live path is read-only. LiveTodoReadClient covers GET /health, GET /todos and GET /todos/field-states — a genuine wire round-trip, but a read.

Keeping them is what lets this pair stay small enough to read in one sitting. The secured, full-stack version is a separate series rather than a retrofit of this one: the Advanced Tom Core Full-Stack Sample — three servers, two databases and two Flutter clients, with live login, write endpoints, an authenticated HTTP client that presents and refreshes a bearer token, per-principal four-state field grading over the wire, and cross-user sharing. Its run_cross_tier_integration.sh drives that whole loop end to end.

What this sample gives you instead is the seam. The screens, forms, session and authorization model are written against TodoApi, not against a transport, so a live backend slots in at the single main.dart line shown in §4 — which is precisely the shape the advanced suite builds out.
