The two Flutter clients

Part 11 of the Tom Core advanced-sample user guide — see the guide index.

Part 09 covered the bound forms and Part 10 the servers behind them. This part is the front of the house: the two Flutter apps that consume the wire. They are deliberately built the same way — a ChangeNotifier session, a state-driven shell, and a single injected backend seam that is either a socket-free in-memory fake or a live HTTP client. Seeing them side by side is the point: almost everything is shared, and the handful of genuine differences (the admin console's two-phase login, its grant-matrix editor) are exactly the new things this sample exists to teach.

The app client (end-user)

AdvancedTodoApp is a MaterialApp whose home is a ListenableBuilder over the session: signed out renders LoginScreen, signed in renders BoardScreen (AdvancedTodoApp.build, app_root.dart). The login↔board swap is therefore a pure function of session.isLoggedIn — no imperative Navigator.push to enter the app, and a dropped session routes back to login by the same mechanism.

The signed-in surface is three screens (detailed in Part 09): the board groups items into one column per TodoStatus; the item-detail editor builds a TodoItemForm against the item's resourceKey → TomAuthState matrix so each field renders at its grade (owner edits all, viewer is read-only, an ungranted field is hidden); and the share dialog grants another user a ProjectRole on the selected project — owner-only, a non-owner's share refused inline. The item editor's grades come from the session's fetched field-state matrix, stamped per field (below), so the four-state model is live over the wire, not faked in the widget.

The item editor also carries the item's attachment, and the board paperclips the items that have one. Both go through AppBackend.files — a TomFileTransferClient alongside the JSON one, backed live by AuthorizedFileTransferClient (it presents the bearer token on all five verbs and replays a transfer once after refreshing an expired token) and in tests by the same in-memory fake as the rest of the backend. The field is graded exactly like the form's fields, and for the same reason: shaping the affordance to what the server will answer, never deciding it (part 13).

The admin console

AdminConsoleApp mirrors the app shell exactly — a MaterialApp whose home is a ListenableBuilder swapping AdminLoginScreen for AdminShellScreen on session.isLoggedIn (AdminConsoleApp.build, admin_root.dart). The signed-in shell is a NavigationRail over an IndexedStack of five destinations:

  • Users / Roles / Groups — three thin StatelessWidgets each configuring the

generic AdminCrudScreen<T> (list / create / edit / delete), so the three CRUD flows share one list/dialog/confirm skeleton rather than triplicating it. Create and edit open a reflected editor bound to a client-local draft (UserDraft/RoleDraft/GroupDraft) that folds into the plain wire DTO on save. Stable keys (a user's username, a role's key) render read-only on edit. - Grants — the four-state grant-matrix editor (below). - Assignments — grants an account a role and/or a group membership via a single AssignmentRequest.

The console is domain-agnostic: it renders whatever role and resource keys the backend reports and never references the application's todo.item.* gradable keys or UserStatus enums — the same "the UI ships no policy" discipline the rest of the guide rests on.

Sessions

Both sessions are ChangeNotifiers that own the single injected backend and hold the principal + token pair; the shell rebuilds on every notifyListeners. They are near-identical (AppSession in app_session.dart, AdminSession in admin_session.dart), with two differences worth calling out.

Two-phase admin login. Because each /admin/* endpoint's contract declares TomRoleAccess(['admin']) (TomApiEndpoint.access) rather than gating login itself (Part 10), a signed-in non-admin authenticates fine but is refused the moment they touch admin data. AdminSession.login therefore authenticates and then probes an admin call (listUsers); only if the probe succeeds is the principal stored and the shell allowed to open. A non-admin is undone (_safeLogout) and the refusal — AdminBackendException keyed admin.access.forbidden — is surfaced on the login screen. AppSession.login has no such probe; any valid principal may use the board.

The second-factor phase. When the account owes a second factor, login returns a LoginResult whose token pair is interim — a challenge carrier that authorizes nothing. Both sessions therefore store nothing but a flag (awaitingSecondFactor) and leave isLoggedIn false, so the shell keeps showing the login screen while it switches to a code phase; submitSecondFactor(code) then runs the shared completion tail that a single-pass login runs. In the console that tail carries the admin probe, which is exactly why the probe lives there and not in login: it cannot run against an interim token, so an enrolled non-admin is refused one pass later rather than never. A refusal keyed non-retryable (AppBackendException.canRetrySecondFactor false) abandons the pending login, dropping the screen back to username/password. The mechanics of the two passes — and why the challenge and its attempt counter live inside the token — are part 06.

The guard seam. Every screen reaches the backend through session.guard, so "the session died" is handled in exactly one place: a backend failure keyed auth.session_expired (the live stack's post-refresh 401) or app.no_session/admin.no_session clears the principal before rethrowing, so the next frame is the login screen (AppSession.guard, AdminSession.guard).

The app session additionally holds the principal's resourceRoles map, fetched once at login (GET /resource-roles) and installed as the global TomAuthorization adapter via AppResourceRoleAdapter (app_session.dart, app_resource_role_adapter.dart); logout resets it. The item detail screen then grades each gradable field synchronously — resolving the item's resource ceiling through the registry (TomAuthorization.resolveAuth(ResourceRoleKeys.item(id))) and narrowing it by the shared projectRoleFieldGrades[role] row, stamped as a per-field TomAuthorizer.fixed(...) (_ItemDetailScreenState._resolveForm, item_detail_screen.dart). This is the bridge between "the principal holds viewer on this item" and "the widget renders its title read-only."

The in-memory vs live backend seam

Each client defines a transport-independent backend interface — AppBackend (app_backend.dart), AdminBackend — that every screen is written against, never a concrete class. That single seam is what lets the widget tests run socket-free:

  • InMemoryAppBackend / InMemoryAdminBackend — seeded fakes that mirror the

server's ownership + four-state model in process. They are the offline teaching default and the contract any live backend must honour, so the widget tests bind them and never touch a socket (deterministic by construction). - LiveAppBackend / LiveAdminBackend — thin adapters over advanced_client_core: an AuthClient (login + token storage) and an API client (AppApiClient / AdminApiClient) sharing one IoJsonTransport via AuthorizedHttp, so the bearer the login stores is the one every subsequent call presents (main.dart _installBackend). They normalise the client core's transport exceptions (AuthClientException / AppApiException / TomAuthExpiredException) into the single typed AppBackendException / AdminBackendException the screens catch, carrying the server's stable error key so a caller can branch without parsing the message.

Because both implementations honour the same interface and the same error keys, the screens — and the tests — behave identically against either.

Bootstrap

Both main.dart entrypoints run the same ordered bootstrap before the first frame (advanced_app_client/lib/main.dart, advanced_authadmin_client/lib/main.dart):

1. initializeReflection() (from the app's generated reflection_seed.dart) registers the reflected entities the backend constructs and the forms bind — the shared advanced_todo_domain entities plus the client-local credentials/drafts/forms, all captured by one seed. It is first because the in-memory backend seeds its reflected tree in its constructor. 2. setCurrentPlatform(clientPlatformUtils) registers the Flutter client platform so kernel runtime probes get the Flutter implementation. 3. (app client only) AdvancedClientConfig.registerDefault() registers the config bean the backend selector reads its server URLs from (G-ENV-2). There is no authorization-adapter install step: the item detail screen stamps each gradable field with its DB-resolved grade directly via TomAuthorizer.fixed (G-AUTHZ-1). 4. await session.loadLoginResources() fetches the public login bundle through the backend seam and installs it as the singleton TomTextResourceProvider, so the sign-in screen renders server-delivered chrome rather than a hardcoded string (Part 08). 5. runApp(...) over the session wrapping the chosen backend.

Backend selection is one place: _buildBackend() builds the live stack over a shared transport by default — this is the normal run mode, so an app started with no dart-defines targets the local servers, reading their URLs from the AdvancedClientConfig config bean (never String.fromEnvironment reads in main()). The seeded in-memory fake is a testing convenience, selected only by an explicit --dart-define=TEST_MODE=true; it is what the widget tests inject directly and how the offline walk-through runs. In-memory is never a default reached by forgetting a flag.

Login-then-full resource staging. The login bundle installed at startup is the pre-login chrome. On a successful login, the session pulls the authenticated full bundle and installs it merged over the current provider (full-bundle keys win), so every post-login screen resolves server texts while the login chrome stays valid; logout restores the captured pre-login provider exactly, so a re-login starts clean (_installFullResources and _clearSession, in both app_session.dart and admin_session.dart). The admin console's full bundle is the admin-gated console bundle, reachable only after the role probe passes — the two-phase login and the staged resources reinforce each other.

The share flow and the grant-matrix editor

These are the two cross-user, mutate-authorization flows the sample adds over the read-only predecessor — one per client.

Share (app client). The board's app-bar Share action opens a dialog that grants another user (entered as a user id, e.g. u-val, since the frozen seam has no "list users") a ProjectRole on the selected project. It submits a ShareRequest through session.guard; the server enforces owner-only, so a non-owner's share surfaces its error inline and keeps the dialog open. A granted share takes effect on the grantee's next read because the server's resolver reads shares immediately (Part 10).

Grant matrix (admin console). The Grants destination is a DataTable of projectRole (rows) × field resource key (columns), each cell the resolved TomAuthState for that pair. Tapping a cell cycles it none → disabled → read → full (wrapping), building an edited GrantMatrixDto locally; Save writes the whole matrix back through putGrants (PUT /admin/grants) and re-reads it, so the grid after a save shows exactly what the backend persisted. Save is offered only while the working copy differs from the loaded one. This is the administrator's half of the four-state model: the app client renders grades, the admin console edits them, and the server is the single source of truth between them.
