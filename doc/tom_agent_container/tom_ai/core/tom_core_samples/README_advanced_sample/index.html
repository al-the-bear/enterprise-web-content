Advanced Tom Core Full-Stack Sample — the whole secured system

> Attribution. The Tom Framework is developed by Peter Nicolai Alexis Kyaw. > These sample projects are BSD-3-Clause licensed and internal (publish_to: none).

This is the secured, full-stack successor to the basic core_server_sample / core_client_sample pair. Where those teach one server and one client in isolation, this suite is three servers, two databases, and two Flutter clients wired together end-to-end: a JWT auth/admin server, a secured task-manager app server, an end-user app, an administrator console, and a back-office operations server running scheduled work over the app database — all sharing one reflected domain and one wire contract, with live four-state field authorization and cross-user sharing.

> Reading this map. This document links the eight packages, draws the > architecture, and gives the one quickstart that stands the whole system up. > Every package ships its own article-grade README.md with the depth — nothing > about a package's internals is re-documented here.

The eight packages

#PackageWhat it isRuntime
1 advanced_todo_domain The shared, reflected domain model ( User , Project , TodoList , TodoItem , label/priority/state enums). Single source of truth for the whole stack. library
2 advanced_todo_contracts The over-the-wire surface: DTOs plus the typed AuthApiService / AdminApiService / AppApiService interfaces, implemented by the servers and called by the client core. library
3 advanced_client_core Flutter-free dart:io authenticated HTTP layer shared by both Flutter clients — presents a bearer token, refreshes it, parses JSON↔DTO. Headless-testable (no sockets in tests). library
4 advanced_auth_server JWT authentication issuer (`/auth/login\ second-factor\ refresh\ me\ logout, incl. a TOTP second pass) + role-gated **administration** API (/admin/users\ roles\ groups\ grants\ assignments`). The grant-mutating admin endpoints are a primary deliverable. HTTP :8081, auth_db :3307
5 advanced_app_server The secured task-manager API. Trusts the JWT signing key shared with the auth server, validates the bearer token on every request, resolves ownership + shares + four-state field grades, and persists app_db . HTTP :8080, app_db :3308
6 advanced_app_client The end-user Flutter app: login, a status-column task board, a bound item-detail editor with per-field four-state authorization driven live over the wire, and cross-user sharing. Flutter
7 advanced_authadmin_client The administrator Flutter console: manages users, roles, groups, role assignments, and the projectRole × field grant matrix via the auth server's /admin/* API. Flutter
8 advanced_ops_server Back-office scheduled work over the app database — a nightly retention purge, a morning digest rendered from a localised text bundle into the messaging outbox, a weekly export into the blob store, and an audit-anchor publisher on its own timer. No HTTP surface and no database of its own. timers, app_db :3308

Four of the five runtime packages carry no example/ directory, and that is deliberate. Each is run directly — flutter run for the two clients, dart run bin/… for the app and auth servers — so an example/ beside them would duplicate the entry point. The ops server is the exception because its entry point needs both databases while its most adaptable seam needs none: advanced_ops_server/example/digest_composition_example.dart runs the real digest pass into a memory outbox and prints one German and one English mail.

The three libraries are a different case, because a library's surface is what a reader calls, and each ships an example/. advanced_client_core ships example/authenticated_call_example.dart: one authenticated call, from the config bean through login to the app API. advanced_todo_contracts ships two: reading an endpoint's route, method and access from the registry, and a DTO's round trip through the reflection path. advanced_todo_domain ships one that builds the entity chain, reads the typed enums, and grades an item's fields for every role — the resource-level ceiling narrowed by the field grade, as the item screen computes it.

Each package without one names what to read instead in its README: its own run section, the curl or screen tour beside it, and — for the whole stack at once — advanced_client_core/tool/run_cross_tier_integration.sh, which boots both databases and both servers, runs the live suites against them and tears everything down.

That is the one thing a reader cannot infer from an absent folder, so each package's README says it too — the three libraries and advanced_ops_server in this family, and core_server_sample and todo_domain elsewhere in tom_core_samples, do ship example/, and a missing folder and a deliberately absent one look identical.

Nor does any of the eight carry a doc/ folder or a doc/api/ summary, and that is deliberate and decided once for the whole sample suite — see the suite map. A sample has no consumers who need its surface indexed: these eight are publish_to: none, and the three libraries among them are imported only by the other five. The ## Current API content an API summary would carry is in each package's own README, in context, and the fourteen guide documents beside this one carry the rest.

Architecture

One reflected domain (advanced_todo_domain) flows into one wire contract (advanced_todo_contracts); both servers implement the contract, both clients call it through the shared advanced_client_core. The two servers share a JWT signing key, so a token minted by the auth server verifies at the app server.

<details><summary>Text / mermaid equivalent</summary>

graph TB admin[advanced_authadmin_client
admin console] --> core appc[advanced_app_client
end-user app] --> core core[advanced_client_core
shared authenticated HTTP] core -- "login + /admin/*" --> auth[advanced_auth_server
:8081] core -- "login + board/share" --> app[advanced_app_server
:8080] auth --> authdb[(auth_db :3307)] app --> appdb[(app_db :3308)] key(["shared JWT signing key"]) key -. "signs" .-> auth key -. "verifies" .-> app

</details>

  • The admin console logs in at the auth server and drives /admin/* to edit

roles and the grant matrix. - The end-user app logs in at the auth server, then calls the app server with the bearer token; the app server reads the grant matrix (sourced from the auth tier) and grades each field hidden / read-only / disabled / editable per request. - An admin's grant edit reaches an end-user's field matrix on their next request; a project share reveals a project to a second user on theirs. That full loop is exactly what the cross-tier integration test asserts.

Run the whole thing

Requirements: Docker (+ Compose v2) and the Dart/Flutter SDK on PATH. Host ports 3307 / 3308 (databases) and 8080 / 8081 (servers) must be free.

1 — Bring up both databases

Each server bundles its own MariaDB. The default ports differ (3307 vs 3308) so both — and a host-local MariaDB — can run side by side without colliding. 

# Auth database (auth_db) on host port 3307
cd tom_core_samples/advanced_auth_server
cp .env.example .env
docker compose up -d auth-db

# App database (app_db) on host port 3308
cd ../advanced_app_server
cp .env.example .env
docker compose up -d app-db

Each docker compose above mounts the database's database_migrations/<db>/<schema>/ tree into MariaDB's docker-entrypoint-initdb.d, so first boot runs that tree's [<version>]-<desc>.sql files in order — schema-creation ([0NN]) first, then the idempotent sample-data seed ([1NN]). The same tree is re-read at runtime by TomDbMigrations, so the seed is the demo cast on first run: the auth server lands the demo accounts and the grant matrix, the app server a starter workspace with shared projects.

2 — Start both servers

Start the auth server first (it mints tokens and owns the grant matrix), then the app server (it verifies those tokens and reads grants). Each runs from its own package root so relative migration/asset paths resolve. 

# Auth server — from advanced_auth_server/
dart run bin/auth_server_start.dart      # HTTP :8081

# App server — from advanced_app_server/ (in a second shell)
dart run bin/app_server_start.dart       # HTTP :8080  (GET /health → 200)

3 — Run both clients

Neither client ships platform folders, so generate one per client before its first run — see each client README's Before the first run, which also names the macOS network entitlement the live stack needs: 

# End-user app — from advanced_app_client/
flutter create --empty --platforms=macos .   # once; or linux, windows
flutter run

# Admin console — from advanced_authadmin_client/
flutter create --empty --platforms=macos .   # once; or linux, windows
flutter run

With no dart-defines both clients target the local servers above by default, reading their URLs from the AdvancedClientConfig config bean. Launch with --dart-define=TEST_MODE=true to boot on a seeded in-memory backend instead — the opt-in offline mode, and the same fake the socket-free widget tests inject.

One-command end-to-end check

To stand the entire stack up, run the scripted scenario, and tear it all down again in a single command (fresh database volumes each run): 

tom_core_samples/advanced_client_core/tool/run_cross_tier_integration.sh

It boots both databases and both servers, runs every live suite in advanced_client_core/test/ against them, and tears the stack down on exit:

SuiteWhat it walks
cross_tier_integration_test.dart an admin grant edit → the end-user's field matrix reflects it → a share reveals a project to a second user → the same kind of edit reaches the file endpoint , taking the upload away from the owner of the row
auth_client_integration_test.dart a real login, including the two-pass 2FA exchange
file_transfer_integration_test.dart bytes through both blob stores, the closed-column and anonymous refusals, and a read -graded principal who gets the download but not the upload
app_api_client_integration_test.dart one end-user call over the wire — health, then alice listing her workspaces through the typed app client
admin_api_client_integration_test.dart the same, one tier down — admin signing in and listing users through the typed admin client

A green run is a genuine live-stack pass — the runner converts a server-unreachable skip into a failure.

The back-office server has its own runner, because its assertions need a database but no server: it boots app_db (and auth_db, which the boot's datasource initialization insists on), applies the migration this package contributes to the app chain, and runs both the live and the connection-free suites. 

tom_core_samples/advanced_ops_server/tool/run_ops_integration.sh

Checking the generated API pages

A third runner needs neither a database nor a server: it runs dart doc over every advanced_* package and fails on any warning. 

tom_core_samples/tool/check_advanced_dartdoc.sh

It asks a question no other check in this repository asks. dart doc resolves a [name] against its canonical library — the barrel — rather than the file that declares it, so it accepts references the comment_references lint rejects and rejects some the lint accepts (a [Type.member] reference cannot reach an extension member, which is why [ProjectRole.name] fails where [ProjectRole.viewer] resolves). Neither guard implies the other, and this is the one that decides whether the published pages contain dead names.

It is a runner rather than one of the tom_ai/core/tool/ gates only because of cost: the whole python gate set takes about fifteen seconds, while dart doc takes twelve to thirty per package. Run it after editing a doc comment here.

Checking that the generated reflection is current

After changing anything a reflector sees — a field, a method, or a parameter type — verify that the package's committed *.reflection.dart still matches: 

cd tom_core_samples/todo_domain
./reflection_generation.sh --check

It exits non-zero and names any generated file that has drifted, without modifying it. The remedy is to drop --check and commit the result.

This matters more than it looks. Widening TodoFieldMatrixDto.parseState from String? to Object? changed a type index in todo_domain's seed and another in advanced_todo_contracts; neither was regenerated, and both were committed stale. Nothing caught it: dart analyze was clean and both suites fully green, with identical test counts before and after regeneration, because the stale part is metadata the tests never read. The mismatch surfaced only because somebody ran the generator for an unrelated reason.

So a reflected signature change is a source edit with a second half, and this is what confirms the second half was done. Reproduced deliberately while building the check: adding one unreferenced field to a reflected DTO left dart analyze clean and the suite at 18/18, and --check still failed.
