Forms & UI

Part 09 of the Tom Core advanced-sample user guide — see the guide index.

Parts 07 and 08 established what a field's basePath means — it is the one name a field uses to look up both its grade and its text. This part shows where that basePath comes from: the TomForm / TomField classes the sample's screens are built from, how a field derives its path from its enclosing form and scope, how a bound form round-trips a reflected entity, and how the two clients assemble those forms into screens. The convention deep dive (why the JSON tree mirrors the form hierarchy, the estimate divergence) is appendix A2.

TomForm and TomField

A screen's editable surface is a TomForm<T> — a reflected container (T extends TomClass) that separates definition (the fields, declared as members typed by their base field type), implementation (the fields, created in createFormElements()), and layout (the screen, which drops each field.widget into place) — G-UI-5: 

@tomReflector
class LoginForm extends TomForm<LoginCredentials> {
  LoginForm() : super(formId: 'login');

  late final TomFormStringInput username;
  late final TomFormStringInput password;

  @override
  void createFormElements() {
    username = TomFormStringInput('username', '', form: this,
        validators: [Validators.required()]);
    password = TomFormStringInput('password', '', form: this,
        obscureText: true, validators: [Validators.required()]);
  }
}

Two things are doing the work here:

  • Each field is itself observable. TomField<T> extends TomObject<T>

(tom_flutter_ui/.../tom_form.dart), so a field holds its value, its validation state, and — via the authorization layer of part 07 — its resolved grade. A field renders itself: field.widget is a self-rebuilding widget (a ValueListenableBuilder wrapped in a TomFieldWidgetAdapter, in TomTextFormFieldBase.widget) that the screen drops straight into its layout. The screen never builds a TextField for the form's fields by hand. - Fields are created in createFormElements() (G-UI-5). The hook runs inside the form's own scope, after the form's basePath is set (it is called from prepareForSelfObservation, before the constructor body enumerates members). So each field captures form: this and derives its path from the form — independent of whatever scope happens to be current when reflection enumerates the members (see the next section). The members are declared late final and typed by their base field type (TomFormStringInput, TomFormStringDropdown, …); they need not be initialised at their declaration site.

The form's lifecycle — bind, save, validate, discard — fans out across its fields (and any nested forms) through reflection; the screens drive only those high-level verbs.

basePath derivation

A field's basePath is built in two hops, each a single line in tom_form.dart:

1. The form's basePath = enclosing scope path + formId (TomForm.prepareForSelfObservation): 

   basePath = parentPath.isNotEmpty ? '$parentPath.$formId' : formId;

2. The field's basePath = the form's basePath + the field's tomId (the TomField constructor): 

   scope    = form != null ? form!.basePath : TomScope.current.getScopePath();
   basePath = scope.isNotEmpty ? '$scope.$tomId' : tomId;

So a field's full path is <enclosing-scope>.<formId>.<tomId> — exactly the basePath parts 07 and 08 key resources and grades on. For LoginForm (no enclosing scope) the username field self-addresses as login.username; for the item editor (run under scope todo, below) the title field self-addresses as todo.item.title, the wire grade key. The whole authorization/text contract rests on this derivation — cross-link A2.

Scoped vs unscoped construction

Whether a form is "scoped" is decided at construction, by whether a TomScope is pushed around the constructor call:

  • Unscoped — the login form and the three admin editors are constructed

plainly, so their parentPath is empty and the form's basePath is its formId. UserForm (formId: 'user') gives fields user.username, user.email, …; LoginForm gives login.username, login.password. - Scoped — the item editor must run under scope todo so its field paths equal the server's grade keys (todo.item.<field>). The screen constructs it inside a pushed scope (_ItemDetailScreenState._resolveForm in item_detail_screen.dart): 

  final form = TomScope.withScope('todo', TodoItemForm.new);

TodoItemForm only declares super(formId: 'item'); the todo scope comes from the call site, so the field at tomId: 'title' lands at todo.item.title.

This is the one place the sample's "one name, two uses" rule could silently break — if the item form were constructed unscoped, its fields would self-address as item.title and every grade lookup would miss (degrading closed-safe to none/hidden). The scope segments (scope = 'todo', formId = 'item') are plain string literals declared where they are used — the formId in the form's super(formId: 'item'), the scope in the screen's TomScope.withScope('todo', …) (G-RES-2/6, no key-catalogue class). The form, the server grade matrix, and the JSON texts stay aligned by naming the same todo.item.<field> keys by convention, not by importing a shared constants file.

Bound reflected forms

A bound form is the bridge between a typed entity and its editable widgets, both ways, driven by reflection over member names (not tomIds):

  • bind(target) snapshots the entity into the form:

setValues(target.getValues()) copies each entity member's value into the form's matching member, then runs the bind lifecycle (TomForm.bind). - save() validates, then writes back: _binding?.setValues(getValues()) copies the form members' values into the bound entity by member name (the write-back inside TomForm.save). Validation failures short-circuit the write and surface inline.

Because the round-trip keys on the member name, a field's tomId (which drives its basePath/grade/text) is free to differ from the entity member it binds. The item editor uses exactly this freedom: the effort field is the entity member estimateHours (so bind/save round-trips into TodoItem.estimateHours) but carries tomId: 'estimate', so it self-addresses as the graded key todo.item.estimate. The sample's three bound-form families:

FormBindsScope · formIdPath shape
LoginForm LoginCredentials — · login login.<field>
AdminLoginForm AdminLoginCredentials — · adminLogin adminLogin.<field>
AdminSecondFactorForm AdminSecondFactorCode — · adminTwoFactor adminTwoFactor.<field>
TodoItemForm TodoItem todo · item todo.item.<field>
UserForm / RoleForm / GroupForm UserDraft / RoleDraft / GroupDraft — · user/role/group user.<field>, …

The app and admin login screens both bind a reflected TomForm and render field.widget; their distinct formIds (login vs adminLogin) give them the distinct public-bundle keys the auth server serves (part 08). A login that returns requires2FA then swaps the credentials phase for a second-factor phase on the same screen, and those texts ship with the login bundle rather than the authenticated one (the interim token buys no session to fetch it with).

The two clients diverge at exactly that phase, and only one of them has a form. The admin console hand-rolls AdminSecondFactorForm, which is why it appears in the table above: it is a bound TomForm with formId: 'adminTwoFactor', and it sizes its code field from the challenge's own clientData['digits'] rather than a hardcoded 6. The end-user app has no second-factor form at all — its login screen renders the framework's Tom2FAFlowPanel over a SessionTwoFactorController, because the chooser, the QR code, the code field's width and the attempt counter are invariant across applications and so live in tom_core_flutter. There, twoFactor is not a formId addressing a form's fields but merely the scope the screen reads its app-bar title from (texts.getText('$scope.title')); notably, the screen never reads clientData['digits'], which is the property the split exists for — a mechanism with a different code shape needs no change in the app.

All bound forms are @tomReflector and captured in each client's reflection_seed.dart; regenerate only on a reflected-signature change (part 03).

The tom_flutter_ui components

The forms are assembled from tom_flutter_ui's field and source primitives — the client packages add no field widgets of their own:

ComponentUsed for
TomFormStringInput free text (title, username, description; obscureText for passwords; maxLines for multi-line)
TomFormStringDropdown enum-valued pickers (status, priority) over a TomSelectableSource
TomFormNDateInputnullable dates (the item's due date)
TomFormNDoubleInput nullable numbers (the estimate, decimals: 1)
TomEnumNameSelectableSource the option list behind an enum picker: valued by the Enum.name the entity stores, labelled from the enum's global.<enumtype>.<value> key (G-RES-5)
StaticSelectableSource / SelectableItem a fixed option list over tokens that are not a Dart enum here (the admin console's account status), each label a bundle key
Validators.required()declarative per-field validation
TomFormFileUpload the item's attachment — a slot , not a bound member: it moves bytes over the file endpoint through a transfer client rather than through save() (part 13 )
TomAuthorizer.fixed(state) a per-field grade (the item screen's DB-resolved grades and the admin forms' stable-key fields — part 07)

Each component derives its basePath from the form (above) and resolves its label/hint/options from the installed resource bundle (part 08) and its grade from the per-field TomAuthorizer.fixed the item screen stamps on it (part 07). The dropdowns illustrate the stored-name-vs-display-text split from part 03: the SelectableItem value is the enum name the entity stores, while its label is resolved from the bundle under the enum's global.<enumtype>.<value> key (G-RES-5). The form hands TomEnumNameSelectableSource the enum's values and nothing else — no client package carries an option table — and the source re-emits when the installed bundle changes, so swapping the bundle relabels an open picker in place.

The screens

The two clients layer screens over these forms. The app client (advanced_app_client):

  • Login (login_screen.dart) — the bound LoginForm; on submit save()s

into LoginCredentials, folds them into a wire LoginRequest, and calls AppSession.login. A rejection surfaces inline without leaving the page. - Board (board_screen.dart) — the signed-in home; cascades workspace→project→list→item reads and groups items into one column per TodoStatus. Its app-bar carries the Share action. - Item detail (item_detail_screen.dart) — the bound TodoItemForm. It lays out the fields by rendering each field.widget and offers Save only when at least one field is editable (_ItemDetailScreenState._buildBody): 

  final canSave = form.gradableFields.any((f) => f.isEditable);
  // …
  for (final field in form.gradableFields) ...[ field.widget, … ],

TomField.isEditable is effectiveAuthState == TomAuthState.full, so the same form renders four ways by role with no per-screen branching — the authorization mechanism of part 07 doing the gating, not the screen. Beneath the form sits the item's attachment: a TomFormFileUpload scoped under board.item.attachment, built outside the form because it holds a FileRef rather than a bound member and its bytes travel over the file endpoint. It is graded by the same rule as the fields all the same — the registry-resolved resource ceiling narrowed by the role's grade — which is why a viewer sees the download and no picker (part 13). - Share dialog (share_dialog.dart) — the cross-user half of the model; grants another user a ProjectRole on the selected project.

The admin console (advanced_authadmin_client):

  • Admin login + shell — a bound AdminLoginForm (formId adminLogin) whose

login is two-phase (authenticate, then probe an admin call, since /admin/* is gated by the contract-declared TomRoleAccess(['admin']) not the login itself), then a NavigationRail over an IndexedStack of five destinations. - Users / Roles / Groups — three thin configurations of the generic AdminCrudScreen<T> (one list/dialog/confirm skeleton, not three), opening a reflected editor (UserForm/RoleForm/GroupForm) bound to a client-local draft. - Grants (grants_screen.dart) — the four-state matrix editor: a DataTable of projectRole × field-resource-key whose cells cycle none → disabled → read → full; Save PUTs the whole GrantMatrixDto and re-reads it. This is the screen that writes the matrix part 07 reads. - Assignments (assignments_screen.dart) — grants an account a role and/or group via a single AssignmentRequest.

Both clients are covered in depth in part 11; the secured endpoints they call in part 10.

Observing widgets

The sample's reactivity has two layers, both pull-based:

  • Session → shell. Each client's AppSession / AdminSession is a

ChangeNotifier; the app root wraps its home in a Flutter ListenableBuilder (AdvancedTodoApp.build in app_root.dart, AdminConsoleApp.build in admin_root.dart), so the login↔home swap is a pure function of session.isLoggedIn — login, logout, and a guarded 401 all rebuild the shell by calling notifyListeners(). - Field → widget. Because TomField is a TomObject observable, its field.widget self-rebuilds on value, validation, or grade change without the screen re-laying-out the form. The TomFieldWidgetAdapter wrapper additionally exposes the field's TomAuthorizable state to an enclosing AclContainer's hide-unauthorized pass, which is how a none-graded field disappears from the layout entirely (part 07's closed-safe default).
