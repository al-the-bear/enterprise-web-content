`todo_domain` — the shared model every sample reuses

> Attribution. The Tom Framework is developed by Peter Nicolai Alexis Kyaw. > This sample is BSD-3-Clause licensed and internal (publish_to: none).

todo_domain is the single source of truth for the Tom Core samples. It is a tiny, pure-Dart package — no Flutter, no server, no UI — that defines the reflected entities of a todo-management application: User, Project, TodoList, TodoItem, and the TodoPriority / TodoLabel enums. Every other sample depends on it: the core_server_sample persists these entities, the core_client_sample edits them, and the showcases render them. Because the model lives in exactly one place, the articles build on one another instead of re-introducing a model each time.

This README is the article companion for the shared domain. Read it first, then follow the learning path up through the server and the client.

---

Why a shared domain package at all

When a model is copied into each app, the copies drift: the server's TodoItem grows a field the client never learns about; an enum gains a case on one side only. The whole point of these samples is to show one application taught across the whole Tom Core layer, so the model has to be shared, not duplicated.

A standalone package gives us that for free:

  • One definition, many consumers. The server and the client both

dependency: todo_domain and import the same classes. A change lands once. - Pure Dart. todo_domain depends only on tom_core_kernel — never on Flutter or on tom_core_server. That keeps it usable from a headless server, a Flutter client, a CLI, or a test, with no platform baggage. - Reflected. Every entity carries @tomReflector, so the kernel's reflection machinery can construct, inspect, copy, and (de)serialize it. That same reflection is what lets the server's persistence layer map entities to MySQL and the client's forms bind fields by name.

---

The model

The entities form a three-level hierarchy, owned by a User:

User  ──owns──▶  Project  ──has──▶  TodoList  ──has──▶  TodoItem
                                                          │
                              assigneeId ─────────────────┘  (points back to a User.id)
EntityKey fieldsRole
User id, displayName, email, role Identity; role drives four-state authorization.
Project id , name , description , ownerId , lists Groups lists under an owning user.
TodoList id, name, projectId, items A named list of items inside a project.
TodoItem id , title , description , done , priority , label , assigneeId , dueDate The leaf task the CRUD forms edit.

Every field is a kernel observable — TomString, TomBool, TomNDateTime, or a TomList<T> of child entities — so any field can be observed, bound to a form, and round-tripped through reflection.

Observable fields, not plain values

Entities extend TomClass and declare their fields as late final observables: 

@tomReflector
class TodoItem extends TomClass {
  late final id = TomString('');
  late final title = TomString('');
  late final done = TomBool(false);
  late final dueDate = TomNDateTime(null);
  // …
}

Reading and writing goes through the observable, so changes are notifiable and form-bindable:

final item = TodoItem();
item.title.set('Write the article');   // or: item.title | 'Write the article'
final isDone = item.done.get();         // or: ~item.done

TomList<T> holds child entities — Project.lists, TodoList.items — and is itself observable, so adding or removing a child notifies list-bound UI.

Enums stored as names

TodoItem.priority and TodoItem.label are closed sets, but they are stored as a TomString holding the enum's name: 

late final priority = TomString(TodoPriority.medium.name);

Storing the name means the value persists to a MySQL VARCHAR/ENUM column and serializes to JSON with no custom codec — the server's persistence layer treats it as an ordinary string. For typed access, TodoItem exposes convenience accessors that convert back to the enum (falling back to a sane default for an unknown stored value): 

item.priorityValue = TodoPriority.high;      // writes 'high' to priority
final p = item.priorityValue;                // reads 'high' → TodoPriority.high

The human-facing text is not in this package (G-RES-5). A value's display string is addressed by a global.<enumtype>.<value> key that the framework derives and resolves against the installed bundle — TomObservableEnum.resolveText(TodoPriority.high) yields whatever global.todopriority.high holds — so a different bundle relabels the same stored value with no change here.

The wire contract

The entities above are what the application holds. What crosses the network is a second, flatter set of shapes under lib/src/wire/, exported from the same barrel:

DTOEndpointShape
TodoItemDto GET /todos (a bare array) flat projection: keys as strings, priority / label as their enum .name token, dueDate as an ISO-8601 string (empty when unset)
TodoFieldMatrixDto GET /todos/field-states {states: {role: {resourceKey: token}}} — the full role → field → TomAuthState grade matrix

Both are reflection-first (G-DTO): a @tomReflector class with plain non-final fields and no hand-written toJson/fromJson. The framework round-trips them through the same kernel reflection path as the entities — the server's endpoint pipeline drives it directly, while off-server consumers (the Flutter client's live read path, the round-trip tests) go through the three one-liners in dto_reflection.dart: 

final map = dtoToMap(dto);                       // DTO  → JSON-ready map
final json = dtoToJsonString(dto);               // DTO  → JSON string
final back = dtoFromJson<TodoItemDto>(map);      // map  → DTO

The string form is a separate kernel path from the map form, so todo_domain_test.dart round-trips both DTOs through it too: the decoded string must equal the map, and read back to the same DTO. dtoFromJson throws a StateError whose message names initializeReflection() when the reflection seed has not been installed, and a NoSuchCapabilityError for a type it does not cover; dto_reflection_failure_test.dart pins both.

Values that cannot cross the wire as their native type travel as a stable token with a typed accessor on the near side, and the readers are closed-safe: every degenerate TodoFieldMatrixDto input a payload can carry — an absent role, a row that is not a map, an unset cell, an unrecognised token, or a cell holding something that is not a string at all — resolves to TomAuthState.none rather than throwing, so an unknown grade denies rather than escalates.

That last case is why parseState takes Object? rather than String?: states is typed Map<String, Object?>, so a cell may hold any JSON value, and keeping the decision in one place is what stops a reader from reintroducing a throwing path by narrowing the type itself. The guarantee matters more here than ordinary leniency would suggest — the matrix is an authorization decision arriving over the network, so a reader that threw on a malformed cell would break the client's read path instead of denying. todo_domain_test.dart asserts each of those inputs against both readers.

The DTOs live beside the entities rather than in a separate contracts package because this deliberately-minimal pair already shares one reflected package across both tiers; the wire/ folder keeps the domain-versus-transport separation without a second package to build and reflect.

Reflection — the program installs its own seed

The entities are @tomReflector classes, so reflection must be installed before one is constructed or a wire DTO is parsed. This package ships no seed. A program generates one from its own entry point — the generator follows that program's imports and reaches these entities along with everything else it reflects — and calls that seed's initializeReflection() once at startup: 

import 'package:todo_domain/todo_domain.dart';

import 'main.reflection.dart'; // this program's seed, from its own root

void main() {
  initializeReflection();               // register the reflected entities
  final list = TodoList()..name.set('Sprint backlog');
  final task = TodoItem()
    ..title.set('Ship todo_domain')
    ..priorityValue = TodoPriority.high;
  list.items.add(task);
}

core_server_sample installs bin/server_start.reflection.dart, rooted at its live-boot entry point, and core_client_sample its lib/reflection_seed.dart, which covers the entities and its forms together. A seed exported from this package would collide with theirs on initializeReflection, and which one a consumer got would be decided by import order — so a library carries none (G-REFL-1/2 in the suite's guidelines).

This package's own tests and examples need reflection too, so it has one seed, in test/: test/run_all_tests.dart is the generator's root and test/run_all_tests.reflection.dart the generated seed. Tests import it directly, and the examples import it as ../test/run_all_tests.reflection.dart.

Regenerating after a model change

If you add a field or an entity, regenerate the reflection:

cd tom_core_samples/todo_domain
./reflection_generation.sh        # runs: dart run tom_reflection_generator

The seed is committed and must stay what the generator emits today — a rule the whole suite shares, stated once in the samples map. It can go stale without a model change here, because it also mirrors the kernel types the entities reach; ./reflection_generation.sh --check reports that, and a stale seed still analyzes and still passes the suite.

The script runs the generator flag-free — it scans the current project only (the framework default is scan ., non-recursive) and reads build.yaml's generate_for. Do not add a build positional argument: the generator reads it as a target filter, matches nothing, and exits with Target not found: build having written no output.

The generator's entrypoint is test/run_all_tests.dart (configured in build.yaml); the generator only processes files that expose a main(), so that file exists solely to give it one — its main() touches each reflected type, and the generator follows the import graph from there to discover every @tomReflector class, rewriting test/run_all_tests.reflection.dart. It is never called at runtime. The generated file is excluded from analysis by the shared workspace analysis_options.yaml.
