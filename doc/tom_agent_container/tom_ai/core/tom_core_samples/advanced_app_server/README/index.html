advanced_app_server

App server for the advanced Tom Core full-stack sample (see ../README_advanced_sample.md).

A secured task-manager API on tom_core_server. It trusts the JWT signing key shared with advanced_auth_server, validates the bearer token on every request, resolves the principal's resource access (ownership + shares) and four-state field grades, persists the app_db, and lets an owner share a resource with another user so the grant takes effect on the grantee's next request.

> Part of the Tom Core user guide. > This package is documented in context by > 05 · Persistence & the two databases and > 10 · Servers & the secured endpoint pipeline.

There is no example/ directory, and that is deliberate: this package is itself the runnable example. It is one of the eight advanced_* packages that together form the full-stack sample, so dart run bin/app_server_start.dart — the secured board API — is the demonstration, and an example/ beside it would duplicate the entry point. The family's index says which of the eight carry an example/, and why.

Read instead, in the order a newcomer wants them: Running it for the boot and its two databases, the curl tour for the endpoints exercised one at a time against a live server, and advanced_client_core/tool/run_cross_tier_integration.sh for the whole stack end to end — it boots both databases and both servers, runs the live suites against them and tears everything down, which is the one path that shows this server doing its job with a real client on the other side.

Architecture

The AppApiService implementation is split into pure, database-free logic classes — each over a store seam — and one thin @tomComponent adapter the endpoint router binds to. Every service is unit-tested against seeded in-memory stores with no server and no MariaDB; the adapter carries the production wiring (the repository-backed stores) and the per-endpoint access annotations.

Logic (unit-tested, no server)ConcernSurface
AppReadService over AppReadStore List workspaces/projects/lists/items; the principal's flat resource-role map GET /workspaces…/items, GET /resource-roles
AppWriteService over AppWriteStore + the resolvers Create/update/delete items, comments, projects with field-grade enforcement POST/PUT/DELETE /items…, POST /projects
AppShareService over ShareDelegationStore + the resolver Owner-only share / revoke POST /share, DELETE /share/{id}

Two resolvers underpin authorization (both database-free over their own seam):

  • ResourceRoleResolver — ownership-or-share → the principal's effective

ProjectRole on a resource. It resolves through the framework TomDelegationResolver (C-5 ownership grants + C-6 share-mode TomPrincipalDelegation rows; strongest role wins), then keeps the strongest over the item → list → project → workspace containment chain. null means no access. - FieldGradeResolver — ProjectRole → per-field TomAuthState (the grant matrix the auth server owns), so a write touching a field the role is not full on is rejected server-side.

The per-endpoint access policy is declared on the contract (TomApiEndpoint.access, G-API-3), not annotated on AdvancedAppApiService's handlers: appHealth is TomPublicAccess, every other endpoint is TomAuthenticatedAccess. The pipeline extracts that declaration on first call and reads the caller's principal from the bearer token via the default tomDefaultAuthenticationMiddleware; the resource- and field-level checks then run inside the handlers. The services throw stable TomEndpointHandlerException keys rather than HTTP responses, and bin/app_server_start.dart installs the server-level appServerErrorHandler that maps those keys (and the pipeline's pre-invocation access-denied) onto the HTTP contract: denials → 403, an unreachable resource → 404 (closed/safe, never leaking existence), a MalformedIdException from persistence/app_mapping.dart → 400 with body {"error": "request.id.malformed"}, everything else → the framework default. AppEndpointErrorHandler, declared on the @TomApiImplementation, applies the same mapping to rejections raised inside a handler — the pipeline catches those in its per-endpoint try/catch, where the server-level handler cannot reach them.

API

The barrel lib/advanced_app_server.dart is the package's stable entry point and exports ten libraries. Each store seam named below is an extension point: the services are written against it, the production wiring binds a repository-backed implementation, and the unit tests bind a seeded in-memory one.

Exported libraryWhat it isSeam it defines
src/endpoints/app_endpoints.dart The HTTP surface — the board's read, write and share endpoints, split into database-free services plus the @tomComponent adapter the router binds AppReadStore, AppWriteStore
src/access/resource_role_resolver.dart Ownership-or-share → the principal's effective ProjectRole on a resource, kept strongest along the item → list → project → workspace chain ResourceContainmentStore
src/access/field_grade_resolver.dart ProjectRole → the per-field TomAuthState grades a write is enforced against GrantStore
src/access/column_grade_resolver.dart The same two layers for an authorized column — the item's attachment , which the file endpoint gates on rather than a JSON field —

Running it

The boot resolves relative asset/migration paths against the CWD, so run it from the package root — with the auth server already up (its DB holds the grant matrix this server reads, and it mints the tokens this server verifies): 

# 1. Auth server + its DB (separate package) — see ../advanced_auth_server.
( cd ../advanced_auth_server && cp .env.example .env \
    && docker compose up -d auth-db \
    && dart run bin/auth_server_start.dart )   # HTTP 8081, auth_db on 3307

# 2. This app server + its DB.
cp .env.example .env
docker compose up -d app-db                    # MariaDB on host port 3308
dart run bin/app_server_start.dart             # HTTP on port 8080

Two datasources are wired (assets/datasources_default.yaml): app_db (port 3308) holds the app's own tables; main points at the auth server's auth_db (port 3307) so the field-grade resolver reads the tom_resource_grant matrix. The app server only reads grants; it never writes them. On first boot it applies the database_migrations/app_db tree (the app schema and demo seed).

Endpoints

POST / PUT bodies are JSON; Authorization: Bearer <authzToken> carries the auth server login's authzToken. All but /status (and the framework's /health liveness probe) require an authenticated principal; resource ownership/share and per-field grade are enforced inside the handlers.

Method & pathAccessPurpose
GET /status public Typed JSON status ({status, service})
GET /health public Framework plain-text liveness probe (OK) — auto-mounted
GET /workspaces · POST /workspaces authenticated List (owner-scoped) / create a workspace
PUT /workspaces · DELETE /workspaces/{id} authenticated Update / delete a workspace (owner-scoped at the database)
GET /projects · POST /projects authenticated List / create a project (workspace owner/editor)
GET /listsauthenticatedLists the caller can reach
GET /items · POST /items authenticated List / create items (create: editor+, field-graded)
PUT /items · DELETE /items/{id} authenticated Update (field-graded) / delete (editor+) an item
GET /attachments authenticated Attachment descriptors for the visible items of a list
GET /items/{id}/comments · POST /items/{id}/comments authenticated Read / add a comment on an item (add: commenter+)
GET /items/{id}/subtasks · POST /items/{id}/subtasks authenticated Read / add a checklist step (add: editor+)
PUT /subtasksauthenticatedUpdate a checklist step (editor+)
GET /resource-roles authenticated The caller's flat resourceKey → roleName map (client grades fields locally)
GET /resources authenticated The app client's text resource bundle
POST /share authenticated Owner-only — grant a user a role on a resource
DELETE /share/{id} authenticated Owner-only — revoke a share

The framework file endpoint additionally publishes POST|GET|HEAD|DELETE /files/app_items/{id}/attachment, mounted by the boot's one-line TomFileSlots.register(itemRepository). It is graded per row by the C-4 column resolver, not by the endpoint access declaration. The item's second file column, internal_note, is deliberately not exposed, so /files/app_items/{id}/internal_note is a 404 however privileged the caller is.

curl tour

Get a token from the auth server and reach an app-server endpoint with it — the cross-server JWT trust in action: 

ALICE=$(curl -s http://localhost:8081/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"alice-pass"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["authzToken"])')

# A token minted by the auth server (8081) verifies at the app server (8080).
curl -s http://localhost:8080/projects -H "Authorization: Bearer $ALICE"

A missing/invalid token is rejected with 403 before the handler runs:

curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/projects

Share a project with another user — only its owner may, and the grant is effective immediately (the grantee's very next request resolves the new role): 

# Look up carol's user id (she is the grantee).
curl -s http://localhost:8081/admin/users -H "Authorization: Bearer $ADMIN"

# alice owns project 1; grant carol `editor` on it.
curl -s -X POST http://localhost:8080/share \
  -H "Authorization: Bearer $ALICE" -H 'Content-Type: application/json' \
  -d '{"resourceType":"project","resourceId":"1","granteeUserId":"4","projectRole":"editor"}'

# carol can now create an item in project 1's list — access she lacked a moment ago.
CAROL=$(curl -s http://localhost:8081/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"carol","password":"carol-pass"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["authzToken"])')

curl -s -X POST http://localhost:8080/items \
  -H "Authorization: Bearer $CAROL" -H 'Content-Type: application/json' \
  -d '{"listId":"1","title":"Filed via a fresh share"}'

A non-owner sharing is rejected with 403; revoking the share (DELETE /share/{id} as the owner) removes the access again.

JWT signing

The app server calls the same installJwtSigning(configuration) as the auth server, which reads the three jwt* configuration fields — jwtSharedSecretKey, jwtRsaPrivKey, jwtRsaPubKey, reachable as the environment variables JWT_SHARED_SECRET_KEY, JWT_RSA_PRIV_KEY, JWT_RSA_PUB_KEY. Hold the identical values in both servers and a token the auth server mints (HS256 + RSA-encrypted authorization payload) verifies here. It also sets the same globalSettingJwtOrganization = 'tom' issuer. This is the standard "resource server trusts the authorization server" split.

Neither sample sets any of them, so both fall back to the framework's bundled sample keys — which is the only reason the two servers currently agree. Uncomment JWT_SHARED_SECRET_KEY in both servers' .env (see .env.example) and the agreement becomes a deliberate one; set it in one only and this server rejects the auth server's tokens with invalid token.

The fallback is not quiet. installJwtSigning refuses to boot on it outside a development or test environment (TomSigningKeyException, naming the unconfigured fields), which is why the sample is started with env=dev; where it is permitted it warns once at boot, and because the resulting TomJwtConfiguration stays marked as a development ("dummy") certificate the framework repeats the warning on every sign and verify — intentionally not suppressed (G-AUTH-2). Configure all three fields and the certificate is no longer a dummy one and the warnings stop. Do that before any real deployment.
