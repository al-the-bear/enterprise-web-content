advanced_auth_server

Auth server for the advanced Tom Core full-stack sample (see ../README_advanced_sample.md).

Two surfaces in one boot on tom_core_server: a JWT authentication issuer (/auth/login, /auth/second-factor, /auth/refresh, /auth/me, /auth/logout — with an optional TOTP second pass) and a role-gated administration API (/admin/users|roles|groups|grants|assignments). The admin endpoints that mutate roles and the grant matrix are a primary deliverable — they do not exist elsewhere in the framework yet.

> Part of the Tom Core user guide. > This package is documented in context by > 06 · Authentication (JWT) and > 10 · Servers & the secured endpoint pipeline.

There is no example/ directory, and that is deliberate: this package is itself the runnable example. It is one of the eight advanced_* packages that together form the full-stack sample, so dart run bin/auth_server_start.dart — the JWT issuer and the admin API — is the demonstration, and an example/ beside it would duplicate the entry point. The family's index says which of the eight carry an example/, and why.

Read instead, in the order a newcomer wants them: Running it for the boot and its database, the curl tour for login, /auth/me, the admin grant read and write, and the 403 a non-admin gets — and advanced_client_core/tool/run_cross_tier_integration.sh for the whole stack end to end, which is where an admin grant edited here is followed until it changes what the end-user client renders.

Architecture

Each surface is split into a pure, database-free logic class and a thin @tomComponent adapter the endpoint router binds to:

Logic (unit-tested, no server) Adapter (@TomApiImplementation) Surface
AuthTokenService over AdvancedAuthenticationService AdvancedAuthApiService /auth/*
AdminService over AdminStore AdvancedAdminApiService /admin/*

The adapters carry the production wiring (the repository-backed stores); the per-endpoint access policy is declared on the contract (TomApiEndpoint.access, G-API-3), not annotated on the handlers: everything a caller needs before it holds a session token is TomPublicAccess — credential exchange, the second factor, the three enrolment passes and the login screen's resource bundle — while the session endpoints (/auth/refresh, /auth/me, /auth/logout) are TomAuthenticatedAccess, and every /admin/* endpoint is TomRoleAccess(['admin']) (the shared adminAccess constant). The endpoint pipeline extracts that declaration on first call, reads the caller's principal from the bearer token via the default tomDefaultAuthenticationMiddleware, and rejects a non-admin before the method runs. The framework answers that rejection itself, with a bare 404 that carries no error key — so nothing here maps it, and the server-level handler this sample used to install for it is gone.

A rejection raised inside a handler needs the other handler, because the pipeline catches it in the per-endpoint try/catch and the server-level one never sees it. AdminEndpointErrorHandler, declared on the @TomApiImplementation, maps a MalformedIdException from persistence/auth_mapping.dart to HTTP 400 with body {"error": "request.id.malformed"} — a group create or update whose memberUserIds names something that is not a persisted user key is the caller's mistake, not a server fault. AdminService checks the membership before it writes anything, because these endpoints declare no transaction and a rejection further down would leave an orphan group, or a persisted rename, behind a request the client was told had failed.

API

The barrel lib/advanced_auth_server.dart is the package's stable entry point and exports eight libraries. The column that matters for a reader deciding what to touch is the last one: two of the eight define a seam to implement, the rest are wiring to reuse or records to read.

Exported libraryWhat it isFor a consumer
src/endpoints/auth_endpoints.dart The /auth/* surface — credential login and the token lifecycle: AuthTokenService , the AdvancedAuthApiService adapter, SecondFactorRetryException , LoginUnauthorizedErrorHandler reuse
src/endpoints/admin_endpoints.dart The /admin/* surface — account, role and group CRUD, assignments, and the four-state grant matrix: AdminService over AdminStore , its repository and in-memory implementations, the AdvancedAdminApiService adapter, GrantRepository , forbiddenOnAccessDenied implement AdminStore
src/auth/authentication_service.dart The credential check the framework's TomAuthenticationServer delegates each login to: AdvancedAuthenticationService over AuthUserStore , with a repository and an in-memory implementation implement AuthUserStore
src/auth/password_hashing.dart Four functions over the auth_db UserRecord shape — hashPassword , verifyPassword , applyPassword , verifyUserPassword — a thin adapter over the kernel's TomPasswordHasher reuse
src/auth/two_factor_enrolment_store.dart The persistent second-factor enrolment store, with LegacyBridging2FAEnrolmentStore over accounts that predate it reuse
src/persistence/auth_persistence_model.dart The auth_db records and their repositories — users, roles, groups, the two membership join tables, and the grant/delegation repositories read
src/persistence/auth_mapping.dart Pure conversions between those records and the two shapes the server works with: the observable advanced_todo_domain.User and the advanced_todo_contracts DTOs reuse
src/resources/auth_resource_bundles.dart AuthResourceBundles — the two text sets this server owns, the public login screen's and the authenticated one's reuse

A seam is where a consumer substitutes its own storage: AdminService and AdvancedAuthenticationService are written against the abstraction, the production wiring binds the repository-backed implementation and the unit tests bind the in-memory one. That is why both ship two implementations rather than one — the in-memory pair is not a test fixture tucked away in test/, it is part of what the package offers.

test/readme_api_section_test.dart derives both the barrel's exports and this table's rows and fails when they disagree, so the list cannot drift from the barrel the way a hand-written mirror would.

Running it

The boot resolves relative asset/migration paths against the CWD, so run it from the package root:

cp .env.example .env
docker compose up -d auth-db          # MariaDB on host port 3307
dart run bin/auth_server_start.dart   # HTTP on port 8081

On first boot the server applies the migrations (creating auth_db + the framework tom_resource_grant table and seeding its grant matrix), then hashes a demo password onto each seed account that has none. The seeded credentials are (sample only — never ship them):

UsernamePasswordGlobal roleNotes
admin admin-pass admin Untagged [002] seed — present in every environment
alice alice-pass — @dev,test [003] demo seed
bob bob-pass — @dev,test [003] demo seed; reads German ( [009] ), so the ops server's digest mails him in de
carol carol-pass — @dev,test [003] demo seed

Endpoints

POST / PUT bodies are JSON; the Authorization: Bearer <authzToken> header carries the login's authzToken (the token that carries the encrypted roles and groups). The token deliberately does not carry a per-resource role map: the bearer is opaque and never read for enforcement, so the effective resourceRoles map (tom_principal_resource_grant ownership rows ∪ share-mode tom_principal_delegation rows) is resolved live instead — the app server re-resolves it from auth_db on every request and exposes it through GET /resource-roles, which the client reads.

Method & pathAccessPurpose
POST /auth/login public Exchange credentials for the token pair (or, for a 2FA account, an interim pair + requires2FA )
POST /auth/second-factor public Answer a pending challenge ( code + challengeToken in the body , not as a bearer) and complete the login
POST /auth/enrol/begin public Start enrolment — generates a fresh secret and returns it once, with the clientData a QR code is built from
POST /auth/enrol/confirm public Confirm enrolment by proving one code against the new secret
POST /auth/enrol/skip public Decline an offered factor and complete the login unchanged
GET /auth/resources/login public The login screen's resource bundle — readable before a token exists

curl tour

Log in as the admin and capture the authorization token:

AUTHZ=$(curl -s http://localhost:8081/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin-pass"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["authzToken"])')

# Who am I?
curl -s http://localhost:8081/auth/me -H "Authorization: Bearer $AUTHZ"

# List the seeded users.
curl -s http://localhost:8081/admin/users -H "Authorization: Bearer $AUTHZ"

Read the grant matrix, raise a cell to full, and write it back — the admin-only grant edit: 

# The seeded matrix: viewer.title is "read".
curl -s http://localhost:8081/admin/grants -H "Authorization: Bearer $AUTHZ"

# Promote viewer.title to full and persist it.
curl -s -X PUT http://localhost:8081/admin/grants \
  -H "Authorization: Bearer $AUTHZ" -H 'Content-Type: application/json' \
  -d '{"viewer":{"todo.item.title":"full"}}'

# Re-read: viewer.title is now "full" (and a tom_resource_grant row carries it).
curl -s http://localhost:8081/admin/grants -H "Authorization: Bearer $AUTHZ"

A non-admin token is rejected with 403 — alice holds no global role:

ALICE=$(curl -s http://localhost:8081/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"alice-pass"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["authzToken"])')

# 403 Forbidden — the admin gate rejects her before the handler runs.
curl -s -o /dev/null -w '%{http_code}\n' \
  http://localhost:8081/admin/users -H "Authorization: Bearer $ALICE"

Two-factor login (dave)

dave is enrolled in TOTP with the base32 secret JBSWY3DPEHPK3PXP (the RFC test vector — a sample credential, seeded only under @dev,test). His login comes back pending: 

# Pass 1: the password is right, but no session is open yet.
INTERIM=$(curl -s http://localhost:8081/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"dave","password":"dave-pass"}' \
  | python3 -c 'import sys,json;d=json.load(sys.stdin);print(d["requires2FA"],d["authzToken"])' \
  | cut -d' ' -f2)          # requires2FA is True

# Pass 2: the current 6-digit code, plus the interim token — in the *body*.
curl -s -X POST http://localhost:8081/auth/second-factor \
  -H 'Content-Type: application/json' \
  -d "{\"code\":\"123456\",\"challengeToken\":\"$INTERIM\"}"

Add the secret to any authenticator app to get the code (or generate one with TomTotp2FAService.expectedCode('JBSWY3DPEHPK3PXP'), which applies this server's own digits/period). A wrong code returns 401 with {"error":"login.error.2fa.invalid-code","challengeToken":"<re-issued>"} — retry with that token; the third failure burns the challenge, as does its 5-minute expiry. On success you get exactly the pair a password-only login would have produced. Full walkthrough: 06 · Two-factor login.

Two-factor enrolment (erin)

erin holds the two_factor_optional role and no factor, so her login is met with an offer rather than a challenge. POST /auth/enrol/begin generates a fresh random secret (TomTotp2FAService.generateSecret) and returns it once with the clientData a QR code is built from; POST /auth/enrol/confirm proves one code against it and stores the enrolment; POST /auth/enrol/skip declines and completes the login unchanged. An account that confirms is challenged on its next login — from tom_user_two_factor_enrolment, not from the legacy two_factor_type column that carries dave's.

JWT signing

The server signs the token pair (HS256) and RSA-encrypts the authorization payload with the key material installJwtSigning(configuration) reads off the merged configuration — jwtSharedSecretKey, jwtRsaPrivKey, jwtRsaPubKey, reachable as the environment variables JWT_SHARED_SECRET_KEY, JWT_RSA_PRIV_KEY, JWT_RSA_PUB_KEY. The app server (advanced_app_server) must hold the identical values for a token minted here to verify there; that is the standard "resource server trusts the authorization server" split.

This sample sets none of them, so all three fall back to the framework's bundled sample keys — which is the only reason the two servers currently agree. Uncomment JWT_SHARED_SECRET_KEY in both servers' .env (see .env.example) and the agreement becomes a deliberate one; set it in one only and the app server rejects this server's tokens.

The fallback is not quiet. installJwtSigning refuses to boot on it outside a development or test environment (TomSigningKeyException, naming the unconfigured fields), which is why the sample is started with env=dev; where it is permitted it warns once at boot, and because the resulting TomJwtConfiguration stays marked as a development ("dummy") certificate the framework repeats the warning on every sign and verify — intentionally not suppressed (G-AUTH-2). Configure all three fields and the certificate is no longer a dummy one and the warnings stop. Do that before any real deployment.
