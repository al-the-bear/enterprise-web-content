Introduction & how to read this guide

Part 00 of the Tom Core advanced-sample user guide — see the guide index.

This guide teaches how to build a full-scale, secured, full-stack application on tom_core, using the advanced full-stack sample as the worked example. The sample is a small but technically complete task manager: three servers — two serving HTTP, one running scheduled back-office work with no port of its own — two databases, two Flutter clients, one shared reflected domain, one wire contract, live four-state field authorization, and cross-user sharing. Every part of this guide explains one cross-cutting concern of that system — and, just as importantly, the implementation rules the framework imposes — then points at the exact code that enforces it.

What the sample is — and is not

The sample optimises for complete framework coverage with deliberately limited business logic. There are only a handful of entities, a couple of forms, one task board and one item editor — but every technical concern of real application creation is present: reflection, wire contracts, two databases with migrations, JWT authentication, four-state field authorization, server-delivered text resources, bound reflected forms, a secured endpoint pipeline, and cross-tier integration testing. Read it as a reference skeleton, not a feature-rich product: when you build your own app you keep this technical spine and grow the business logic.

It is the secured, full-stack successor to the basic core_server_sample / core_client_sample pair. Those teach one server and one client in isolation, but they stop at a read-only seam — the server is publicly accessible, and login plus writes are faked in-memory on the client. This sample closes that gap end-to-end: real login, JWT issuance, bearer-token-secured endpoints, a per-request principal, and per-resource and per-field authorization.

Two pieces in this sample are its headline deliverables — capabilities no other framework sample demonstrates:

1. *HTTP admin endpoints that mutate roles and the grant matrix — the authorization-administration surface (`/admin/). 2. **An *authenticated* HTTP client** that presents and refreshes a bearer token — the shared advanced_client_core`.

Two framework rules are made literal throughout, and the guide keeps returning to them:

  • All UI texts are externalized into server-delivered resources, keyed by a

field's basePath — the client ships no UI strings. (Part 08, appendix A2.) - UI authorization is driven by scope/form/field names, not hand-wired: the screen fetches each field's DB-resolved four-state grade (keyed by basePath) and stamps it onto the field with a per-field TomAuthorizer.fixed; there is no per-field installed adapter, and an unsent grade is closed-safe (TomAuthState.none). (Part 07, appendix A1.)

Who this guide is for

You are building (or evaluating) an application on the Tom Core stack and want a complete, end-to-end worked example rather than isolated feature snippets. You are comfortable with Dart and Flutter. You do not need prior Tom Core experience — the guide introduces each concept where it is first used and collects the vocabulary in the glossary — but if you have read the basic core_*_sample pair, this is the natural next step.

The worked scenario in one sentence

An administrator edits the grant matrix in the admin console; that edit reaches an end-user's field grades on their next request to the app server; and when an owner shares a project, a second user sees it on theirs — the exact cross-tier loop the integration test asserts live. The sample seeds four accounts to exercise it: admin (manages roles + grants), alice (owns the starter project, can share), and bob / carol (an editor and a viewer on alice's project via seeded shares).

Conventions used in this guide

  • Cite, don't duplicate. Each package ships its own article-grade

README.md with the depth. This guide explains the cross-cutting concern and the rule, then links the package README or the enforcing source file. It does not re-document a package's internals. - Every rule is grounded in code, by name. Implementation rules name the live enforcement point (kernel / tom_flutter_ui / server) and a sample usage site, always as a declaration you can search for — a type, a member, a top-level function — with the file that holds it (e.g. TomField.resolveEffectiveAuth in tom_form.dart), so you can verify them. Deliberately never a line number: a line moves on the next edit to a file nobody reading this guide has open, and the citation then points at unrelated code while still reading plausibly. A name survives that edit, and tool/check_source_citations.py keeps line anchors out of these guides the same way it keeps them out of the source. - basePath notation. A field's basePath is written <scopePath>.<formId>.<tomId> (e.g. todo.item.title). The same path is used two ways — as the authorization key, and (with a suffix) as the resource key basePath.suffix (e.g. todo.item.title.label). That one-path-two-uses fact is central; appendix A2 unpacks it. - Terminology. Unfamiliar terms (grade, scope, adapter, draft, bundle, seed, graded DTO, grant matrix) are defined in the glossary. - Running the code. Part 02 has the full build/run steps and the seeded accounts; the index has the one-command end-to-end check. Flutter suites take a plain flutter test — part 12 explains why no concurrency flag is needed.
