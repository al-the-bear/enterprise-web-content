Tom Core Samples — one app, taught across the whole layer

> Attribution. The Tom Framework is developed by Peter Nicolai Alexis Kyaw. > These sample projects are BSD-3-Clause licensed and internal (publish_to: none).

tom_core_samples is the code companion to the Tom Core articles. Instead of a scattering of unrelated snippets, every sample here contributes to one running application — a todo-management system — so the same domain model flows from the server, through the client, into the showcases. Read an article, open the matching sample, run it, change it.

This document is the map; each sample ships its own article-grade README.md with the depth. Nothing about a package's API is re-documented here — the samples use the Tom Core packages and link back to their READMEs (repository map).

No sample package carries a doc/ folder, and none carries a doc/api/ summary. That is a decision, not an omission, and it is the same for all fifteen. The framework packages carry API mirrors because they have consumers who need the surface without reading the source; a sample has none. Every one here is publish_to: none, nothing outside this folder imports one, and the three libraries among them (advanced_todo_domain, advanced_todo_contracts, advanced_client_core) are consumed only by their siblings in this same tree.

What a reader of a sample wants is how the pieces fit, which is narrative — the article-grade README beside each package, and the twenty-two guide documents in this folder — rather than a symbol index. And a mirror here would be one nothing holds true: the framework's summaries are derived and gated by their packages' own suites, while a hand-copied index of a sample's internals would drift from the first refactor with nothing to notice.

Where a sample exports a library surface worth indexing, its own README does it instead, under a test that holds the index to the source: todo_domain, core_server_sample, advanced_client_core, advanced_ops_server and advanced_todo_domain carry a signature-level ## API section checked in both directions, advanced_app_server and advanced_auth_server a library-level ## API table, and advanced_todo_contracts an endpoint table generated from its registry.

a type-safe persistence layer against MySQL-in-Docker, configuration, caching, healthcheck, and four-state authorization. - A real Flutter client — a login-gated todo app on tom_core_flutter + tom_flutter_ui, with CRUD forms whose fields render hidden / read-only / disabled / editable straight from the server's authorization decisions. - A working mental model of tom_flutter_ui — the widget set, the forms framework, and the Advanced Container Layout engine, each shown beside the exact instantiation code that produced the rendered result. - Responsive layouts done the Tom way — breakpoints, family-swap, and adaptive composition on the ACL engine across phone / tablet / desktop.

The one application

Every sample shares a single domain — the reflected entities in todo_domain (User, Project, TodoList, TodoItem, plus label/priority enums). The server persists them, the client edits them, and the showcases render them. That single source of truth is what lets the articles build on one another instead of restarting from scratch each time.

Examples

Which samples ship an example/ folder, and why the others do not. A sample is itself an example, so the rule is about what a reader runs: a package whose entry point is an application needs no second one, while a library or a server whose most useful seam needs no infrastructure gets a runnable file.

Projectexample/Why, or what to run instead
todo_domain yes — three examples and run_all_examples.dart a library; see example/README.md
core_server_sample yes — run_all_examples.dart a database-free walkthrough of the server core — the domain ↔ record mapping and the four-state field authorization — that asserts its own results
core_client_sample no — exempt a Flutter GUI app: lib/main.dart is the entry point and the serial widget suite is its smoke test; argued in its README, §13 Tests
core_flutter_ui_showcase, core_flutter_form_showcase no — exempt Flutter showcase apps: each screen is an example, run with flutter run
core_flutter_acl_sample, core_flutter_acl_responsive no — exempt Flutter showcase apps, as above
the eight advanced_* packages the three libraries and advanced_ops_server — yes; the other four runtimes — no, exempt stated per package in the advanced family's index

An exempt row is a decision, not a gap: a sweep that finds no example/ in one of those packages has found what this table says.

Running the samples

Each sample documents its own run command in its README.md. The common shape:

# Headless / server samples
cd tom_core_samples/<sample>
dart run                       # or: dart run example/run_all_examples.dart

# Flutter samples (UI showcases, client)
cd tom_core_samples/<sample>
./reflection_generation.sh     # regenerate reflection if the model changed
flutter create --empty --platforms=macos .   # once per machine; or linux, windows, web
flutter run                    # pick a device when prompted

No Flutter sample ships platform folders, so each needs one generated before its first run. --empty keeps flutter create from writing a counter-app test the package cannot compile, and every sample's .gitignore covers what it writes. Each sample's README names the platforms it supports — the two that talk to a server over dart:io cannot target web — and tool/check_flutter_platform_step.py holds every README to naming the step.

core_server_sample additionally brings up MySQL in Docker (compose file + bootstrap) — see its README.md for the one-command bring-up.

Reflection seeds

Thirteen of the fifteen packages carry a generated *.reflection.dart — the reflection seed a program or a test installs with initializeReflection(). The rule for them is the same in every package, decided once here:

Seeds are tracked, and kept equal to what the generator emits today. They are not gitignored, because a fresh checkout must analyze, test and run without anyone running the generator first: every server and client entrypoint imports its own, and each domain package's tests and examples import the one rooted at its test/run_all_tests.dart. No library barrel exports a seed — a consumer installs its own, so two would collide on initializeReflection. And they are not pinned to a generator version, because a pinned seed is one that no run of ./reflection_generation.sh reproduces — a consumer who regenerates then sees a diff indistinguishable from a real model change.

What makes the rule hard to keep is that a seed goes stale without any edit in its package. It mirrors every type reachable from its root, including the framework's, so a change in tom_core_kernel or tom_core_server, or a new generator release, moves it. A stale seed still analyzes and still passes the suites, so nothing fails; the check that sees it is the generator's own: 

cd tom_core_samples/<sample>
./reflection_generation.sh --check   # exits non-zero, naming the file, when stale

Run it after a model change, after a framework change the sample reaches, and before committing a regenerated seed. When it fails: regenerate, run the package's suite — and its live runner, where it has one — against the result, and commit the seed together with the change that moved it.
